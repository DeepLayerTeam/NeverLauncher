# Ядро SDK Java и среды выполнения Launcher 0.31.0

**Рабочий SDK для Java 17+**, использующий существующие API расширений `1.0`, манифест `2.0` и локальный протокол хоста расширений на Go `1.0`. SDK не создаёт другой манифест, серверный API или реестр. Для сборки его JAR не нужны загрузки зависимостей Maven.

## Сборка и запуск тестов

```bash
sh sdk/java/core/build.sh test
# Результат: sdk/java/core/build/launcher-java-sdk-core-$(cat VERSION).jar
sh examples/extensions/java-lifecycle/build.sh
python3 examples/extensions/java-lifecycle/test-runner.py  # Linux/macOS: требуется Java в переменной PATH
```

JAR ядра можно включить в пакет расширения как `backend/lib/launcher-java-sdk-core.jar`; все Java-классы компилируются с `--release 17`. CI проверяет сборку и тесты SDK на Java 17/21 для разных платформ, а Linux CI запускает пример как настоящий дочерний процесс.

## Исполняемое расширение

Реализуйте `ru.launcher.sdk.core.Extension` с методами `start(ExtensionContext)` и `stop(ExtensionContext)`. Поставляемый `ExtensionRunner` загружает класс реализации, проверяет поставленный манифест и идентичность хоста, выполняет настоящий аутентифицированный `POST /v1/hello`, поддерживает `POST /v1/heartbeat` и вызывает методы жизненного цикла в управляемых потоках исполнителя. При недоступности хоста или завершении процесса работа прекращается.

Цель Backend для Linux/macOS — исполняемый скрипт запуска (см. `examples/extensions/java-lifecycle/backend/bin/java-lifecycle`). Существующий супервизор на Go запускает его с рабочим каталогом активного содержимого пакета и внедряет переменные `LAUNCHER_EXTENSION_*`. Процесс расширения **нельзя запускать как универсальную публичную сетевую службу**: SDK принимает только адрес петлевого интерфейса хоста. `ExtensionRunner` поддерживает типизированные подписки и вызовы обработчиков. Для непосредственного запуска JAR используйте Хост расширений Java 0.30.4, описанный ниже.

## Упаковка через существующий CLI расширений

```bash
sh examples/extensions/java-lifecycle/build.sh
nl extension pack examples/extensions/java-lifecycle/build/package \
  --output java-lifecycle.nlext --private-key /secure/location/ed25519-signing.pem
nl extension verify java-lifecycle.nlext --public-key /secure/location/ed25519-verify.pem
```

Зарегистрируйте открытый ключ подписи издателя в **существующем** реестре и политике доверия, затем опубликуйте и установите пакет штатным процессом Extensions. `pack` может создавать неподписанные артефакты, но их запрещено считать доверенными и устанавливать. **Никогда** не кладите закрытые ключи в пакет или репозиторий расширения. Метаданные сборки (`+...`) сохраняются при проверке точной идентичности пакета по хосту.

## Реальное поведение и ограничения

- Анализатор манифеста проверяет схему, идентичность, целевые пути, ограничения зависимостей и конфликтующие записи при ограниченном размере JSON. Определяющими остаются средство проверки пакета на Go и политика подписи и доверия. Чтение манифеста этим SDK **не** проверяет подпись пакета.
- `SemVer` использует правила приоритета SemVer 2.0 и принятые в Go Extensions диапазоны `^`, `~`, `>=`, `<=`, `>`, `<`, `=`, `x`, `*`, объединение пробелом через И и `||`. Недопустимые ограничения отклоняются, а не молча совпадают.
- `DependencyResolver.resolve(available, roots)` выбирает старшие совместимые версии, поддерживает обязательные/необязательные транзитивные зависимости, конфликты, поиск с возвратом и детерминированный порядок запуска «сначала зависимости». Циклы и несовместимые графы вызывают отказ. Этот локальный планировщик **не** загружает пакеты и не заменяет авторитетный Go-резолвер реестра.
- `Cancellation` предоставляет кооперативную отмену, дочерние области и обработчики с вызовом ровно один раз; `Deadline` использует монотонные часы; `ExtensionLifecycle` — ограниченные ожидания, прерывание потоков и явные состояния переходов. Java не может принудительно завершить произвольный некооперативный обработчик внутри той же JVM. Окончательная граница исполнения — существующий Go Supervisor.
- Код SDK Java **не** изолирован внутри собственной JVM; разрешения применяются существующим брокером хоста на Go. Не заявляется произвольная совместимость JAR JavaFX/LaunchServer/Gravit.
- Текущие примеры запуска ориентированы на POSIX. Сам SDK Java и тесты работают в Linux, macOS и Windows; исполняемая обёртка Windows и отдельный хост Java-расширений намечены для последующих выпусков.

## Поставляемые API среды выполнения Java (0.30.3)

После подключения к хосту на Go `ExtensionContext.runtime()` предоставляет **работающие** сервисы:

- `runtime().events().subscribe(type, "async" | "sync", schema, decoder, handler)` регистрирует обработчик в существующем устойчивом Go EventBus. `RuntimeCallbackServer` слушает только `127.0.0.1`, проверяет отдельный токен обратного вызова, конверт события и ограничивает обработку 1,8 секунды. Ключи идемпотентности доступны; при необходимости обработчики должны устранять дубли побочных эффектов, потому что шина гарантирует доставку как минимум один раз.
- `runtime().commands().register(name, schema, decoder, handler)` регистрирует команды, только если они объявлены в подписанном `cli.commands` манифеста расширения. Существующий административный путь `nl x <namespace> <command>` запускает краткоживущую Java CLI-цель через диспетчер процессов на Go. `ExtensionRunner --cli` вызывает обработчик и печатает JSON в stdout. `RuntimeCallbackServer` также поддерживает аутентифицированные обратные вызовы `/v1/commands`, но внешне поддерживаемый путь — Go CLI.
- `runtime().config()` и `runtime().storage()` читают, записывают и удаляют принадлежащие расширению JSON-документы через возможности брокера `runtime.config.*` и `runtime.storage.*`. Go проверяет `storage:read`/`storage:write` при **каждом** запросе, в том числе после отзыва. Документы изолированы по ID расширения и области установки, переживают обновления/перезапуски; ограничения — 128 КиБ на ключ, 256 ключей и 4 МиБ на расширение и область.
- `runtime().secrets().withSecret(name, projectId, callback)` использует существующий зашифрованный брокер Go `secret.get`. Нужен действующий свежий доступ `secrets:read`; SDK обнуляет временный массив декодированных байтов после обработчика. Приложение не должно сохранять или журналировать копии секретов.
- `JsonSchema` отклоняет неизвестные ключевые слова и проверяет реализованное строгое подмножество: object/array/string/number/integer/boolean/null, properties, required, additionalProperties (boolean), items, enum, min/max-length, min/max-items, minimum, maximum. Это **не** полная реализация схемы JSON 2020-12. Конфигурация проверяется при чтении и записи, содержимое событий и ввод команд — до пользовательских обработчиков.

Демонстрация на настоящих Backend и CLI:

```bash
sh examples/extensions/java-runtime/build.sh
python3 examples/extensions/java-runtime/test-runner.py
# Подготовьте пакет к подписанию существующими командами nl extension pack/sign/verify.
```

Среда выполнения SDK Java работает поверх **существующего** процесса хоста расширений, разрешений, подписи и локального протокола событий. Хост на Go не изолирует состояние ОС от недоверенных программ с тем же пользователем файловой системы; при исполнении враждебного кода используйте границу песочницы ОС, контейнера либо отдельной учётной записи и контроль доступа к `data/extensions`. JVM не является песочницей. Хост расширений Java 0.30.4 поддерживает прямые JAR-цели на Windows, macOS и Linux. Старые POSIX-примеры остаются доступными; не полагайтесь на песочницу безопасности JVM.

## Хост Java-расширений (0.30.4)

Цели манифеста `backend` и `cli` могут указывать напрямую на один **самодостаточный JAR**, а не shell-скрипт. Соберите JAR с SDK (`ru.launcher.sdk.host.JavaExtensionHost`), классами расширения и основными атрибутами JAR:

```
Manifest-Version: 1.0
Main-Class: ru.launcher.sdk.host.JavaExtensionHost
Launcher-Extension-Class: org.example.MyExtension
```

Go Launcher проверяет JAR до исполнения, запускает его как `java -jar <entrypoint>` через Java, настроенную администратором, либо `java` из PATH и передаёт **только** очищенные переменные среды расширений. JAR обязан находиться внутри подписанного `.nlext`, а его точка входа `backend` должна быть в подписанном манифесте. До обмена приветствиями (`hello`) хост Java запрашивает **авторитетный манифест** через аутентифицированный Go `GET /v1/manifest`; копия манифеста в содержимом пакета не нужна и не считается доверенной. Java-цель становится исправной только после аутентифицированного `POST /v1/ready`, отправляемого **после** успешного `Extension.start()`. Одного `hello` для готовности Java недостаточно.

JVM открывает аутентифицированный сервер обратных вызовов на локальном интерфейсе. Существующий брокер Java→Go остаётся единственным способом получить возможности Backend. RPC Go→JVM — `POST /v1/rpc` с версионируемым конвертом, одноразовым значением каждого запроса, лимитом тела/ответа 64 КиБ, явным списком методов (`health`, `command.invoke`, `event.deliver`, `hook.deliver`) и предельным временем 1,8 секунды. Java-обработчики работают в ограниченных пулах потоков и очередях; некооперативный обработчик может исчерпать пул, но Go не ждёт бесконечно. Supervisor Go периодически отправляет конкурентные пробы готовности и завершает неотзывчивую JVM после трёх подряд ошибок RPC, даже если обычные сигналы активности продолжают поступать. Сохраняются ограничения памяти/процессов дерева, экспоненциальные паузы перезапуска и защита от циклов падения. Права событий и команд по-прежнему применяются в брокере Go и объявленном реестре CLI-команд Java.

Сборка и запуск рабочего примера:

```bash
sh examples/extensions/java-host/build.sh
python3 examples/extensions/java-host/test-runner.py
nl extension pack examples/extensions/java-host/build/package --output /tmp/java-host.nlext --private-key /secure/signing-key.pem
```

На сервере Backend обязательна Java 17+. Сама среда выполнения Java — внешняя зависимость, заданная администратором: можно закрепить абсолютный путь к Java через `extensionhost.Config.JavaExecutable` в Go. Самодостаточный JAR не изолирован и работает с правами пользователя процесса. Подпись издателя подтверждает лишь происхождение пакета, а не безопасность; враждебные пакеты требуют границы песочницы ОС, контейнера или служебного аккаунта. Для релизной сертификации обязательны модульные/интеграционные Go-тесты и CI E2E хост Java. Произвольная совместимость JAR Gravit/LaunchServer не подразумевается.

Пример `java-host` содержит намеренно некооперативную команду `hang` исключительно для проверки устойчивости Supervisor. Не устанавливайте этот пример в промышленной среде.

## 0.42.1 — двоичная и протокольная совместимость Host/SDK 1.0

Протокол хоста (`Host Protocol`) и API расширений (`Extension API`) сохраняют версию `1.0` при изменении версии продукта. Аутентифицированный JSON-запрос `POST /v1/hello` сохраняет все поля 0.42.0, в том числе `protocolVersion`, `extensionApiVersion`, `instanceId`, `extensionId` и `pid` с необязательным `callbackUrl`. Расширения, собранные для 0.42.0, продолжают использовать этот точный формат обмена.

После возврата хостом идентичности подписанного экземпляра и согласованного списка возможностей SDK Java отклоняет необъявленные или невыданные операции брокера **локально, ещё до HTTP-запроса**. Для обязательной при запуске возможности вызовите `host.connect(callbackUrl, Set.of("runtime.config.get"))`; отсутствие возможности даёт `HostSession.CompatibilityError` с кодом `HOST_CAPABILITY_UNAVAILABLE`. Перегрузка работает и с хостами 0.42.0, поскольку формат запроса не меняет. Java-код, вызывающий лишь `connect()` или `connect(callbackUrl)`, сохраняет совместимость исходников и бинарников и получает проверку возможностей Runtime при каждом вызове.

SDK проверяет независимый `eventProtocolVersion`, доступные названия событий, период отправки сигнала активности и идентичность ответа. Нельзя подписаться на отсутствующий тип события. `HostSession.HostError.code()` предоставляет структурированные коды причин Go 0.42.1; старые текстовые ошибки Go по-прежнему представляются `HOST_HTTP_<status>`. Повторные hello-запросы и вызовы возможностей до hello запрещены. Управляемый класс Java-расширения инициализируется и создаётся **только после** успешного аутентифицированного hello, перед `start()`; для `ready` нужно положительное подтверждение Go Supervisor.

Теперь Go объявляет `runtime.config.delete` и `runtime.storage.delete` только при реально выданном `storage:write`; брокер остаётся авторитетным проверяющим каждой операции, в том числе после отзыва. При несовместимости протокола/API, идентичности процесса, неподдерживаемом обратном вызове и повторе hello Go Supervisor возвращает `409` с `error` и `code`. Никаких публичных маршрутов или ослабления прав не добавляется.

Для настоящих регрессий совместимости HTTP через петлевой интерфейс выполните `sh sdk/java/core/build.sh test`, включая старый конверт hello 0.42.0. Полная интеграция с промышленным хостом на Go всё ещё требует Go 1.27.3 и действующую релизную матрицу; одной HTTP-фикстуры JVM недостаточно для сертификации.

## 0.42.3 — долговременные подписки и размеры событий

Теперь Java `runtime().events().close()` закрывает лишь локальные обработчики. Подписки Backend остаются долговременными: обновление либо перезапуск JVM не удаляет ожидающие события EventBus. Для намеренного удаления подписки вызовите `runtime().events().unsubscribe(eventType, mode)` при активном сеансе с хостом. EventBus гарантирует доставку как минимум один раз, поэтому вызывающие стороны должны предотвращать дубли неидемпотентных побочных эффектов.

Аутентифицированный сервер обратных вызовов принимает конверты событий/хуков до 2 МиБ, чтобы передавать существующий лимит содержимого EventBus 1 МиБ; для команд и RPC сохраняется отдельный лимит 64 КиБ. `null` Java допустим как результат JSON-команды. Полная документация и тесты: `docs/extensions/eventbus-rpc-persistence.md`.

## 0.48.3 — настоящий реестр провайдеров Java SPI

`ExtensionContext.providers()` предоставляет типизированный `ProviderRegistry` отдельной JVM. Модули реализуют `JavaProvider`, регистрируют `ProviderDescriptor` для `ProviderService<T>` и вызывают `select(serviceId, providerId, timeout)` до использования `call(service, action)`. Регистрация проверяет точную идентичность контракта, совместимый диапазон SPI SemVer и подписанный диапазон API манифеста. Выбор ожидает завершения вызовов, плавно заменяет активную реализацию и строго отказывает при ошибках или тайм-аутах. `ExtensionLifecycle` автоматически останавливает провайдеров после `Extension.stop()` или неудачного запуска. Устойчивый выбор читается через существующий брокер Go конфигурации с проверкой прав; изменения путь классов ядра лаунчера не требуются.

Настоящая интеграция сборки/запуска: `sh sdk/java/core/build.sh test`, `sh examples/extensions/java-spi/build.sh` и `python3 examples/extensions/java-spi/test-runner.py`. Фикстура проверяет настоящий хост JVM, встроенную библиотеку закреплённого JAR, аутентифицированную конфигурацию, переключение активного провайдера через существующий RPC команд, CLI, сигналы активности, завершение и отказ неизвестному выбору. См. `docs/extensions/java-spi.md`. Этот SPI — *внутри одной JVM расширения*, а не межпакетный реестр и не Java-песочница.

## 0.48.4 — Java-сервисы Backend

`context.runtime().backend()` предоставляет типизированные сервисы проектов, профилей, каналов, выпусков и статуса заданий только для чтения через аутентифицированный брокер хоста на Go. Отдельные возможности требуют действующих прав `project:read` или `release:read` и соблюдения области проекта. Ограниченная постраничная выдача использует `Page<T>` с необязательным `nextOffset`; перечень операций, прав и ограничений — в [Java-сервисах Backend](../../../docs/extensions/java-backend-services.md).

## 0.48.5 — SPI авторизации и идентификации

`IdentityServices.CONTRACT` подключает одну выбранную реализацию `IdentityProvider` к существующему аутентифицированному RPC обратных вызовов. Реализации проверяют внешние учётные данные, предоставляют стабильный неизменяемый subject, проверяют и отзывают **собственные** сеансы провайдера. Они никогда не выпускают токены Launcher или свидетельства аутентификации Microsoft/Minecraft. Конфигурация, права и активация: `docs/authentication/java-identity-spi.md`. Выполните `sh sdk/java/core/build.sh test`, чтобы проверить живые обратные вызовы JVM.

## 0.48.6 — SPI содержимого и распространения

`context.runtime().content()` предоставляет реальное разрешение источников/текстур/доставки провайдерами, обогащение метаданных, ограниченные побайтовые преобразования до подписи и чтение содержимого с проверкой SHA-256 через существующий брокер хоста на Go. Зарегистрируйте `ContentProvider` через `ContentServices.CONTRACT`; выбранным провайдером управляет `ExtensionLifecycle`. Преобразованный файл не является опубликованным выпуском и обязан пройти обычную цепочку подписи и целостности. Соберите исполняемый пример: `sh examples/extensions/java-content-spi/build.sh`. Промышленный включаемый параметр `contentExtensionId` для multipart-преобразования пакета, права, строгие лимиты и оставшиеся границы публичной доставки описаны в `docs/extensions/java-content-spi.md`.

### 0.48.7 — задания по событиям и хуки политик

Используйте `runtime().events().subscribeJob(...)` для устойчивых фоновых заданий, поддерживаемых событиями; `subscribeHook(...)` с явными `HookDecision.allow()/deny()` — для синхронного запрета перед изменением; `subscribeDetailed(...)` — для получения порядка событий, схемы, агрегата и метаданных упорядочения/идемпотентности. Go EventBus управляет арендами, повторами и очередью невыполнимых сообщений. Для необратимых ошибок используйте `RuntimeEvents.PermanentFailure`; другие ошибки callback запрашивают повтор. **Не считайте внешние эффекты исполняемыми ровно один раз.** См. `docs/extensions/java-events-hooks.md`.

### 0.48.8 — интеграция ServerBridge с Java

`context.runtime().serverBridge()` предоставляет настоящие, ограниченные разрешениями узлы проектов ServerBridge v3, живой статус, консультативные проверки уже существующих билетов входа, команды, сохраняемые через аутентифицированный брокер Go, опрос статуса и типизированные обратные вызовы долговременных серверных событий. Команды по-прежнему подчиняются подписанным возможностям адаптера, защите среды выполнения от устаревших исполнителей, RBAC игровых доменов и идемпотентности PostgreSQL. `server.console` и `server.shutdown` Java не предоставляются. Фактический допуск Minecraft-сеанса остаётся прежним. Подробности и тесты: `docs/extensions/java-serverbridge.md`, `sh sdk/java/core/build.sh test`.

### 0.48.9 — интеграция интерфейсов Admin/Desktop и CLI

`RuntimeServices.ui()` регистрирует `registerAction("admin"|"desktop", actionId, JsonSchema|null, (actor, payload)->result)` и `registerSetting(surface, key, JsonSchema, defaultValue)` во время `Extension.start()`. ID UI-действий должны быть перечислены в подписанном манифесте `admin.actions`/`desktop.actions`. Существующий iframe Admin/Desktop отправляет хосту `rpc.request` с методом `java.action.invoke`, `java.settings.get` либо `java.settings.put` и параметрами, включающими текущие `version` и `generation` расширения; Backend аутентифицирует пользователя и направляет авторизованные запросы работающей Java-цели Backend. У исходного кода UI нет прямого сетевого доступа и Bearer-токенов. Настройки сохраняются существующим брокером `runtime.config`, требуют подписанных прав `storage:read`/`storage:write`; доступны только зарегистрированные ключи, а ошибка схемы запрещает изменение.

Действующая политика требует аутентифицированного `extension:manage` для всех трёх методов Java UI. Подписанное разрешение UI (`ui:contribute` либо `desktop:contribute`) независимо проверяется до и после RPC; отзыв пакета, устаревшее поколение, выход процесса и изменение области проекта вызывают отказ. Ответ обратного вызова Java ограничен 48 КиБ и выполняется с существующим сроком 1,8 секунды. CLI остаётся изолированной краткоживущей целью с подписанным пространством имён и `RuntimeCommands.register()`.

Соберите и проверьте полный пример с обоими iframe и исполняемым JAR: `sh examples/extensions/java-ui/build.sh && python3 examples/extensions/java-ui/test-runner.py`. Промышленная подпись и установка выполняются обычным конвейером расширений и не обходятся примером. `sh sdk/java/core/build.sh test` также проверяет внутрипроцессные HTTP-регрессии.

### 0.48.10 — версионируемая миграция состояния при безопасных обновлениях

Зарегистрируйте миграции в `Extension.start(ExtensionContext)` до достижения готовности Host:

```java
context.runtime().stateMigrations().register("1.0.0", "2.0.0", (config, storage) -> {
    Object prior = storage.get("preferences", null).orElse(java.util.Map.of());
    storage.put("preferences", prior, null);
});
```

Аутентифицированный хост вызывает миграции только при обновлении с изменением версии. Зарегистрированные переходы должны образовывать непрерывный путь только вперёд от установленной версии до целевой; пробелы блокируются. Отсутствие переходов означает намеренное сохранение прежней схемы документов. Все записи используют существующий брокер хоста на Go с проверкой области, прав и квот. Менеджер обновления Go сохраняет дисковый снимок с контрольной суммой и восстанавливает прежние данные *до* перезапуска старой версии при ошибках здоровья, callback или прерванном обновлении. Миграция не должна изменять внешние ресурсы, для которых нет компенсирующего действия. Не полагайтесь на вызовы ровно один раз: прерванное обновление безопасно повторяется после отката.
