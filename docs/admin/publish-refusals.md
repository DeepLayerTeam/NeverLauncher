# Публикация: причины отказов в Admin (0.38.5)

В рабочей области выпуска на этапах «Проверка» и «Публикация» выполняется GET `/api/v1/packages/{packageId}/validations`. Поле `publishReadiness` формируется Backend из реальных проверок файлов, подписи, текущей проверки целостности и обязательного свидетельства работы Runtime. Для stable используется независимая проверка ValidationEvidence v4 и матрицы обязательных целей.

Каждая блокировка содержит `reasonCode`, `resource` (файл, пакет или целевой экземпляр среды выполнения), `message`, `action`. В частности: `package-files-empty`, `file-unavailable`, `file-integrity-mismatch`, `manifest-signature-invalid`, `signed-file-set-mismatch`, `manifest-compatibility-invalid`, `integrity-pass-missing`, `stable-runtime-target-blocked`, `runtime-policy-unsatisfied`. Прямой запрос публикации и предварительная проверка сохраняемой операции возвращают структурированную ошибку `publish-blocked` при отказе.

Порядок восстановления: загрузить недостающие файлы / исправить профиль и создать новую сборку при необходимости; Проверка → Подписание → Подготовка → Проверка целостности → предоставить доверенное свидетельство работы Runtime для установленных целей → повторить предварительную проверку. Для stable загрузка старого свидетельства версии 1 не заменяет полную независимую сертификацию. Отправка ошибки или HTTP 200 с `status: invalid` не означает допуск.

`publishReadiness.eligible` обозначает только предварительный результат на момент чтения. Перед исполнением Backend повторно проверяет точные байты, подписи, доверие и актуальность разрешений; сама диагностика не выдаёт пропуск и не меняет состояние канала. Окончательный успех определяется состоянием сохраняемого задания и указателя канала.
