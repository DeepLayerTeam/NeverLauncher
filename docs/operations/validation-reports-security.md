# Launcher 0.34.12 — отчёты проверки и усиление безопасности (V12)

## Порядок развёртывания

1. Создайте резервную копию БД и примените миграции API штатным мигратором, включая `0106_validation_audit_03412.sql`. Она создаёт таблицу событий только на добавление и триггеры **AFTER INSERT** существующих таблиц подготовленного исполнения и аттестаций. Сбой вставки в триггере откатывает запись соответствующего доказательства. События до миграции остаются доступными через старые записи этапов/аттестаций, но прежние отклонённые запросы нельзя восстановить задним числом.
2. Разверните API и Admin **обеих версий 0.34.12 вместе**. Обработчики V12 отклоняют отправку аттестаций и подготовленных запусков, если новый журнал аудита недоступен. Сохраните блокировки stable-head PostgreSQL из 0.34.11 и доверенные ключи. **Не отключайте и не удаляйте V11**.
3. Запускайте независимо размещённый аттестатор с `--diagnostics-dir /secure/validation-diagnostics --diagnostics-ttl-hours 168`. Каталог должен иметь режим 0700, принадлежать непривилегированному аккаунту аттестатора и находиться на зашифрованном постоянном хранилище. Параметр обязателен; недоступный каталог блокирует выдачу доказательства. Хранятся только очищенные журналы (максимум 2 МиБ на запуск), SHA-256 и время истечения; сырой stdout исполнителя временный. Новые задания удаляют истёкшие записи. Настройте внешнюю уборку по расписанию, чтобы сроки соблюдались и без новых заданий.
4. Ограничьте запись в `validation_attempt_events_03412`, `package_validation_attestations_0345`, `stable_runtime_permits_03411` и функции миграций/триггеров выделенными ролями Backend. Таблица аудита запрещает UPDATE/DELETE; резервные копии и WAL храните по эксплуатационной политике. Владелец или суперпользователь PostgreSQL, способный изменить триггеры, находится вне модели угроз уровня приложения; наблюдайте за такими действиями в серверном аудите PostgreSQL. Отклонённые SQL-транзакции откатываются и не создают автоматически долговременную запись внутри той же транзакции.

## Аудит и конфиденциальность

`GET /api/v1/packages/{packageId}/validation-report` требует `project:read` и выдаёт страницу неизменяемых событий (100 последних, `nextBefore` для курсорной пагинации), последние подготовленные запуски с хешами этапов, сводки подписанных подтверждений без самих подписанных данных, сроки действительности и актуальное покрытие/блокеры целей V11. `?runId=<runId>` получает **точный исторический** запуск и его аттестацию за пределами окна списка. Для отчётов используется `Cache-Control: no-store`. Детали этапов очищаются при приёме и при чтении старых строк. Backend не считает диагностическую строку или событие аудита решением о сертификации.

Записи аудита содержат только ID пакета/запуска, итог, ограниченный код причины, SHA-256 отправленных/наблюдаемых данных и время создания. Принятые отчёты и аттестации журналируются транзакционно в PostgreSQL. Повреждённые, поддельные и устаревшие запросы получают `rejected`, сбои до фиксации V11 — `blocked`. При ошибке аудита приложение не выдаёт разрешение stable. Событие `stable-gate/eligible` **не доказывает фиксацию**: проверяйте Durable Publish и фактическую вершину канала.

Токены, пароли, OAuth-секреты, чувствительные аргументы Java, bearer-заголовки, аккаунты, e-mail и UUID по умолчанию скрываются без HTTP-способа отключить редактирование. Не помещайте секреты в пути, ID релиза, строки версии и метаданные манифеста: это неизменяемые поля идентичности, а не диагностика. Само подписанное доказательство содержит хеши и публичные метаданные; ради скрытия данных его подпись переписывать нельзя.

## Атакующие проверки

- Подмените подпись Ed25519 или издателя: `rejected/untrusted-signature`; stable не меняется.
- Передайте устаревшее, отозванное, повторное или чужое целевое доказательство: фиксируется причина отказа, покрытие Runtime остаётся неполным.
- Отправьте `{"certified":true}` или неизвестное поле: декодер отклоняет запрос, никакой обработчик не выставляет сертификацию на основе заявления клиента.
- Измените в скомпрометированном исполнителе локальные Java/JAR, скриншоты, тики игрока или хеши: независимый аттестатор должен отклонить запуск. Компрометация **самого хоста аттестации** — отдельная угроза, сдерживаемая правами доступа, аттестацией хоста, закреплёнными дайджестами образов и ротацией ключей.
- Создайте гонку между отзывом ключа, истечением доказательства, изменением релиза и вершины stable: SQL-ограничение V11 обязано отказать без действительного одноразового разрешения и точной подписанной матрицы целей. `eligible` в аудите не равно опубликованному выпуску.
- Попробуйте UPDATE/DELETE записей аудита: оба действия должны быть отклонены триггерами. Проверьте курсорную пагинацию и исторический `runId` после более 100 попыток.

## Команды тестирования

`python -m unittest discover -s tools/validation-attestor -p 'test_*.py'`

`cd services/api && go test ./internal/httpapi ./internal/repository ./internal/model`

`LAUNCHER_TEST_POSTGRES_DSN=<disposable-db> go test ./internal/repository -run 'TestV12|TestV11'`

`cd apps/admin && npm ci && npm run build`

**Приёмка промышленного выпуска требует** одноразовую БД PostgreSQL, предусмотренную проектом версию Go, настоящего аттестатора и подписанные подготовленные артефакты Minecraft-клиента/сервера. Одни модульные тесты и проверки схемы не устанавливают промышленную безопасность и совместимость реальных клиента и сервера.
