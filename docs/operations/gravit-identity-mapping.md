# Launcher 0.33.4 — сопоставление идентичностей и UUID (MIG04)

Этот выпуск реализует исполняемый этап согласования идентичностей. Он **не** создаёт пользователей, не переносит хеши паролей, не принимает устаревшие учётные данные и не переключает серверы. Состояние запуска `prepared` не означает успешную миграцию.

## Поддерживаемые форматы исходных данных

Передайте тот же защищённый ZIP, который ранее прошёл инвентаризацию MIG03:

- JSON Gravit FileAuthSystem по пути, заканчивающемуся на `FileAuthSystem/Database.json` или `FileAuth/Database.json` (без учёта регистра, допускаются родительские каталоги). Это карта с ключами UUID, используемая исходным модулем FileAuthSystem. Средство сопоставления отбрасывает поля пароля, разрешений, ролей, скина и плаща. `Sessions.json` также разбирается как данные идентичности.
- `sql-export/users.csv` — возможно, во вложенном каталоге. Это **не** дамп SQL-выражений, а снимок, экспортированный из реальной таблицы пользователей SQL системы Gravit, с нормализованными заголовками **`id,username,uuid`** и неизменяемым уникальным исходным ID в пределах провайдера. Дополнительные столбцы, в том числе хеши паролей, игнорируются. Экспортируйте фактический UUID из игровой системы: не создавайте и не пересчитывайте его по никнейму или номеру SQL-строки. Названия столбцов SQL в Gravit LaunchServer настраиваются, поэтому при экспорте администратор должен сопоставить используемые столбцы.

ZIP может содержать оба формата. Дубликаты и коллизии между ними фиксируются и блокируются. Неизвестные пользовательские хранилища аутентификации и провайдеры не трактуются как поддерживаемые автоматически.

## Порядок действий оператора

```sh
nl migrate gravit create --backend https://.example --token "$TOKEN" --project my-project --key migration-ticket-42
nl migrate gravit execute --backend https://never.example --token "$TOKEN" --run RUN_ID
nl migrate gravit inventory --backend https://never.example --token "$TOKEN" --run RUN_ID --source /secure/gravit.zip
nl migrate gravit map-identities --backend https://never.example --token "$TOKEN" --run RUN_ID --source /secure/gravit.zip --output /secure/uuid-map.json
nl migrate gravit identities --backend https://never.example --token "$TOKEN" --run RUN_ID
nl migrate gravit verify-identities --backend https://never.example --token "$TOKEN" --run RUN_ID
```

Для `map-identities` API сверяет точный SHA-256 и размер с сохранённой инвентаризацией MIG03, проверяет содержимое ZIP/CRC и подтверждает хеш манифеста инвентаризации. Backend не принимает доверенный путь к исходному каталогу или место распаковки ZIP. CLI требует HTTPS, кроме явно указанного loopback-IP.

## Значения результатов

- `matched`: исходный UUID **и** имя пользователя Minecraft без учёта регистра совпадают с одним существующим пользователем Never. Целевой ID пользователя хранится только как ссылка; право владения необходимо повторно подтвердить после импорта аутентификации и до переключения.
- `pending_import`: в Never нет пользователя с таким UUID/именем. Сопоставление сохраняется для дальнейшего аутентифицированного импорта учётной записи (MIG05); MIG04 **не создаёт учётную запись**.
- `blocked`: повторяющийся исходный ID/UUID/имя, конфликтующий или неоднозначный целевой UUID/имя Never либо неподдерживаемое исходное содержимое. Такие записи не должны автоматически переходить к переключению. UUID не переназначаются только ради устранения конфликта.

`ready=true` — узкое условие готовности карты идентичностей: каждая строка в данный момент соответствует существующей цели. **Это не разрешение переносить пароли, данные инвентаря и миров, импортировать модули, развёртывать или переключать серверы.** Повторная проверка сверяет сохранённые ID с действующими таблицами профилей Never и официальных идентичностей и создаёт новое событие аудита лишь при изменении результатов.

## Безопасность и согласованность

Таблицы PostgreSQL `migration_identity_snapshots_0334` и `migration_identity_rows_0334` сохраняют сопоставление исходных UUID и очищенное состояние. Необработанные хеши учётных данных, сеансы, токены, ключи и исходные файлы в эти таблицы не попадают. Первый принятый набор учётных записей закрепляется хешем SHA-256. Передача другого набора для того же запуска приводит к конфликту вместо перезаписи проверенной карты идентичностей. Новый источник проекта требует отдельного запуска миграции и повторной инвентаризации.

MIG04 никогда не объединяет учётные записи по email или никнейму, не может сбрасывать уже закреплённые неизменяемые UUID Never и не меняет профили Minecraft. После импорта или любых изменений целевого хранилища идентичностей выполняйте `verify-identities`. Полная миграция файлов, разрешённое создание аккаунтов/перенос паролей, поэтапное переключение и эксплуатационный откат остаются задачами последующих этапов.

Для проектов со старыми, нестандартными или сторонними модулями Gravit и снимков SQL с неизвестной семантикой UUID совместимость считается неподтверждённой, пока для соответствующего провайдера нет явно протестированного адаптера. При создании SQL CSV и хранении исходных ZIP используйте защищённую рабочую станцию и каталоги.
