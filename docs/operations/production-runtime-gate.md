# Launcher 0.34.11 — контроль допуска промышленного Runtime (V11)

## Условия перед публикацией

Релиз должен быть подготовлен с корректной подписью, актуальной успешной проверкой целостности `PASS`, настроенной **полной** матрицей `LAUNCHER_VALIDATION_REQUIRED_TARGETS_JSON` и одним действующим доверенным подтверждением v4 для каждой обязательной конфигурации. Каждое подтверждение должно охватывать все девять этапов V02/V03/V07/V08/V09. Необходимо настроить доверенный ключ проверки Ed25519 и закреплённый образ OCI для исполнителя. Отчёты CI, устаревшие подтверждения v1 и флаг администратора не принимаются за сертификацию Runtime.

Рабочая область релизов Admin показывает действующую политику `trusted-runtime`, число обязательных/проверенных конфигураций, блокирующие причины по каждой конфигурации и пригодность текущего пакета. Эти данные уже входят в ответ `/api/v1/packages/{packageId}/validations`. Недоступная база, отозванный ключ, изменённый пакет, отсутствующая конфигурация, неуспешный/неопределённый этап или просроченное подтверждение блокируют стабильный канал.

## Долговременная публикация

API проверяет авторизацию, подписанный манифест, текущую целостность и **всю** обязательную матрицу конфигураций. Непосредственно перед `CommitDurablePublish` подтверждения проверяются повторно и создаётся случайное 256-битное одноразовое разрешение на пять минут. Оно не содержит заявления `certified=true`, а ссылается на существующие строки подписанных подтверждений для каждой обязательной конфигурации. Внутри той же транзакции PostgreSQL триггеры статуса стабильного релиза и указателя канала проверяют разрешение, текущую целостность, точные поля конфигураций, сохранённые испытательные вызовы, срок действия и отзывы. Триггер указателя атомарно расходует разрешение. Токен не сохраняется в долговременном задании; после перезапуска или повторной попытки требуется новое разрешение после новой проверки.

Прямое изменение статуса SQL, публикация непосредственно через репозиторий, манипуляция указателем SQL, переключение или откат без корректного разрешения остаются запрещёнными по умолчанию. Каналы разработки и тестирования сохраняют собственные политики. Активация и откат через центр миграции получают такое же свежее разрешение для целевого релиза; удаление указателя стабильного канала запрещено. Откат в виде нового пакета сначала подготавливается для отдельной проверки Runtime и только затем может быть опубликован.

`0105_production_runtime_gate.sql` заменяет прежние безусловные защитные функции на месте, сохраняя ранее опубликованные стабильные релизы. **Не отключайте** существующие триггеры по именам. Применяйте миграции штатным инструментом репозитория. После миграции строки подтверждений, испытательных вызовов и отзывов доступны только для добавления. Право выдачи разрешений должно оставаться исключительно у проверяющего механизма Backend; ограничьте прямую запись в таблицы проверки и административные привилегии PostgreSQL. Суперпользователь БД способен изменять защитные функции и находится за пределами модели угроз API.

## Обязательная проверка перед включением промышленного режима

Выполните тесты Go для API и репозитория с заявленным комплектом инструментов и одноразовым экземпляром PostgreSQL. Запустите `TestV11StableSQLRejectsForgedPermitAndManualWrites03411` и прежний `TestStableSQLTriggersRejectAllHeadAndManualStatusWrites0341`. Проверьте успешную подготовку, полные доверенные E2E-тесты всех конфигураций и настоящую стабильную публикацию. Повторите сценарии с одной отсутствующей/неуспешной/неопределённой конфигурацией, просроченными/отозванными подтверждениями, изменённым пресетом/Java/плагином, конкурентной публикацией и отзывом, перезапуском/повтором, ручными SQL-записями, переключением/откатом через центр миграции и откатом как новым подготовленным пакетом. Только после этого развёртывание можно признать проверенным для промышленной эксплуатации.
