# Launcher 0.34.4 — реальная проверка соответствующего сервера и игрового процесса

Эта реализация **запускает** точный подписанный подготовленный клиент, уже установленный в 0.34.2, а не пересобранный Client Factory или выдуманный тестовый пакет. Сначала выполняется проверка меню и загрузчика версии 0.34.3. **Второй обычный запуск Runtime** подключает ту же установку к настоящему локальному выделенному серверу Minecraft через `--matching-server-port`. PID запущенной Java наблюдается средствами X11, а не выводится из сгенерированного CI поля JSON `joined the game`.

## Подготовка изолированного сервера

- Vanilla: `nl runtime vanilla-server --minecraft <signed version>` скачивает дистрибутив Mojang и проверяет SHA-1 Mojang и производный SHA-256. Подготовленный исполнитель повторно хеширует `server.jar` после установки и требует совпадения версии в журнале запуска.
- Fabric, Quilt, Forge и NeoForge: из защищённой конфигурации исполнителя должен быть предоставлен **полный ZIP дистрибутива сервера** с независимо закреплённым SHA-256 (`NL_MATCHING_SERVER_BUNDLE_URL`, `NL_MATCHING_SERVER_BUNDLE_SHA256`). Серверный `server.jar` (Fabric/Quilt) либо `run.sh` (Forge/NeoForge) запускается из изолированного распакованного каталога. В журнале запуска должны быть видны загрузчик и точная версия. Отсутствие версии, JAR или загрузчика — ошибка, а не повод переходить на Vanilla.
- Модифицированным серверам нужен JAR мода ServerBridge в `mods/` с независимо закреплённым SHA-256 (`NL_MATCHING_BRIDGE_PATH`, `NL_MATCHING_BRIDGE_SHA256`) и ожидаемой версией (`NL_MATCHING_BRIDGE_VERSION`). Плагин должен явно сообщить о запуске и версии в настоящем журнале сервера. Если Bridge не может связаться с обязательным Backend согласно политике входа, подключение завершается отказом; этот исполнитель никогда не обходит политику аутентификации.
- Поставляемый сервер принимается **только** после совпадения SHA полного ZIP, проверки безопасных путей и наличия точки входа. Вместо закреплённого пакета не вызываются сборщик или установщик загрузчика.

Исполнитель создаёт новый `server.properties` с сервером и RCON только на петлевом интерфейсе, временными портами, случайным паролем RCON, EULA и временным плоским миром в творческом режиме. Дерево процессов сервера завершается после каждого запуска. Никогда не раскрывайте пароль RCON в артефактах. Локальные настройки автономного сервера **не эквивалентны** проверке настоящей пользовательской/официальной аутентификации (V07).

## Положительные проверки

1. Настоящий выделенный сервер записывает точную версию Minecraft, соответствующий загрузчик/версию и, при необходимости, идентичность/версию ServerBridge, завершает подготовку мира и отвечает на аутентифицированную команду RCON `time query gametime`.
2. Настоящий клиент Runtime автоматически подключается к `127.0.0.1:<ephemeral port>` штатным механизмом Minecraft `--server/--port` либо `--quickPlayMultiplayer`. Подписанный манифест, материализованные файлы клиента и закреплённый ключ выпуска не меняются относительно проверки запуска.
3. Существует **новый** журнал подключения клиента; сервер записывает вход названного игрока, а RCON `list` показывает того же игрока в сети. Процесс окна X11 принадлежит запущенному подпроцессу Java с точным выбранным исполняемым файлом Java.
4. Исполнитель захватывает реальный отрисованный кадр мира и считывает NBT `Pos` игрока и игровые тики мира с работающего сервера. Затем активирует именно это окно Java, нажимает стандартную клавишу `W` через X11 и отпускает её.
5. Обязательны новые игровые тики, ненулевое **наблюдаемое сервером** изменение позиции игрока, изменившийся кадр изображения и отсутствие позднего сбоя JVM, Guard, загрузчика или сервера. Команды телепортации или выдуманное состояние игрока никогда не считаются действием клиента.

К существующему отчёту подготовленного запуска с сохранением в PostgreSQL добавлены этапы `server-readiness`, `matching-server` и `gameplay-smoke`, помимо прежних `manifest-files`, `materialization`, `startup` и `loader-readiness`. Каждый этап имеет независимый результат. Диагностика включает журнал загрузки сервера, SHA неизменяемого серверного артефакта, наличие журнала подключения, снимки экрана мира с привязкой к PID и их SHA-256, наблюдения игровых тиков, снимки состояния игрока и результат запуска Runtime. Backend хранит только сводки этапов и ссылки SHA-256, а CI сохраняет подробные артефакты. Учётные данные разрешений и пароли RCON исключаются.

## Преднамеренные ограничения

Для этой цели необходимы настоящий совместимый серверный дистрибутив, инициализированный ServerBridge и исполнитель Linux с GUI X11 и утилитами `xdotool`, `scrot`, `identify`, `xwininfo`, `xprop`, `glxinfo` и Tesseract. Другие графические платформы не входят в область этого этапа. Поддерживается игровой процесс для подписанного профиля с автономным входом и изолированного автономного сервера; профили, которым необходимы настоящие учётные данные провайдера, **блокируются**, а не сертифицируются посредством имитационного входа.

Эти результаты — **наблюдения, а не доверенная аттестация выпуска**. Строгий шлюз стабильного выпуска 0.34.1 сохраняется; будущие V04–V06 обеспечат доверие к исполнителю, привязку свидетельств и их актуальность.
