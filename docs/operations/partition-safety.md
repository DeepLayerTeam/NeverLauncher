# Launcher 0.51.4 — безопасность при разделении сети и изоляции прежнего владельца

## Что действительно обеспечивает код

- PostgreSQL (`durable_scope_leases`, `durable_jobs`, `event_outbox`) служит авторитетным источником состояния долговременных захватов заданий, владения арендой изменений, последовательности fencing и завершения работы. Время истечения определяет `clock_timestamp()` на **одном и том же основном узле PostgreSQL**; расхождение часов узлов не может сдвинуть этот срок.
- При использовании `FOR UPDATE` / `FOR UPDATE SKIP LOCKED` только одна транзакция может захватить конкретную строку в каждый момент времени. Каждый перехват увеличивает `lease_fence` / `fencing_token`. С истёкшим токеном аренды нельзя продлить, освободить, пометить ошибкой, остановить или завершить работу в PostgreSQL. Истёкшие задания и записи outbox, достигшие лимита попыток, завершаются, а не остаются навсегда в работающем состоянии. SQL-изменения указателя канала релиза транзакционно защищаются текущим токеном задания, токеном области, последовательностью fencing и CAS указателя канала.
- Если аренда outbox истекла до ACK, исходный обработчик не может отметить доставку как завершённую. **Доставка outbox остаётся «не менее одного раза»**, а не «строго один раз»: внешний эффект мог произойти перед отказом обработчика. Получатели обязаны удалять дубли по стабильной идентичности события/операции.
- Идентичность аренды команд Redis ServerBridge проверяется *до* нормализации ключа: разные некорректные идентификаторы не могут привести к одному временному ключу Redis. Долговременным источником управления остаётся журнал команд PostgreSQL. Потерянные ACK команд ServerBridge должны оставаться в состоянии `indeterminate` и **не приводить** к автоматическому повторному выполнению.

## Обязательные эксплуатационные условия

1. Запускайте плоскость управления на кластере PostgreSQL, который обеспечивает **единственный доступный для записи основной узел посредством кворума/fencing (STONITH или аналогичного механизма)**. Два записываемых лидера PostgreSQL по разные стороны разделённой сети могут независимо принимать корректные аренды; транзакционные ограничения приложения не исправят нарушенный кластер PostgreSQL. Одних проверок Patroni `/primary` и HAProxy недостаточно для доказательства fencing при разделении сети.
2. Используйте Redis с проверенным основным узлом и запретом операций аренды при ошибках. Маршрутизация не должна позволять узлу API продолжать взаимодействие со старым независимо записываемым лидером. При недоступности Redis управляющий API должен вернуть ошибку, а не обходить координацию.
3. Никогда не подключайте одни и те же записываемые файлы репозитория SQLite, миров Minecraft или расширений сразу на двух узлах независимо друг от друга. Оперативная память процесса Minecraft и запись в мир требуют **отдельной процедуры fencing узла/мира**. Аренды PostgreSQL сами по себе не делают каталоги миров безопасными для одновременной записи.
4. Часы API и обработчиков всё равно должны быть синхронизированы для сопоставления журналов, подписей и TLS. Время PostgreSQL решает только проблему **истечения аренды**.
5. После разделения сети считайте неизвестный результат завершения состоянием `indeterminate` и исследуйте сохранённый журнал операций. Никогда без проверки не отправляйте повторно `server.shutdown`, `server.save`, финансовые/административные изменения или произвольные консольные команды с новым ключом идемпотентности.

## Воспроизводимая проверка

- С настоящим PostgreSQL запустите `LAUNCHER_DURABLE_DSN=postgres://... go test -race -count=1 -run 'Test(PostgresPartitionFencing0514|PostgresExpiredLeaseFailClosed0514)' ./internal/repository` из `services/api` (версия Go указана в `go.mod`). Тесты используют два независимых пула SQL, завершают аренду одного владельца средствами PostgreSQL и проверяют монотонность перехвата и отклонение устаревших операций.
- Задание CI `.github/workflows/partition-fencing-0514.yml` запускает PostgreSQL 17, эти тесты и регрессионные проверки идентичности Redis. Пропущенные или отсутствующие интеграционные тесты PostgreSQL не являются доказательством готовности релиза.
- На испытательном HA-стенде с независимыми узлами изолируйте узел API/обработчика A от PostgreSQL и Redis, оставив узел B подключённым. Проверьте, что A не может фиксировать новые метаданные, подтверждать доставленные события или захватывать аренды Bridge, а B продолжает работать с основным узлом. Восстановите сеть узла A и убедитесь, что старые токены отклоняются, а новым операциям выдаются новые поколения fencing. Запишите временную шкалу экземпляра БД, состояние кворума, затронутые идентификаторы операций, строки до и после и точные хеши Runtime.
- Отдельно разделите сеть самого **кластера** PostgreSQL или Redis и принудительно переключите лидера; убедитесь, что запись на старом основном узле запрещена. Используйте изолированную одноразовую лабораторию с разрешением на испытания; **не** добавляйте произвольные правила файрвола на промышленных хостах. Зафиксируйте RTO/RPO, отклонённые транзакции и любые внешние побочные эффекты с неопределённым результатом.

## Преднамеренные ограничения

Изменение устраняет реальные ошибки проверки актуальности fencing на стороне приложения и коллизии идентичности Redis. Оно не реализует выборы лидера PostgreSQL, кворум/fencing Redis, принудительное разделение удалённой сети или перехват владения действующим узлом/миром. **Статус HA GA версии 0.51.4 должен оставаться BLOCKED**, пока физически разделённые узлы, реальные сценарии сетевых разделений и все внешние зависимости не пройдут независимую сертификацию. Модульные и интеграционные тесты либо декларации конфигурации не могут заменить такие испытания.
