# Launcher 0.51.10 — хаос-тестирование нескольких узлов и наблюдаемость

Документ описывает **исполняемую инъекцию отказов** для двух или более *независимых Docker-хостов* с многохостовым Launcher. Это **не** промышленный сертификат GA. Команды намеренно нарушают работу настоящих контейнеров: запускайте их только на разрешённом временном/тестовом развёртывании с раздельно управляемыми PostgreSQL/Redis/S3 и внешним HTTPS-балансировщиком.

## Предварительные условия (запрет при ошибке)

1. Разверните `deploy/production/docker-compose.multi-host.yml` как минимум на двух разных Docker-хостах; заранее выполните проверки работоспособности и инвентаризации 0.51.2/0.51.7. Никогда не используйте CLI хаос-тестов с однохостовым Compose Network-HA. Перед воздействием средство через `multi_host_0512.py` проверяет неизменяемые образы, разные ID машин, готовность API и рабочих процессов и реальные обращения к общим внешним PG/Redis/S3.
2. Установите **оба** скрипта `scripts/operations/multi_host_chaos_05110.py` и `scripts/operations/multi_host_0512.py` с одинаковыми файлами/путями на компьютере оператора и каждом Docker-хосте. Разрешите SSH-оператору только нужные Docker-операции. Обязательны строгая проверка `known_hosts`, неинтерактивный SSH и явный токен `I-ACCEPT-REAL-OUTAGE`. Используйте отдельных SSH-пользователей для каждого хоста. Не выполняйте одновременно учения и посторонние выпуски приложения или миграции БД.
3. Размещайте `--state` и `--report` в заранее созданном закрытом каталоге оператора (`0700`), например `/var/lib/launcher-chaos`; не используйте имена файлов повторно. Сохраняйте закрытые журналы восстановления до полного подтверждённого исправления. Ошибка или SIGKILL могут оставить удалённый узел изолированным. **До новых учений выполните `recover`.**
4. На каждом потенциально изолируемом узле создайте *закрытый обычный файл `0600`* `/opt/launcher/deploy/production/.chaos-approval-05110.json`, ограниченный настоящим ID узла и текущим проектом:

```json
{"project":"launcher", "nodeId":"lab-a", "allow":["network-partition"], "expiresUtc":"2026-11-03T21:00:00Z"}
```

Срок действия должен быть в будущем, но не более четырёх часов. Замените иллюстративную временную метку на настоящий UTC-срок. Для `host-stop` вместо этого нужен явный токен разрешения разрушительного воздействия. Никогда не добавляйте файлы одобрения или секреты в Git.

## Реальное внедрение сбоев и восстановление

Запускайте с доверенного хоста оператора (обязательны абсолютные удалённые пути):

```bash
python3 scripts/operations/multi_host_chaos_05110.py run \
  --project launcher --directory /opt/launcher/deploy/production \
  --node a=ops@node-a.example.org --node b=ops@node-b.example.org \
  --failed-node a --fault network-partition \
  --edge-url https://launcher.example.org/ready \
  --state /var/lib/launcher-chaos/partition.state.json \
  --report /var/lib/launcher-chaos/partition.report.json \
  --allow-disruption I-ACCEPT-REAL-OUTAGE
```

Для **повторяемого набора E2E из четырёх случаев на итерацию** создайте заранее **пустой закрытый** каталог (`mkdir -m 700 /var/lib/launcher-chaos/suite-01`). Затем выполните:

```bash
python3 scripts/operations/multi_host_chaos_05110.py suite \
  --project launcher --directory /opt/launcher/deploy/production \
  --node a=ops@node-a.example.org --node b=ops@node-b.example.org \
  --edge-url https://launcher.example.org/ready \
  --suite-directory /var/lib/launcher-chaos/suite-01 \
  --iterations 1 --allow-disruption I-ACCEPT-REAL-OUTAGE
```

Процедура по детерминированному порядку останавливает весь стек служб хоста и отделяет сеть Docker на **каждом** хосте. Неудавшийся или невосстановленный случай прерывает дальнейшие шаги и создаёт `suite-report.json`, отдельные свидетельства и SHA-256 для каждого случая. Максимум повторов — три. Перед следующим запуском восстановите конкретный журнал `*.state.json` командой `recover`. Это не подтверждает безопасность кворума внешнего хранилища, непрерывность JVM или гарантированную доставку оповещений.

Выберите `--fault host-stop`, чтобы полностью остановить четыре продуктовые службы (`api`, `worker`, `admin`, `ingress`) одного Docker-хоста. Повторите для второго узла и разных нагрузок, приближённых к промышленным; каждому запуску нужны отдельные пути состояния/отчёта. Сетевое разделение использует настоящие `docker network disconnect --force` для контейнеров API и рабочих процессов и отдельно убеждается, что оба отключились от моста `launcher_launcher`. Это **разделение Docker-контейнеров**, а не отключение питания физического хоста, блокировка межкоммутаторной сети или отказ кворума.

После воздействия контроллер требует три последовательных успешных проверки HTTPS-готовности, пять дополнительных устойчивых измерений и исправные оставшиеся API и рабочие процессы с настоящими обращениями к зависимостям; фиксируются фактически наблюдаемые успехи, ошибки и задержки p50/p95 без предположений. Он всегда пытается восстановить узел, затем повторно проверяет весь кластер. Одного успешного ответа отдельного API о готовности недостаточно для заявления об отсутствии видимых пользователю ошибок при аварии.

Если SSH или процесс оператора завершился во время внедрения сбоя, выполните:

```bash
python3 scripts/operations/multi_host_chaos_05110.py recover \
  --project launcher --directory /opt/launcher/deploy/production \
  --node a=ops@node-a.example.org --node b=ops@node-b.example.org \
  --edge-url https://launcher.example.org/ready \
  --state /var/lib/launcher-chaos/partition.state.json
```

Команда заново подключает исходные проверенные ID контейнеров **с прежними DNS-псевдонимами Compose** (чтобы ingress разрешал `api`) либо перезапускает остановленный хост и проверяет исходное состояние. Если исходный контейнер был заменён, средство **отказывается** подключать непроверенную замену: исправьте вручную и сохраните журнал как свидетельство. Восстановление никогда не означает откат БД/мира и не может незаметно отменить подтверждённые записи.

## Оповещения и воспроизводимые наблюдения

`deploy/production/docker-compose.observability.yml` теперь поддерживает раздельные правила оповещений Prometheus через `LAUNCHER_PROMETHEUS_ALERT_RULES`. Сформируйте принадлежащие оператору конфигурации опроса/оповещений Prometheus для **разных прямых имён ingress-хостов**, а не двух DNS-имён одного балансировщика:

```bash
mkdir -m 700 -p /opt/launcher/deploy/production/monitoring/ha-05110
python3 scripts/operations/multi_host_chaos_05110.py monitor-config \
  --node-url a=https://node-a.example.org/ready \
  --node-url b=https://node-b.example.org/ready \
  --edge-url https://launcher.example.org/ready \
  --output-directory /opt/launcher/deploy/production/monitoring/ha-05110
```

Полученные файлы — JSON-документы с расширением `.yml` (строго корректный YAML); используйте их напрямую в Prometheus. Установите `LAUNCHER_PROMETHEUS_CONFIG=./monitoring/ha-05110/prometheus-05110.yml` и `LAUNCHER_PROMETHEUS_ALERT_RULES=./monitoring/ha-05110/alerts-05110.yml` **в окружении оператора Compose**. Сохраните существующий Blackbox exporter из Compose-надстройки наблюдаемости. Строгий модуль `https_2xx_strict` проверяет TLS, принимает только HTTP 200 и отвергает перенаправления. Настройте HTTPS webhook-получатель Alertmanager через существующую `observability_0459.py configure` в закрытом файле. Убедитесь, что Alertmanager действительно доставляет тестовое уведомление получателю оператора: HTTP 200 от API Alertmanager **не** доказывает доставку.

Формируются три настоящих правила: недоступен ingress отдельного хоста; исправны менее двух ingress-хостов; недоступен публичный входной HTTPS-шлюз. Они срабатывают после настоящего 30-секундного отказа; стандартная проверка Alertmanager ожидает не более 100 секунд. Чтобы требовать наблюдения активного оповещения в тесте, добавьте `--alertmanager-url https://alerts.example.org --alert-name LauncherHostIngressDown`. Без этих аргументов поле отчёта `alertState=UNVERIFIED` не заявляет о доставке. Наблюдаемый тест не может получить PASS, если ожидаемое оповещение не обнаружено.

## Подтверждения и независимый допуск

Каждый результат записывается в новый JSON с правами `0600` только после попытки восстановления. Поля результата различают фактический сбой, проверки оставшихся узлов, краевые измерения, наблюдение Alertmanager, длительность, восстановленное состояние и неподтверждённые условия. Никогда не сохраняйте учётные данные, Bearer-заголовки, полное окружение или исходные журналы Docker. Журнал `recover` переживает неудачный откат и содержит строгий путь ручного исправления.

Для настоящей приёмки всё ещё обязательны **физическое** отключение питания хостов, реальное разделение инфраструктурной сети и связей кворума БД, переключение Patroni/Redis, репликация и восстановление S3, сценарии устаревших аренд и блокировки устаревших владельцев, устойчивое обратное чтение состояния обработчика заданий и очереди исходящих событий, снимки и повторный вход в мир Minecraft JVM, доставленное конечному получателю оповещение и количественные RTO/RPO/SLO на независимо развёрнутых окончательных исполняемых файлах выпуска. Учения зависимостей 0.51.3 и восстановление 0.51.8/0.51.9 можно выполнять отдельно со ссылками оператора на свидетельства; скрипт 0.51.10 не подменяет их совокупный результат вымышленным сертификатом GA. Автоматических санкций и принудительного назначения primary БД нет.
