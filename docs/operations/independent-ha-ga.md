# Launcher 0.52.0 — независимая приёмка HA (условие выпуска)

**Область действия:** промышленный код для выполнения и наблюдения независимых многохостовых учений по HA на настоящей инфраструктуре. **Сам по себе не сертификат GA.** Приложенные исходники не содержат физического стенда, подписанных окончательных пакетов, действующих учётных данных или одобрения независимого проверяющего. Команда `gate` возвращает `BLOCKED` (код завершения 3), пока отдельные свидетельства оборудования, хранилищ, JVM и выпуска не будут предоставлены и проверены независимым экспертом. Не принимайте успешные тесты Python в CI или разделение Docker bridge за физическую приёмку отказоустойчивости.

## Предварительные требования

* Используйте отдельную **машину, не совпадающую** ни с одним промышленным Docker-узлом, и назначенного независимого непривилегированного оператора приёмки (`--publisher` обозначает основного оператора выпуска и должен отличаться). Требуется проверенная рабочая копия исходников с `VERSION=0.52.0` и точный `--commit` (40 шестнадцатеричных символов); переданный коммит — заявленная идентичность выпуска, которую дополнительно сверяют с внешними подписанными свидетельствами происхождения.
* Не менее двух независимых Docker-хостов с настоящими образами 0.51.10 либо 0.52.0, SSH со строгой проверкой ключей, внешний PostgreSQL/Patroni, Redis, версионируемый S3, TLS ingress с независимым балансировщиком и Alertmanager с действующим HTTPS-получателем. Тестовый инструмент не создаёт эти кластеры и не подменяет разные физические машины изолированными контейнерами. Не используйте промышленную нагрузку заказчиков для разрушающих тестов.
* Установите `multi_host.py`, `multi_host_chaos.py` и `rolling_update_variant2.py` на машину оператора и Docker-хосты по совпадающим абсолютным путям. На каждом хосте подготовьте закрытый 0600 `.env.rolling-target-0520`, где *только* целевой образ API и рабочих процессов заменён точным неизменяемым OCI-дайджестом. Схема БД должна совпадать с неизменяемым пополняемым каталогом, а HTTP/Bridge-контракты обоих выпусков — быть идентичными.
* Заранее создайте каталог квитанций 0700 под управлением оператора и *пустой* каталог набора chaos-тестов 0700. Подготовьте для каждого хоста закрытые 0600 разрешения на ограниченное по объёму и сроку сетевое воздействие по документу `multi-host-chaos-observability.md`. Сначала восстановите любые устаревшие или неопределённые журналы сбоев. Не выполняйте chaos-тесты и поэтапные обновления одновременно.
* Для `cross_host_recovery.py` подготовьте отдельные промежуточные/восстановительные цели и согласованную контрольную точку 0.51.8 с настоящими WAL PostgreSQL, S3, копиями всех томов/миров и независимым журналом подтверждений. DR требует независимого fencing исходной системы и восстановления внешних учётных данных. Нельзя выводить RPO миров или входа в игру из журнала аудита.

## Реальное поэтапное обновление 0.51.10 → 0.52.0

Новый `scripts/operations/rolling_update_variant2.py` — рабочая версия прежнего управляемого процесса обновления с другими версиями источника/цели и **отдельными** именами журнала, резервной копии и подготовленного env. Он не удаляет процедуру отката 0.51.6→0.51.7. С `--allow-update` независимый CLI приёмки вызывает `cluster-roll`, который получает консультативную блокировку PostgreSQL, предварительно проверяет контрольные суммы всех хостов, загружает образы до остановки, обновляет API и обработчик заданий по одному хосту, наблюдает входящий HTTPS-трафик при переключении, сверяет схему/Bridge на каждом узле и при сбое пытается откатить только этот узел. Ingress, Admin и процессы миров контроллер не заменяет.

Пример с независимого узла оператора (замените все адреса хостов, URL, коммит, аккаунт и пути):

```bash
export COMMIT=<40-hex-release-commit>
mkdir -m 700 -p /var/lib/launcher-ga-0520
python3 scripts/operations/independent_ha_ga.py rolling \
  --node a=ops@node-a.example.org --node b=ops@node-b.example.org \
  --directory /opt/launcher/deploy/production --project launcher \
  --edge-url https://launcher.example.org/ready \
  --pg-dsn-file /var/lib/launcher-ga-0520/pg-connection.conf \
  --publisher release_operator --commit "$COMMIT" --allow-update \
  --output /var/lib/launcher-ga-0520/rolling.json
```

Средство требует, чтобы до обновления API и рабочие процессы имели версию *0.51.10* на **всех** узлах, а после успешного переключения на каждом должна быть *0.52.0*. Квитанция узла `.rolling.json` содержит фактически измеренные ошибки HTTPS и версии процессов. При обнаружении частичного обновления исследуйте `.rolling-state-0520.json` хоста и используйте `local-rollback` либо управляемое восстановление, вместо попытки стирать данные PostgreSQL.

## Реальные сбои, независимые оповещения и восстановление

Выполняйте после обновления на тех же двух или более настоящих целевых машинах:

```bash
mkdir -m 700 /var/lib/launcher-ga-0520/chaos
python3 scripts/operations/independent_ha_ga.py chaos \
  --node a=ops@node-a.example.org --node b=ops@node-b.example.org \
  --directory /opt/launcher/deploy/production --project launcher \
  --edge-url https://launcher.example.org/ready \
  --alertmanager-url https://alerts.example.org \
  --pg-dsn-file /var/lib/launcher-ga-0520/pg-connection.conf \
  --suite-directory /var/lib/launcher-ga-0520/chaos --iterations 1 \
  --publisher release_operator --commit "$COMMIT" --allow-disruption \
  --output /var/lib/launcher-ga-0520/chaos.json
```

Процедура **действительно выполняет** остановку стека хоста и отключение Docker-сети на каждом узле через исполнитель 0.51.10; требует наблюдаемого настоящего отказа, пяти последовательных измерений ingress, живых проверок оставшихся узлов и PostgreSQL/Redis/S3, активного состояния оповещения Alertmanager `ACTIVE`, полного проверенного восстановления и отсутствия осиротевших журналов разделения. Для каждой дочерней квитанции независимо пересчитывается SHA-256. Один API Alertmanager не подтверждает фактическую доставку webhook. Разделение Docker-сети не эквивалентно разделению стоек или коммутаторов; физическое выключение хостов и разделение кворума БД проверяются отдельно.

Для DR сначала выполните **настоящую** последовательность `cross_host_recovery.py prepare`, `replay-postgres`, `admit` по руководству восстановления 0.51.9 на свежей **отдельной** инфраструктуре с временем инцидента и журналом подтверждений. Живой допуск должен завершиться, а восстановленный кластер — работать с `0.52.0`. Затем с другого независимого наблюдателя:

```bash
python3 scripts/operations/independent_ha_ga.py recovery \
  --node a=ops@new-a.example.org --node b=ops@new-b.example.org \
  --directory /opt/launcher/deploy/production --project launcher-dr \
  --edge-url https://recovered.example.org/ready \
  --pg-dsn-file /var/lib/launcher-ga-0520/recovered-pg.conf \
  --recovery-work /var/lib/launcher-ga-0520/recovery-work \
  --maximum-rto 180 --maximum-sample-rpo 60 \
  --publisher release_operator --commit "$COMMIT" \
  --output /var/lib/launcher-ga-0520/recovery.json
```

Контроллер перечитывает **живые** версии API и рабочих процессов, миграции и входящий HTTPS-трафик, проверяет журнал и результат восстановления точных новых машин и отклоняет отсутствующий/неопределённый выборочный RPO аудита или слишком большой измеренный RTO входящего трафика. Выборочный RPO аудита **не доказывает** RPO миров, S3 и системы в целом. Отдельно должны быть собраны свидетельства настоящего запуска/входа в Minecraft и обратного чтения состояния мира.

## Окончательно скачанный пакет, независимая проверка и допуск GA

Сначала проверьте **настоящие** шесть подписанных окончательных пакетов платформ (без подмены артефактов выпуска) существующим проверяющим бинарной поставки с обязательными `RELEASE_MANIFEST.json` и `DELIVERY_VERIFIED_0462.json`:

```bash
python3 scripts/operations/independent_ha_ga.py bundle \
  --bundle /var/lib/launcher-ga-0520/final-release \
  --publisher release_operator --commit "$COMMIT" \
  --output /var/lib/launcher-ga-0520/bundle.json
```

После получения всех четырёх квитанций этапов независимый оператор запускает шлюз согласованности **без продвижения выпуска**:

```bash
python3 scripts/operations/independent_ha_ga.py gate \
  --bundle /var/lib/launcher-ga-0520/final-release \
  --receipt /var/lib/launcher-ga-0520/rolling.json \
  --receipt /var/lib/launcher-ga-0520/chaos.json \
  --receipt /var/lib/launcher-ga-0520/recovery.json \
  --receipt /var/lib/launcher-ga-0520/bundle.json \
  --publisher release_operator --commit "$COMMIT" \
  --output /var/lib/launcher-ga-0520/ga-blockers.json
```

Он привязывает каждую квитанцию к одному выпуску, коммиту и оператору, повторно хеширует окончательные файлы выпуска, отклоняет отсутствующие/повторные/изменённые свидетельства, несоответствие групп хостов и OCI, ненулевые краевые ошибки, изменение схемы, отсутствие результата DR или превышение RTO. Шлюз **никогда не продвигает** сборку и не создаёт вымышленный GA PASS. Для приёмки промышленного GA независимо соберите подписанные извне свидетельства отключения питания, физической сетевой изоляции, переключения кворума, сверки объектов/БД/миров, фактической доставки оповещения, игрового подключения, нативных подписей и независимого одобрения точных окончательных байтов; также пройдите соответствующие нативные/платформенные проверки. Реализация 0.52.0 фиксирует блокирующие условия вместо их отмены.

## Ограничения приёмки

* Выбор версий **намеренно явный**: 0.51.10→0.52.0. Нельзя заявлять общую гарантию N/N−1 для неуказанных версий, DDL PostgreSQL, JVM-агентов или игровых миров.
* `rolling` принимает только предварительно проверенный однородный кластер 0.51.10. Частично обновлённый кластер требует исследования/восстановления низкоуровневым контроллером, а не второй приёмочной квитанции.
* `recovery` проверяет ранее **фактически исполненный** DR-процесс и живую восстановленную площадку. Он сам не клонирует тома, не повышает PostgreSQL и не заменяет свидетельства физической машины утверждением администратора о fencing.
* Независимый код ориентирован на Linux-хост оператора; шесть подписанных нативных платформенных установщиков проверяются отдельно. Этот архив содержит изменения исходников, а не окончательные подписанные установщики и не свидетельства с реальных машин.
* По результатам модульных тестов не заявляется промышленный GA или измеренный SLA HA.
