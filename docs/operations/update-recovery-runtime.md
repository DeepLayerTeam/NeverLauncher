# Launcher 0.34.9 — V09: сертификация настоящего обновления, восстановления и отката Runtime

## Что действительно запускается

Этап V09 выполняет `e2e/scripts/staged_lifecycle_0349.py` **после** успешного прохождения обычным подготовленным клиентом реального запуска, готовности загрузчика, реальной авторизации, подключения к нужному серверу и игровых испытаний. Используются действующие промышленные команды `launcher client install`, `update`, `verify`, `repair`, `rollback`, `launcher update recover`, `runtime adopt-staged` и `launch`. Замены или имитации обновлятора нет.

Эталон **обязательно** должен состоять из точных подписанных байтов ранее выпущенного клиента **того же проекта и профиля**, а не собранной заново или выдуманной старой версии. Экспортируйте каталог `payload` предыдущего выпуска после независимо проверенного подготовленного запуска; создайте ZIP с `staged-package-description.json`, `signed-release-manifest.json` и всеми указанными путями в корне ZIP. Закрепите SHA-256 всего архива в конфигурации хоста аттестации; сохраняйте ID исходного релиза и хеши оригинальных артефактов в записях выпуска. Не добавляйте в ZIP учётные данные и разрешения runner. Исполнитель сверяет все файлы и идентичность подписанного манифеста до обновления. Runtime проверяет подпись Ed25519 манифеста ранее установленной версии по закреплённому оператором открытому ключу перед запуском.

Конфигурация только хоста аттестации (помимо существующих входных данных V04–V08):

```
--previous-bundle-file /sealed/releases/0.34.8.zip
--previous-sha $(sha256sum /sealed/releases/0.34.8.zip | cut -d' ' -f1)
--replacement-java-home /sealed/java/approved-alternative-jre
--managed-java-manifest-file /sealed/java/approved-temurin/MANAGED_JRE_MANIFEST.json
--managed-java-sha $(sha256sum /sealed/java/approved-temurin/MANAGED_JRE_MANIFEST.json | cut -d' ' -f1)
```

Предыдущий выпуск и альтернативная JRE монтируются только для чтения в изолированный исполнитель с закреплённым дайджестом образа. Новая Java должна быть **другим исполняемым файлом** той же основной версии, которая требуется текущему подписанному выпуску. Отсутствие JRE, совпадающий файл или неудачный настоящий запуск GUI дают `blocked`/`failed`, а не положительный V09. Ключ подписи аттестатора и промышленные данные не монтируются в исполнитель.

Для **наблюдательного CI** настройте `NL_VALIDATION_PREVIOUS_BUNDLE_URL` (HTTPS), `NL_VALIDATION_PREVIOUS_BUNDLE_SHA256`, `NL_VALIDATION_REPLACEMENT_JAVA`, `NL_VALIDATION_MANAGED_JRE_BUNDLE_URL`, `NL_VALIDATION_MANAGED_JRE_BUNDLE_SHA256` и `NL_VALIDATION_MANAGED_JRE_MANIFEST_SHA256`. Загрузчик CI сверяет дайджест старого пакета до выполнения; исполнитель повторно проверяет внутренние манифесты и хеши. Этот workflow никогда не подписывает подтверждения стабильной сертификации.

## Реальные сценарии сбоев

1. Установите и проверьте старую версию в пустом каталоге клиента. Измените байт **текущего подписанного входного файла** и запустите штатное обновление: операция должна отказать, сохранив все хеши старой установки.
2. Восстановите настоящие подготовленные байты и обновите через `client update`. Требуются `applied-and-verified` и долговременный снимок для отката.
3. Измените байт установленного файла и отдельной предпочтительной кеш-копии. `client repair` обязан отвергнуть повреждённый кеш. Удалите его, повторите штатный repair из проверенного подготовленного содержимого и сверьте весь набор файлов установки.
4. Запустите **тот же настоящий подписанный загрузчик** по HTTP с обрывом посреди подготовленного файла. Требуются ненулевой код отказа, удаление `.partial` и успешный проверенный повтор для тех же исходных байтов. Локальный маршрут API для имитации отказа не заменяет настоящий источник пакета при обычной материализации.
5. Установите старую версию в двух изолированных каталогах. Запустите реальный обновлятор и завершите группу процессов SIGKILL после наблюдения **сохранённых в журнале** этапов `staging` и `committing` (отдельный сценарий на каталог). Выполните публичный `launcher update recover`: предыдущий выпуск должен побайтово сохраниться, затем требуется успешное настоящее обновление с повторной проверкой. Если этап журнала не наблюдался, тест блокируется; синтетический результат запрещён.
6. Подключите новый подписанный клиент к Runtime из установленных байтов, запустите через альтернативную JRE и проверьте хеш Java, версию/основную версию, рендерер и положительное наблюдение готовности меню/загрузчика. Отдельно выполните `runtime java ensure --manifest --manifest-sha256` в изолированном управляемом каталоге с закреплённым архивом Temurin. Повредите установленный исполняемый Java, снова запустите **тот же** менеджер, потребуйте переустановку без кеша с исходным SHA-256 и успешный реальный запуск меню Minecraft на восстановленной Java.
7. Выполните `client rollback` к снимку перед успешным обновлением. Сверьте размер и SHA-256 **каждого ранее подписанного файла**. Повторно подключите восстановленный клиент к Runtime и подтвердите запуск.

Подписанная аттестация `update-recovery` невозможна без `update-recovery.json`, независимо сверенных байтов прежнего выпуска на диске, отчётов транзакций CLI, двух отчётов готовности Runtime и подтверждений аварий/восстановления. Этап обязателен для проверки подготовленного отчёта Backend и проверяющего доказательств; правка отчёта исполнителя не позволяет его пропустить.

**Ограничения:** V09 проверяет GUI Linux, отдельный альтернативный Java-бинарник и промышленный менеджер `runtime java ensure`. Менеджер обязан поместить намеренно повреждённый Java в карантин, переустановить из закреплённого Temurin и повторно запустить Minecraft. Это не заменяет межплатформенную матрицу Java-manager. Для полностью доверенного прогона нужны утверждённый ZIP старого выпуска, альтернативная JRE той же основной версии, закреплённый манифест управляемой Java и архив производителя, настоящий Minecraft-пакет, целевой сервер и реальные учётные записи провайдера. Одних Python unit-тестов недостаточно.

Stable остаётся заблокированным отдельным шлюзом V11 этапа 1 до доставки и сертификации сквозной интеграции публикации.

Устройство пакета Managed JRE: `MANAGED_JRE_MANIFEST.json` в корне ZIP рядом с `.tar.gz` производителя, указанным в `targets[].archive`. Манифест должен объявлять `productVersion=0.34.9`, точные платформу/архитектуру, SHA-256 и размер архива, путь исполняемой Java и производителя Temurin. Независимая контрольная сумма оператора закрепляет манифест, контейнер вызывает промышленный установщик управляемой Java, а не заменяющий скрипт. Хост аттестатора монтирует распакованный каталог только для чтения.
