# Launcher 0.37.6 — минимальное развёртывание: согласованное резервное копирование и восстановление

Для 0.45.2 переносимой **зашифрованной** резервной копии на новый Linux-хост используйте [minimal-recovery.md](deployment/minimal-recovery.md).

Это рабочий офлайн-инструмент резервного копирования Linux с одним узлом, **не средство резервного копирования без остановки сервисов**. Для общей точки согласованности SQLite, конфигурации и файлов требуется остановить API и все процессы, которые могут изменять `storage`, `extensions` или `factory` (включая внешние расширения и задачи). API и SQLite должны находиться на локальной файловой системе, поддерживающей flock. Нельзя использовать это средство как механизм резервирования без остановки или высокой доступности.

## Резервирование

```bash
# 1. Остановить службу API и зависимые процессы (systemctl stop ...).
python3 scripts/install/minimal-install.py backup --root /var/lib/launcher
# При необходимости сохранить сразу в отдельном приватном каталоге:
python3 scripts/install/minimal-install.py backup --root /var/lib/launcher \
  --destination /private/offsite/minimal-2026-10-29
```

Операция требует закрытых SQLite-хранилищ: под неблокирующими flock API/HTTP/coordinator используется API резервного копирования SQLite для двух основных баз и всех дополнительных локальных SQLite-файлов, включая зафиксированные WAL-транзакции, затем файловый снимок. Создаётся приватный каталог `backups/minimal-.../` с `payload/` и `manifest.json`. Исходные файлы WAL, SHM и журналов, файлы блокировок и сам каталог резервных копий не копируются. Все остальные объекты под корнем установки перечисляются без молчаливого пропуска; символические ссылки, файлы с жёсткими ссылками, небезопасные пути и необычные типы объектов запрещены.

Файлы синхронизируются с диском, сверяются SHA-256, а обе БД проходят `PRAGMA integrity_check` и `PRAGMA foreign_key_check`. Неполный снимок остаётся скрытым во временном каталоге и удаляется при ошибке. **Сторонние процессы записи, игнорирующие блокировки и работающие после остановки API, могут нарушить согласованность**; перед резервным копированием необходимо остановить и их. Рекомендуется выполнить резервную копию на выделенном обслуживаемом хосте.

## Проверка и восстановление

```bash
python3 scripts/install/minimal-install.py backup-verify \
  --bundle /var/lib/launcher/backups/minimal-YYYYMMDDTHHMMSSZ-XXXXXXXXXXXX

# Копию предварительно разместить за пределами повреждённой установки.
# Восстановление доступно только в отсутствующий каталог — действующие данные не затираются.
python3 scripts/install/minimal-install.py restore \
  --bundle /private/offsite/minimal-2026-10-29 \
  --target-root /var/lib/launcher
```

Команда проверки подтверждает точное совпадение файлов и каталогов с индексом, хеши и целостность SQLite до первой записи целевого каталога. Восстановление создаётся в закрытой временной папке, переписывает только известные абсолютные пути установки в `backend.env`, синхронизирует файлы и атомарно переименовывает каталог. **Уже существующая установка не перезаписывается.** При пересоздании хоста должны быть заново установлены и проверены бинарники API/CLI, системная служба, обратный прокси-сервер HTTPS, а также внешние файлы и ключи, не лежавшие в корне минимальной установки; восстановление директорий не означает автоматического восстановления инфраструктуры хоста.

Копия содержит учётные данные, ключи подписи, данные пользователей и прочие секреты **в открытом виде**. Доступ к архиву должен ограничиваться владельцем, перенос выполняться по защищённому каналу и с шифрованием при хранении вне сервера. SHA-256 проверяет целостность, **не** удостоверяет источник: атакующий, способный изменить архив и манифест, может пересчитать хеши. Доверять можно только копиям из защищённого доверенного хранилища.

## Проверки разработчика

```bash
python3 -m unittest discover -s scripts/install -p 'test_minimal_backup.py' -v
python3 -m unittest discover -s scripts/install -p 'test_minimal_install.py' -v
```

Положительные проверки: обе WAL-БД, файлы, перемещение установки и сохранение секретов. Отрицательные: приложение удерживает блокировку flock; повреждён файл или БД; вложенная символическая ссылка; существующая целевая установка. Реальный приёмочный сценарий на хосте с собранным Go API и полноценной проектной конфигурацией остаётся отдельной обязательной проверкой.
