# Аутентификация и внешние провайдеры

Backend включает внутреннюю систему аутентификации, поддержку SQL/HTTP/OIDC-провайдеров, федерацию учётных записей Microsoft, MFA/WebAuthn, сессии и доверие к устройствам. Реальная доступность способа входа зависит от конкретной конфигурации и тестов.

| Вариант | Конфигурация | Особенности |
| --- | --- | --- |
| Встроенные аккаунты | `LAUNCHER_AUTH_TOKEN_*` | Выдача и отзыв токенов, политика сессий |
| SQL | `LAUNCHER_AUTH_SQL_PROVIDERS_JSON` или `_FILE` | Изолированные DSN и проверка хеширования паролей |
| Действующая FileAuthSystem (только чтение) | `LAUNCHER_AUTH_FILE_PROVIDERS_JSON` или `_FILE` | Файл Gravit `Database.json`, динамическое обновление и точный формат паролей |
| HTTP | `LAUNCHER_AUTH_HTTP_PROVIDERS_JSON` или `_FILE` | HTTPS, список разрешённых хостов и подписанные ответы |
| OIDC | `LAUNCHER_AUTH_OIDC_PROVIDERS_JSON` или `_FILE` | Authorization Code с PKCE и проверкой издателя/JWKS |
| учётных записей Microsoft | `LAUNCHER_AUTH_MICROSOFT_PROVIDERS_JSON` или `_FILE` | Федерация учётной записи; **не тождественна** владению Minecraft Java Edition |
| Ключи доступа (Passkeys/WebAuthn) | `LAUNCHER_WEBAUTHN_RP_*`, `LAUNCHER_WEBAUTHN_ORIGINS` | HTTPS и RP ID, соответствующий домену |

## Различие между входом через Microsoft и входом в Minecraft

Аутентификация Microsoft OAuth/OIDC удостоверяет идентичность пользователя. Получение Minecraft-токена и подтверждение владения игрой и игрового профиля — отдельная цепочка. Не считайте наличие федерации Microsoft готовой официальной Minecraft-аутентификацией без сквозных проверок Minecraft Services.

## Рекомендации по защите

Секреты провайдеров передавайте через менеджер секретов или переменные окружения. Не смешивайте JSON и FILE-конфиг одного провайдера, если обработчик запрещает это. Ограничивайте URI перенаправления, разрешённые источники и список разрешённых хостов. Используйте короткие сессии, отзыв, аудит и защиту от повторного воспроизведения. Актуальные примеры ключей и названий параметров: [`.env.example`](../../.env.example), [`deploy/production/env.production.example`](../../deploy/production/env.production.example).

## Маршрутизация провайдеров и привязка аккаунтов (0.29.3)

`POST /api/v1/auth/login` принимает `identifier`, `password` и необязательный `providerId`. Если `providerId` передан, выбирается **только** он. Если не передан, применяются точные правила `emailDomain`, затем `defaultProvider`. Для несопоставленного identifier настройка `requireExplicitProvider: true` требует `providerId`; по умолчанию сохраняется `local` для обратной совместимости. Ошибки пароля, отказ/недоступность, отсутствие identity и конфликты **никогда** не вызывают попытку входа в другом провайдере.

Настройка передаётся через `LAUNCHER_AUTH_ROUTING_JSON` **или** `LAUNCHER_AUTH_ROUTING_FILE`:

```json
{
  "version": 1,
  "defaultProvider": "local",
  "requireExplicitProvider": false,
  "rules": [
    { "emailDomain": "company.example", "providerId": "website", "strict": true }
  ],
  "linkingAllowProviders": ["website"]
}
```

Маршрутизация применяется к **входу по паролю**. OIDC/Microsoft вход через браузер уже требует явного указания `providerId` в URL, привязан к серверной транзакции PKCE/state/nonce и не подбирает провайдер по адресу электронной почты. Если в конфигурации задан `strict: true`, указание другого провайдера при входе с соответствующим адресом электронной почты отклоняется. `strict: false` разрешает явно выбрать другой провайдер, не разрешая автоматический переход к запасному поставщику. Правила проверяют строку идентификатора электронной почты; они **не** доказывают владение доменом или email.

Для привязки используются только `POST /api/v1/auth/providers/{providerId}/link/password` (с действительной сессией и новым успешным паролем внешнего провайдера) либо `link/begin` + `link/complete` (с действительной сессией, привязанной браузерную транзакцию PKCE и подтверждённой внешнюю идентичность). `linkingAllowProviders` задаёт allowlist для обоих потоков; опциональный `disableLinking: true` полностью запрещает новые привязки, не затрагивая вход или безопасное обновление credentials уже связанных identity. Без этих полей существующее явное связывание остаётся разрешённым. Указание произвольного email, username или subject без доказательства от провайдера **не** связывает аккаунты. Повторная привязка `(provider, issuer, subject)` к чужому Launcher user и смена subject текущего `(user, provider, issuer)` запрещены. Различные issuer никогда не объединяются по одинаковому email.

Конфигурация валидируется при старте: неизвестные/провайдеры без поддержки входа по паролю, некорректные/дублирующиеся домены, неизвестные версии, конфликт JSON+FILE и превышение 64 KiB останавливают запуск, не активируя частичное правило. При изменении маршрутизации проверяйте реальные login + явную привязку на тестовых учётных записях до доставки в промышленную среду; конфигурация применяется при перезапуске Backend. Для защиты от обхода через имя пользователя без email задавайте `requireExplicitProvider: true` и полагайтесь на авторизацию уже проверенного identity/issuer.

## Сопоставление SQL и устаревшие хеши (0.29.4)

Настройте **один явно выбранный алгоритм проверки паролей для каждого SQL-провайдера**. Продолжают работать `argon2id`, `bcrypt`, `pbkdf2-sha256` и включаемый отдельно `legacy-sha256`. Дополнительно поддерживаются Gravit AdditionalHash: `digest`, `doubleDigest` и переносимый WordPress PHPass (`$P$`, `$H$`). Для дайджестов явно выбирается `md5`, `sha1`, `sha256` или `sha512`; формат записанного значения — `hex` (по умолчанию) либо канонический `base64` с дополнением. `doubleDigestHex: true` хеширует шестнадцатеричную строку первого дайджеста в нижнем регистре, `false` — его исходные байты. Дайджесты Gravit **не имеют соли**, PHPass хранит соль и число итераций внутри хеша. Не предполагайте совместимость с пользовательскими солями CMS, нестандартными алгоритмами паролей или любыми сторонними модулями Gravit.

```json
[
  {
    "id": "gravit-site",
    "driver": "postgresql",
    "dsnEnv": "GRAVIT_SQL_DSN",
    "table": "public.accounts",
    "columns": {
      "id": "uuid",
      "username": "username",
      "email": "email",
      "password": "password_hash",
      "status": "status",
      "minecraftUuid": "minecraft_uuid"
    },
    "password": {
      "algorithm": "doubleDigest",
      "digestAlgorithm": "SHA256",
      "digestEncoding": "hex",
      "doubleDigestHex": true,
      "allowLegacyHashes": true
    },
    "provisioning": {"mode":"explicit-only"}
  }
]
```

Для WordPress `$P$`/`$H$` используйте `password: {"algorithm":"phpass","allowLegacyHashes":true}`. PHPass отвергает нестандартную сложность вне диапазона log2 итераций 7–17 для защиты от перегрузки CPU; bcrypt — отдельный проверяющий алгоритм. Для Gravit `digest` указывайте `algorithm: "digest"` и точные алгоритм/кодировку. Старые дайджесты без соли, особенно MD5/SHA-1, слабы: включайте только для проверенной ранее существующей БД с TLS, короткими сеансами Launcher и ограниченными SQL-правами. В 0.29.4 Launcher не записывает хеши обратно во внешнюю SQL-БД и не выполняет неявное обновление или сброс. Управляемый переход на Argon2id — отдельный этап 0.29.5; изменять можно только собственные записи с разрешением.

При запуске SQL-коннектор открывает **транзакцию только для чтения** и выполняет `SELECT` на ноль строк по настроенным столбцам. Драйвер обязан подтвердить наличие таблицы и каждого столбца; поля пароля и Minecraft UUID не должны иметь бинарный тип БД. Отсутствующие поля, нехватка прав или несовместимая схема блокируют запуск провайдера ещё до попытки входа. Предпросмотр отображения показывает только логические поля, имена SQL-столбцов и типы — никогда записи или хеши паролей. SQL-идентификаторы проверяются и экранируются для конкретного диалекта; пользовательский ввод привязывается параметрами. После проверки схемы готовятся запрос и проверка состояния подключения.

Для живых тестов направьте `LAUNCHER_SQL_TEST_POSTGRES_DSN`, `LAUNCHER_SQL_TEST_MYSQL_DSN` и `LAUNCHER_SQL_TEST_MARIADB_DSN` на изолированные одноразовые БД. Workflow `sql-mapping-legacy-hash-0294.yml` поднимает все три движка; до промышленного запуска должны пройти правильный/неверный пароль, ошибка отображения и отказ неизвестному хешу. Справка Gravit: https://gravitlauncher.com/auth/ (PasswordVerifier); AdditionalHash: https://github.com/GravitLauncher/LauncherModules.

## Работающий Gravit FileAuthSystem — 0.42.6

Launcher умеет проверять вход непосредственно по **доступному только для чтения** `FileAuthSystem/Database.json` Gravit; прежний одноразовый импорт остаётся. Коннектор включается отдельно, не смешивается с `local` и не читает `Sessions.json`. UUID Gravit — неизменяемый внешний идентификатор субъекта и утверждение `minecraftUuid`. Launcher выдаёт собственные сеансы и **не** импортирует роли администраторов Gravit, access-токены, разрешения, скины и исходные сеансы.

```sh
LAUNCHER_AUTH_FILE_PROVIDERS_JSON='[{"id":"gravit-files","displayName":"Gravit FileAuth","databasePath":"/run/launcher/gravit/FileAuthSystem/Database.json","passwordFormat":"phpass","provisioning":{"mode":"jit","defaultRole":"player"}}]'
```

Используйте только один источник: `LAUNCHER_AUTH_FILE_PROVIDERS_JSON` или `LAUNCHER_AUTH_FILE_PROVIDERS_FILE` (файл с тем же JSON-массивом). `databasePath` должен быть абсолютным, оканчиваться `Database.json` и указывать на обычный файл, **недоступный всем пользователям**. В Docker подключайте настоящий файл или каталог через bind mount только для чтения; переменная окружения сама не монтирует хостовый путь. `passwordFormat` обязателен, значение `auto` запрещено (поддерживаемые форматы определены в `internal/fileauth`). `provisioning.mode: "explicit-only"` — значение по умолчанию с предварительной аутентифицированной привязкой; `jit` создаёт Launcher-аккаунт **только** с настроенной ролью Launcher, обычно `player`. Для промышленной среды задавайте явную маршрутизацию или обязательный `providerId`.

Коннектор проверяет источник при запуске, перед каждым входом/поиском хеширует и проверяет байты и повторно использует неизменяемый разобранный снимок только при точном совпадении содержимого. Отсутствующий, повреждённый, заменённый при чтении файл, символическая ссылка, чрезмерный размер или запрет чтения приводят к **отказу без понижения требований**. Обновляйте источник атомарной заменой (приватный временный файл, fsync, rename); редактирование `Database.json` на месте может вызвать временные ошибки входа. Изменённый пароль FileAuth действует при следующей авторизации. Ранее выданный сеанс Launcher независим и живёт по политике времени/отзыва Launcher; смена исходного пароля сама по себе **не отзывает его немедленно**.

Исторические Gravit `digest` и `doubleDigest` предназначены **для проверки** старых паролей, **не для безопасного нового хранения**. Импортированные локальные аккаунты Launcher при первом успешном входе атомарно (CAS) пересчитывают допустимые старые пароли в Argon2id. Работающий FileAuth только для чтения **не может** переписать хеш источника; для обновления переводите пользователей в собственные аккаунты. Поддерживаются явно определённые PHPass и старые дайджесты; неизвестные сторонние соли CMS, произвольная Java-логика Gravit и пользовательские форматы паролей не поддерживаются. Live-провайдер не пишет состояние авторизации в Gravit и не является бинарно-совместимым Java-модулем Gravit.
