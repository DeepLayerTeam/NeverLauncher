# SkiF4er ID — NeverLauncher 1.0.4

1. В realm `skif4er` зарегистрируйте отдельный public OIDC client (например `neverlauncher-desktop`). Standard flow включён, implicit/direct access grants выключены, PKCE S256 обязателен. Redirect URI: строго `http://127.0.0.1:8765/callback`. Scopes: openid profile email. Подтвердите email пользователя.
2. Установите `LAUNCHER_SKIF4ER_ID_CLIENT_ID` в Backend и перезапустите его. Пустая настройка отключает интеграцию. Не добавляйте одновременно generic OIDC provider с ID `skif4er-id`. Секрет не требуется.
3. Обновите Backend и Desktop вместе. Используйте HTTPS Backend (HTTP допускается только на localhost для разработки). На экране входа нажмите «Войти через SkiF4er ID». Вернитесь в Desktop после callback.

Backend выполняет discovery, обмен кода, проверку RS256/JWKS, issuer, audience, nonce, срока действия, подтверждённого email и соответствия sub в UserInfo. Создание аккаунта осуществляется существующей федерацией по identity, с ролью player, без автоматической привязки по совпадению email. Применяются существующие политики MFA, ограничения входа, device trust, аудит и локальная ротация сессии. Desktop сохраняет локальные токены в keyring ОС. Keycloak-токены не передаются renderer. Истечение ожидания callback — 5 минут. Если локальная политика требует MFA, Desktop показывает отдельный challenge TOTP/recovery либо WebAuthn. Выход Desktop отзывает локальную сессию, не завершает глобальный SSO Keycloak.

Проверки: `go test ./internal/oidcconnector ./internal/httpapi` из services/api; `cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml skif4er_login`; `npm run build` из apps/desktop. Реальная приёмка требует зарегистрированного клиента, доступного Keycloak и платформенного keyring. Проверить успешный вход, отказ, неверный state, повтор callback, занятый порт, восстановление сессии и локальный выход.


## Управление идентичностями (1.0.2)

1. Обновите Backend и Desktop одновременно. Войдите в существующий аккаунт Launcher; для привязки требуется аутентификация не старше 15 минут.
2. В разделе авторизации откройте «Связанные идентичности» и нажмите «Привязать SkiF4er ID». Keycloak запрашивает повторный вход (`prompt=login`). Завершите подтверждение в браузере.
3. Список обновляется после успешной операции. Привязка не меняет канонический ID пользователя, роли или текущую сессию. Уже привязанный к другому пользователю субъект отклоняется с 409; совпадение email не объединяет аккаунты.
4. Для отвязки выйдите из внешней сессии и заново войдите с локальным паролем, затем подтвердите удаление связи. Без активного локального способа входа удаление запрещено. Удаление не удаляет аккаунт Keycloak или Launcher, но отзывает сессии Launcher, созданные через эту связь. Для возврата в тот же локальный аккаунт привяжите SkiF4er ID повторно **до** нового самостоятельного входа через SkiF4er ID: при включённом JIT самостоятельный вход после отвязки может создать отдельный аккаунт.
5. Операции: `GET /api/v1/auth/identities`, `POST /api/v1/auth/providers/skif4er-id/link/begin`, `POST /api/v1/auth/providers/skif4er-id/link/complete`, `DELETE /api/v1/auth/identities/{identityId}`. Нужен Bearer-токен текущей сессии; начало и завершение привязки используют одну и ту же сессию. Старая незавершённая транзакция 1.0.1 должна быть начата повторно.

Проверки регрессий: `go test ./internal/repository ./internal/httpapi ./internal/federation` из `services/api`; для PostgreSQL требуется отдельная тестовая БД. Ручная приёмка: привязка существующего аккаунта, повторный вход через SkiF4er ID в него, отказ другому владельцу, отвязка, отказ старому access/refresh-токену, сохранение локальной сессии, отказ при отсутствии локального пароля, повторная привязка с новым ID. Реальный Keycloak и нативный Desktop необходимо проверить в целевом окружении.


## Desktop Authentication (1.0.3)

- Вход выполняется через системный браузер с одноразовой транзакцией Backend, фиксированным loopback URI и возможностью отмены из Desktop. Сессия сохраняется только после успешного ответа Backend. В 1.0.3 отдельный локальный MFA continuation отклонялся; в 1.0.4 он реализован (см. ниже).
- Вход по паролю и SkiF4er ID, проверка сохранённой сессии, ротация и выход выполняются в Rust. В WebView возвращаются только access token, ID сессии/пользователя, email и срок действия access token. Refresh token не передаётся через IPC и не записывается в конфигурацию, localStorage или журналы. Старые записи keyring 1.0.2 читаются без миграции.
- Backend должен быть HTTPS с корневым URL; HTTP разрешён только для локального localhost/127.0.0.1. HTTP redirects в нативных запросах с credentials запрещены. При запуске после загрузки нативной конфигурации проверяется `/api/v1/auth/identities`; каждые 30 секунд выполняется повторная проверка, при оставшемся сроке до 90 секунд — ротация. При 401 с ещё действующим по локальному времени access token сохранённая сессия удаляется; при истёкшем токене используется refresh с подтверждением ключом устройства, если требуется. При временной сетевой ошибке до ротации интерфейс не считает пользователя авторизованным и повторяет проверку. Перед отправкой refresh удаляется старый credential: если результат запроса потерян, требуется новый вход, чтобы не повторять использованный refresh. Файл `auth-session.lock` содержит только блокировку, не credentials; процессы с общим каталогом конфигурации не ротируют токен одновременно.
- Выход сначала удаляет локальные credentials, затем отзывает сессию через Backend. Если access token истёк, допускается однократная ротация исключительно для отзыва без повторного сохранения. При отсутствии подтверждения Backend интерфейс сообщает об этом отдельно. Глобальная SSO-сессия Keycloak не завершается: выход относится к NeverLauncher, а следующий браузерный вход может использовать SSO. Для глобального выхода используйте интерфейс SkiF4er ID.

Проверка: `cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml desktop_auth`, `cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml skif4er_login`, `npm run test:auth-experience`, `npm run build` (последние две команды из `apps/desktop`). Ручная приёмка на Windows/macOS/Linux с системным keyring и зарегистрированным Keycloak client: вход, отмена, истечение callback, перезапуск, истечение access token, подпись привязанного устройства, временно недоступный Backend, потеря ответа refresh, отозванная сессия, выход онлайн/офлайн, конкурентный запуск Desktop, повторный вход. Проверить отсутствие refresh token в DevTools/IPC. При смене Backend проверить, что старые токены не передаются новому серверу.


## Authentication Security (1.0.4)

- Обновите Backend и Desktop одновременно. Для входа с локальным паролем также можно указать TOTP или recovery-код (например, для последующей отвязки). Если у аккаунта включён локальный TOTP, после Keycloak Desktop показывает форму кода или recovery. Если требуется устойчивый к фишингу passkey либо единственный доступный метод — passkey, используется существующий WebAuthn challenge. Для WebAuthn нужна поддержка `navigator.credentials.get` в целевом WebView и соответствие настроенных RP ID и origins фактическому безопасному origin приложения; не отключайте проверку origin. Если WebView не поддерживает этот сценарий, вход отклоняется; используйте поддерживаемый клиент.
- `POST /api/v1/auth/oidc/skif4er-id/complete` возвращает 202 `mfa-required` без локальных токенов. Для TOTP/recovery `POST /api/v1/auth/oidc/skif4er-id/mfa/complete` принимает одноразовый `transactionToken` и ровно один фактор: `totp` или `recoveryCode`. Passkey использует существующий `/api/v1/auth/passkeys/mfa/complete`. Challenge действует до 5 минут, расходуется при первой валидной по формату попытке завершения; после серверного отказа требуется новый браузерный вход. При отмене токен challenge удаляется из нативного процесса. Никаких токенов сессии до MFA.
- Challenge связан с каноническим пользователем, конкретным ID внешней идентичности, провайдером и устройством. Внешние AMR не считаются локальным MFA. Отвязка, смена политики или отключение аккаунта до завершения проверки препятствуют выдаче сессии. Уже выданные SkiF4er-сессии с недостаточным локальным фактором отклоняются и отзываются при следующей проверке/ротации. Ошибка чтения политики не ослабляет MFA. Повтор подтверждённого TOTP при входе SkiF4er ID отклоняется в течение окна защиты 120 секунд; recovery расходуется существующим атомарным хранилищем. Защита распространяется на SkiF4er ID, не заменяет общую политику TOTP других методов входа.
- PostgreSQL использует существующие транзакционные хранилища challenge и nonce; SQLite — существующее шифрованное runtime-хранилище и durable nonce; Memory предназначен для разработки. Новый формат БД не требуется.
- Не сохраняйте query string OIDC callback в access-логах reverse proxy. Backend не должен логировать тела auth-запросов. Аудит фиксирует отказ, повтор callback, MFA challenge, успешный вход, refresh и отзыв без кода, пароля, state или токена.
- Приёмка: `go test ./internal/httpapi -run 'TestSkif4erMFA104|TestBrowserReplayAcrossAPIReplicas0525'` из `services/api`. Дополнительно проверьте нативный `cargo test ... skif4er_login`, реальную платформу, Keycloak, правильный и неверный TOTP, повтор TOTP, одноразовый recovery, отмену и истечение challenge, passkey RP/origin, отвязку между callback и MFA, ротацию и отзыв refresh. Обязателен запуск на фактическом Go/Rust/Tauri toolchain; тестовая фикстура OIDC не заменяет реальный Keycloak.
