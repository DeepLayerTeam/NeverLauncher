# Launcher 0.50.5 — принудительный контроль целостности Runtime

## Применение защитных мер (рабочий код, а не флаг возможностей)

Источниками доверия являются **проверенный манифест выпуска**, проверенная политика ClientFactory/Guard с подписью Ed25519 и установленный доверенный агент JVM. Rust Runtime запускает Java только после проверки точных выбранных JAR из путей классов и модулей Java и нативных релизных артефактов по подписанному манифесту, а также модов, JAR загрузчика, агента Java, доверенных плагинов и нативных библиотек, разрешённых независимо подписанной политикой совместимости Guard. Принятая эпоха политики, отзывы, область действия, срок действия и внешний открытый ключ повторно проверяются через `guard_compatibility_0502`. Изменённый, отсутствующий, заменённый символической ссылкой или конфликтующий исполняемый файл блокирует запуск.

При запуске Rust создаёт **приватную краткоживущую конфигурацию premain** из проверенных входных данных. `RuntimeIntegrity0505` повторно рассчитывает хеши фактических файлов в этой конфигурации перед выполнением исходного main Minecraft и сверяет **эффективное значение `java.class.path`** JVM с разрешёнными JAR. При определении класса пути JAR, полученные из `CodeSource` внутри установленной игры, должны принадлежать подписанным файлам кода. Затем монитор повторно хеширует закреплённые файлы и примерно каждые **четыре секунды** сканирует исполняемые элементы `mods/` и `natives/`. Несовпадение, неожиданный исполняемый файл или символическая ссылка завершают JVM с кодом **79**; резервного варианта «только успешный аудит» нет. Монитор работает как демон и не претендует на устойчивость к произвольному вредоносному коду с полными привилегиями того же процесса.

В **Linux** монитор JVM также читает реальные исполняемые отображения `/proc/self/maps` и требует точный одобренный SHA-256 для нативных `.so` из корня игры. Удалённые отображённые файлы и неподписанные игровые библиотеки отклоняются. Нативные файлы выбранного отдельно проверенного управляемого дистрибутива Java относятся к границе доверия управляемой Java и не переопределяются как пользовательские моды. Эта внутрипроцессная проверка Linux **не** является системной или ядерной аттестацией.

В **Windows** аутентифицированный нативный Module Guard теперь получает точные хеши DLL из подписанного релиза и политики Guard для защищаемого запуска игры. Он отклоняет неподписанные и изменённые загруженные DLL во всём корневом каталоге установленной игры при первоначальном осмотре и аутентифицированных событиях загрузки/согласования, кроме отдельно проверенного каталога управляемой JRE и точной заранее закреплённой DLL Guard Sensor. Прежние самостоятельные правила доверия к системным файлам, JRE и Guard Sensor сохраняются. Новым DLL модов не предоставляются разрешения на весь корень. В macOS выполняется проверка артефактов перед запуском и Java-монитор файлов, но в 0.50.5 **не заявляется перечисление загруженных нативных образов во время работы**.

Прежний **Go ClientFactory** создаёт действующий реестр целостности из артефактов подписанной политики Guard и отклоняет изменённые либо отозванные исполняемые входные файлы перед premain. Его монитор JVM намеренно использует `integrity.code.strict=false`, поскольку этот старый путь пока не может предоставить полный эффективный подписанный путь классов Java (classpath), как Rust Runtime. Нельзя утверждать, что контроль происхождения classpath здесь равнозначен современному нативному запуску. Существующие проверки целостности перед созданием процесса по-прежнему действуют.

## Порядок развёртывания оператором

1. Создайте и подпишите совместимый релизный Manifest со всеми выбранными JAR из путей классов и модулей Java и нативными артефактами. Необязательные выбранные компоненты должны присутствовать в активном пресете и проходить проверку. Не считайте сгенерированные неподписанные нативные файлы разрешёнными только потому, что они находятся рядом с каталогом `natives/`.
2. Опубликуйте подписанную политику Guard со всеми исполняемыми модами, JAR загрузчика, доверенным агентом Java, JVM-плагинами и нативными библиотеками, указанными по точному относительному пути от корня клиента и SHA-256 в нижнем регистре. Поддерживайте монотонно возрастающую неотозванную эпоху и храните открытый ключ вне установленного клиента. Для защищаемых проектов сохраняйте `LAUNCHER_GUARD_COMPAT_REQUIRED=1`.
3. Установите пакет Trusted JVM с точно одобренным Guard хешем агента и запустите клиент обычным Runtime. **Не** добавляйте вручную неподписанные `-javaagent` или `-agentpath`. Ранее работавший модпак с распакованными или нативными файлами, отсутствующими в подписанном реестре, намеренно **блокируется** до их объявления и повторной подписи.
4. Исследуйте ошибки `[Launcher Guard 0.50.5]` и `Guard runtime inventory`. Для исправления заново скачайте и проверьте подписанный релиз либо установите новую корректно подписанную политику Guard. Не добавляйте глобальных исключений Java или файловой системы.

## Что проверено и что не проверено

- **Локально:** агент, совместимый с Java 8, собран с OpenJDK 21. Скрипт `scripts/tests/guard_runtime_integrity.py` выполнил **семь реальных испытаний дочерних процессов JVM**: разрешённые и заменённые JAR, неподписанный JAR в пути поиска классов, поздно добавленный неодобренный мод и загрузка разрешённых/неразрешённых нативных библиотек Linux. Целевые Go-тесты завершились успешно. Метаданные версии релиза прошли `scripts/version/manage.py check`.
- **Локально не выполнялись:** нативная компиляция Rust, работа датчика Windows x64/ARM64, нативные сборки macOS, CI для шести платформ, опубликованные подписанные установщики, настоящий запуск Minecraft с исходными загрузчиками Fabric/Quilt/Forge/NeoForge, официальный вход и подключение к серверу. Процесс CI планирует такие проверки, но **не** является доказательством их завершения. Статус **GA для 0.50.5 остаётся BLOCKED**.
- Четырёхсекундное сканирование хешей выявляет устойчивые изменения файлов, но не гарантирует отсутствия кратковременных окон между проверкой и использованием. Guard не контролирует каждое преобразование загрузчика классов Java или путь нативного внедрения в ОС. Ни одна клиентская политика в одном процессе не образует песочницу против полностью доверенного вредоносного кода Java/Native. Независимая серверная проверка и отзыв политики/сессии остаются задачами следующих этапов.
