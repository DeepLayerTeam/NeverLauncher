# NeverLauncher 0.50.5 — Runtime Integrity Enforcement

## Enforcement (code, not a capability flag)

A **verified release Manifest**, verified ClientFactory/Guard Ed25519 policy and an installed Trusted JVM Agent are the sources of authority. The Rust Runtime launches Java only after checking the exact selected classpath/modulepath JARs and native release artifacts against the signed Manifest, plus the mods, loader JARs, Java agent, trusted plugins and native libraries authorized by the independently signed Guard compatibility policy. The Guard policy's accepted epoch, revocations, scope, expiry and external public key are rechecked via `guard_compatibility_0502`. A modified, missing, symlinked or conflicting executable file prevents the launch.

The Rust launch generates a **private short-lived premain configuration** from verified inputs. `RuntimeIntegrity0505` rehashes the actual files in that configuration before Minecraft's original main runs and checks the JVM's **effective `java.class.path`** against authorized JARs. At class definition, `CodeSource` JAR paths inside the game installation must come from signed code files. It then rehashes the pinned files and scans executable `mods/` and `natives/` entries approximately every **four seconds**. A mismatch, unexpected executable or symlink terminates the JVM with code **79**; there is no success-only audit fallback. The monitor runs as a daemon and does not pretend to survive arbitrary hostile code with full same-process privileges.

On **Linux** the JVM monitor additionally reads its real `/proc/self/maps` executable mappings and requires the exact approved SHA-256 for native `.so` images mapped from the game root. Deleted mapped files and unsigned mapped game libraries are rejected. Native images from the selected independently verified managed Java distribution are handled by the managed-Java trust boundary rather than being reclassified as user mods. This in-process Linux check is **not** a system-wide or kernel attestation.

On **Windows** the authenticated native Module Guard now receives exact native DLL hashes from the signed release and Guard policy for guarded game launches. It rejects unsigned/changed loaded DLLs anywhere in the game installation root during baseline and authenticated load/reconciliation events, except for the independently verified managed-JRE home and the exact pre-pinned Guard Sensor DLL. Existing separate system/JRE/Guard Sensor trust handling remains; this does not grant full-root permissions for new mod DLLs. On macOS, pre-launch artifact verification and the Java file monitor run, but **live native image enumeration is not claimed** in 0.50.5.

The legacy **Go ClientFactory** generates a live integrity inventory from signed Guard-policy artifacts and refuses changed/revoked executable inputs before premain. Its JVM monitor intentionally uses `integrity.code.strict=false`, because this legacy path cannot yet provide the Rust Runtime's complete effective signed classpath. Do not claim that its classpath origin enforcement equals the modern native launch. The existing legacy pre-spawn integrity checks continue to apply.

## Operator rollout

1. Produce and sign a compatible release Manifest containing every selected classpath/modulepath JAR and native artifact. Optional selected components must be included in the active preset and verified. In particular, do not treat generated native binaries that are not signed as approved by proximity to the `natives/` directory.
2. Publish a signed Guard policy containing every executable mod, loader JAR, Trusted Java Agent/JVM plugin and native library under its exact client-root-relative path and lowercase SHA-256. Maintain a non-revoked monotonic epoch and store the public key outside the client installation. Keep `LAUNCHER_GUARD_COMPAT_REQUIRED=1` for guarded projects.
3. Install a Trusted JVM package with the exact signed Guard-approved agent hash, then launch through the normal Runtime. Do **not** manually add unsigned `-javaagent` or `-agentpath` options. A previously working modpack with unpacked/native files not in a signed inventory is intentionally **blocked** until those artifacts are declared and re-signed.
4. Investigate `[Launcher Guard 0.50.5]` / `Guard runtime inventory` failures. Repair by re-downloading and verifying signed releases or installing a newer properly signed Guard policy. Do not add global Java or filesystem exemptions.

## What is verified and what is not

- Local: the Java 8-compatible agent compiled using OpenJDK 21. `scripts/tests/guard_runtime_integrity_0505.py` executed **seven real JVM subprocess tests**, including authorized and replaced JARs, an unsigned classpath JAR, a late unapproved mod, and authorized/unauthorized native library loading on Linux. Targeted Go tests completed successfully. Release version metadata passed `scripts/version/manage.py check`.
- **Not performed locally**: native Rust compilation, Windows x64/ARM64 module sensor behavior, macOS native builds, six-target CI, published signed installers, real upstream Fabric/Quilt/Forge/NeoForge Minecraft launch, legitimate login and join. The workflow schedules these checks; it does **not** constitute their completed evidence. The 0.50.5 **GA status remains BLOCKED**.
- A four-second file hash scan detects persistent edits; it cannot guarantee zero transient time-of-check/time-of-use windows. The guard does not mediate every Java class-loader transform or OS-native injection route. No client-side same-process policy is a sandbox against fully trusted hostile Java/native code. Independent server-side verification and policy/session revocation remain subsequent milestones.
