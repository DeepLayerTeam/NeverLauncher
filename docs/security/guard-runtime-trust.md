# Guard 0.31.7 — список разрешённых Runtime и серверное применение политики

Сервер **не** делает вывод, что JVM защищена, только на основании аппаратно защищённого Device Key, результата TPM Certify или цитаты PCR. Эти механизмы подтверждают **разные** свойства. Текущий Windows Guard v2 — это **наблюдение пользовательского режима с подписью устройства**. Оно не гарантирует отсутствие вредоносного привилегированного внедрения в JVM, вмешательства ядра или подмены всей клиентской среды.

## Включение авторизации Runtime в Windows

Перед развёртыванием API `0.31.7` настройте `LAUNCHER_GUARD_RELEASE_ALLOWLIST_JSON` с Windows-профилями `runtimeProfiles` для каждого разрешённого релиза Desktop. В backend версии 0.31.7 и новее отсутствие профилей при наличии Windows-релиза считается **ошибкой конфигурации**, а не откатом на Guard v1. Это распространяется и на старые версии, оставленные в списке релизов во время последовательных обновлений.

Указывайте собственные *измеренные и проверенные* SHA-256, никогда — буквальные значения-заполнители. Прежнее требование пары `guardSha256` + `launcherSha256` сохраняется.

```json
{
  "schemaVersion": "2.0",
  "releases": {
    "0.31.7": {
      "protocolVersion": 4,
      "platforms": {
        "windows": {
          "signingMode": "authenticode",
          "artifacts": [{
            "guardSha256": "<SHA-256 УТВЕРЖДЁННОГО ИСПОЛНЯЕМОГО ФАЙЛА GUARD>",
            "launcherSha256": "<SHA-256 УТВЕРЖДЁННОГО ИСПОЛНЯЕМОГО ФАЙЛА ЛАУНЧЕРА>",
            "requireAuthenticode": true
          }],
          "runtimeProfiles": [{
            "javaMajor": 21,
            "moduleSetSha256": "<SHA-256 ПРОВЕРЕННОГО НАБОРА МОДУЛЕЙ СРЕДЫ ВЫПОЛНЕНИЯ>"
          }]
        }
      }
    }
  }
}
```

`moduleSetSha256` и `javaMajor` обязательны для каждого профиля Runtime. Необязательные `codeSetSha256` и `hookSetSha256` можно указывать для дополнительного ограничения образов кода и хуков, если их значения достаточно воспроизводимы. Ограничьте права доступа к операторской конфигурации политики. Одобрение не может исходить из манифеста расширения или объекта политики, отправленного клиентом.

**Путь применения политики:** аутентифицированная сессия и активное проверенное доверенное устройство → одноразовое случайное значение (nonce), созданное сервером → подписанные свидетельства Windows Guard v2 → проверка пары релизных артефактов → точное совпадение политики Runtime → краткоживущий одноразовый билет → новая проверка сессии, устройства и эпохи → при подключении повторная проверка активного устройства, свежести аттестации, текущей пары артефактов и отпечатка политики Runtime. Смена или удаление одобренного набора модулей аннулирует ранее выданные, но ещё не использованные билеты. Это **не** сохраняет доверие за пределами подключения к игре. Для защиты длительных игровых сессий нужны отдельные постоянные задачи/ответы и серверная проверка активности.

При успешной передаче v2 сервер возвращает `runtimeAssurance=device-signed-user-mode-observation`, но **не** предоставляет на этом основании уровень удалённо проверенной гарантии Guard Runtime или профиль `strict`.

## Эксплуатационное восстановление и негативные тесты

- При `412 Guard runtime denied` проверьте одобренную версию JVM и набор модулей. **Не** разрешайте неизвестный набор автоматически.
- При `Continuous Guard runtime policy changed after attestation` заново начните аттестацию после проверки и одобрения администратором нового набора модулей.
- При восстановлении устройства или смене ключа получите новую аттестацию для текущего устройства и эпохи привязки; прежние билеты обязаны отклоняться.
- Проверьте отозванную пару Windows-артефактов, неизвестную основную версию Java, изменённый хеш модулей, изменение политики, повторное использование израсходованного билета и отозванное устройство.
- Стандартные профили Linux и macOS сохраняют платформенные проверки Guard v1. **Применение политики Windows v2 для Runtime не означает кроссплатформенную изоляцию ОС или абсолютную защиту от читов.**
