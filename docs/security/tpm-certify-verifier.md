# Launcher 0.31.2 — проверка TPM Certify и корни доверия AK

## Принудительно обеспечиваемое поведение

API принимает **настоящие подтверждения TPM2 `Certify`** через `POST /api/v1/auth/devices/{deviceId}/tpm-certify/begin` и `/complete` для аутентифицированных, актуально привязанных и проверенных **аппаратных устройств P-256**, зарегистрированных в Windows или Linux. При `begin` создаётся криптографически стойкий случайный вызов; в существующем одноразовом хранилище хранится только его SHA-256, а клиенту возвращается хеш SHA-256 с разделением доменов для TPM `extraData`, вместе с `issuedAt`, `expiresAt`, ID сеанса и `bindingEpoch`. Клиент ничего не подписывает серверным секретным ключом: TPM AK подписывает TPMS_ATTEST, сформированный `TPM2_Certify` для ранее зарегистрированного ключа идентичности устройства.

При `complete` Backend **атомарно расходует** вызов (в том числе при неудачной проверке), заново сверяет текущий связанный сеанс, метаданные вызова и отпечаток устройства и разбирает бинарные TPM2B_PUBLIC, TPM2B_ATTEST и TPMT_SIGNATURE. Проверяются TPM `magic`, `TPM_ST_ATTEST_CERTIFY`, точное `extraData` SHA-256, TPM Name подтверждаемого объекта, действительный P-256 ключ подписи с fixedTPM/fixedParent/sensitiveDataOrigin, зарегистрированный открытый ключ SEC1 и подпись AK по ECDSA-P256, RSA PKCS#1 v1.5 или RSA-PSS SHA-256. Конечный сертификат AK обязан быть сертификатом подписи без полномочий CA и иметь действительную цепочку X.509 к **настроенному оператором CA сертификации AK**. Ограничения сертификата, срок действия, статус корня и отзывы по умолчанию блокируют доступ.

Проверенный результат сохраняется отдельно в `device_hardware_evidence_0312` (PostgreSQL) или репозитории в памяти, а не в историческом заявлении `trusted_devices.remote_hardware_provenance`. Запись содержит точный отпечаток сертификата корня SHA-256 (не позволяет повторному использованию ID корня оживить старое доказательство), отпечаток AK, сеанс, эпоху, отпечаток ключа и срок **не более часа**. `GET /api/v1/auth/device-trust` каждый раз заново проверяет запись, эпоху, сеанс и обновлённую политику корней доверия. Отзыв корня/AK, замена ключа, истёкший срок или другая эпоха сеанса **сразу понижают** эффективное аппаратное доверие. Профиль `strict` при этом продолжает **отказывать**: TPM-происхождение ключа не доказывает измеряемую загрузку, целостность процесса или Guard.

## Создание и отзыв корня доверия оператором

`LAUNCHER_TPM_AK_ROOTS_FILE` должен указывать на абсолютный путь к **обычному файлу**, подготовленному и контролируемому администратором Backend. Сервер не загружает автоматически и не доверяет произвольным цепочкам издателей, корням EK и сертификатам от устройства. Отсутствующий/повреждённый файл означает отказ, заявленное имя провайдера не является доказательством. Разрешите запись в файл только администраторам. Пример (используйте настоящий PEM издателя AK, а не обычный публичный корень WebPKI):

```json
{
  "schema": "launcher/tpm-ak-trust-roots/v1",
  "roots": [{
    "id": "ak-issuer-prod-2026",
    "certificatePem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
    "status": "active",
    "notBefore": "2026-10-01T00:00:00Z",
    "notAfter": "2027-10-01T00:00:00Z",
    "platforms": ["windows", "linux"]
  }],
  "revokedAkFingerprints": []
}
```

Ротация: добавьте второй активный корень, проверьте переход сертификатов клиентов, затем установите старому `revoked` или удалите его. Для немедленного отзыва AK добавьте в `revokedAkFingerprints` SHA-256 DER конечных сертификатов AK в нижнем регистре. JSON заменяйте **атомарно** (временный файл, fsync, rename). Сервер перечитывает корни при каждой проверке и запросе статуса, перезапуск не нужен. Не выдавайте сертификаты AK через CA, который независимо не проверяет аппаратное происхождение: программный AK с произвольным X.509 **не является надёжной TPM-аттестацией**. Настроенный издатель и правила регистрации образуют критичную границу доверия.

## Формат передачи

Передайте поля `begin` в запрос `complete`:

```json
{
  "challengeId": "htc_...",
  "challenge": "htn_...",
  "evidence": {
    "tpm2bPublic": "<байты в base64url без заполнения, включая внешний размер>",
    "tpm2bAttest": "<байты в base64url без заполнения, включая внешний размер>",
    "tpmtSignature": "<байты TPMT_SIGNATURE в формате base64url без заполнения>",
    "akCertificatePem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
    "intermediatesPem": []
  }
}
```

`TPM2_Certify.qualifyingData` должно совпадать с возвращённым `tpmExtraDataSha256` (декодирование base64url без padding в дайджест 32 байт). Дайджест связывает пользователя, устройство, сеанс, эпоху привязки, ID вызова, nonce, время выдачи и срок истечения. Подтверждайте TPM-объект, чья открытая часть совпадает с **уже зарегистрированным** открытым ключом устройства. Клиент не вправе прислать новый ключ для замены прежнего. Проверяющая сторона принимает только SHA-256 и TPM ECC NIST-P256 ключи объектов подписи с пустыми symmetric/scheme/KDF; прочие даже легитимные конфигурации TPM явно отклоняются без подтверждённого статуса.

## Границы безопасности

- TPM2_Certify подтверждает, что TPM AK удостоверяет имя/свойства TPM-объекта, **если** издатель AK действительно проверил TPM-происхождение. **Это не доказательство PCR, измеряемая загрузка или целостности пользовательского процесса**. TPM Quote/PCR и принуждение Guard — отдельные последующие этапы.
- Производители доказательств TPM для Windows/Linux реализуются отдельно в 0.31.3/0.31.4; здесь предусмотрены общий исполняемый проверяющий Backend и протокол. В macOS не поддерживается универсальное утверждение о происхождении открытого ключа Secure Enclave.
- Тестовый CA не является доверенным промышленным издателем. Не используйте тестовые корни в production; цепочка от EK сама по себе недостаточна без обязательных проверок подготовки TPM и активации учётных данных.
- Старый `challenge-response-v1` доказывает только владение ключом и не повышает аппаратное доверие. Backend не переводит устройство незаметно в `strict`; запись в старое поле БД сама по себе не может повысить доверие.

## Проверка

Выполните из `services/api`:

```sh
go test -race -count=1 ./internal/attestverify ./internal/trustbaseline ./internal/repository ./internal/httpapi
go build ./cmd/launcher-api
```

`internal/attestverify` использует только стандартную библиотеку Go и допускает автономную проверку. Тестовые фикстуры создают настоящие X.509-ключи CA/AK, криптографически подписывают заявление в формате TPM2 Certify и проверяют неправильные ключи, имена, nonce, сеансы, пользователей, устройства, эпохи, сроки, подписи, отзыв корней и AK. Это доказывает работу проверяющего, но не сертифицирует реальные TPM-прошивки и промышленных издателей AK.
