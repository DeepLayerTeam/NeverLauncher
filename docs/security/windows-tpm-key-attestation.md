# Launcher 0.31.3 — аттестация ключа TPM на Windows

## Реализованный сценарий

Только в Windows функция `windows_tpm_certify_0313` проверяет привязанный `deviceId` локального хранилища ключей, алгоритм, провайдера подписи `hardware-enclave` и зарегистрированный открытый ключ P-256. Она открывает ключ **по исходному имени PCP**, получает через `PCP_PLATFORMHANDLE` дескриптор загруженного TPM-объекта и контекст TBS, затем вызывает `TPM2_ReadPublic`. Возвращённые координаты P-256 и атрибуты происхождения TPM обязаны совпадать с зарегистрированным устройством; новый ключ устройства не создаётся. Отдельный **предварительно зарегистрированный AK** открывается через Microsoft Platform Crypto Provider по имени оператора.

Клиент вызывает существующий `POST /api/v1/auth/devices/{deviceId}/tpm-certify/begin` в рамках аутентифицированного привязанного сеанса. 32-байтовое `tpmExtraDataSha256` с разделением доменов передаётся как `TPM2_Certify.qualifyingData` для объекта и AK. Поля ответа TPM (`TPM2B_PUBLIC`, `TPM2B_ATTEST`, `TPMT_SIGNATURE`) направляются в существующий `/complete` версии 0.31.2. **Только сервер** назначает `tpm-ak-certified` после проверки цепочки сертификатов, свойств ключа, nonce, ID устройства, активного сеанса, эпохи привязки, срока и одноразовости. При следующем запросе статуса доверие корня проверяется снова. Неуспешное доказательство не изменяет уровень доверия устройства.

Заявление на основе `NCryptCreateClaim`, имя CNG-backend, программная подпись или самостоятельно объявленный сертификат не превращаются в подтверждение происхождения. `NCryptCreateClaim` может применять другой временный ключ, а сервер требует AK, реально подписавший `TPM2_Certify`. Состояние PCR/измеряемая загрузка и целостность Guard не подтверждаются.

## Предварительные требования и настройка

1. Физический или встроенный TPM 2.0 с существующим ключом идентичности Windows, сохранённым через **Microsoft Platform Crypto Provider**. Имя PCP должно быть действительным именем созданного `hardware-enclave` ключа. Если библиотека хранит ключ под другим именем либо не выдаёт дескриптор TPM, клиент **отказывает** без незаметной замены ключа или резервного программного варианта.
2. Независимо зарегистрируйте **отдельный аппаратный ключ аттестации (AK)** через доверенный центр сертификации аттестации, *проверяющий настоящее TPM-происхождение AK* (например, привязкой выдачи к учётным данным TPM). Сохраните имя AK в PCP и выданный конечный сертификат X.509 с промежуточными. Launcher не регистрирует AK. Обычный программный CA и самоподписанный AK недопустимы в качестве промышленного доверенного корня.
3. Настройте в Backend `LAUNCHER_TPM_AK_ROOTS_FILE` (см. `tpm-certify-verifier.md`) с настоящим CA издателя AK и разрешённой платформой Windows. Сервер управляет состоянием корня и отзывом AK.
4. Войдите, зарегистрируйте и проверьте P-256 устройство Windows, подтвердите привязку к текущему сеансу. Откройте **Управление устройствами → Аттестация ключа TPM Windows**, укажите имя AK в PCP и подготовленный PEM-сертификат AK (при необходимости промежуточный), затем выполните **Подтвердить TPM-происхождение**. Локальный сертификат — публичные данные; никогда не вставляйте приватные данные AK и секреты EK/AK.

Непосредственный TPM2_Certify использует **два сеанса авторизации с пустыми паролями** для роли ADMIN ключа и роли USER у AK. Объекты с непустым authValue, PolicyAuthorize, требованием присутствия пользователя или авторизацией исключительно через PCP отклоняют команду, возвращая ошибку TPM в UI. Пока нет реализации нужных авторизованных сеансов, **такое оборудование не поддерживается**. Нельзя подменять проверку недостоверными метаданными. Backend не принимает экзотические неподдерживаемые форматы ключей и недоверенных издателей. Сам факт наличия TPM не означает совместимость со всеми политиками Windows Hello и корпоративной подготовки устройств.

## Безопасность и ошибки

- Хост Windows, зарегистрированный ключ, AK и сертификат издателя должны указывать на действительные ключи TPM. Другое имя, несовпадение ключа, отсутствие TPM, контекста TBS, поддерживаемого сеанса авторизации или параметров TPM, неправильная цепочка X.509, отозванный корень/AK либо истёкший/повторный вызов вызывают явную ошибку **без подтверждения аппаратной идентичности**.
- Ключи устройства и AK остаются под управлением ОС/TPM. Desktop не экспортирует приватные данные и не записывает секретные ключи устройства в журналы. Файл корней доверия существует только на сервере; присланный клиентом PEM не является корнем доверия.
- `TPM2_ReadPublic` криптографически сопоставляется с зарегистрированным ключом точным сравнением SEC1; проверяющая сторона независимо вычисляет TPM Name из `TPM2B_PUBLIC` и проверяет подписанное имя и qualifyingData SHA-256.
- Процесс продолжает работать в пользовательском режиме. Аттестация **не устраняет** возможность злоумышленника изменить или подменить пользовательский процесс. Гарантии измеряемая загрузка или Guard не заявлены; для `strict` нужны отдельные проверки.

## Проверка

На Windows с Rust/MSVC:

```powershell
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml tpm_wire_0313
cargo build --manifest-path apps/desktop/src-tauri/Cargo.toml
```

Повторите испытания минимум у двух производителей TPM 2.0, с одной поддерживаемой пользовательской парой AK/PCP и отозванным CA-сертифицированным AK; соберите подтверждение успешного `/complete`. Платформенные тесты обязательны для выпуска; Linux-тесты не подтверждают поведение Win32/TBS. Устройство с непустой авторизацией отклоняется до реализации нативной авторизации. Сборка и CI необходимы, но не заменяют аппаратную проверку.

При подготовке Windows AK ключ может находиться в **машинном** пространстве имён. Сначала производитель открывает AK у пользователя, затем при необходимости с `NCRYPT_MACHINE_KEY_FLAG`; идентичность устройства всегда открывается у пользователя. Машинный AK должен быть доступен вызывающему аккаунту согласно ACL. Само пространство имён не считается доверенным: сервер проверяет подписанный AK Certify и закреплённого издателя.
