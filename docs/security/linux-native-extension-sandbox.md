# Launcher 0.31.9 — изоляция нативных расширений Linux

## Границы исполняемой защиты

Цели Backend и CLI с подписанным Ed25519 манифестом `sandbox.mode: isolated` используют **один** механизм запуска Linux. Они не передаются старому запускателю групп процессов. Ядро создаёт новые пространства имён пользователя, монтирования, PID, сети, IPC и UTS. Дочерний процесс создаётся сразу в своей cgroup через `CLONE_INTO_CGROUP` (Go `UseCgroupFD`), а не переносится после запуска, что устраняет гонки первоначального расхода CPU и создания дочерних процессов.

Запускатель формирует отдельный корень tmpfs, рекурсивно монтирует проверенный пакет в `/package` только для чтения и аналогично монтирует выбранные системные библиотеки и исполняемые файлы (`/usr`, `/bin`, `/lib*`, `/sbin`). Каталоги `/etc`, `/home`, `/var` и `/run` **не монтируются**; из `/etc` явно разрешены только кэш динамического загрузчика и системные файлы CA. `/proc` изолирован в пространстве PID. Для `/tmp` и `/scratch` используются отдельные tmpfs с ограничениями квоты. `pivot_root` отсоединяет файловую систему узла. `mount_setattr(AT_RECURSIVE, MOUNT_ATTR_RDONLY)` обязателен: без рекурсивного ограничения только для чтения запуск отклоняется.

При инициализации сбрасываются эффективные, разрешённые и наследуемые capabilities, задаются заблокированные securebits, `PR_SET_NO_NEW_PRIVS` и запрещающий фильтр BPF seccomp для изменения пространств имён, манипуляций монтированием, ptrace/process_vm, атакуемых API ядра и привилегированных вызовов. Вход в расширение выполняется через `execve` в том же заблокированном потоке ОС после проверки `/proc/self/status`. Пространства имён пользователя обеспечивают границу изоляции; UID узла отображается на UID 0 внутри пространства имён, **а не** на отдельный выделенный UID узла. Backend должен запускаться под ограниченной непривилегированной служебной учётной записью; службы от root отклоняются.

Ограничения `memory.max`, `memory.swap.max=0`, `pids.max`, `cpu.max` и `cgroup.kill` задают пределы ресурсов. Cgroup создаётся в заранее делегированном поддереве cgroup-v2; отсутствие делегирования или любого требуемого контроллера приводит к жёсткому отказу. Таймер времени жизни расширения по истечении периода убивает всю cgroup, включая потомков, создавших новые группы процессов. Для изолированных пакетов переход к группам процессов узла не допускается.

В сетевом пространстве имён доступен **только loopback**. Внутренний TCP-слушатель передаёт аутентифицированные запросы Host Protocol по закрытой заранее открытой паре Unix-сокетов существующему обработчику HTTP Backend. Сеть узла и каталог секретов Backend не видны. Конфигурация/токен передаются через запечатанный Linux memfd, а не через argv, файл на диске или переменную окружения. Пока отклоняются права на общую ФС, произвольные исходящие сетевые соединения и ограниченные секреты; брокеры ограничений запланированы на 0.31.10. Нативные URL обратных вызовов и Java RPC callback также запрещены до появления защищённого обратного брокера. Доверенные и устаревшие пакеты по-прежнему работают в явно неизолированном режиме; сама подпись не делает их изолированными.

## Предварительные требования к развёртыванию

- Linux x86-64, непривилегированный служебный UID, включённые user namespaces и доступный `clone3(CLONE_INTO_CGROUP)`.
- Поддерево cgroups v2, делегированное службе Launcher (контроллеры `memory`, `pids`, `cpu`). Используйте подходящую службу systemd с `Delegate=yes` и убедитесь, что она может создавать дочерние cgroup и записывать в них данные. **Не** выдавайте root или дополнительные capabilities ради обхода ошибки делегирования.
- Поддержка ядром рекурсивного `mount_setattr` (Linux 5.12+), `pivot_root`, фильтрации seccomp и tmpfs/proc в user namespaces.
- Отдельный минимальный корень Runtime `/usr`. Каталоги Runtime монтируются только для чтения, но их публично доступное содержимое остаётся видимым. Не храните в них секреты.
- Linux arm64 и платформы не на Linux отклоняют `isolated` до проверки собственной нативной реализации.

## Реальная приёмка и ограничения

На специально подготовленной машине выполните:

`cd services/api && NL_RUN_LIVE_LINUX_SANDBOX=1 go test -v ./internal/linuxsandbox -run TestLinuxIsolationLive0319`

Также с настоящими вредоносными расширениями необходимо проверить невозможность исходящего трафика, записи в пакет, чтения секретов Backend и выхода потомков за пределы cgroup после `setsid`, сохранение работоспособности API узла и отказ запуска при отключении возможностей ядра. Отрицательные тесты запускайте в настоящей службе. Условный тест не равнозначен сертификации оборудования/ядра. Песочница обеспечивает эшелонированную защиту, но не гарантирует отсутствие уязвимостей ядра.
