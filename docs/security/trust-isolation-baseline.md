# Launcher 0.31.1 — работающая базовая защита доверия и изоляции

## Реализовано и принудительно применяется в 0.31.1

`TrustAssessment` вычисляется API по привязке аутентифицированного сеанса и сохранённой записи устройства. Маршруты `GET /api/v1/auth/device-trust` и `/api/v1/auth/devices` возвращают решения по профилям со стабильными машиночитаемыми причинами. `GET /api/v1/auth/device-trust?requireProfile=standard|strict` возвращает HTTP 403 с причиной отказа, если требуемый профиль не удовлетворён (и HTTP 400 для неизвестного профиля). Обычный маршрут статуса остаётся обратно совместимым.

**Стандартный профиль** допускает активное проверенное устройство с разрешённым алгоритмом и отпечатком ключа только при наличии действующего сеанса, привязанного к этому устройству. TPM не обязателен: потеря TPM не означает общий отказ лаунчера. Поддерживаемыми способами восстановления остаются существующая ротация ключей с двойным подтверждением и восстановление с повышением уровня аутентификации через passkey. Указанное клиентом имя провайдера помечается `client-reported`, а не считается удалённо проверенным. Истёкший challenge-response не повышает уровень доверия и **не** является основой стандартного профиля в 0.31.1.

**Строгий профиль** отказывает по умолчанию: в этом выпуске отсутствуют как средство удалённой проверки происхождения аппаратного ключа, так и полноценный анализатор свидетельств Runtime Guard. Поэтому строгая проверка всегда отклоняется, в том числе для старых записей БД с `remoteHardwareProvenance=verified`. Будущая реализация должна проверять реальные аппаратные свидетельства по *точному зарегистрированному ключу*, одноразовым значениям, сеансу, эпохе и доверенным корням до изменения результата. Одно редактирование поля БД не активирует строгий режим. Запись устройств в Repository понижает устаревшие утверждения; сериализация API и ответы аттестации делают то же самое.

Runtime Backend-расширений сообщает `legacy-unisolated`, `isolationStatus=unsupported`, `osSandbox=none`, `networkSandbox=none` и `filesystemSandbox=none`; автоматическое повышение статуса до доверенного либо изолированного невозможно. Ограничения Linux PGID/RSS, очищенное окружение и проверки брокерного RPC **не** являются песочницей ОС. Действующие правила допуска неподписанных или недоверенных пакетов не заменяют изоляцию Runtime. Совместимость старых расширений сохраняется, однако нельзя утверждать, что 0.31.1 делает их безопасными при исполнении от имени недоверенных локальных пользователей.

## Исполняемая диагностика

Из установленного исполняемого файла Backend без подключения к БД:

```shell
launcher-api diagnose device-trust
launcher-api diagnose extension-sandbox
launcher-api diagnose device-trust --require-strict       # exit 2 until verifier is implemented
launcher-api diagnose extension-sandbox --require-isolation # exit 2 until isolation is enforced
```

Диагностика выводит в stdout машиночитаемый JSON с причинами, платформой, архитектурой и **наблюдаемыми возможностями**. Повышения привилегий, чтения ключевого материала и изменения системных ресурсов нет. Обнаружение интерфейсов ядра в режиме только чтения не доказывает возможность создать соответствующее пространство имён, границу ресурсов либо сетевого брокера. Диагностика относится к **хосту Backend**, а не к удалённому игровому устройству. Наличие локального символьного устройства TPM или имени провайдера не подтверждает происхождение удалённого ключа.

WSL, виртуальные машины, отключённые пользовательские пространства имён, контейнерные службы, ограничения прав TPM, сброс прошивки, отозванные или отсутствующие корни изготовителя, недостающие entitlement и старые манифесты могут менять доступность функций. Для заявления о поддержке нужен результат настоящей проверки и принудительного применения, а не только версия платформы или архитектура CPU.

## Коды причин, интерфейс и восстановление

- `device-not-verified`: войдите заново и подтвердите владение устройством либо выполните поддерживаемое восстановление с повышением уровня аутентификации через passkey; отозванные ключи не восстанавливаются простым возвратом записи.
- `session-device-binding-missing`: проверьте фактическую привязку устройства к сеансу; сеанс другого устройства не может использовать положительное заключение.
- `challenge-response-expired-or-invalid`: при необходимости обновите challenge-response для существующей функции; это не то же самое, что происхождение аппаратного ключа.
- `remote-hardware-verifier-unavailable`, `guard-runtime-evidence-unavailable`: строгий профиль явно не поддерживается. Если защищённая операция допускает, пользователь может выбрать стандартный профиль; нельзя незаметно ослаблять строгую серверную политику.
- `extension-os-sandbox-not-enforced`: нельзя показывать состояние «изолировано». Будущий пакет, для которого изоляция обязательна, должен отказывать, а не исполняться с доверенными привилегиями.

Сброс прошивки/TPM, замена материнской платы или утрата ключа не отключают обычную аутентификацию. Используйте существующее восстановление ключа с новым устойчивым к фишингу повышением уровня аутентификации: оно создаёт новый ключ и эпоху привязки и отзывает прежнюю идентичность согласно политике сервера. **Не** изменяйте локальные метаданные ради ложного подтверждения происхождения оборудования. Администраторам нельзя разрешать операции только для строгого профиля, пока его проверка недоступна.

## Модель угроз и ограничения гарантий

Угрозы: вредоносное расширение или дочерний процесс; подделанные строки об оборудовании, переданные клиентом; устаревшие, проксированные, повторно использованные либо полученные в чужом сеансе свидетельства устройства; присоединение и внедрение кода в пользовательском режиме; скомпрометированная локальная ОС; недоступный TPM; ложные срабатывания из-за средств доступности, экранных оверлеев и антивирусов. Границы: проверки протокола, RPC и подписи сами по себе не мешают расширению с правами того же пользователя читать произвольные локальные файлы, устанавливать прямые исходящие соединения либо выходить за пределы группы процессов. Локальное хранение аппаратного ключа не аттестует целостность JVM или Guard; измерения PCR/Measured Boot (после реализации) представляют **отдельное утверждение**, не равнозначное происхождению ключа.

Абсолютная защита от читов и защита от скомпрометированного ядра не заявляются. Совместимость с оверлеями, программами доступности и антивирусами нельзя сертифицировать без воспроизводимых нативных испытаний на настоящем оборудовании. Эти испытания — критерии допуска версии 0.31.14, а не вымышленные успешные результаты версии 0.31.1.

## Воспроизводимые тесты и ограничения

Выполните `go test ./internal/model ./internal/trustbaseline ./internal/repository ./internal/extensionhost ./internal/httpapi` в `services/api`. Тесты покрывают стандартный доступ без TPM, отказ отозванным устройствам и чужим сеансам, понижение поддельных старых утверждений о происхождении ключа, отказ строгого профиля по умолчанию, истёкшие свидетельства и правдивость проверок интерфейсов ядра. Соберите `go build ./cmd/launcher-api` и выполните приведённую выше диагностику. CI собирает и проверяет платформы на точных коммитах. Аппаратная аттестация и настоящая проверка песочницы при враждебных воздействиях **не** входят в 0.31.1 и не должны выводиться из успешных тестов.
