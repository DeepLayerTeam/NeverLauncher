# NeverLauncher 0.50.10 — совместимость модов и программного обеспечения

## Что действительно изменилось

**Windows.** Внутрипроцессный нативный Hook Engine теперь инструментирует нативные модули самой игры либо установленной Java, но не импорты произвольных сторонних DLL. Независимый Windows Module Guard продолжает проверять **каждый загруженный модуль**: подписанные исполняемые файлы установленной игры закрепляются по хешу, а DLL за пределами доверенных корней должны проходить проверку Authenticode средствами ОС. Исключения по подстроке или имени производителя и обходы через переменные окружения не добавлялись. Известное ограничение: сторонние хуки оверлеев, обращающиеся к защищаемой области игры/JVM, всё ещё могут срабатывать на проверках целостности памяти и хуков. Внешний подписанный оверлей *не является автоматическим доказательством безопасности*.

**Linux.** Доступными остаются системные библиотеки в каталогах `/usr/lib`, `/usr/lib64`, `/lib` и `/lib64`, принадлежащих root и недоступных для записи группе или всем пользователям. Прочие внешние исполняемые отображённые библиотеки (пользовательские слои Vulkan и оверлеи, нативные компоненты захвата изображения, дополнения производителей) допускаются только при наличии **точного абсолютного пути и SHA-256** в существующей подписанной оператором политике Guard с привязкой к проекту, версии и загрузчику, в поле `externalNativeModules`. Внешний наблюдатель Rust за `/proc` и наблюдатель JVM проверяют путь и хеш загруженной библиотеки во время сессии с учётом действующей политики и эпохи. Наблюдатель Rust дополнительно сверяет inode отображённого файла с текущим файлом. Неизвестные или изменённые нативные модули, доступные пользователю для записи, блокируются. Это не предоставляет им привилегий доверенных Java-хуков и не создаёт исключений для JAR модов, JVMTI, неизвестных агентов, отладчиков процессов или читов.

**macOS.** Сохраняются Hardened Runtime, проверка подписи Guard, проверки процесса JVM в пользовательском режиме и подписанный реестр модов и нативных модулей. Захват экрана или окна отдельным процессом не означает разрешения на внедрение в JVM. Прямое внедрение кода не разрешается лишь на основании названия OBS, производителя GPU или средства специальных возможностей. Никакого ослабления SIP, AMFI или Gatekeeper не реализовано.

### Обновление подписанной политики для оверлея Linux

1. Найдите настоящий путь библиотеки, загруженной приложением. Независимо проверьте происхождение пакета и права доступа: не принимайте пути и хеши, предоставленные игровым клиентом или игроком.
2. Выполните `sha256sum /absolute/path/to/overlay.so`. Предпочтителен стабильный путь установки без компонентов-символических ссылок. Пути в `/proc`, `/sys` и `/dev` отклоняются. В системах, где `/lib` является символической ссылкой, по возможности используйте канонический путь внутри `/usr/lib`.
3. Добавьте следующее *необязательное* поле в существующую **полезную нагрузку** `launcher.guard-compatibility.v1` для соответствующей игры, проекта и загрузчика. В политике без внешних библиотек поле должно отсутствовать:

```json
"externalNativeModules": [
  {"path":"/home/example/.local/share/example/libcapture.so", "sha256":"<exact lower-case 64-digit SHA-256>"}
]
```

4. Увеличьте `epoch`, проверьте всю подписываемую полезную нагрузку, подпишите её **автономно** командой `go run ./cmd/guard-policy-sign --mode sign ...` и установите существующей командой `launcher guard-policy-install`. `guard-policy-verify` проверяет новую политику, но не факт выполнения оверлея. Новая версия или хеш требуют новой подписанной эпохи. Для отзыва старого файла внесите прежний хеш в `revokedDigests`.
5. Запустите реальную игру и Guard с точной конфигурацией Vulkan/оверлея. Подписанный хеш подтверждает только установленные байты, но не отсутствие читов. Не используйте `LAUNCHER_GUARD_COMPAT_REQUIRED=0` как обходной способ обеспечения совместимости.

`externalNativeModules` предназначен **только для Linux**. Политики с этим полем нельзя считать универсальными для разных ОС. Допускается до 64 внешних нативных модулей. Библиотеки должны быть настоящими обычными файлами размером не более 512 МиБ; пути через символические ссылки и их компоненты отклоняются. Политики без этого поля остаются действительными с прежними правилами Guard.

### Границы приёмки

Автоматизированные исполняемые тесты включают положительные и отрицательные сценарии настоящих Java/JNI с нативной `.so` за пределами корня игры: подмену внешней библиотеки, загрузку неизвестного внешнего файла, прежние изменения модов, JAR и classpath, а также проверки подписи и отзыва Go. Тесты области действия хуков Windows выполняются нативным CI, независимый Module Guard продолжает проверять подписи. До заявления о поддержке CI обязан скомпилировать Rust на каждой целевой платформе. В данных из окружения разработки Linux **нет завершённых реальных установочных испытаний OBS Studio, оверлеев Discord/Steam, антивирусных пакетов либо нескольких версий драйверов NVIDIA/AMD/Intel**. Приёмка на настоящем оборудовании и с реальными приложениями требует матрицы версий установленного ПО, режимов захвата, загрузчика Minecraft и модов, ОС, GPU, драйверов, JVM и отчётов Guard, с обычным подключением и продолжительной работой, а также контролируемыми негативными проверками подмены. Отсутствующие конфигурации остаются `BLOCKED`; универсальная поддержка не предполагается.

Выпуск 0.50.10 GA заблокирован, пока не собраны результаты реальных запусков хостов и Minecraft/ServerBridge, проверка подписанных артефактов и подтверждения независимого проверяющего.
