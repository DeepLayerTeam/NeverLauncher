# Launcher 0.31.4 — аттестация ключа TPM 2.0 на Linux

## Реализованный исполняемый сценарий

**Исходный ключ устройства не заменяется.** Launcher сохраняет регистрацию `P-256/hardware/LinuxTpm` из `hardware-enclave` 0.2.10. При проверке Tauri перечитывает собственную запись в системном хранилище ключей ОС, совпадение `userId/deviceId`, проверяет реальный механизм подписи TPM в Linux и публичный ключ, затем читает защищённые TPM файлы `*.tpm_pub` и `*.tpm_priv` существующего ключа из каталога ключей приложения XDG. Ни программный ключ, ни WSL Bridge, ни резервный механизм Linux Secret Service, ни неподтверждённое имя TPM не получают подтверждение происхождения на удалённой стороне.

Во вспомогательном компоненте Linux используется `tpm2-tools` 5.x, установленный из доверенных пакетов дистрибутива в `/usr/bin`. Запуски — с отдельными аргументами командной строки без командной оболочки; код ограничивает время и размер файлов, проверяет UID, запрещает символические ссылки и удаляет приватную временную директорию. **`.tpm_priv` — зашифрованный блок данных TPM, а не экспортируемый приватный ключ.** Для загрузки используется точно заданный родительский ключ ECC P-256 в иерархии владельца из `hardware-enclave` 0.2.10 (`SHA256`, `AES-128-CFB`, `restricted decrypt`, `fixedTPM/fixedParent/sensitiveDataOrigin/userWithAuth`). С `TPM2_Load` получается прежний ключ подписи, а не новый.

После `TPM2_ReadPublic` полная TPM2B_PUBLIC побайтово сверяется с сохранённой, а P-256 SEC1 — с серверным идентификатором устройства. `TPM2_Certify` вызывается с отдельным TPM AK по постоянному дескриптору `0x81xxxxxx`, с `qualifyingData` — ровно 32-байтовым серверным SHA-256, вычисленным на основе одноразового значения. Клиент отправляет двоичные TPM2B_PUBLIC, TPM2B_ATTEST, TPMT_SIGNATURE и материалы AK X.509, заверенные издателем в существующий `POST /api/v1/auth/devices/{id}/tpm-certify/complete` (после `begin`). Никакая локальная опция не выставляет `verified`: его присваивает только сервер.

0.31.4 исправляет реальную несовместимость с 0.31.2: `hardware-enclave` Linux создаёт ключ подписи `TPMT_ECC_SCHEME=ECDSA(SHA256)`, тогда как Windows ранее проверял `NULL`. Общий бинарный парсер и проверяющий компонент Go теперь принимают **только** `NULL` или `ECDSA(SHA256)`; SHA-1, остальные схемы и кривые остаются запрещёнными. TPM Name пересчитывается из полной фактической открытой области ключа, включая схему и хеш, поэтому чужой объект не может пройти проверку только по открытому ключу.

## Требования оператора

1. Linux glibc, устройство `/dev/tpmrm0`, права текущего пользователя на диспетчера ресурсов TPM, установленный `tpm2-tools` 5.x, `libtss2` (зависимости tss-esapi/hardware-enclave). На системах, где нет этих условий, отображается конкретный отказ, без программного обходного варианта для удалённо подтверждённого доверия.
2. *Существующий зарегистрированный* аппаратный ключ устройства: механизм подписи `LinuxTpm`, P-256. Для уже зарегистрированного программного ключа необходим явный стандартный процесс ротации на аппаратный ключ, а не скрытая замена в ходе аттестации.
3. Раздельный **настоящий ключ аттестации (AK), защищённый TPM**, предварительно размещённый в NVRAM TPM под разрешённым постоянным дескриптором, например `0x81010001`. Его издатель должен независимо подтвердить происхождение AK в TPM и выдать конечный сертификат X.509, не являющийся сертификатом центра сертификации, с назначением ключа `DigitalSignature`. Launcher не создаёт локальный самоподписанный CA/AK и не принимает предоставленный клиентом PEM в качестве корня доверия.
4. На Backend: `LAUNCHER_TPM_AK_ROOTS_FILE`, активная политика с Linux в разрешённых платформах и доверенным AK CA, как в `tpm-certify-verifier.md`. Должны работать ротация и отзыв корневых сертификатов и ключей AK.
5. Открыть **Вход → Аттестация ключа TPM Windows/Linux**, ввести `0x81xxxxxx`, PEM AK и (при необходимости) промежуточные сертификаты; нажать «Подтвердить TPM-происхождение». Закрытый ключ AK/EK никогда не вводится в интерфейсе. Объекты TPM, требующие нестандартной политики или непустой авторизации, отвергаются без повышения уровня доверия.

## Гарантии и ограничения

- Отдельно проверяются нативная открытая область ключа, подпись AK команды `TPM2_Certify`, привязка к одноразовому запросу сервера, устройству, пользователю, сеансу и поколению привязки, срок действия, одноразовость, корневой сертификат УЦ и отзыв. Ответ сервера — единственный источник подтверждения аппаратного доверия.
- Проверки **не** подтверждают измеряемую загрузку, PCR или целостность среды выполнения Guard и не заменяют античит. `strict` по-прежнему требует независимых проверок Guard и отвергается без них.
- Смена подписи программного пакета или имени каталога ключей не повышает доверие. При неподдерживаемых параметрах ядра или учётных данных TPM возвращается отказ с указанием причины и дальнейших действий.
- Текущий компонент Linux, формирующий подтверждение требует пустую парольную авторизацию TPM для пользовательского ключа и AK и AK с постоянным дескриптором. Варианты с password/PolicyAuthorize или AK в непостоянном контексте не поддерживаются. Отказ не является общим сбоем лаунчера.
- Код защищает от случайного доступа к защищённому блоку данных и недоверенных параметров CLI, но **не обеспечивает изоляцию от суперпользователя root или вредоносного ПО с правами того же пользователя**.

## Проверка

Выполнить на Linux со средой сборки и пакетами для разработки Tauri/tss-esapi:

```sh
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml tpm_linux_0314
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml tpm_wire_0313
cargo build --manifest-path apps/desktop/src-tauri/Cargo.toml
(cd services/api && go test -race ./internal/attestverify ./internal/trustbaseline)
```

Аппаратная приёмка обязательна отдельно: реальный TPM 2.0 и выданный TPM AK сертификат не менее двух поставщиков; пройти полный цикл `begin → TPM2_Certify → complete → status`; негативные пробы с чужим AK/subject, несовпадающим ключом, отсутствующим TPM, неправильным родительским ключом, повторённым одноразовым значением, сменой эпохи, отозванным AK или корневым сертификатом, истёкшим запросом аттестации и обязательным по политике AK. Наличие CI без физического TPM **не доказывает успешность этих испытаний**.
