# 0.50.7 — сеансы Guard, привязанные к серверу

## Рабочая реализация

Защищённый режим использует существующие подписанные сообщения активности ServerBridge Protocol v3 (Ed25519), подписанную устройством одноразовую аттестацию **непрерывной защиты Windows Guard v2**, подписанный аппаратным ключом точный план компонентов, авторитетное состояние игровых сеансов в PostgreSQL и привязанные к Runtime команды `player.kick` с идентификатором корреляции. Код выполняется непосредственно при допуске по HTTP, проверке подключения через ServerBridge и обработке подписанных сообщений активности сервера. Отдельного имитационного конечного адреса аттестации нет.

1. Включите **PostgreSQL**, включая миграцию `0116_server_bound_guard_sessions_0507.sql`. ServerBridge с хранением только в памяти не допускается для защищённого входа.
2. Настройте существующие списки разрешённых выпусков и Runtime Guard v2 для развёрнутой платформы, включая проверенные хеши Launcher 0.50.7 и Guard. Хеши выпуска 0.50.6 не разрешают новые исполняемые файлы.
3. Подготовьте подписанную политику плана компонентов ServerBridge с `LAUNCHER_SERVERBRIDGE_REQUIRE_PLAN_POLICY=1`, `LAUNCHER_SERVERBRIDGE_PLAN_POLICY_FILE=/secure/path/signed-policy.json` и `LAUNCHER_SERVERBRIDGE_PLAN_POLICY_PUBLIC_KEY=<pinned-ed25519-key-hex>`. Ключ подписи должен храниться вне сети. Политика должна явно разрешать каждый точный кортеж (сервер, проект, профиль, канал, подпись выпуска, SHA-256 каталога, SHA-256 плана).
4. Обновите плагины Runtime ServerBridge до подписанного **протокола v3** с идентификацией Runtime и аутентифицированными сообщениями активности узла. При включённой защищённой политике протокол v2 и отсутствие идентичности Runtime приводят к отказу.
5. Разрешите Launcher получать как проверенный одноразовый билет Guard, так и подписанный устройством одноразовый запрос для точного плана. Во время `sessionJoin` Backend проверяет оба доказательства до создания неизменяемой привязки Guard к игроку. Если долговременная запись не удаётся, выдача отклоняется.
6. Узел ServerBridge подтверждает подключение подписанным аутентифицированным запросом. Backend сравнивает сохранённые данные аккаунта, сеанса Launcher, сеанса Minecraft, доверенного устройства, эпохи ключа, сервера, UUID, профиля и сборки с записью допуска, после чего повторно проверяет доверие, аттестацию, разрешённые артефакты Guard, профили Runtime Guard и подписанный план. При переносе между серверами целевой сервер должен быть отдельно внесён в список разрешённых для точных байтов этой сборки.
7. Каждое принятое подписанное сообщение активности узла ServerBridge проверяет подлежащие проверке защищённые сеансы игроков по актуальному авторитетному состоянию PostgreSQL и политике. При отзыве или несовпадении сеанс атомарно становится недействительным, а для работающего прокси/Backend ставится в очередь команда `player.kick` с идентификатором корреляции. Адаптер исполнения должен работать и опрашивать очередь управления.

## Эксплуатация и ограничения

- Действующий сеанс без неизменяемой привязки Guard не получает исключения из правил защищённого режима: следующее сообщение активности узла поставит в очередь команду отключения с идентификатором корреляции.
- Повторные проверки запускаются реальными сообщениями активности узла и выполняются пакетами до 32 активных сеансов на сообщение сервера; записи должны иметь возраст не менее 10 секунд. Настройте частоту сообщений ServerBridge и измерьте максимальную задержку очереди при вашем количестве игроков. **Не считайте 10 секунд гарантированным временем для каждого игрока.** При недоступности моста или базы данных автоматический отзыв внутри игры доставить невозможно, хотя допуск и ответы на сообщения активности в защищённом режиме завершаются отказом.
- При проверке отзыва используется последнее уже выданное аутентифицированное свидетельство клиента. **Это не новые измерения памяти или Runtime работающего клиента.** Введённый в 0.50.6 клиентский сторожевой процесс продолжает контролировать локальную целостность. Для криптографически свежих удалённых измерений потребуется будущий протокол одноразовых запросов и сигналов активности между клиентом и сервером.
- Непрерывная проверка политики Runtime Guard сейчас требует Windows Guard в пользовательском режиме. Эта реализация не подтверждает аналогичную защиту Linux/macOS или реальный игровой процесс на этих системах.
- Доверенное Java-расширение обладает полными привилегиями процесса. Подписанные свидетельства не доказывают отсутствие читов на скомпрометированном компьютере игрока.
- Политики и отзывы могут отключать уже подключённых игроков; нельзя ослаблять проверки ради устранения переподключений. Ошибки PostgreSQL/Guard должны вызывать оповещения операторов. Индексы и размеры пакетов настраивайте только по измеренной пропускной способности и достоверным данным корреляции.

## Команды реальных тестов

```sh
cd services/api
export LAUNCHER_TEST_POSTGRES_DSN='postgres://user:password@127.0.0.1:5432/disposable_db?sslmode=disable'
go build ./cmd/...
go test -race -count=1 ./internal/httpapi -run '^TestGuardBoundSession0507'
go test -race -count=1 ./internal/repository -run '^TestServerBoundGuardPostgres0507$'
```

Интеграционный тест PostgreSQL применяет весь каталог миграций, создаёт настоящего активного игрока и Runtime прокси, сохраняет неизменяемую привязку Guard при подключении, отклоняет повторное использование, получает список реально подключённых игроков, регулирует интервалы проверок, отзывает сеанс и подтверждает постановку в очередь ровно одной команды `player.kick` с тем же идентификатором корреляции. Миграция 0116 также обновляет общий триггер отзыва сеансов PostgreSQL, добавляя идентификатор корреляции в JSON очереди и сохраняя устранение дубликатов совместно с кодом отзыва в приложении. Процесс CI дополнительно компилирует API и CLI. Эти проверки **не заменяют** независимую приёмку на реальном Minecraft/Windows/HA с финальными подписанными артефактами. Промышленный выпуск GA заблокирован до получения таких свидетельств.
