# 0.31.6 — доверие к устройству и восстановление на macOS

## Реализованное поведение

- На macOS нативный процесс Desktop проверяет существующую запись Keychain и при её наличии подтверждает подлинность аппаратного средства подписи P-256 и отпечаток открытого ключа. Устройства с программным Ed25519 разрешены для **стандартного** профиля. Локальный ключ Secure Enclave **не** эквивалентен дистанционно аттестованной аппаратной идентичности.
- `DCAppAttestService.sharedService.isSupported` вызывается через DeviceCheck/Objective-C Runtime от Apple, а не определяется по строке версии ОС. Apple добавила App Attest в **macOS 27** для поддерживаемых основных приложений. Более старые версии macOS и неподдерживаемые типы приложений могут вернуть false. Статус `api-supported-not-attested` **не** означает, что аттестация создана или проверена.
- Ключ устройства Launcher создаётся независимо от ключа Apple App Attest. **Серверного доказательства связи этих двух ключей нет.** Поэтому даже при `isSupported == true` состояние `remoteDeviceKeyProvenance` остаётся `not-verified`, а строгий профиль обязан отказать. Нельзя обещать удалённо подтверждённое происхождение ключа Secure Enclave на произвольных конфигурациях macOS.
- Восстановление устройства требует **нового усиленного подтверждения через защищённый от фишинга ключ доступа (passkey)** и доказательства владения **новым** ключом устройства. Прежний отпечаток повторно использовать нельзя. Прежняя запись устройства и связанные с ней сеансы/вызовы отзываются существующим механизмом замены. Новому устройству присваивается уровень доверия `proof-of-possession`, а не унаследованная аттестация TPM/Guard/PCR.
- Подготовленный ключ должен восстанавливаться после потери HTTP-ответа. `stage_device_key_replacement` использует существующую подготовленную идентичность; перед следующим запросом клиентский интерфейс пытается согласовать её с активным серверным устройством. Автоматический разрушительный сброс ключа после HTTP 409 отключён. Удаление подготовленной идентичности должно выполняться явно.

## Инструкция оператора и поддержки

1. Войдите с ещё действующими учётными данными и пройдите новое подтверждение ключом доступа. Наличие утраченного локального ключа **не требуется**. Ключ доступа может находиться на другом доверенном устройстве. Если защищённых от фишинга учётных данных не осталось, потребуется альтернативное проверенное восстановление аккаунта: API не обходит обязательный этап усиленной аутентификации.
2. Выберите **Восстановить ключ**. Launcher создаёт или повторно использует подготовленный ключ в Keychain ОС и отправляет его открытый ключ. При потере HTTP-ответа **не** удаляйте элементы Keychain приложения и не сбрасывайте ключи. Выполните повторную аутентификацию и восстановление, чтобы клиент согласовал подготовленную идентичность с сервером.
3. Сервер отзывает старый отпечаток; прежний ключ и устаревший запрос проверки нельзя использовать повторно. Заново подтвердите сеанс и при поддержке получите свежую аттестацию устройства для нового ключа. Строгий профиль остаётся недоступным без отдельно проверенных доказательств Guard.
4. На macOS откройте **Доверие к устройствам macOS** на экране аутентификации и проверьте значения `localSecureEnclave` и `appAttest`. `api-unavailable` не означает общую неисправность Launcher: стандартное подтверждение устройства может работать. `keychain-unavailable-or-key-invalid` указывает на локальную проблему Keychain/Enclave.

## Проверка и ограничения

- Тесты Backend требуют новую проверку ключа доступа, отвергают одинаковые старые/новые отпечатки, подтверждают новый ключ, отзывают прежнюю запись и запрещают повторное воспроизведение. Тесты доверия отклоняют поддельное `remoteHardwareProvenance=verified` на macOS, в том числе с упоминанием Apple silicon.
- CI компилирует и запускает тесты на macOS-хостах GitHub. Отдельно на настоящем оборудовании необходимо проверить Intel Mac, Apple silicon, macOS 27 с `isSupported` true/false, восстановление утраченного ключа, офлайн-режим/тайм-аут сети при замене, заблокированный Keychain, переустановку приложения и сброс Secure Enclave.
- В этом выпуске **не реализованы** проверка сертификатов и утверждений Apple App Attest и Managed Device Attestation. Это самостоятельные протоколы, которые нельзя подменять TPM2 Certify. Выпуск не даёт права заявлять удалённо подтверждённое происхождение ключа macOS, полное строгое доверие или независимую целостность пользовательского процесса.
