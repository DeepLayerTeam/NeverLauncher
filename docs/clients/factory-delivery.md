# Фабрика клиентов → пространство сборки → Desktop / Runtime (0.40.1)

API использует существующий CLI Client Factory для создания настоящего клиента Minecraft. Операция `POST .../deliver` переносит проверенные файлы в полноценные объекты Build Workspace: оператору не нужно повторно загружать экспортированный локально ZIP. При этом операция намеренно **не** публикует выпуск и не создаёт фиктивные результаты проверки Runtime.

## Порядок действий оператора

1. Укажите абсолютный путь к доверенному исполняемому файлу в `LAUNCHER_FACTORY_CLI` и абсолютный путь к закрытому каталогу в `LAUNCHER_FACTORY_ROOT`. Для установки Forge-подобных загрузчиков при необходимости настройте `LAUNCHER_FACTORY_JAVA`.
2. В Admin создайте профиль клиента с **точной** версией Minecraft и точной версией загрузчика (для модифицированных клиентов); затем создайте новое пустое Build Workspace с подходящей основной версией Java и стандартными параметрами запуска.
3. Выберите целевые ОС и архитектуру, соберите клиент из Minecraft либо поддерживаемого модпака и изучите проверенный InstallPlan завершённого задания и журналы исполнения.
4. Выберите **Перенести сборку в Build Workspace**. Будет вызван `POST /api/v1/build-workspaces/{workspaceId}/factory/jobs/{jobId}/deliver` с `{ "revision": <текущая ревизия рабочего пространства> }` и разрешением `file:write`. Принимается только завершённое задание, принадлежащее тому же пространству, оператору и проекту.
5. Backend повторно вызывает `runtime client-factory verify`, проверяет хеш воспроизводимости, байтовое содержимое исходных файлов и отсутствие символьных ссылок/выхода за пределы каталога; шифрует каждый результат в частном хранилище Workspace; повторно считывает объекты; затем одной транзакцией с проверкой ревизии фиксирует все файлы и точный путь метаданных версии.
6. В Admin выполните Stage → Validate → Build. Backend создаст неизменяемый пакет версии в существующем подписанном конвейере доставки. Продолжайте проверку пакета, подписание, тесты подготовленного Runtime/игры и публикацию.
7. В Desktop загрузите **опубликованный и подписанный** манифест и выполните обычное скачивание/восстановление Runtime, выбор Java, создание совместимого плана запуска, старт и подключение к серверу. Сам перенос результатов Factory не подтверждает успешный запуск Minecraft.

## Поведение при ошибке и повторной попытке

- Некорректный или изменившийся результат Factory, неверные Minecraft/загрузчик/Java, недействительные метаданные, занятый Workspace, устаревшая ревизия либо отсутствие разрешений приводят к **безопасному отказу**. Существующая запись Workspace не изменяется частично.
- Файловые объекты, записанные до неудачной фиксации, остаются закрытыми и не упоминаются в списке файлов Workspace; отложенная очистка хранилища может удалить неиспользуемые объекты.
- Прямая передача требует пустого и ещё не собранного Workspace, чтобы исключить случайную замену уже подготовленного оператором содержимого.
- Результат Factory помечается целевой ОС. Архитектура платформы всё равно требует независимой сертификации Runtime: факт сборки клиента не доказывает совместимость x64/ARM64.
- Подписание и публикация пакета по-прежнему должны проходить независимые проверки доверия, приёмки Runtime и подтверждения выпуска.

## Статус локальной проверки

Существующие тестовые образцы материализатора Client Factory исполняются на Go 1.23.2. Модуль API требует Go 1.27.3 и внешние зависимости; в автономном контейнере его тесты не удалось запустить. Здесь были недоступны настоящий исполняемый файл Minecraft, игровой аккаунт, подключение к реальному серверу и межплатформенный исполнитель Desktop. Не отмечайте E2E-приёмку успешной без настоящих журналов Runtime/сервера и точных доказательств проверенного артефакта выпуска.
