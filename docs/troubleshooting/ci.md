# Диагностика GitHub Actions

## Источники

Файлы процессов CI: `.github/workflows/ci.yml`, `compatibility.yml`, `device-trust.yml`, `security.yml`, `extensions-ga.yml`, `production-release-candidate.yml` и процессы доставки. Проверяйте **точный SHA и журнал задачи**, а не только общий счётчик проверок.

## Порядок расследования

1. Зафиксировать SHA коммита, URL запуска, имя задачи, платформу и первую содержательную ошибку (не финальное `exit code 1`).
2. Определить тип: проверка стиля/контрактов, компиляция, модульные и интеграционные тесты, реальный Minecraft, безопасность/атаки, сбор сертификатов.
3. Для контракта воспроизвести соответствующий `scripts/smoke/offline/*.py` и проверить, что тест утверждает *поведение*, а не только точную фразу.
4. При платформенном отказе изучить подтверждения выполнения и повторить с той же Java/ОС/архитектурой. Не помечать непроверенные сочетания как PASS.
5. При ошибке сертификата релиза проверить наличие всех обязательных подтверждений, их SHA, хеши и соответствие версии.
6. После исправления выполнить все обязательные задачи CI **на новом коммите**. Результаты предыдущего SHA не доказывают готовность текущего.

## Базовые команды

```bash
python3 scripts/version/manage.py check
python3 scripts/contracts/validate-openapi.py
python3 scripts/smoke/offline/repository-policy.py
python3 scripts/release/test_fetch_exact_certifications.py
python3 scripts/compatibility/matrix.py validate --targets compatibility/targets.json
```

Если тест падает из-за недостающего строкового маркера в комментарии, не отключайте блокирующую проверку: сначала проверьте реальное требование безопасности, затем исправляйте источник рассинхронизации. Перед публичным релизом используйте [сертификацию релиза](../security/release-certification.md).

### Серверные комплекты матрицы Minecraft

Временные GitHub-hosted runners не имеют файлов из каталога локального оператора.
Для обычных клиентских целей `compatibility.yml` поддерживает загрузку одного
утверждённого серверного комплекта из GitHub Release того же репозитория:

1. Опубликуйте release с ZIP-файлами настоящих выделенных серверов (с соблюдением
   лицензий и условий распространения). Каждый файл должен соответствовать
   точной версии Minecraft и разрешённой версии загрузчика клиента.
2. Добавьте `compatibility-server-pins.json` со схемой
   `launcher.compatibility-server/0.52.4` и объектом `targets`, индексированным
   идентификатором из `compatibility/targets.json`. Поля записи: `loader`,
   `minecraft`, `loaderVersion`, `file`, `sha256`, необязательное `serverEntry`.
   `file` — имя ZIP в release; `sha256` — независимо проверенный SHA-256 его байтов.
3. В Settings → Secrets and variables → Actions → Variables задайте
   `LAUNCHER_E2E_SERVER_RELEASE_TAG` (тег релиза) и
   `LAUNCHER_E2E_SERVER_PINS_SHA256` (SHA-256 точных байтов манифеста pins).
   Не подменяйте закрепление вычислением хеша из непроверенного скачивания.

При заданном теге манифест должен содержать все клиентские цели с модами и Vanilla,
для которых недоступен проверяемый официальный сервер Mojang. Официальный Vanilla
без записи использует проверенный CLI серверный JAR. CI сверяет SHA-256 манифеста
и, при наличии записи, ZIP до запуска сервера. Установленная версия загрузчика ещё
раз сверяется непосредственно перед запуском; отсутствие записи модифицированного
сервера, ZIP или совпадающего хеша блокирует цель. При отсутствии release tag сохраняются
`LAUNCHER_E2E_SERVER_PINS_PATH` и `LAUNCHER_E2E_SERVER_BUNDLE_DIR` для
самостоятельно подготовленных runners. Современный Vanilla без pins использует
официальный Mojang JAR; старые версии без подходящего серверного JAR/RCON требуют
отдельно проверенного комплекта. Никакая подстановка mock-сервера или
игнорирование отсутствующего доказательства подключения не допускается.

#### Подготовка комплекта из проверенных локальных дистрибутивов

`e2e/scripts/prepare_server_bundle.py` упаковывает уже установленные и проверенные оператором
серверы в детерминированные ZIP, формирует манифест и проверяет его тем же читателем,
который используется CI. Он **не** скачивает неизвестные JAR, не подтверждает происхождение
или работоспособность сервера и не создаёт сертификат совместимости.

Пример `server-sources.json` (пути относительно файла спецификации; реальная версия
загрузчика должна соответствовать установленному клиенту):

```json
{
  "fabric-1.21-linux-x64": {
    "directory": "verified-servers/fabric-1.21",
    "loaderVersion": "0.16.14",
    "serverEntry": "server.jar"
  }
}
```

```bash
python3 e2e/scripts/prepare_server_bundle.py --spec server-sources.json --output ci-server-release
```

Включите все необходимые обычные клиентские цели, проверьте содержимое и SHA-256
независимо, затем опубликуйте файлы (только при наличии прав на распространение)
и настройте переменные из предыдущего раздела. Для локального self-hosted runner
можно использовать абсолютные пути к манифесту и каталогу вместо публикации.
