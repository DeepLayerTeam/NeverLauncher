# Диагностика GitHub Actions

## Источники

Файлы процессов CI: `.github/workflows/ci.yml`, `compatibility.yml`, `device-trust.yml`, `security.yml`, `extensions-ga-0210.yml`, `production-release-candidate.yml` и процессы доставки. Проверяйте **точный SHA и журнал задачи**, а не только общий счётчик проверок.

## Порядок расследования

1. Зафиксировать SHA коммита, URL запуска, имя задачи, платформу и первую содержательную ошибку (не финальное `exit code 1`).
2. Определить тип: проверка стиля/контрактов, компиляция, модульные и интеграционные тесты, реальный Minecraft, безопасность/атаки, сбор сертификатов.
3. Для контракта воспроизвести соответствующий `scripts/smoke/offline/*.py` и проверить, что тест утверждает *поведение*, а не только точную фразу.
4. При платформенном отказе изучить подтверждения выполнения и повторить с той же Java/ОС/архитектурой. Не помечать непроверенные сочетания как PASS.
5. При ошибке сертификата релиза проверить наличие всех обязательных подтверждений, их SHA, хеши и соответствие версии.
6. После исправления выполнить все обязательные задачи CI **на новом коммите**. Результаты предыдущего SHA не доказывают готовность текущего.

## Базовые команды

```bash
python3 scripts/version/manage.py check
python3 scripts/contracts/validate-openapi.py
python3 scripts/smoke/offline/repository-policy.py
python3 scripts/release/test_fetch_exact_certifications.py
python3 scripts/compatibility/matrix.py validate --targets compatibility/targets.json
```

Если тест падает из-за недостающего строкового маркера в комментарии, не отключайте блокирующую проверку: сначала проверьте реальное требование безопасности, затем исправляйте источник рассинхронизации. Перед публичным релизом используйте [сертификацию релиза](../security/release-certification.md).
