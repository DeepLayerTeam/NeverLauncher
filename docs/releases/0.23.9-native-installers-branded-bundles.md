# 0.23.9 — Native Installers & Branded Bundles

## Actual deliverables

- `prestarter/cmd/neverinstaller`: a native Go installer, no Java dependency. `install`, `verify`, `repair`, `uninstall`. An embedded Ed25519 public key is **mandatory** in production.
- `prestarter/installer`: verified installer-managed releases, durable active records, cross-process installation lock, offline bundle preservation, re-provisioning and limited uninstall. It calls the actual signed Prestarter and therefore existing NeverRuntime / Managed Java, rather than substituting Java scripts.
- Signed config fields `branding` and `installerTargets` become part of the Ed25519 payload. The installer requires an exact SHA-256 for the Prestarter of the current OS/arch.
- `scripts/release/build-branded-installers.py`: Windows single-file PE `.exe`, Linux `.deb` with a first-run launcher, macOS `.pkg` with a signed `.app`. Files are obtained from a *signed* project configuration, not from a downloaded trust URL.
- `.github/workflows/native-installers.yml`: test matrix and protected-environment, fail-closed platform signing jobs.

## Signed payload additions

```json
{
  "branding": {"displayName":"Example Launcher","publisher":"Example Team","websiteUrl":"https://example.org"},
  "installerTargets": [
    {"os":"windows","arch":"amd64","prestarter":{"url":"https://example.org/prestarter.exe","sha256":"<64-hex-digest>","size":123456}}
  ]
}
```

These fields are **inside the original signed `payload`**, not added to the outside envelope. The root key comes from the provisioned embedded release key, not the bundle itself. Every target must be present in the signed config; builders refuse a missing target. Sign the config *after* building the Prestarter (and after Apple `codesign` for macOS), because signing changes the component hash.

## Build

Prepare: `bootstrap.signed.json`, the matching OS/arch `neverprestarter` executable, a protected file with the Ed25519 root public key and, for offline packages, an offline source directory containing `objects/<sha256>` for each signed component/profile manifest and `managed-jre/manifest.json` plus the required Managed Java archives. The Rust Managed Java code checks archive hashes, JVM major/arch and filesystem inventory.

```bash
python scripts/release/build-branded-installers.py \
  --platform linux --arch amd64 --project example --version 0.23.9 \
  --config /secure/bootstrap.signed.json \
  --prestarter /release/neverprestarter-linux-x64 \
  --root-key-file /secure/root-public-key.hex --output dist/native
```

For an offline bundle add `--offline-source /release/offline-source`. This must be a regular-file tree, not symlinks. A `--unsigned-test` build is available **only** for automated packaging tests and **must not** be published as a production installer.

Production signing requirements (build fails without them):

- Windows: platform `signtool`, code signing cert thumbprint in `NEVERLAUNCHER_WINDOWS_CERT_THUMBPRINT`. Sign with SHA-256 plus timestamp, verify with `signtool verify /pa`.
- macOS: on a macOS host, `NEVERLAUNCHER_MACOS_CODESIGN_ID` and `NEVERLAUNCHER_MACOS_INSTALLER_ID`. Prestarter must **already** be codesigned before signing the config. The builder verifies Prestarter signature, signs the app with hardened runtime and signs the .pkg; notarization can be a separate release gate.
- Linux: `dpkg-deb`, GPG and `NEVERLAUNCHER_GPG_SIGNING_KEY`. The `.deb` is released with a verified detached `.deb.asc` signature, in addition to normal signed APT repository metadata where applicable.

CI injects trust from the protected release environment and downloads only explicitly selected signed bootstrap source artifacts. Do not replace the protected root key with a key inside the downloaded bundle.

## User lifecycle

- Windows: run the signed `.exe` (default `install`). It extracts the embedded bundle; an offline installer includes `objects/` and `managed-jre/`. Other actions: `repair`, `uninstall`. Installer uses `%LOCALAPPDATA%/NeverLauncher` by default.
- Linux: install `.deb`, then start `neverlauncher` or use `neverlauncher repair` / `neverlauncher uninstall`. Package install itself performs no network or root-context game downloads. The first user launch prepares Desktop and Managed Java.
- macOS: install signed `.pkg`, open `NeverLauncher.app`; its native Go main executable invokes the installer and runs Prestarter. `.../Contents/MacOS/NeverLauncher repair` is also supported.

Uninstall deliberately removes **only** `.neverlauncher-installer` and a managed launcher shortcut. It preserves `launcher/`, `profiles/`, user saves, cache and Managed Java. This is not a "purge all user data" operation. On Windows the `.lnk` is removed only if it still points inside the owned root.

Installer-managed releases are installed into a new directory, SHA-256 verified and then activated using two generation slots. On interrupted install the previous valid slot is eligible for recovery. Installer `repair` can re-provision or reconstruct a damaged Prestarter from a retained, signed offline source. Installer and Prestarter use separate process locks.

## Verification

- `cd prestarter && go test -count=1 ./... && go vet ./...`
- `python scripts/release/test_build_branded_installers.py`
- Cross compile the installer for linux/windows/darwin amd64/arm64.
- Production exit gates: run a real Windows Authenticode build on Windows and signed/notarized `.pkg` on macOS; on clean VMs verify actual Desktop Java/Minecraft startup, repair, downgrade policy, app uninstall and preservation of saves. These gates are **not** satisfied by cross-compiling Go or by unit tests alone.
