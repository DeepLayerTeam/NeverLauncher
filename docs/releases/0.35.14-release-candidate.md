# NeverLauncher 0.35.14 — Source Release Candidate & real acceptance

## Scope and safety boundary

This release implements a reproducible *source RC gate*, not a self-issued GA certificate. Actual native processes (not a generated manifest) must pass signed install, SHA-256, repair, warm update, wrong-key and forged-manifest denial on Windows, Linux and macOS. Each platform must compile a real Tauri binary plus production React assets. A disposable, authenticated Backend HTTP journey and true PostgreSQL stable-release immutability tests must succeed. Historic 0.32.16 live Redis/PostgreSQL/S3/WAL/crash/load Go tests now execute for the current release, including additional owner publication, rollback and diagnostic-consent regressions. All skipped, failed or missing tests block the release.

An independent isolated staging deployment is required for actual full-state snapshot, fresh restore and PostgreSQL/API chaos. The provided `operations_03514.py` invokes the existing real 0.35.12 Docker Compose DR engine, with readback checks and measured RTO, but **does not assert an achieved RPO**, restoration of external secrets, global backend HA or a real Minecraft join. It accepts only two distinct `nl-dr-*` projects and loopback readiness endpoints, and requires `NEVERLAUNCHER_RC_DR_ISOLATED=YES`.

**Critical correction:** the `build-release.sh` protected Backend runtime preflight was formerly gated only on literal `0.35.0`, which would make newer releases bypass the live readback. Version 0.35.14 enforces that preflight for all versions `>=0.35.0`. The read-only Backend preflight checks the *exact* staged package version, current SHA, target matrix, actual signed runs, expiration, stages and complete coverage. CI does not sign or forge that evidence, and the atomic Backend transaction remains authoritative. The Release Candidate workflow also checks the current version, rather than comparing against a hard-coded 0.35.0.

## Reproducible execution

The new `.github/workflows/release-candidate-03514.yml` runs across 3 real native OS environments and executes:

```bash
python scripts/version/manage.py check
python -m unittest discover -s scripts/rc -p 'test_*.py' -v
python -m unittest discover -s scripts/ga -p 'test_runtime_acceptance_0350.py' -v
cargo build --release --manifest-path runtime/neverruntime/Cargo.toml --bin neverruntime --example cert_sign_fixture
python scripts/rc/native_03514.py \
  --runtime runtime/neverruntime/target/release/neverruntime \
  --signer runtime/neverruntime/target/release/examples/cert_sign_fixture \
  --commit "$(git rev-parse HEAD)" --output /tmp/native-03514.json
```

On Windows append `.exe`. The runner generates local disposable test fixtures with the **fixture-only signing seed**; these are not acceptable as production game artifacts. For each OS, the workflow builds `apps/desktop` using `npm ci && npm run build`, executes real unit tests, compiles/tests Tauri with Cargo, hashes the resulting executable/renderer bytes, and writes per-platform evidence. The real Backend workflow runs Go race/security tests with PostgreSQL 17 and starts a disposable Backend to exercise authenticated owner/player requests; these operations never target production data. `gate_03514.py` rejects missing platforms, wrong SHA, mismatched version, stale/missing test outcomes, faked `simulated` success, and missing negative native checks.

For the larger operational RC use a **dedicated, access-controlled, isolated staging runner** with Docker Compose and pre-provisioned distinct loopback ports:

```bash
export NEVERLAUNCHER_RC_DR_ISOLATED=YES
python scripts/rc/operations_03514.py \
  --source nl-dr-rc-source --target nl-dr-rc-fresh \
  --env-file /protected/staging.env \
  --snapshot /protected/empty/dr-snapshot \
  --source-ready-url http://127.0.0.1:18080/ready \
  --target-ready-url http://127.0.0.1:18081/ready \
  --output /protected/rc03514-operations.json
```

The sample paths and ports are illustrative, not a preconfigured environment. Source must already be running and all *external* writers must be fenced during snapshot. Target must be completely new and have its own isolated network/listener. Network-HA uses additional `--network-ha`, distinct pre-provisioned S3 buckets and endpoint. Never point this runner at a production Compose project. The protected production workflow requires an explicit staging runner labelled `rc-staging`, a protected `rc-operations` environment, staging-only secret and operator-controlled project names; missing configuration prevents release rather than silently skipping DR.

## Acceptance and next steps

- `rc-source-checks-passed`: real source-level signed transactional workflows and native builds/Backend checks for the observed commit, **not** installed-game E2E.
- `recovery-exercised`: measured isolated fresh-site RTO and component failures, **not** measured RPO or multi-node HA.
- `backend-eligible-not-published`: a read-only runtime preflight; only the protected Backend transaction can publish stable.
- No GUI test that actually logs into Minecraft, receives an entitlement, connects to ServerBridge, enters the game, and returns to the Launcher has been executed by the new runner. Existing independent runtime/game/Guard certification must remain required for the GA release.
- No operator-signed, six-architecture native delivery package or completion of all 54 G/M target journeys is inferred from these source-level results. They require separate protected real-world evidence.

The workflow is intentionally fail-closed when Rust, Go 1.27.3, npm dependencies, Docker, platform runners, protected identities or external services are unavailable. No green GA status is generated by this source patch alone.
