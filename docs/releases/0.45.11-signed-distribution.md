# NeverLauncher 0.45.11 — Signed Distribution

## Реальная цепочка поставки

Это не режим `manifest-first`: подпись release выдаётся только поверх *готовых* OS-signed packages, проверенных независимой GA-приёмкой. Не следует генерировать фиктивные аттестации для прохождения gate.

1. На Windows runner собрать/подписать x64 и ARM64, извлечь **конечные ZIP** и проверить встроенные EXE через `Get-AuthenticodeSignature` с `Valid` и реальным сертификатом. Действующие проверки доставки также выполняются.
2. На macOS runner собрать, подписать и notarize x64 и ARM64, извлечь **конечные ZIP** и проверить `codesign --verify --deep --strict`, Gatekeeper (`spctl --assess`) и `xcrun stapler validate` на вложенных `.app`. Действующие проверки доставки также выполняются.
3. На Linux runner выполнить реальную сборку x64/ARM64 и `launcher delivery verify-linux`; проверка Ed25519 происходит в рамках независимых GA- и release-gates. Нативная проверка Linux не заменяется наличием ELF magic bytes.
4. Независимый оператор выполняет настоящий игровой цикл и отрицательные сценарии на каждом целевом пакете, подписывает отдельным ключом exact-byte GA evidence (`LAUNCHER_GA_EVIDENCE_DIR`, `LAUNCHER_GA_TRUSTED_PUBLIC_KEY_FILE`). `BLOCKED`/`NOT RUN` не преобразуются в `PASS`.
5. `scripts/release/build-release.sh` проверяет разрешённый version/commit, собирает реальные файлы, проверяет подписанные платформенные пакеты, создаёт `RELEASE_BOM.json`, `SBOM.spdx.json` (включая SHA-256 шести конечных установщиков), `PROVENANCE.json` (субъекты соответствуют финальным байтам), `RELEASE_MANIFEST.json` и `SHA256SUMS`.
6. До подписи новая команда `launcher release distribution-verify dist/release-0.45.11` сравнивает все шесть хешей с фактическими пакетами, SPDX, SLSA, независимым GA receipt и BOM. Ошибка блокирует подпись. Прямой `launcher release sign` выполняет тот же gate; `launcher release verify` проверяет данные ещё раз после сверки подписи и trust anchor.
7. Отдельный `PROVENANCE.json.sig` и подпись `SHA256SUMS.sig` создаются штатной Ed25519 цепочкой. `release publish-check` и удалённая проверка **скачанных** опубликованных файлов остаются обязательны; никакие дополнительные неподписанные файлы не разрешаются в релизном каталоге.

## Что считается готовностью

`0.45.11` в исходниках означает наличие исполняемого механизма проверок, а **не** наличие подписанных здесь релизных файлов. Полная приёмка требует ключи производителя для Windows/macOS, аппаратные/виртуальные цели для шести платформ, независимый ключ GA, реальные итоговые пакеты и результат публикационного round-trip. Без них выпуск блокируется. SBOM отражает dependency manifests и зафиксированные артефакты; он не является побайтовой инвентаризацией всех транзитивных исполняемых компонентов внутри модпаков Minecraft.

## Проверки разработчика

```bash
python3 scripts/version/manage.py check
(cd cli && go test -race ./cmd/launcher -run '^TestReleaseDistribution04511' -count=1)
bash -n scripts/release/build-release.sh
```

Негативные проверки повреждают пакет, SPDX checksum, provenance source commit и GA package digest: в каждом случае выпуск должен прекращаться до подписи. Тестовые байты в unit-тестах не являются подписанными OS-пакетами и никогда не используются как production GA evidence.
