# NeverLauncher 0.35.12 — isolated chaos and recovery runbook

## Scope and safety

`scripts/operations/dr_03512.py` is an executable Docker Compose V2 disaster-recovery tool, not a GA certificate. Chaos faults are restricted to `nl-dr-*` projects with exact `--confirm`. Production maintenance backups and fresh-site restores are available only with both the explicit `--production-source` / `--production-target` flag and `--maintenance-approved`, plus exact confirmation. Production chaos is always rejected. Prepare isolated credentials and deployments for the source and destination. Never point it at a production Compose project or a shared live S3 bucket.

The backup procedure stops API / Admin / Nginx, then (in network-ha) Redis. This is an **offline maintenance snapshot**, not a zero-downtime backup. It captures a PostgreSQL custom dump plus Docker volumes for storage, factory, coordinator, backups, and (network-ha only) Redis AOF state. S3 mode uses the AWS CLI to mirror the whole source bucket. Archives are streamed rather than buffered in RAM. Snapshot hash manifests and tar member checks precede restore; PostgreSQL restore uses `--single-transaction`, and S3 uploads are read back and compared byte-for-byte.

**Not captured:** deployment .env, signing private keys, TLS certificates, external authentication secrets, third-party OAuth settings, external Minecraft server data, DNS or external object-storage configuration. Restore these separately from your secret manager and other disaster-recovery systems. If Redis leases are restored across replica IDs, application-level reconciliation is still required. This tool cannot establish multi-node HA.

Prerequisites: Docker/Compose V2, `postgres:16-alpine`, `alpine:3.20`; AWS CLI for S3 mode, configured external credentials and a pre-created empty *distinct* target S3 bucket. Do not put credentials on the command line. Source and target must have matching NeverLauncher application schema and deployment mode. Use isolated HTTP host ports, not the default production port. These commands assume a properly configured `.env` for each isolated project.

## Real snapshot and verification

```bash
python3 scripts/operations/dr_03512.py backup \
  --project nl-dr-source --confirm nl-dr-source \
  --env-file /secure/source.env --snapshot /secure/off-host-backups/dr-copy-03512
python3 scripts/operations/dr_03512.py verify \
  --snapshot /secure/off-host-backups/dr-copy-03512
```

For network-ha use `--network-ha --s3-source-bucket neverlauncher-dr-source --s3-endpoint https://s3.example.internal` on backup. This adds network-ha overlay and captures actual S3 objects (including checksums) in the snapshot. **Do not use a shared production bucket.** The source environment must reference that isolated source bucket.

## Fresh-site recovery

The target project **must not already own any application volumes**. Provision credentials, DNS, external dependencies and (S3 mode) an empty S3 bucket beforehand. Do not use the source project or bucket.

```bash
python3 scripts/operations/dr_03512.py restore-fresh \
  --project nl-dr-restored --confirm nl-dr-restored \
  --env-file /secure/restored.env --snapshot /secure/off-host-backups/dr-copy-03512 \
  --ready-url http://127.0.0.1:18081/ready
```

For network-ha add `--network-ha --target-s3-bucket neverlauncher-dr-restored --s3-endpoint https://s3.example.internal`. The target Compose env must also reference the distinct target bucket and replica ID. `restore-fresh` validates all snapshot bytes before mutating the target, refuses populated volumes and S3 buckets, starts PostgreSQL, performs transactional `pg_restore`, restores S3 with full readback and starts application services. If restore fails before service startup, the API remains stopped; diagnose the target before retrying from a *new* empty project. A successful `/ready` alone does not prove client/ServerBridge workflows or all queues have recovered: perform release/publish/rollback and real Minecraft/ServerBridge acceptance afterward.

## Actual chaos tests

Start the isolated project first and verify `/ready` is healthy. Do not run on production.

```bash
python3 scripts/operations/dr_03512.py chaos \
  --project nl-dr-source --confirm nl-dr-source \
  --env-file /secure/source.env --snapshot /secure/off-host-backups/dr-copy-03512 \
  --ready-url http://127.0.0.1:18080/ready
```

`--network-ha` adds actual Redis failure injection. The test stops PostgreSQL (and Redis in network-ha), checks `/ready` fails closed, restarts the dependency, measures recovery, then kills the API process, stops its service to keep the outage observable and verifies restart/readiness. It uses bounded timeouts and `finally` restart for interrupted stages. The report provides measured seconds only for successfully executed cases. Only test with an isolated loopback URL.

## What the 0.35.12 release does not prove

- Failure of a second node and transparent cross-node failover; Redis is not HA by itself.
- Queue saturation, exactly-once semantics, or replay of each durable job after a real multi-node outage.
- Remote storage provider disaster or restoration of external services not part of the snapshot.
- Real RPO/RTO before the full source→off-host snapshot→fresh-site restore has run.

For these items, keep GA blocked until a dedicated external staging cluster, load generator, explicit data-loss assertions, release E2E and actual DR drill are completed. Do not publish hypothetical RPO/RTO values.

## Planned downtime / actual production-source backup and fresh-site restore

These are genuine executable commands, **not** safe to try without a scheduled maintenance window, out-of-band credential backup, and verification that all external writers are fenced. The backup pauses the production API. It does not alter a live production database during recovery: the target must be new and empty.

```bash
python3 scripts/operations/dr_03512.py backup \
  --project neverlauncher --confirm neverlauncher --production-source --maintenance-approved \
  --env-file /secure/production.env --snapshot /off-host/neverlauncher-dr-03512
python3 scripts/operations/dr_03512.py restore-fresh \
  --project neverlauncher-restored --confirm neverlauncher-restored \
  --production-target --maintenance-approved \
  --env-file /secure/new-site.env --snapshot /off-host/neverlauncher-dr-03512 \
  --ready-url http://127.0.0.1:18081/ready
```

For network-ha / S3 use the corresponding `--network-ha`, source bucket and **distinct empty** target bucket options described above. Application compatibility, external secret restoration, ServerBridge connection recovery and post-DR game-launch smoke are independently required before traffic is switched. Snapshot files must be copied off-host before a site disaster; retaining them in the lost host's filesystem does not satisfy DR.
