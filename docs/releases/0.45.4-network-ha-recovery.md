# NeverLauncher 0.45.4 — Network-HA cold disaster recovery

**Поставка кода, не сертификат реального двуххостового восстановления.** Используется действующий `scripts/operations/dr_03512.py`, реальный `pg_dump`/`pg_restore`, S3 через AWS CLI, проверенный Go world-backup и транзакционный fencing в восстановленной PostgreSQL. Требуется строго **чистый** целевой Compose project/хост и отдельный пустой S3 bucket. Отсутствие активных старых систем — внешнее обязательное условие.

## Границы операции

- Это **cold disaster recovery** с окном простоя, а не online multi-primary backup и не автоматическая Kubernetes/HA-оркестрация. Источник и все внешние writers (другие API-реплики, агентские процессы, хост-супервизоры, игровые JVM, фоновые задания, S3 writers) должны быть фактически остановлены / изолированы. Скрипт останавливает **только сервисы целевого Docker Compose проекта**, сам не отключает внешние хосты, старые VM и внешние сети. Согласование окна и блокировка старых источников обязательны, флаги `--maintenance-approved` не являются технической аттестацией.
- **Нельзя** запускать восстановленный API одновременно со старым работающим cluster с теми же БД, S3 credentials, доменом и ключами. Отозвать сетевой доступ старого к target PG/Redis/S3 и перевести трафик только после проверки восстановленной инсталляции.
- Миры могут находиться на независимых Linux-узлах. Каждый исходный host должен выполнить штатный `nl server-bridge host world-backup create` в остановленном состоянии. Скопировать каждый законченный каталог ID на DR-хост (зашифрованным защищённым транспортом) и **не включать активные JVM обратно**. Пути `--world-backup` доступны локально DR-оператору; назначения `--world-destination` должны быть локальными смонтированными каталогами целевого хоста или управляемыми монтированиями восстановляемых game-нод. Операция не утверждает безопасность атомарного `rename` на любой произвольной NFS/сетевой ФС: используйте проверенную локальную Linux ФС или отдельный staged restore на game-host до переключения.
- Секреты (`.env`, private signing keys, TLS, auth, S3) восстанавливаются из **отдельного** менеджера секретов. Дамп и игровые файлы **не шифруются этим инструментом**; используйте шифрованный канал и offsite storage с контролем доступа. Точка консистентности источника определяется окном без записей. Необходимость восстановить внешние auth-provider базы подтверждается отдельно.

## 1. Источник: реальные остановленные миры

На **каждом** игровом host (версия `nl` должна соответствовать установленной версии):

```bash
nl server-bridge host world-backup create \
  --server-root /srv/minecraft-paper --backup-root /srv/world-backups \
  --consistency stop
nl server-bridge host world-backup list \
  --server-root /srv/minecraft-paper --backup-root /srv/world-backups
nl server-bridge host world-backup verify \
  --server-root /srv/minecraft-paper --backup-root /srv/world-backups \
  --id <32_HEX_BACKUP_ID>
```

`create` посылает штатный `stop` через Host Supervisor при `--consistency stop`, ожидает доказанного завершения процесса и удерживает maintenance gate при копировании. Неподконтрольную JVM сначала остановить/доказать завершение отдельно. Запрещено отключать gate или копировать живые region-файлы. Перенести полный `BACKUP_ID/` на приватный DR-узел, сохранив структуру `manifest.json` + `payload`. На DR-хосте можно указать несколько миров: `--world-backup paper=/mnt/source/paper/<ID>` и `--world-backup proxy=/mnt/source/proxy/<ID>`.

## 2. Cold backup Network-HA

Подготовить Linux с Docker Compose, `aws` CLI, Python 3 и исходниками **того же commit 0.45.4**. В `deploy/production/.env` восстановить настройки реального Network-HA overlay и S3, иметь доступ к snapshot storage вне Compose volumes.

```bash
python3 scripts/operations/dr_03512.py backup \
  --network-ha --project launcher --confirm launcher \
  --env-file deploy/production/.env \
  --snapshot /srv/never-dr/ha-0454 \
  --s3-source-bucket launcher-source-objects --s3-endpoint https://s3.example.net \
  --world-backup paper=/mnt/source/paper/0123456789abcdef0123456789abcdef \
  --production-source --maintenance-approved
```

Штатный `snapshot()` останавливает действующие API/Admin/Nginx/Redis **в этом Compose проекте**, делает настоящий PostgreSQL custom dump, сверяет структуру через `pg_restore --list`, архивирует четыре файловых тома (storage/backups/factory/coordinator), проверяет реальные Go world-backup/v1 метаданные и каждый SHA-256 файл, копирует миры. S3-объекты дважды загружаются и сравниваются **по хешам полных файлов**; изменения блокируют снимок. PostgreSQL WAL LSN проверяется до и после. Исходные остановленные Compose-сервисы запускаются обратно только в соответствии с их прежним состоянием; внешние игровые writers оператор контролирует сам.

**Redis AOF специально не копируется и не включается в restore**. Его ключи ServerBridge presence/command lease эфемерны. Новый формат `schema=3` содержит `ephemeralRedis=true`, `redis=fresh-ephemeral-not-restored` и `worlds` с полными данными в `worlds/NAME/ID/payload`. Legacy Network-HA snapshot `schema=1/2`, содержащий старую Redis lease/AOF, **отклоняется** для `restore-fresh` в режиме Network-HA; он не «конвертируется» в безопасный автоматически.

Проверка перед переносом:

```bash
python3 scripts/operations/dr_03512.py verify \
  --snapshot /srv/never-dr/ha-0454
```

`verify` хеширует и проверяет реальные tar-файлы, структуру PG custom dump, S3 blobs, world backups и инвентарь. Хеши в manifest проверяют **целостность**, но без доверенной внешней подписи/неизменяемого хранилища не доказывают автора снимка.

## 3. Restore в новую инфраструктуру

На **новом** хосте восстановить точно `LAUNCHER_IMAGE_TAG=0.45.4`, TLS и подписывающие ключи из vault, создать **новый пустой S3 bucket**, перенести снимок в приватный каталог и заранее создать только **родительские директории** будущих игровых root. Сами `/srv/restored-paper` и Docker volumes/containers целевого проекта должны отсутствовать. Mount/файловая система назначения должны поддерживать атомарный rename и fsync.

```bash
python3 scripts/operations/dr_03512.py restore-fresh \
  --network-ha --project launcher --confirm launcher \
  --env-file deploy/production/.env \
  --snapshot /srv/never-dr/ha-0454 \
  --target-s3-bucket launcher-recovered-objects --s3-endpoint https://s3.example.net \
  --world-destination paper=/srv/restored-paper \
  --ready-url https://launcher.example.net/ready \
  --production-target --maintenance-approved
```

Порядок **исполняемых действий**:

1. До первой записи: проверить все SHA-256, содержимое world manifests, PostgreSQL dump, правильную версию, все пустые Docker volumes включая `launcher_redis`, отсутствие существующих контейнеров и world root, отдельный пустой S3 bucket.
2. Создать пустые volumes; проверить **реальную пустоту Redis volume**, не переносить старый AOF; восстановить и перепроверить остальные тома; запустить только PostgreSQL и выполнить `pg_restore` в одной транзакции.
3. **До API/Redis/ServerBridge** выполнить транзакционный SQL fencing. Перевести `leased` команды в `indeterminate` (требует ручной проверки эффекта), `pending` в `expired`; инвалидировать игровые join tickets, handoffs, transfers и player sessions; завершить исторические runtime instances; перевести ранее активные узлы в `credential-rotation-required` и увеличить `runtime_epoch`. Дополнительно погасить взятые в работу durable jobs/outbox/extension event deliveries, увеличить fencing tokens постоянных leases, остановить непроверенные migration/extension-upgrade операции. Проверить, что счётчики небезопасных активных состояний равны нулю. Сбой SQL или read-back останавливает restore до запуска API.
4. Скопировать **реальные мировые файлы** во временные каталоги под целевым host, перепроверить SHA-256 и атомарно опубликовать только в ранее отсутствующих путях. Игровая JVM автоматически **не запускается**.
5. Загрузить S3-объекты в новый bucket и считать их обратно для сравнения полного содержимого. Только затем запустить пустой Redis, API, Admin, Nginx и проверить `/ready` сначала **из контейнера API**, затем публичный HTTPS с обычной проверкой сертификата.
6. Вручную сверить UUID игроков, миры, плагины, прежние профили, download и ServerBridge. Каждый игровой узел требует **новую регистрацию/ротацию ключа** и подтверждённый первый runtime/heartbeat; не доверять старой зарегистрированной сессии. Не возобновлять `indeterminate` внешние команды без расследования. Только после этого разрешить запуск game JVM, переключить DNS/VIP и открыть игрокам вход.

**Ошибка после частичного restore:** API не должен быть запущен при ошибке fencing/world/S3. Если сломалась финальная readiness-проверка, API/Admin/Nginx останавливаются. Каталоги миров, volumes, bucket и следы выполнения не удаляются автоматически — это forensic material; повторять restore только в полностью чистой новой среде.

## 4. Приёмка и ограничения

Локальные тесты `scripts/operations/test_network_ha_recovery_0454.py` проверяют настоящие байты миров, SHA-256, символьные ссылки/траверсал, обработку аварий и порядок остановки/запуска через doubles Docker/PG. Дополнительный тест с `NL_WORLD_CLI=/path/to/nl` собирает реальный Go world-backup и восстанавливает его новым Python механизмом. Отдельно требуются **реальные** два Linux/Docker-хоста, живые PostgreSQL, Redis, S3, игровые сервера, действительные ключи и независимый оператор. В этом репозитории локальное выполнение Python/Go тестов **не доказывает** network failure, multi-API failover, RPO/RTO или реальную 2-host восстановимость. Это этап `0.45.5–0.45.6` и последующая эксплуатационная приёмка.
