# NeverLauncher 0.45.9 — эксплуатационная наблюдаемость

Новые операции исполняются на **собственном доверенном Linux-хосте**. Защищённая внутренняя Docker-сеть не предназначена для внешнего доступа к Prometheus, Alertmanager или blackbox-exporter. В этой версии **не** заявляется готовность всей сети и межхостового HA без отдельного испытания.

## 1. Установка мониторинга (Standard)

Используйте актуальные секреты, TLS и работающую production-установку `0.45.9` (смотрите 0.45.1/0.45.8). Не храните URL webhook в Git или истории shell. Создайте отдельный файл `/etc/launcher/monitoring/webhook.url` со строкой HTTPS-адреса вашего приёмника оповещений, доступного с Docker-хоста. Права: `0600`. Вебхук должен поддерживать формат Alertmanager POST; успешная отправка должна реально приниматься адресатом.

```bash
python3 scripts/operations/observability_0459.py configure \
  --webhook-url-file /etc/launcher/monitoring/webhook.url \
  --output /etc/launcher/monitoring/alertmanager.json
# Задайте в файле env /etc/launcher/.env:
# LAUNCHER_ALERTMANAGER_CONFIG=/etc/launcher/monitoring/alertmanager.json
# LAUNCHER_MONITOR_GID=<GID, напечатанный configure>
# LAUNCHER_PROMETHEUS_CONFIG=./monitoring/prometheus-standard.yml
cd deploy/production
docker compose --env-file /etc/launcher/.env \
  -f docker-compose.yml -f docker-compose.observability.yml \
  up -d prometheus blackbox alertmanager
```

`alertmanager.json` имеет права `0640`. У процесса Alertmanager пользователь `65534` и группа `LAUNCHER_MONITOR_GID`; файлы и родительские каталоги должны быть доступны этой группе на чтение. Не делайте конфигурацию или URL webhook общедоступными. Путь к конфигурации указывается **абсолютный**, хостовый. Вариант с другим UID/GID допускается только при целенаправленном изменении Compose и проверке разрешений. Если путь к конфигурации монтируется некорректно, сервис должен не стартовать; не подставляйте в URL фиктивный адрес ради PASS.

Для Network-HA используйте все три Compose-файла: `docker-compose.yml`, `docker-compose.network-ha.yml`, `docker-compose.observability.yml` и установите `LAUNCHER_PROMETHEUS_CONFIG=./monitoring/prometheus-network-ha.yml`. Вторая цель API доступна только в этом режиме. Потребление метрик ограничено приватной сетью. **Не публикуйте** в `ports` Prometheus 9090, Alertmanager 9093 или blackbox 9115 без дополнительного контроля доступа.

## 2. Что собирается

- Backend: штатный `/metrics` с временным агрегированием запросов, ошибок, 429, p95, in-flight; новые gauges uptime, heap bytes и goroutines; ServerBridge HA-показатели при наличии backend v2. Значения строятся на **реальном процессе**, не на статических декларациях.
- HTTP: JSON-записи `http_request` с локально сгенерированным `correlation_id` (возвращается в `X-Correlation-ID`), методом, группой маршрутов, фактическим статусом и длительностью. Пользовательский X-Correlation-ID игнорируется как недоверенный. Пути, параметры, тела, IP и токены **не записываются** этим middleware.
- Nginx: JSON-журнал TLS-прокси с внутренним request ID, correlation ID upstream, кодом и временем; без URL или IP.
- Worker: loopback-only `/ready` и `/metrics` (свежесть последнего PostgreSQL poll); по сети worker не открывает API и metrics. Оператор собирает его метрики локально через `docker compose exec` в ходе диагностики.
- Blackbox: реальные GET на каждый `/ready` через внутреннюю сеть, с оповещением при несоответствии HTTP 200. Это дополняет Prometheus `up`, который отдельно проверяет доступность `/metrics`.

Правила для отказа API, потери readiness, частоты 5xx, высокой p95, 429 и устаревших ServerBridge-узлов: `deploy/production/monitoring/alerts.yml`. Пороги должны корректироваться по измеренным нагрузкам. Доставка идёт через действующий Alertmanager по приватно настроенному HTTPS webhook. Проверяйте тестовый алерт и получение в приёмнике вручную; наличие конфигурации не доказывает доставку.

## 3. Диагностика инцидента

На хосте с доступом к Docker daemon:

```bash
python3 scripts/operations/observability_0459.py incident \
  --compose deploy/production/docker-compose.yml \
  --project my-launcher \
  --since 15m --version 0.45.9 \
  --output /secure/operator/incident-001.zip
```

Для HA добавьте `--overlay deploy/production/docker-compose.network-ha.yml`. Скрипт читает Compose `ps`, whitelisted JSON-логи, безопасные числовые метрики `/metrics` внутри API и workers. ZIP создаётся с правами `0600` без перезаписи, включает SHA-256 содержимого. Он **не** собирает переменные окружения, непроверенные stderr, сырые журналы, URL запросов, HTTP-тела, ключи или файлы БД. Логи старого формата пропускаются. Сам ZIP всё равно требует хранения как конфиденциального артефакта: в нём есть имена сервисов и идентификаторы корреляции. Не загружайте его на публичные трекеры.

## 4. Независимая приёмка

1. На работающем Standard или Network-HA создать два пользовательских запроса (200 и управляемый отказ), найти `X-Correlation-ID` в ответе и в JSON логе **того же** backend, убедиться в фактических status и duration без URL/секретов.
2. Через `docker compose exec -T api wget -qO- http://127.0.0.1:8080/metrics` проверить изменение счётчиков после запросов и наличие показателей памяти; для worker проверить `launcher_worker_poll_fresh` на localhost внутри worker.
3. Проверить, что Prometheus targets и blackbox probes находятся в состоянии UP; затем на тестовом стенде остановить API и подтвердить срабатывание правила, маршрут Alertmanager и **доставку** webhook адресату. Повторить после восстановления и подтвердить resolved.
4. Отключить PostgreSQL/Redis/S3 на выделенном DR-стенде и убедиться, что `/ready` отказывает, а alert `NeverLauncherBackendNotReady` отражает отказ (настройки данного режима обязаны учитывать требуемые зависимости).
5. Создать incident ZIP при отказе, открыть его offline, проверить SHA-256 и отсутствие секретов. Зафиксировать время обнаружения, обработки тревоги и восстановления в отдельном эксплуатационном отчёте.
6. Проверить отсутствие публичного доступа к портам мониторинга, корректные права конфигурации и свободное место на volume Prometheus. Только после этого считать реальный контур мониторинга принятым.

**Ограничения:** local unit/negative tests не подтверждают доставку webhook, реальный Docker Compose failover, внешние SMTP/alert-получатели, Kubernetes или гарантированную диагностику каждого legacy-пути. В 0.45.9 не внедряется отдельный distributed tracing backend/collector, а логи фоновых legacy-job могут оставаться неструктурированными; корреляция HTTP и аудит уже связаны по ID, для worker дополнительно есть свежесть опроса и штатные журналы systemd/Docker.
