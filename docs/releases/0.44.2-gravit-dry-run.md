# NeverLauncher 0.44.2 — Gravit dry-run and migration plan

This release delivers an executable dry-run for one selected ClientProfile on a previously inventoried Gravit source. It reuses the real inventory, compatibility detector, identity reader, module analyzer and content converter. It does **not** import a user's data, stage client files, deploy ServerBridge, or switch traffic. The saved plan is an operator preview, not GA/cutover approval.

## Operator procedure

1. Run normal Migration Center setup for an existing Never project. Complete `execute` to `prepared/source_assessment`.
2. Upload the original Gravit ZIP through **Compatibility** and **Source Inventory**. Both reports must refer to exactly the same source SHA-256.
3. Choose source `profiles/<name>.json`, a **new** Never profile ID, name, supported loader, channel and release version. Upload the same original ZIP and select **Perform full dry-run**.
4. Inspect the returned file-by-file `automatic | transformed | manual | blocked | excluded` table, bytes to stage, identity count and duplicate-identity warnings, replacement modules, and operator checklist. The `planSha256` includes all these inputs and the target project fingerprint. The caller must explicitly review any `manual` items before treating a project as ready to cut over.
5. `GET /api/v1/admin/migration-runs/{runId}/dry-run` retrieves the saved plan and computes `targetUnchanged` against the current project. Re-run dry-run when source, target, selected profile, loader, channel, version, or converter output changes. **A failed or blocked plan never authorizes import.**
6. To import the selected profile's files later, upload the unchanged ZIP through `content/import` with existing confirmation headers and `X-Migration-Plan-SHA256`. The import re-runs the production content verifier and checks the plan, source and selected destination. The repository checks the stored plan inside its serializable profile/workspace transaction. Retry after network uncertainty with the same source, run ID, operator and destination; the existing workspace is reverified before acknowledging staged data.

A dry-run uses a private bounded upload spool, never executes a Gravit JAR, and does not create player accounts, alter profiles, publish releases, create Bridge nodes, import skins or change `channel_heads`. It persists only sanitized plan metadata and a migration audit event in PostgreSQL. Old keys are excluded; passwords, token values and raw account data never enter the plan.

## Explicit limits and blockers

- Current plan targets **one selected** ClientProfile. All remaining profiles and non-selected client trees are listed for manual follow-up. Full multi-profile orchestration is scheduled for 0.44.3.
- Supported FileAuthSystem/SQL account sources are parsed for counts and source-internal duplicate UUID/name/provider IDs. **Target account ownership, password verifiers and world/permission continuity still require the separate authenticated MIG04/MIG05 checks**; failures are blockers, not guessed matches.
- Modules and ServerWrapper are inspected statically; source JARs are neither loaded nor considered compatible by filename. Textures and non-portable optional behaviors remain manual or blocked, with explicit reasons.
- Transfer bytes are calculated from the converter-selected source files, not a measured installation duration. Downtime and backup disk requirements cannot be estimated reliably until rehearsal against the actual installation and deployment topology.
- A plan marked `manual` is **not** a certificate of migration readiness. A `blocked` plan refuses selected content import. The operator's remaining checklist is mandatory before cutover.
- The plan binds the selected content-import path. The legacy identity, auth, texture and cutover endpoints keep their own independent guards; this version does **not** claim to enforce a universal `planSha256` across every migration subsystem. Full integration and real Minecraft acceptance are later roadmap stages.

## Verification

Unit/regression tests cover real ZIP processing, deterministic digest, changed destination, SHA tamper, unsupported identity source, source/destination collision, key exclusion, content conversion and module parsing. A PostgreSQL integration test verifies durable save, source pin, retries without duplicate revision, and rejection before prerequisites. The CI workflow compiles Backend and runs the new test packages against PostgreSQL 17.

Local validation is limited to Go 1.23.2 using a **temporary modified modfile** because the actual project requires Go 1.27.3. The seven dependency-light packages passed `go test -race` and `go vet`; SQL integration and the full Backend require the project toolchain and PostgreSQL. Admin's TSX parsed successfully but its production build was not executed locally because the pinned Vite 8.0.14 package was unavailable in the offline npm cache. This is source/test coverage, **not** evidence of live Gravit migration or stable release acceptance.
