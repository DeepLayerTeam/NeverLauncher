# NeverLauncher 0.32.12 — Standard & Network Growth (DEP03/07)

## Runtime behavior

The API performs **live, fail-closed infrastructure checks before migrations, workers or the HTTP listener** when `NEVERLAUNCHER_DEPLOYMENT_MODE=standard` or `network-ha` is selected. A config-only detection is not treated as proof of distribution.

- **Standard**: PostgreSQL must accept two separate sessions and provide transaction-scoped advisory lock exclusion/release. An S3 storage selection is checked with a signed upload, a read through an independent client, a SHA-256 comparison, a signed delete and a 404 after deletion. In Standard, the existing single-instance OS lock remains mandatory; a local SQLite coordinator can be used in place of Redis.
- **Network/HA**: in addition to PostgreSQL, two independent Redis connections must demonstrate mutual exclusion, protection against non-owner release, takeover after release, and rejection of stale-owner release; shared S3 must complete the same read/write/delete integrity test. There is no fallback to SQLite, memory or local storage.
- Check keys and PostgreSQL advisory locks are generated randomly per invocation. Temporary S3 probes are deleted even if verification fails; an inability to delete or verify deletion fails the check. The probe requires the configured S3 principal to have write/read/delete rights to the designated bucket.

## Diagnostic command

Execute from a host with the actual production environment configured:

```bash
neverlauncher-api diagnose growth
```

Outputs `checks.postgresql`, `checks.redisLease`, `checks.s3RoundTrip`, timestamp and `verified`. Exits nonzero on any failed required check. The existing `diagnose deployment` remains offline and **does not** assert that services are reachable.

## Deployment and safe growth

Begin with a PostgreSQL-backed Standard installation, persistent data, one Backend and a verified instance lock. To grow, provision external PostgreSQL, Redis and S3, copy all real production keys and release BOM across replicas, transfer local artifacts to S3 with checked hashes and preserve exact PostgreSQL records. Set `NEVERLAUNCHER_DEPLOYMENT_MODE=network-ha`, `NEVERLAUNCHER_SERVERBRIDGE_HA_REQUIRED=true`, `NEVERLAUNCHER_STORAGE_DRIVER=s3`, nonempty `NEVERLAUNCHER_REDIS_URL`, `NEVERLAUNCHER_REPOSITORY_DRIVER=postgres` and `NEVERLAUNCHER_SQL_DRIVER=pgx`; configure S3 credentials and keep Redis-backed rate limiting fail-closed. Do not start a second writer against local storage.

**Important:** The 0.32.11 SQLite→PostgreSQL transfer stores data in a *staging schema* that is **not** yet the active PostgreSQL HTTP repository. This release does **not** implement a live cutover from the SQLite Core schema into the HTTP repository, nor automatic local→S3 blob migration. The live growth checks do not change these limitations.

## Verification and remaining HA requirements

GitHub Actions runs the checks against real PostgreSQL 18 and Redis 7 and a signed, fault-injectable HTTP S3 fixture. Production readiness still requires staging tests against the actual S3 provider plus at least two **separate hosts**, actual client/Guard/ServerBridge sessions, lease expiry, replica death while handling a command, partition/fencing behavior, failover under load, long-lived connections and restore procedures. Passing startup probes alone is **not** a Network/HA certification.

The startup probes add storage write/delete permissions and startup latency. The HTTP endpoint isn't opened until they succeed; failure is visible in logs and process exit. Run `diagnose growth` before a planned rollout and during the readiness review.
