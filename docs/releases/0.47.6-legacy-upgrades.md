# NeverLauncher 0.47.6 — existing installation upgrade (source implementation)

The upgrade operator in `scripts/operations/legacy_upgrade_0476.py` is for **in-place** installations only. It never converts a project into demo configuration, overwrites a database schema, reissues signing keys or downloads unsigned binaries. It calls the same *existing* updaters used by production: `component_upgrade_0458.standard`, signed `launcher update components`, the pinned Linux systemd binary updater and signed `neverinstaller update`.

### Accepted source metadata

The operator recognizes `0.45.14`, `0.46.0–0.46.3` and `0.47.0–0.47.5` when supplied with an existing supported installation layout. These are **input-version checks**, not a certificate that all historical installations, third-party extensions or Minecraft versions are backward compatible. The installed Desktop source comes from `.launcher/component-update-state.json`. Linux binaries are queried with `version`. Docker Backend is read from a private deployed source env (`LAUNCHER_IMAGE_TAG`). Prestarter stores an opaque *signed release ID*, not product SemVer: operator must supply `--from-version` if no native client state is present, and Prestarter verifies the old installed bundle using its pinned embedded public key before update.

The operator refuses installations with an unrecognized version or format. There is no automatic source-to-source chain for unknown versions, no migration of PostgreSQL/SQLite by this tool and no use of its own signature-verification bypass.

### Maintenance preparation

1. Stop Desktop/game processes, world writers and any external writers. This tool is **not** a live game-world snapshot coordinator. Supply each actual user-data path via `--data` (paths are relative to existing install root). Pre-existing application data is independently copied outside the installation. The backup parent must exist, be mode `0700`, and have enough free space. The new backup path must not exist. Never place it under the installation tree.
2. Prepare and independently pin all signed binaries and delivery manifests. Do not use the app's current running binary as an untrusted source for a new signature policy.
3. Run on a test clone first; validate Minecraft startup, signed profile, account re-login, client download, ServerBridge heartbeat, old project/profile, and file digest after the upgrade.
4. On an interrupted/failed operation, read the private `journal.json` and inventory, then use the native updater's recovery facility. **Do not rerun with a fresh backup path** until the old/new native transaction is reconciled; this prevents applying a partially committed update twice. Do not restore older data while any writers are active.

### Backend (Standard Docker + PostgreSQL)

The existing Standard operator verifies actual old `/ready`, checks immutable image digests, creates a cold PostgreSQL + local file-storage snapshot, switches API/Admin, validates new backend and rolls images back on failure. Database schema and encryption keys are not silently migrated. External PostgreSQL writers must be stopped separately.

```sh
sudo python3 scripts/operations/legacy_upgrade_0476.py backend \
  --project launcher-prod --confirm launcher-prod \
  --source-env /etc/launcher/production-old.env \
  --target-env /etc/launcher/production-0476.env \
  --backup /srv/launcher/private-backups/backend-0476 \
  --production-source --maintenance-approved
```

Private source/target environments must agree on **every** value except the image tag and explicit `LAUNCHER_DATABASE_AUTO_MIGRATE=false`. For SQLite Minimal Backend use the `host` path for the binary and separately perform the verified SQLite backup/schema upgrade; do not claim it is a PostgreSQL cutover. For Network-HA use the existing `component_upgrade_0458.py network-ha` command with `--from-version` and `--to-version 0.47.6` and its mandatory S3/world snapshots, not the Standard route.

### Desktop, Runtime and Guard (signed multi-component package)

```sh
python3 scripts/operations/legacy_upgrade_0476.py client \
  --root /home/USER/.local/share/Launcher --backup /srv/private/upgrade-0476-client \
  --data profiles --data settings --data instances \
  --cli /opt/neverlauncher/launcher --cli-sha256 PINNED_INSTALLED_CLI_SHA256 \
  --package /opt/releases/verified-components.zip \
  --sha256 EXACT_EXTERNAL_SHA256 --delivery-manifest /opt/releases/DELIVERY_MANIFEST.json
```

The existing CLI's transactional updater validates signed per-platform artifacts, trust epoch, security generation and digest; `legacy_upgrade_0476` verifies the native component state advanced to 0.47.6, plus all protected user data matched the pre-upgrade backup (bytes, directory layout and permissions). Unknown desktop layout is **rejected**, not installed as a new demo client.

### Prestarter / signed NeverInstaller

```sh
python3 scripts/operations/legacy_upgrade_0476.py prestarter \
  --root /home/USER/.local/share/Launcher --backup /srv/private/upgrade-0476-prestarter \
  --from-version 0.47.5 --data profiles --data settings \
  --installer /opt/releases/neverinstaller --installer-sha256 PINNED_INSTALLER_SHA256 \
  --bundle /opt/releases/signed-bootstrap
```

The *actual* signed `neverinstaller` is invoked in order: `verify` new bundle, `verify-installed` old release, `update --no-start`, `verify-installed` new release. The underlying installer already prohibits project ID, profile ID, channel or profile public-key replacement and uses redundant generation records. The operator verifies that generation increased. Unsigned or missing trust root stops the updater. It does not synthesize signed metadata.

### Linux CLI, Minimal Backend and ServerBridge native executable

```sh
sudo python3 scripts/operations/legacy_upgrade_0476.py host \
  --root /opt/neverlauncher --backup /srv/private/upgrade-0476-bridge \
  --data config --data data --component bridge \
  --install /opt/neverlauncher/bin/launcher-bridge \
  --executable /opt/releases/launcher-bridge --sha256 EXACT_EXTERNAL_SHA256 \
  --service launcher-bridge.service
```

The existing root-owned Linux updater performs a same-filesystem atomic swap with `.previous-0476` retained, pinned SHA-256, `version` check and `systemctl` restart/check. Minimal Backend additionally checks a genuine `/ready` response using `--component api --service launcher.service`. For Java ServerBridge JAR/plugin updates use the dedicated `bridge-jar` route below. Changes to world/plugin data must not be done while a world is running.


### Java ServerBridge plugin JAR (existing server)

This route accepts a full pinned release `PLUGIN_MANIFEST.json` (not an unsigned, unpinned JAR name), validates the release matrix and the exact SHA-256 of the selected platform artifact, inspects embedded plugin version, stops the systemd-managed Minecraft server, atomically replaces only the plugin JAR, and restores its original byte-for-byte version if restart fails. Neither server worlds nor plugin configuration are rewritten. Operator must obtain the manifest SHA from the separately approved release channel.

```sh
sudo python3 scripts/operations/legacy_upgrade_0476.py bridge-jar \
  --root /srv/minecraft/paper --backup /srv/private/upgrade-0476-paper \
  --data world --data plugins/LauncherBridge --plugin-type paper \
  --service minecraft-paper.service \
  --install /srv/minecraft/paper/plugins/launcher-paper-bridge.jar \
  --executable /opt/neverlauncher/artifacts/launcher-paper-bridge-0.47.6.jar \
  --release-manifest /opt/neverlauncher/artifacts/PLUGIN_MANIFEST.json \
  --manifest-sha256 EXACT_INDEPENDENT_MANIFEST_SHA256
```

A successful `systemctl is-active` does not prove ServerBridge authenticated its node or accepted a real Minecraft join: perform a separate game-server heartbeat and actual join E2E. The script reports `runtimeJoinVerified: false` until independently tested.

### Verified Linux executable rollback

For an already committed 0.47.6 host executable upgrade (not JAR), `rollback-host` reads the private original journal and pinned old binary SHA-256, invokes the native rollback engine with the `.previous-0476` file and validates preserved user data after recovery:

```sh
sudo python3 scripts/operations/legacy_upgrade_0476.py rollback-host \
  --root /opt/neverlauncher --backup /srv/private/upgrade-0476-bridge \
  --component bridge --install /opt/neverlauncher/bin/launcher-bridge \
  --service launcher-bridge.service
```

Rollback is intentionally blocked if an earlier failed update has no complete committed binary receipt; use controlled incident recovery instead of guessing which bytes to restore. Do not roll back when the old executable cannot interpret newer persistent state.

### Recovery and limits

Each non-Backend operation writes a private journal under the new backup directory. It marks `updater-invoked` **before** calling the native operation and `manual-reconciliation-required` on any exception. After a native commit, a byte-level check verifies user data; when mismatch occurs, the backup remains available and no success report is issued. It deliberately does not blindly roll back an already committed signed updater, which could erase acknowledged new data.

**Important acceptance boundary:** The tests in this patch cover local filesystem preservation, rollback refusal and native updater invocation. They do not supply six independently signed OS packages, run a real cloud backend/PG cluster, verify a live ServerBridge plugin upgrade, or certify Minecraft startup. The full user criterion (all claimed historical versions upgraded with no data loss) requires a tested inventory of archived installers and independent E2E for each source version.
