# 0.29.9 — HWID Risk & Recovery

## Runtime behaviour

- Desktop **only on explicit user action** collects a limited native machine-continuity hint. On Linux it uses an available DMI UUID and machine ID; on Windows the system installation MachineGuid; on macOS the IOPlatform UUID. No hostnames, usernames, disk serial inventories or MAC address lists are collected. Unavailable native hints fail visibly rather than falling back to fabricated values.
- Desktop sends only a locally SHA-256-hashed hint to authenticated API `POST /api/v1/auth/hwid/observe`. TLS remains required for production. The API HMACs the hint using `NEVERLAUNCHER_AUTH_TOKEN_SECRET` and user-ID domain separation. PostgreSQL only stores the HMAC digests for a *single user's trusted-device binding*, not raw host identifiers or cross-account hashes.
- First observation records a baseline, matching observations maintain it, changed observations create a *pending* signal. It is untrusted and spoofable. The risk engine adds at most a **20-point risk contribution** and requests step-up; it never automatically bans or marks a session compromised based only on this signal. Existing independent compromise signals can still revoke a session.
- Recovery: `POST /api/v1/auth/hwid/confirm` requires fresh phishing-resistant Never MFA and atomically promotes the pending signal; `POST /api/v1/auth/hwid/appeals` creates a review request without supplying secrets; a permitted admin with fresh phishing-resistant MFA approves or rejects via `/api/v1/admin/auth/hwid/appeals/{appealId}/resolve`. Approval is fenced to the exact signal observed when the appeal was created; stale approvals fail.
- `GET /api/v1/auth/hwid` and `GET /api/v1/auth/hwid/appeals` return redacted state. `DELETE /api/v1/auth/hwid` deletes current-device observations and appeal data. `GET /api/v1/admin/auth/hwid/appeals` returns review metadata without digests. These operations require an active user/session and validated trusted-device ownership.
- Observations and appeals expire within 30 days of relevant observation/creation. Authorization ignores expired hints immediately; a recurring PostgreSQL/Memory janitor physically purges expired rows at startup and every six hours. Each observation refreshes the TTL. All policy decisions are read from authoritative repository state across API replicas.

## Deployment

- Apply sealed SQL migration `0084_hwid_risk_recovery_0299` (Backend + CLI copies).
- Keep `NEVERLAUNCHER_AUTH_TOKEN_SECRET` identical across all API replicas and rotate with the standard token-rotation procedure; rotating it also requires rebuilding the optional HWID baseline by consent. Never log request bodies or calculated HMAC digests.
- Desktop must be built with the native Tauri command included. On environments without accessible OS-provided hint the UI reports the limitation; this does **not** prevent login/game launch.
- Review queued appeals via admin endpoints; user confirmation requires passkey/MFA freshness. Approval does not resurrect revoked sessions or lift Protection bans.
- Monitor `auth:hwid:changed`, `auth:hwid:appeal`, `auth:hwid:confirmed`, `auth:hwid:appeal:approved` audit actions. No bulk automated HWID bans.

## Verification and limitations

Unit and memory-repository tests cover first/changed/duplicate observations, cross-user isolation, expiry/purge, appeal replay, confirmation/forget and risk non-revocation. PostgreSQL cross-replica tests and Desktop TypeScript/native build are included in CI. Live PostgreSQL/API/Desktop E2E is not certified until these CI tests are run successfully against release artefacts.

HWID is not an immutable or tamper-proof identity, and this implementation intentionally never claims vendor TPM/Secure Enclave provenance. A privacy-preserving first-party proof-of-possession device key remains the stronger signal. Host OS reinstall or motherboard replacement may change the optional hint; account recovery is supported without banning the user.
