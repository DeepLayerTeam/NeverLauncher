# NeverLauncher 0.27.2 — Modern Loader Adapters

## Production source changes

This release improves the *existing executable materializers*, rather than introducing a second mock resolver or a metadata-only API. The Client Factory invokes the same Vanilla, Fabric, Quilt, Forge and NeoForge installers as the standalone `runtime *-install` paths. This preserves file download, SHA checks, Forge processor execution/recovery, transactional staging and the `install-plan.json` replay mechanism from 0.27.1.

- **Deterministic loader version selection:** Fabric and Quilt `latest` select the newest available valid loader, including pre-release. `latest-stable`, `stable` and `recommended` select the highest compatible stable version. Numeric components, prerelease numbers and historical `+build.N` suffixes are compared deterministically; upstream list order no longer affects selection.
- **Strict compatibility and artifact identity:** Loader versions are selected only from the matching Minecraft version's official Meta API compatibility list. Selected Fabric/Quilt loader coordinates must be the correct Maven group/artifact and contain the exact selected version. Conflicting duplicate entries or mismatched Maven identities fail closed.
- **Snapshot metadata URLs:** Minecraft version IDs with spaces and other URL-special characters are encoded for Fabric/Quilt compatibility and launch-profile endpoints. Mojang `release` and `snapshot` aliases now use the corresponding authoritative latest entries rather than treating `release` as an explicit, non-existent version.
- **Forge/NeoForge input validation:** Explicit selectors and candidate versions from Maven metadata are restricted to safe artifact version tokens; traversal, query/fragment injection and other malformed coordinates are rejected before URL construction.
- **Provenance and pinning:** Client Factory records Vanilla release type and exact resolved loader/Maven/intermediary coordinates in the canonical InstallPlan. Loader source metadata hashes, installer/profile SHA-256 and output SHA-256 remain pinned in the existing lock and verified on rebuild. Incompatible changes do not silently update a build.
- **Library source conflict handling:** two profile entries that target the same destination with different repository URLs are rejected even if the SHA-1 values match. No jars are downloaded before the conflicting profile has been checked.

### Use

```bash
cd cli
go run ./cmd/neverlauncher runtime client-factory build \
  --loader fabric --minecraft 1.21.1 \
  --loader-version latest-stable \
  --client-dir /srv/neverlauncher/clients/snapshot

go run ./cmd/neverlauncher runtime client-factory verify \
  --client-dir /srv/neverlauncher/clients/snapshot
```

The factory requires an empty destination on the first build. It refuses to rebuild an existing modified destination. A subsequent call with `latest-release`/`latest-stable` **replays the exact locked Minecraft and loader versions**, without picking newer upstream releases. To intentionally upgrade a loader, produce a new plan in a new client directory; in-place upgrade planning is out of scope.

### Verification and limits

The offline HTTP-fixture tests cover source selection (including unsorted lists and prereleases), exact version/coordinate compatibility, unsafe version rejection, special-character path handling, duplicate library URLs, immutable replay and tamper detection, and the existing five-family materializer fixtures. CLI build and `go vet` pass. A full package-wide test suite was attempted but exceeded the local execution budget; it is not certified as passing.

**Not certified as GA:** graphical Minecraft starts, online-mode client/server joins, native OS/architecture matrices and all upstream permutations have not been exercised in this environment. These remain required gates for the later Runtime E2E & Certification milestone; an immutable metadata lock is not itself a certificate of a real client launch.
