# NeverLauncher 0.31.13 — Resource Enforcement & Security UX

## Delivered

This release retains the Linux OS-enforced cgroups v2 limits (`memory.max`, `pids.max`, `cpu.max`, `cgroup.kill`, finite lifetime), Windows AppContainer + Job Object limits (job/individual memory, CPU hard cap, active-process count, kill-on-close and no breakaway), signed sandbox policy and scoped brokers from earlier releases. None of these primitives are claimed to have been validated end-to-end on physical hosts in the offline release environment.

**New, operational Host Protocol quotas:** for every isolated extension instance, the Backend enforces a sliding **fixed one-second window** of authenticated requests (default 64/s), a cap of 16 concurrent Host requests, and an 8 MiB cumulative output budget. Both the loopback Host Protocol and authenticated private IPC proxies use the same middleware. A rejected request returns HTTP 429. Output includes responses and Host-logged stdout/stderr/protocol messages; overlong stdout/stderr lines fail the instance. The cumulative output limit terminates the isolated process rather than allowing it to print indefinitely. CLI stdout and stderr share a single process output budget, enforced alongside Host Protocol responses.

The canonical **Ed25519-signed sandbox manifest** can specify tighter optional `maxRequestsPerSecond` (1..64) and `maxOutputBytes` (1..8388608). Zero/unset applies the host hard ceilings. These fields are included automatically in policy digest and owner review. Any update changing signed policy needs the same explicit review as other grants. No extension-owned configuration can override the Backend's limits. Signed `maxProcesses`, `maxMemoryBytes`, `maxCpuPercent`, and `timeoutSeconds` continue to be OS-managed where a verified OS boundary exists. Filesystem scratch on Linux is capped with an actual tmpfs mount; no equivalent disk guarantee is claimed elsewhere.

## macOS fail-closed correction

The signed App Sandbox helper inherits an OS sandbox, but `setrlimit` constrains **each process** and a POSIX process group is **not** an inescapable tree/aggregate resource container: a descendant can call `setsid()` and evade process-group kill. Thus, until an actual verifiable aggregate process-tree enforcement mechanism is provided, `macossandbox.Available` and `Prepare` return `macos-aggregate-process-tree-resource-boundary-unavailable`; `sandbox.mode=isolated` cannot be launched on macOS. No automatic downgrade to `trusted` is permitted. This is an explicit security correction; it reduces availability rather than pretending the requested guarantees exist. Legacy `trusted` execution remains unconfined and is shown as such.

## Security UX

Extension Manager distinguishes *signed requested policy* from *kernel-verified effective restrictions*, reports `isolated` vs `unsupported`, runtime OS/network/filesystem boundaries, exact reason codes, current PID/RSS/processes, request rate and output budgets, active/rejected requests, and recent failures. Seeing a signature or a UI iframe sandbox does not qualify as OS process isolation.

## Limitations and verification

- Compile-only Windows/macOS cross-target checks do not prove AppContainer ACL, actual Job containment, or signed macOS App Sandbox behavior.
- Run negative process tests on prepared, dedicated hosts: child process calls `setsid()`/`setpgid()` then attempts to exceed CPU, memory, PID and disk limits; direct forbidden sockets/mount paths fail; broker denied grants fail; cgroup/Job cleans all descendants. For macOS, verify clean refusal until a non-escapable tree boundary exists.
- Host request quotas apply to authenticated Host Protocol operations, not directly to raw syscalls of trusted/unconfined extensions.
- A rolling **fixed window** can permit burst traffic across window boundaries; CPU and wall-time are separately governed by OS runtime limits.
- No absolute anticheat or kernel integrity guarantee is implied. Require signed package policy, least privilege and a dedicated test machine for end-to-end certification.

### Example signed policy additions

```json
{"maxRequestsPerSecond": 16, "maxOutputBytes": 1048576}
```

These members are part of the existing `sandbox` object, not a separate unsigned configuration file.

## Verification commands

```sh
cd services/api
go test -race ./internal/extensionhost ./internal/extensionpolicy ./internal/linuxsandbox ./internal/windowssandbox ./internal/macossandbox
go vet ./internal/extensionhost ./internal/extensionpolicy
go build ./...
cd ../../apps/admin && npm ci && npm run build
```

With dependencies absent, `-tags neverlauncher_nopgx` is an **offline-only subset test**, not a substitute for normal production build. Cross-compilation and unit-test results must be recorded separately from genuine OS enforcement tests.
