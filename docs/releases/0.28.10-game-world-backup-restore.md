# 0.28.10 — Game World Backup & Restore

## Product implementation

`nl server-bridge host world-backup` operates on the **game server root** and
reuses the 0.28.2 Host Supervisor for clean shutdown. It is NOT a Backend DB,
Redis, object storage or NeverLauncher API backup. There is no new generic
shell/Host remote permission and the HTTPS RemoteControl v1 surface is unchanged.

Available operations: `create`, `list`, `verify`, and `restore`.

The default store is a private sibling directory of the canonical server root,
uniquely derived from the path. `--backup-root` can select a separate storage
volume; neither it nor a restore destination may overlap the live server root.
Only private (0700) stores are accepted. A process-identity-bound exclusive lock
fences concurrent backup and restore operations on that store.

## Examples

```sh
# Stop a supervised Minecraft server gracefully, then snapshot saved worlds:
nl server-bridge host world-backup create --server-root /srv/minecraft/survival --consistency stop

# When the game is already stopped, do not implicitly start or stop it:
nl server-bridge host world-backup create --server-root /srv/minecraft/survival --consistency stopped

# Include an additional Multiverse/world-directory (repeatable):
nl server-bridge host world-backup create --server-root /srv/minecraft/survival --world survival --world adventure

nl server-bridge host world-backup list --server-root /srv/minecraft/survival
nl server-bridge host world-backup verify --server-root /srv/minecraft/survival --id <BACKUP_ID>

# Mandatory exact confirmation; destination must not already exist:
nl server-bridge host world-backup restore --server-root /srv/minecraft/survival \
  --id <BACKUP_ID> --confirm <BACKUP_ID> --destination /srv/minecraft/recovery-test
```

`--backup-root /mnt/secure-backups` can be passed to each operation to use
non-default storage. Full JSON manifests are included in CLI output (or
`--output <file>`), with `id`, UTC creation, selected worlds, relative paths,
file sizes, modes and SHA-256 hashes.

## What is preserved

The primary world directory is derived from `level-name` in `server.properties`
(default `world`); existing `<level-name>_nether` and `<level-name>_the_end`
are auto-selected. For Bukkit/Multiverse/custom worlds, specify each desired
world using repeated `--world`. The backup also includes `plugins/`, `config/`,
`server.properties`, permissions/ops/whitelist/ban JSON and common Bukkit/proxy
configuration files if present. Entire selected world directories preserve
`level.dat`, region files, UUID-based playerdata, inventories, advancements,
stats, and plugin user data as regular files. Symbolic links, device files,
unsafe paths and escaping directory names cause a hard failure.

Files are copied to a private unpublished staging tree. Every file is
SHA-256 hashed as copied, source stability is checked, and the staged snapshot
is verified before atomic publication of the backup directory. Restore first
verifies every file and rejects unknown payload entries, then copies and
rechecks hashes in a separate staging tree, which is renamed into a **new**
destination. Existing destination directories are never overwritten. Restore
never starts a Minecraft process or modifies the running server root.

## Consistency guarantees and limitations

- `stopped` (default) rejects a recorded running process, starting/restarting
  host, crash/failure state, and a forced/unknown previous stop. `stop` requests
  the configured Host Supervisor to send Minecraft's `stop` command through
  stdin, waits for a clean exit (exit code 0 and console-stop), and refuses to
  take a snapshot after SIGTERM/SIGKILL or unverifiable/orphan runtime state.
  It does **not** automatically restart the game after creating the backup.
- Offline backups cannot prove the absence of an independently launched game
  process outside Host Supervisor. Operators must stop any unmanaged server.
  Filesystem copy is **not** a database transaction and cannot provide an
  online-consistent backup if another process modifies the files concurrently.
- SHA-256 checks are integrity detection, **not** cryptographic provenance or
  authenticity. Protect backup storage against actors with write access.
- Restore produces a directory tree for an **isolated test server**. It does
  not provision the test server, install matching plugins, launch Minecraft or
  prove UUID/inventory/plugin data semantics inside the game runtime.
- Backup restore is deliberately a host-local privileged operation. No Admin
  remote World Backup API, live save-all/flush acknowledgement protocol,
  online snapshot, automated retention/offsite copy or cluster-wide backup
  coordinator is claimed in this release.
- Windows uses flushed files and rename; directory-fsync is not available via
  the Go standard library on Windows. Use filesystem/volume-level durability
  practices for that platform.

## Verification

```sh
cd cli
go test ./cmd/neverlauncher -run 'TestWorldBackup|TestServerBridgeHostStopSupervisedProcess01910' -count=1
go test -race ./cmd/neverlauncher -run TestWorldBackup -count=1
go vet ./cmd/neverlauncher
go build -o ./nl ./cmd/neverlauncher
python3 ../scripts/test/world-backup-host-e2e-02810.py --cli ./nl
```

The CLI integration test starts a **real supervised child process**, responds
to `stop` by writing `world/level.dat`, creates/verifies/restores the snapshot,
and checks playerdata and plugin data bytes. It is a lifecycle integration
fixture, **not** live Paper/Vanilla/Forge Minecraft runtime E2E. The latter
must still be run with actual installed game/server plugins and UUID inventory
assertions before claiming Game World Backup production certification.
