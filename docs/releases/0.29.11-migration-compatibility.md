# NeverLauncher 0.29.11 — Migration & Compatibility

## Runtime changes

- Added a real PostgreSQL upgrade protocol to **`nl db auth-upgrade`**. `preflight` reads the production database under a PostgreSQL repeatable-read, read-only transaction, validates account and identity consistency, and writes a mode-0600 preservation checkpoint. No password hash, access/refresh token, device/HWID, active session or raw account identifier is written to the checkpoint. The on-disk data contains only aggregate counts, provider identifiers and SHA-256 digests of canonical identity records. The scanner also incorporates an ephemeral, database-computed MD5 of the stored password hash into the fingerprint to detect accidental hash resets; it never persists or prints individual hashes.
- `apply` compares the current users, `(identity ID, user ID, provider, subject)` associations and `(user ID, Minecraft UUID, name)` mappings against the preflight checkpoint **before applying the real, checksum-verified Backend/CLI SQL migration chain**. It then verifies all sealed migrations and compares the preserved associations again. `verify` independently repeats the same verification after deployment. Unexpected drift aborts the operation; it does not relink accounts or rewrite UUIDs.
- Preflight rejects unknown local password formats, inconsistent/orphaned identities, duplicate UUIDs/emails and invalid issuer-scoped subjects. Any non-local provider — particularly a custom Gravit provider — requires a deliberate repeated `--allow-provider <exact-ID>` after external validation. This acknowledges the existing external source; it **does not** import unknown provider credentials or certify that an external IdP is trustworthy. A matching email alone is never proof of account ownership.
- SQL migration `0086_auth_upgrade_integrity_02911.sql` seals existing identity ownership: the identity ID, Never account ID, provider, verified issuer and subject become immutable for UPDATE. New verified account links continue through INSERT, and normal claims/last-authenticated metadata updates remain supported. Migration is byte-identical in the Backend and CLI catalogs. The already-existing `0081` Minecraft UUID immutability trigger remains enforced.
- The FileAuthSystem `Database.json` import and transactional dry run from 0.29.5 remain the supported legacy Gravit entry point. `Sessions.json`, unsupported hashes and custom provider data are **never** silently imported. SQL/HTTP/OIDC/Microsoft settings use the provider-specific migration and conformance checks from 0.29.2–0.29.10.

## Production upgrade procedure

1. Stop new login, Minecraft join and Gravit source writes. Take and **restore-test an independent PostgreSQL backup**; archive the original Gravit Database.json securely. The tool cannot create or validate an external backup itself. A checkpoint alone cannot serve as a database backup.
2. Build a CLI from the exact 0.29.11 release and set `NEVERLAUNCHER_DATABASE_DSN` without embedding secrets into shell history. Run `nl db auth-upgrade preflight --snapshot /secure/identity-02911.json` (append `--allow-provider <ID>` for each independently confirmed non-local provider).
3. Investigate rejected hashes, issuer ambiguity, collisions or missing references rather than resetting passwords, forcing a merge or changing a provider route. `preflight` never makes database changes and refuses to overwrite an existing snapshot.
4. Run `nl db auth-upgrade apply --snapshot /secure/identity-02911.json --backup-confirmed --maintenance-confirmed`. This rechecks the current data, uses the real checksum-enforced migration runner, then validates the final database. Credentials are never exported to the checkpoint. Do not resume writes between `preflight`, `apply` and `verify`.
5. Deploy the Backend and run `nl db auth-upgrade verify --snapshot /secure/identity-02911.json`. Perform real local, SQL, HTTP/OIDC/Microsoft login, Minecraft launch/join, admin provider activation and revocation smoke tests before restoring user traffic.
6. For rollback of **database migrations**, restore the previously validated database backup while services remain stopped. Do not run an automatic down-migration that could discard identities, UUIDs, issuers or sessions. Configuration rollback is separate (Auth Provider Wizard revisions).

## Limitations and honest verification status

- The procedure intentionally preserves existing account associations and cannot automatically merge same-email accounts, infer custom issuers, recover unknown password hashes or translate arbitrary Gravit authentication modules. Unverified cases require explicit operator review.
- The checkpoints are preservation fingerprints, not a physical backup, authorization proof or tamper-proof signed artifact. Operators must stop writers; `preflight`/`apply`/`verify` are separate PostgreSQL transactions, and active writes between them can invalidate correctness. `--backup-confirmed` and `--maintenance-confirmed` attest operator preparation; they do not inspect infrastructure.
- CI workflow `auth-migration-compat-02911.yml` tests the full CLI against PostgreSQL 16 with two overlapping upstream subjects in different issuers, active UUID preservation, immutable identity keys and drift detection. Results in CI must be checked before declaring GA. The local environment may not have `psql` or PostgreSQL to run this integration itself.
