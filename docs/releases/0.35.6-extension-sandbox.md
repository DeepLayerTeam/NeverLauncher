# NeverLauncher 0.35.6 — Desktop sandbox and least privilege

## Changes that run in production paths

- `apps/desktop/src/extensions_0209.tsx` now checks extension IDs/scope/version/generation on every HTML load, renders only matching HTML, rejects oversized RPC payloads and invalid message origins, prevents concurrent duplicate IDs, drops in-flight results after iframe/extension replacement and requires a fresh Backend `bridge.authorize` RPC **before** calling native `tauri.*` commands.
- Existing Backend Desktop RPC endpoint checks `desktop:bridge` for the *current* enabled extension install, verified device/session, scope, version, and generation on every invocation. The catalog's `bridgeAllowed` is only a hint, not an authorization receipt. Revoking the grant immediately denies new native requests.
- Extension HTML now receives a restrictive CSP inserted **before** untrusted content, including markup that precedes a malformed `<head>`. Opaque-origin iframes keep `sandbox="allow-scripts"` without `allow-same-origin`, network/forms/workers/objects/popups remain blocked.
- The Tauri main window has an explicit local-only capability granting only event listening; there are no remote webview grants, filesystem or shell permissions. Production CSP does not allow arbitrary local HTTP/WebSockets; the Vite development server is allowed only in `devCsp`. Prototype freezing is enabled.
- Native `open_game_directory` opens only the canonical saved player game directory (no arbitrary renderer path), and owner-signed HTTPS project/news links plus device-code links open the system browser after native URL validation, not inside the privileged WebView.

## Operational constraints and important limitation

- Production Backend URLs for the Desktop now require **HTTPS**. Local `http://localhost:*` origins remain development-only and must not be distributed as a production bundle.
- **Unresolved browser compatibility:** HTML loaded with `iframe srcDoc` inherits its parent document's CSP according to CSP3. Therefore a sandboxed extension's inline scripts can be blocked by the main window's `script-src 'self'`, even if the extension HTML has a meta policy allowing them. This was already a limitation of the previous embedding scheme and is **not** solved by this release; do not claim full interactive third-party extension UI support or weaken the main-window CSP to make it work. A later release must host scripts in a separately constrained origin, with live WebView E2E proof. Data-only themes and signed branding remain supported.
- Per-RPC authorization prevents *new* native operations after revocation; it does not interrupt an already-running OS action between authorization and execution. There is no blanket multi-node HA claim.
- React/Tauri native compilation and real sandbox browser integration require a supported target runner. Security tests, gofmt/Go AST checks and bounded local Node/Go tests do not substitute for that evidence.
