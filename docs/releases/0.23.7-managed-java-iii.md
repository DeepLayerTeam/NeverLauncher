# NeverLauncher 0.23.7 — Managed Java III

## Executable changes

- Desktop now invokes `ensure_profile_managed_java` and verifies the pinned Ed25519 release manifest before selecting the profile's exact Java major/distribution. The standalone administrative `ensure_managed_java` command remains available.
- `neverruntime::managed_java` shares the existing SHA-256 object cache (`content_cache.rs`) and resumable verified HTTP transfer (`http_resume.rs`, `network_resilience.rs`) with Desktop and Repair. Object leases prevent concurrent downloads of the same archive between processes/profiles.
- Source selection: a verified shared-cache object, an already verified archive, local manifest/package or an offline archive directory, and finally a resumable HTTPS network fetch. `NEVERLAUNCHER_OFFLINE=1` explicitly forbids HTTP catalog/package fetches.
- `NEVERLAUNCHER_MANAGED_JAVA_OFFLINE_DIR` can contain `<sha256>.zip`, `<sha256>.tar.gz`, or the basename declared in the pinned local JRE distribution manifest. `NEVERLAUNCHER_MANAGED_JAVA_PROXY` accepts HTTP(S) proxy URLs. Standard `HTTP_PROXY`/`HTTPS_PROXY` settings also remain available through reqwest.
- New installs use unique staging directories, sync the install record, perform a bounded Java `-XshowSettings:properties -version` process self-test, validate OS/architecture/major, and atomically move the staged directory into place. Installed directories are keyed by release and archive digest. Failed staging is deleted; earlier verified installs with different digests remain available.
- The runtime record v1.3 includes SHA-256 for the complete file inventory (including JVM libraries). Runtime reuse detects modified, missing, and unexpected files. Damaged installs are quarantined before restoration from verified packages.
- Install serialization uses OS-level `fs2` file locks, not stale lock-file age heuristics. Locks are never unlinked while in use.
- An implicitly bundled JRE distribution manifest remains Java 21 only; other supported versions (8/16/17/25) use an explicitly configured matching manifest or Adoptium metadata. An explicitly configured mismatched manifest fails closed.

## Tests

```sh
python3 scripts/version/manage.py check
python3 scripts/contracts/validate-openapi.py
cargo test --manifest-path runtime/neverruntime/Cargo.toml managed_java -- --nocapture
cargo test --manifest-path runtime/neverruntime/Cargo.toml
cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml
cd apps/desktop && npm ci && npm run build
```

The Rust tests cover JVM property parsing, full-inventory corruption, and an end-to-end local distribution installation and recovery without accessing the archive's HTTPS source (on Unix with `tar`). Before promoting to production, validate clean installs and recovery on Windows x64/ARM64, macOS x64/ARM64, and Linux x64/ARM64; test real Temurin archives for each supported major; verify proxy, explicit offline mode, archive transfer resume and actual application launch. An application release is not certified by static checks alone.

## Compatibility and migration

Existing v1.2 runtime records are not reused as v1.3 inventory records because they lack checksums for non-executable JVM files. They are left on disk rather than blindly removed. New installations use the exact archive checksum in the installation path, preventing a same-name package from overwriting a prior verified JVM.
