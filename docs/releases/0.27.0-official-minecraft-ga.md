# NeverLauncher 0.27.0 — Official Minecraft Authentication GA

## Delivery status and mandatory external blockers

This release contains real Rust/Tauri Microsoft browser PKCE and Device Code login, native Xbox Live → XSTS → Minecraft Services token exchange, encrypted OS-keyring storage, multiple accounts, Never identity linking, and official/Yggdrasil/offline launch isolation from releases 0.26.1–0.26.12. Release 0.27.0 adds fail-closed GA admission, migration hardening and the release/signing integration below. **The presence of this code, passing unit tests, or a ZIP of modified sources is not a signed GA distribution.**

The signed production release is **BLOCKED** until the following real external checks are completed and independently attested for the *exact candidate commit* on **Windows/Linux/macOS × amd64/arm64**:

- Own Microsoft public client registration, personal Microsoft account (`consumers`), approved Minecraft Services access; independently confirmed provider approval for this application ID.
- Live system browser PKCE S256 + Device Code including cancellation/expiry/denial, refresh, live Xbox Live → XSTS → Minecraft and Mojang `join/hasJoined` using an entitled Java Edition account.
- Actual Java client world entry against vanilla and a supported Fabric/Forge/NeoForge server with `online-mode=true`, reviewed genuine logs, matching official UUID; mock logs alone do not suffice.
- Native OS keyring persistence across restarts, multiple accounts, refresh/expired or revoked refresh, logout, re-login, cancellation; no secrets via renderer/crash reports; strict offline/Yggdrasil separation.
- Exact native release artifact on each target, verified Windows Authenticode, macOS Developer ID **and notarization**, or Linux signed release manifest, with pinned production publisher; a build matrix is not signature proof.

Tests must not set `simulated`/`mocked` to `false` unless an actual operator ran and reviewed the named tests. An operator's signed assertion is not a direct cryptographic certificate from Microsoft; the operator remains responsible for independently confirming the external application permission. **Never put an OAuth grant, session cookie, refresh/access token, real user email or OS keyring dump in evidence.** Retain original unredacted server logs only in restricted operator storage, not source control or CI artifacts.

## 1. Candidate setup and live execution

1. Pick a clean release commit, and verify `VERSION=0.27.0`: `python3 scripts/version/manage.py check`.
2. Register/configure your own Microsoft application in Admin (client ID, browser/device policy). The browser redirect is the desktop loopback callback (`http://localhost:<dynamic-port>/minecraft-poc/callback`); confirm that the registered redirect and provider permissions actually support the flow.
3. For each physical/VM target run the real Desktop, repeat the supported flows, and run the POC **on that same OS/architecture**, using a real Java account. Run from `services/api`:

   ```sh
   go run ./cmd/official-provider-poc --client-id 'YOUR-OWN-CLIENT-ID' --flow browser --online-session=true --report './browser.json'
   go run ./cmd/official-provider-poc --client-id 'YOUR-OWN-CLIENT-ID' --flow device --online-session=true --report './device.json'
   ```

4. Capture the authentic vanilla and modded `server.properties`/`logs/latest.log`, and run `python3 scripts/certification/official-game-join-02612.py` per server. Inspect actual client world entry separately. For per-target signed GA proof copies, add **only reviewed** source/target/observedUTC/actualExecution fields and a clear `reviewedOriginalLogs: true` and `actualClientWorldEntry: true` to the private outputs; the signer verifies their consistency.
5. Execute the real OS-vault migration/restart/refresh/relogin/logout/adversarial modes on each native target, and record `vault.json`. Verify code-signing and notarization on the **actual artifact digest** and record `signature.json`. Browser and Device Code must authenticate the same official Minecraft UUID for a target.
6. Confirm the external application's admission independently; record that approval's ticket/reference and time in `attestation.json` (`externalApproval`). A successful OIDC token **alone** is not external Minecraft application approval.

## 2. Independent signed attestation format

The gate requires exactly these target directories with direct files, no symlinks, paths or hidden fallbacks:

```
private-evidence/
  windows-amd64/     windows-arm64/
  linux-amd64/       linux-arm64/
  darwin-amd64/      darwin-arm64/
```

Each directory must have `attestation.json`, `attestation.sig`, `browser.json`, `device.json`, `vanilla.json`, `modded.json`, `vault.json`, and `signature.json`. All JSON files are at most 1 MiB; the signed attestation is at most 64 KiB. Hashes in the `objects` map are SHA-256 of **exact file bytes**, not a reserialized representation. The operator must review the original private proof material and its integrity **before** signing. Provider reports use existing `neverlauncher.official-provider-poc.v1` format, `version: 0.27.0`, `result: online_session_verified`, the verified Java subject hash, the exact platform and successful stages including `sessionserver_join_has_joined`.

The following example illustrates the fields of **one** attestation. Placeholders must be replaced with genuine independent evidence; **this example does not pass the gate**.

  "commit": "<exact 40-character source commit>",

  "status": "passed",
  "gitTreeClean": true,
  "observedUTC": "<real UTC time no older than 14 days>",
  "clientId": "<own registered Microsoft public application UUID>",
  "externalApproval": {
    "provider": "Minecraft Services",

Additional checked proof fields are defined in executable verifier `scripts/ga/official_minecraft_0270.py`; use its strict schema rather than inferring that any `status: passed` label is sufficient. Each vault/signature/game report must include `schema`, `commit`, `productVersion`, `target`, `status: passed`, `simulated: false`, `mocked: false`, `actualExecution: true`, `observedUTC`. Game evidence must include `reviewedOriginalLogs: true`, `actualClientWorldEntry: true`, and the original subject hash; native signature evidence must include `productionKey: true`, a pinned `trustedSigner`, `artifactSha256`, and a platform signing type. `vault.json` must record each verified lifecycle check, no raw credentials. Rejection occurs on missing, stale, inconsistent, duplicated or altered evidence.

## 3. Sign with an authorized independent operator identity

Use a separate Ed25519 evidence key **provisioned outside this repository** (not the production installer-signing key). Store the private seed only in the protected signing environment; pin the 32-byte public key in the protected GitHub `NEVERLAUNCHER_OFFICIAL_GA_PUBLIC_KEY` environment variable. **Do not generate a new key merely to satisfy this gate.** The signer refuses overwrite, wrong key, mismatched commit and unverified attached evidence.

```sh
export NEVERLAUNCHER_OFFICIAL_GA_ED25519_SEED='<external protected seed, never commit>'
python3 scripts/ga/sign_official_minecraft_0270.py \
  --target-dir '/private/evidence/windows-amd64' \
  --public-key "$NEVERLAUNCHER_OFFICIAL_GA_PUBLIC_KEY" \
  --commit '<exact git SHA>'
unset NEVERLAUNCHER_OFFICIAL_GA_ED25519_SEED
```

Repeat with independent actual runs on all six targets. Evidence reports and signatures must be stored privately. A tool capable of signing operator assertions does not validate whether the operator is honest; restrict access to the signing key and peer-review all original external evidence.

Verify *all six* using only the pinned public key:

```sh
python3 scripts/ga/official_minecraft_0270.py \
  --attestations '/private/evidence' \
  --public-key "$NEVERLAUNCHER_OFFICIAL_GA_PUBLIC_KEY" \
  --commit '<exact git SHA>' --output '/private/official-ga-receipt.json'
```

## 4. Production release integration

- `.github/workflows/official-compatibility-02612.yml` tests the live POC implementation, native build on Windows/macOS/Linux and offline negative cases; **this is only preflight**.
- `.github/workflows/production-release-candidate.yml` requires `official_minecraft_ga_evidence_run_id`: six `official-minecraft-ga-0270-{target}` artifacts from a reviewed **protected operator run**. It independently verifies their Ed25519 signatures using the pinned public key before preparing a candidate.
- `scripts/release/build-release.sh` for `0.27.0` requires `NEVERLAUNCHER_OFFICIAL_GA_ATTESTATIONS_DIR`, `NEVERLAUNCHER_OFFICIAL_GA_PUBLIC_KEY`, an exact clean git commit, and successful six-target signature verification **before output cleanup/building**. Failure is terminal. Once the release build completes, `OFFICIAL_MINECRAFT_GA_CERTIFICATION.json` is included in the signed release directory and the normal `release sign` / `release verify` flow runs using configured, externally provisioned production keys.
- Before `release build` creates `RELEASE_MANIFEST.json` and `SHA256SUMS`, `scripts/ga/verify_official_artifacts_0270.py` hashes the **actual imported release archives** and requires equality with the independently attested `signedArtifactSha256` on all six targets: `neverlauncher-desktop-0.27.0-windows-{x64,arm64}.zip`, `neverlauncher-linux-{x64,arm64}-0.27.0.tar.gz`, and `neverlauncher-desktop-0.27.0-macos-{x64,arm64}.zip`. This prevents a successful test of one build from blessing a different shipping package. Attestation operators must therefore test and record the digests of these **same exact signed artifacts**, supplied by the approved production signing jobs, before sealing evidence.
- The official GA receipt is marked required in the CLI release manifest, included in signed `SHA256SUMS`, and checked again on release verification. Existing Windows Authenticode, macOS Developer ID/notarization, Linux manifest signing, signed `SHA256SUMS.sig`, `PROVENANCE.json.sig` and public delivery verification remain mandatory. The GA receipt does not substitute for those signatures.
- No unsigned fallback, fixture approval, empty receipt, missing platform, stale commit or skipped E2E can publish `0.27.0` as GA. Public release/public download E2E must be verified after publication and any failure triggers release rollback/withdrawal.

## 5. Upgrade / migration

1. Back up PostgreSQL and operator configuration. Apply the already-existing 0.26.8/0.26.11 migrations (`0075_official_never_identity_0268.sql`, `0076_official_provider_management_02611.sql`) if not applied. **No database migration is introduced in 0.27.0**; never rerun or rewrite applied migrations.
2. Deploy Backend/Admin 0.27.0 together before Desktop rollout. Confirm the registered Client ID and issuer policies match the native application. Never migrate Microsoft refresh tokens to Backend or renderer.
3. On first Desktop access, the existing `0.26.2` OS credential record is moved into the multi-account registry by Rust. The GA migration preserves a newer native account over an interrupted legacy copy and does **not** retire the recoverable old slot until the new slot is readable. If keyring access fails or the official UUID mismatches, the migration stops. No plaintext filesystem fallback.
4. Accounts using a legacy backend ticket remain legacy until the user signs in via the native Microsoft flow. Native re-login replaces that entry. It is not possible to extract or infer Microsoft's refresh token from an unrelated OIDC session or prove official identity by email/nickname alone.
5. Check account switching, restore, revoked refresh, Never linking/unlinking, textures, and `online-mode=true` join. Verify no token appears in command previews, logs, crash reports or renderer IPC. Never modify official authentication to bypass Mojang sessionserver.
6. If a rollout fails, stop publication and roll back signed binaries + matching Backend/Admin. Preserve OS keyring state. Do not replay tokens or silently downgrade official accounts into offline/Yggdrasil.
