# NeverLauncher 0.27.11 — Adapter Lifecycle & Compatibility

## Executable implementation

The existing `runtime client-factory build` command now records independent adapter
versions and implementation SHA-256 fingerprints directly in `install-plan.json`.
The fingerprint is derived from **source code embedded in the executing Go binary**
for each adapter (including shared materialization/recovery code), never from
untrusted files in the Minecraft client. Adapter IDs and versions are not coupled
to the end-user client profile or the NeverLauncher product version.

Tracked execution stages are `vanilla`, optionally one of `fabric`, `quilt`,
`forge`, `neoforge`, `sha256-verify`, and `atomic-publish`. Existing artifacts,
loader resolution locks and canonical output SHA-256 remain part of the plan
identity. Changes to adapter code or the separately managed adapter version
change the adapter pin and the full reproducibility SHA-256.

## Commands

```sh
# Inspect the binary's registered adapter versions and fingerprints:
neverlauncher runtime client-factory adapter-inspect

# Compare the recorded lock with the currently executing binary:
neverlauncher runtime client-factory adapter-inspect --client-dir ./client

# Strict verification of adapter identity, Java/target policy and all files:
neverlauncher runtime client-factory adapter-verify --client-dir ./client

# Normal replay. If an adapter has changed, this fails without modifications:
neverlauncher runtime client-factory build --client-dir ./client \
  --loader fabric --minecraft 1.21.1 --loader-version latest-stable

# *Explicit* re-materialization using the new adapters and original exact
# version, target, source and loader constraints:
neverlauncher runtime client-factory build --client-dir ./client \
  --loader fabric --minecraft 1.21.1 --loader-version latest-stable \
  --upgrade-adapters=true
```

You may need to supply the same `--version-manifest`, loader metadata endpoint,
installer path or processor Java options originally used for a nonstandard or
self-hosted build. The build verifies the previous locked outputs before staging
any updates. An upgrade continues to forbid a changed Minecraft version,
loader version, OS/arch target or SHA-256 of an already pinned source at the
same path. The operation runs real materialization and processor steps, scans
new outputs, verifies all files and atomically replaces the previous directory.
Failure retains the old directory. Result differences require separate runtime
certification (0.27.12) and follow existing publication gates.

## Backwards compatibility

Install plans made before 0.27.11 have **no** adapter pins. Their file integrity
can still be checked by legacy routines and their metadata inspected; the
application does not silently insert adapter IDs into their old hashes.
Strict `adapter-verify` and `client-factory verify`, in contrast, refuse to
certify such plans as current. To get new adapter evidence, perform an explicit
`--upgrade-adapters=true` materialization. A future binary with changed adapter
source code must use an explicit upgrade in the same way. An older adapter
implementation is not silently emulated by a new binary.

Modpack redistribution verification/export now requires current adapter pins.
MirrorHelper state-changing operations reject **versioned** but obsolete pins.
Legacy unversioned workspaces remain editable without implicitly claiming new
adapter identity; their publication check still refuses missing adapter pins.

## Target policy

Each target must pass the current OS/architecture parser. Classic Forge 1.7.10
and 1.12.2 require Java 8; Cleanroom/lwjgl3ify require separately certified
bridge recipes, not automatic Java 17 reclassification. Other compatibility
claims are left to upstream version/loader metadata and real runtime tests;
passing these static checks does **not** certify successful Minecraft launch.

`adapter-verify` proves local build integrity and adapter equivalence to the
running binary, **not** a real client/server E2E test or a redistribution grant.
The stronger runtime certification matrix remains scheduled for 0.27.12.

## Test coverage

```sh
cd cli
# Source-code fingerprints, old locks, explicit upgrade, source pinning:
go test ./cmd/neverlauncher -run 'TestAdapterLifecycle02711' -count=1
# Existing modern/legacy materializers and mutation regressions:
go test ./cmd/neverlauncher -run 'TestClientFactory0271|TestMirrorHelper0274|TestAuthlibClassloader0279|TestModernLoader0272' -count=1
go vet ./cmd/neverlauncher
```

CI also runs race tests and cross-platform Go builds. Real Minecraft GUI
launches are **not** claimed as completed by these tests.

## Release validation notes (2026-10-24)

Canonical product-version metadata for CLI, desktop, runtime, server bridge and
OpenAPI has been synchronized with `scripts/version/manage.py sync` and passes
`manage.py check`. Relevant Client Factory, loader, legacy, modpack and authlib
integration tests and targeted Race Detector checks pass; the CLI cross-builds
for Linux amd64, Windows amd64 and macOS arm64.

The **unfiltered** CLI suite still has inherited failures unrelated to the
adapter lifecycle feature: the Quilt `latest-stable` negative test expects an
outdated Russian error-message substring while the resolver correctly rejects
prerelease-only data, and `release doctor` rejects the existing Windows signing
workflow dependency chain. The affected resolver, test, signing checker and
workflow were byte-for-byte unchanged from the provided 0.27.10 archive.
Do not label an official signed production release as certified until those
baseline checks and full real Minecraft E2E are resolved.
