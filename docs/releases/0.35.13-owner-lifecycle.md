# NeverLauncher 0.35.13 — Owner Lifecycle, G/M scenario closure

## Рабочий сценарий владельца

1. В Admin откройте `Мастер релизов`; выберите проект и создайте/восстановите server-owned черновик. При необходимости сначала создайте проект и профиль в соответствующих разделах.
2. Подготовьте набор файлов через **Build Workspace** (реальное серверное хранилище, SHA-256, component graph). Создайте пакет, выполните `validate → sign → stage → integrity-check` и требуемое runtime evidence. Изменение компонента требует повторной проверки и подписи.
3. В разделе **Публикация и откат** прочтите *фактический* channel head, откройте Backend preview и подтвердите ожидаемый эффект. После подтверждения UI сохраняет intent с уникальным idempotency key в sessionStorage **до** отправки операции. Этот ключ привязан к текущим Backend, административной сессии и проекту; токены и секреты не сохраняются.
4. Backend через `POST /api/v1/operations/execute` принимает durable job. **HTTP 202 = принято, а не опубликовано.** UI опрашивает `GET /api/v1/operations/{id}` и `GET /api/v1/projects/{project}/profiles/{profile}/channels/{channel}/head`. Для publish проверяется ID опубликованного пакета и продвижение ревизии; для rollback — новый ID и **точное совпадение с `job.result.packageId`**.
5. Если сеть оборвалась после отправки, мастер блокирует создание нового publish/rollback и предлагает только явное восстановление **того же** request body и idempotency key. Backend сам обеспечит авторизацию, неизменность операции и replay существующего durable job. При расхождении с channel head не объявляйте выпуск завершённым: проверьте audit/job и параллельные операции.
6. Для `stable` отката Backend может вернуть `rollback-staged-runtime-validation-required`. **Это не переключение канала.** Мастер показывает фактический результат и предлагает открыть подготовленный rollback пакет: проверяет project/profile/channel и создаёт реальный server-owned черновик. Пройдите новую trusted runtime certification для этого пакета и опубликуйте его через тот же штатный pipeline.
7. После наблюдения дефекта воспользуйтесь переходами в **Диагностику**, **ServerBridge** и **Аудит**. Монитор durable job показывает состояние и доступные действия на стороне Backend; старый прямой publish в панели пакетов заменён переходом в мастер.

- Историческая матрица `compatibility/gravit/user-journeys-0351.json` остаётся неизменной: 54 сценария, actor/action/expected/negative/test refs и UX01–UX12. Ранее это блокировало аудит на всех версиях после 0.35.1.
- Улучшена повседневная реализация G07/G12/G32/G34/G35: server-owned черновики и пакеты, подпись, обязательные проверки, durable publish/rollback, audit/recovery/readback. Наличие реализации **не подтверждает** E2E каждого G/M пункта.
- `M17` по-прежнему **security-exclusion**: небезопасные операции с credentials/classloaders не реализуются. Native Windows/Linux/macOS, live Microsoft/Minecraft, защищённый ServerBridge join, миграция внешних Gravit инсталляций и production GA должны быть проверены независимо.

Для реальных Backend тестов требуется Go из `services/api/go.mod`, затем `go test ...` и `scripts/acceptance/run_owner_player_0351.sh` на **одноразовом локальном** Backend. Запрещено запускать этот mutation runner на production. CI `.github/workflows/owner-lifecycle-03513.yml` выполняет эти проверки, но наличие workflow не доказывает успешного прогона.

**Условие выпуска:** сертификация G/M и 0.36 GA не следует из локальных Node/HTTP-unit-тестов. Отдельно требуется end-to-end owner create → stage → real signed runtime validation → publish → observe fault → rollback с точной фиксацией channel-head изменения, реальная игровая установка/ServerBridge join и runtime targets.
