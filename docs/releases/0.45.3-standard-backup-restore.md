# NeverLauncher 0.45.3 — Standard: согласованный PostgreSQL + blobs + служебное состояние

## Область поддержки

**Реальный путь:** Standard (один Linux Docker Compose-хост): PostgreSQL 16 из `deploy/production/docker-compose.yml`, API, Admin, TLS Nginx, локальное Docker-хранилище, factory/backups и **SQLite coordinator**. Операция делает *холодный согласованный снимок с простоем*, а не online backup с непрерывной записью. Network/HA (Redis, S3, несколько API) — отдельный этап 0.45.4–0.45.6, не приписывать ему результат Standard.

Для безопасного снимка необходимо **остановить всех пишущих клиентов**. Инструмент останавливает API и публичные сервисы, сравнивает состояние контейнеров, проверяет отсутствие других клиентских сессий PostgreSQL и сравнивает WAL LSN до/после дампа PostgreSQL и архивации томов. Изменения WAL (в том числе autovacuum или сторонние записи) **блокируют снимок**; допускается повторить в более спокойное окно. Если сторонний процесс способен менять файловые тома напрямую, его необходимо отдельно остановить и оградить. Проверка двух LSN не защищает от произвольной записи в файлы из внешних контейнеров и не заменяет административное ограждение всех писателей.

**Секреты не входят в эту копию:** `.env`, TLS private key/chain, ключи подписи, секреты внешних auth-провайдеров, внешние SQL/file provider базы и Minecraft-миры за пределами Standard volumes. Храните их отдельно в защищённом хранилище секретов и восстанавливайте с исходными значениями при восстановлении того же проекта. Снимок PostgreSQL и архивы файлов содержат **чувствительные данные в открытом виде**, поэтому хранение, транспорт и offsite-копии должны быть зашифрованы вне данного инструмента. Нельзя сохранять снимок в публикуемой директории сайта, Git/CI artifact или в одном из резервируемых томов.

## 1. Подготовка источника

На работающем Linux-хосте версии **0.45.3**:

- Убедитесь, что действителен стандартный production Compose и `/ready` с `repository=postgres`, `storage=local`. Не применяйте Network-HA overlay.
- Держите проверенную копию `.env` (`0600`, без symlinks), TLS cert/key и внешних provider-конфигураций в одобренном secret manager. Не допускайте вращения этих ключей между backup и restore без отдельного migration/rotation процесса.
- Согласуйте окно простоя, остановите все **внешние** workers/записывающие интеграции, запретите дополнительные PostgreSQL соединения и прямую запись в Docker volumes.
- Убедитесь, что доступны Docker Compose v2, образы `postgres:16-alpine` и `alpine:3.20`, достаточно свободного дискового места для PostgreSQL custom dump и полных архивов томов.
- Подготовьте закрытый **внешний каталог** для снимков (не часть Compose volumes):

```bash
sudo install -d -m 0700 /srv/launcher-dr
cd /path/to/NeverLauncher
sudo python3 scripts/operations/dr_03512.py backup \
  --project launcher --confirm launcher \
  --env-file deploy/production/.env \
  --snapshot /srv/launcher-dr/standard-0453-20261101 \
  --production-source --maintenance-approved
```

Двойное подтверждение `--production-source --maintenance-approved` даёт право остановить сервисы; оно **не** подменяет фактическое разрешение на обслуживание. Команда сохраняет состояние до остановки: ранее неработающие сервисы автоматически не запускаются. Ранее работавшие сервисы запускаются обратно даже при ошибке резервирования. Если команда завершилась неуспешно, отклоните снимок и проверьте фактическое состояние исходного проекта, контейнеров и системы мониторинга.

### Что создаётся

Каталог снимка содержит:

| Артефакт | Реальный источник |
| --- | --- |
| `database.dump` | `pg_dump -Fc --no-owner --no-acl` реального PostgreSQL |
| `launcher_storage.tar.gz` | Local blobs (в том числе опубликованные игровые/texture-объекты) |
| `launcher_backups.tar.gz` | Служебные резервные файлы API |
| `launcher_factory.tar.gz` | Фабрика клиентов и подготовленные файлы |
| `launcher_coordinator.tar.gz` | SQLite WAL-координатор, lease/fencing и другие durable-состояния |
| `manifest.json` | Размеры, SHA-256 всех архивов, версия, исходный project name, исходное состояние сервисов, WAL LSN |

`manifest.json` версии schema=2 создаётся только после `pg_restore --list`, SHA-256 и **чтения настоящего SQLite coordinator**: `PRAGMA integrity_check`, `foreign_key_check`, `coord_meta.version=1`. Снимок публикуется после проверки данных. Сообщение об ошибке `PostgreSQL WAL advanced` означает, что согласованная точка не подтверждена: такой каталог не публикуется.

## 2. Проверить пакет перед переносом

```bash
sudo python3 scripts/operations/dr_03512.py verify \
  --snapshot /srv/launcher-dr/standard-0453-20261101
```

`verify` перечитывает все SHA-256, безопасные tar-члены, координатор SQLite и структуру PostgreSQL custom dump. Успех означает проверку архива, **не** гарантирует успешный login игрока, восстановление внешних секретов, производительность PostgreSQL или подлинность источника (SHA-256 manifest не подписан). Перенесите каталог снимка в шифрованном виде по защищённому каналу. Держите независимые offsite-копии с контролем доступа.

## 3. Восстановить на другом чистом Linux-хосте

1. Подготовьте хост Docker Engine + Compose v2 и точный исходный checkout **0.45.3**. Убедитесь в наличии или заранее соберите с **того же commit** `launcher-api:0.45.3`, `launcher-admin:0.45.3`. Проверьте исходные подписи/хеши поставляемых файлов по отдельной release-процедуре.
2. Перенесите `manifest.json`, `database.dump` и все четыре `launcher_*.tar.gz` в приватный каталог. **Не** создавайте заранее тома/контейнеры восстанавливаемого Compose project.
3. Восстановите **исходные значения** `.env` и все отдельные подписывающие/auth-ключи из secret manager. Укажите `LAUNCHER_IMAGE_TAG=0.45.3`; при необходимости адаптируйте только публичный адрес и TLS, с согласованным обновлением WebAuthn origins, CORS и DNS. Нельзя генерировать новые signing/auth keys для прежних клиентов, просто чтобы `preflight` прошёл.
4. Настройте публичный HTTPS hostname, который **фактически ведёт на новый узел**. Переключение DNS/VIP или отдельный проверенный тестовый endpoint выполняйте в заранее согласованное окно. Проверяйте внешний маршрут отдельно: общий DNS может всё ещё указывать на старый сервер.
5. Запустите восстановление:

```bash
cd /path/to/NeverLauncher
sudo python3 scripts/operations/dr_03512.py restore-fresh \
  --project launcher --confirm launcher \
  --env-file deploy/production/.env \
  --snapshot /srv/launcher-dr/standard-0453-20261101 \
  --ready-url https://launcher.example.org/ready \
  --production-target --maintenance-approved
```

Восстановление **не перезаписывает существующие Docker volumes или контейнеры**. На чистом другом хосте разрешён прежний project name `launcher`. На исходном рабочем хосте тот же project name уже занят, и восстановление будет заблокировано. Скрипт сначала сверяет manifest, версию целевого образа, структуру PostgreSQL dump и пустоту целевых ресурсов. Затем создаёт новые volumes, проверяет точные файлы после записи, запускает PostgreSQL, выполняет `pg_restore --clean --if-exists --single-transaction --exit-on-error` и только затем запускает API/Admin/Nginx.

Первичная проверка проводится через **`docker compose exec api wget http://127.0.0.1:8080/ready` в восстановленном контейнере**, чтобы нельзя было принять ответ старого хоста за работоспособность нового. Проверяются статус `ready`, версия, `repository=postgres`, `storage=local`. После этого проверяется публичный HTTPS `/ready` с обычной проверкой доверенного сертификата. При ошибке приложение останавливается: незавершённый целевой проект не следует использовать повторно как fresh; диагностируйте и начинайте восстановление заново на чистых ресурсах.

## 4. Проверки оператора после восстановления

```bash
curl --fail --show-error https://launcher.example.org/ready
# Должно быть status=ready, version=0.45.3, repository=postgres, storage=local.
```

Проверить в Admin вход старого администратора (без повторного bootstrap), наличие проектов, профилей, выпусков, blob-объектов, работу скачивания и реальный клиентский запрос. Сверить доступность расширений, factory-артефактов и сохранность служебных jobs. Состояния lease/queue могут потребовать штатного пересоздания/истечения: **не** допускайте одновременно к управлению старый и восстановленный сервер с теми же идентичностями и ключами. Отдельные Minecraft-миры и ServerBridge узлы резервируются собственным согласованным способом.

## 5. Настоящая интеграционная приёмка

На изолированном стенде с доступными Docker/PG, **двумя различными Compose projects или двумя хостами** используйте существующий `scripts/rc/operations_03514.py` — он реально выполняет `backup` → `verify` → `restore-fresh` → проверки `/ready` и изолированное выключение PostgreSQL/API. Исходные RC-переменные и URL должны вести к реальным API, а не мок-серверам. Для полноценной независимой приёмки вручную проверить ещё и вход/чтение файлов/воспроизведение реального выпуска на другом хосте, включая отрицательные сценарии.

Локальные `scripts/operations/test_standard_backup_0453.py` проверяют SQLite и tar реальными байтами, а работу Docker/PG оркестратора — контролируемым тестовым double. **Эти локальные тесты не доказывают реальный PostgreSQL restore или перенос между хостами.** Без успешного live-теста и сверки реальных данных функцию нельзя называть независимо сертифицированной в production.
