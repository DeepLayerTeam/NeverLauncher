# NeverLauncher 0.29.12 — Security & Real Auth E2E

## Runtime changes

1. `authrequest.Decode` limits login/refresh bodies to 16 KiB, rejects duplicate JSON keys (including case variants), nested collisions, unknown fields, non-object bodies and trailing payloads. These properties protect both `POST /api/v1/auth/login` and `POST /api/v1/admin/login` from ambiguous `providerId` / `password` interpretation; `POST /api/v1/auth/refresh` is also protected.
2. Signing failures after server-side session creation now revoke that specific session/refresh family, not leave active credentials stranded after the HTTP request fails.
3. Every successful refresh rotation checks the account's current `active` status and the authoritative `AfterAuth` protection policy again before minting the access token. Denials revoke the rotated session. This limits stale-role/ban windows; database 0.29.7/0.29.8 revocation constraints remain the authoritative cross-replica boundary.

## Executable tests

- `go test -race ./internal/authrequest` — safe to run without database drivers.
- `go test -race ./internal/httpapi -run '02912' -count=1` — launches a real loopback HTTP listener to exercise strict routing, issuer isolation, downstream Never-session creation, refresh replay and bans.
- `NEVERLAUNCHER_SECURITY_E2E_POSTGRES_DSN=postgres://... go test ./internal/httpapi -run TestSecurityRealAuthPostgresTwoReplicas02912 -count=1 -v` — requires a disposable PostgreSQL instance and the real pgx driver. Applies production migrations and launches two independent API instances, connected by PostgreSQL only. The test skips without this opt-in variable; the CI workflow supplies it.
- `.github/workflows/security-real-auth-e2e-02912.yml` — tests the actual PostgreSQL/MySQL/MariaDB engines, native API build, race detector, HTTP/OIDC/Microsoft connector test IdPs and migration catalogues. Existing Minecraft/ServerBridge end-to-end workflows remain separate and must be run for the complete game runtime release gate.

Do not run the PostgreSQL E2E against a production database. E2E fixtures contain synthetic identities, passwords and tokens only; database names and DSNs used in CI are integration-only. Production credentials must never be embedded in CI workflow files.
