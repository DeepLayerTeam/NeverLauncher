# NeverLauncher 0.45.6 — Chaos & Disaster Recovery

**Scope:** executable fault injection on an explicitly isolated Network-HA Docker lab; fresh-host restore acceptance. This is **not** a production failover certificate and does not assert a tested RPO/RTO until a real run emits a report.

## Required environment

- Linux host with Docker Engine, Docker Compose **2.24.4 or newer** (`!override` is used to remove public Nginx port bindings), AWS CLI v2, Python 3.12+, network connectivity to image registries. Use a dedicated `nl-dr-*` Compose project on an otherwise isolated host. No Minecraft player traffic or real users.
- Prepare production-compatible PostgreSQL, Redis and Go Backend/Worker images using 0.45.6. Maintain unique replica IDs. Run the one-shot database migration before creating the four API/worker processes (see `0.45.5-multi-node-ha.md`). Never attach the chaos override to a production Compose project.
- `.env` mode 0600 with `LAUNCHER_IMAGE_TAG=0.45.6`, all required backend/TLS secrets, `LAUNCHER_STORAGE_S3_BUCKET=nl-dr-chaos`, `LAUNCHER_STORAGE_S3_ACCESS_KEY` and `LAUNCHER_STORAGE_S3_SECRET_KEY` set to **test-only** credentials. Export matching `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` for AWS CLI. Never commit either secret.
- HTTPS listener on host `127.0.0.1:18443` with a CA-trusted certificate containing 127.0.0.1 as SAN; certificate verification **must not** be disabled. A private local CA trusted by the operator host is suitable. `--ready-url https://127.0.0.1:18443/ready` must return JSON `status: ready`, `repository: postgres`, `storage: s3` from actual Backend API.
- The additional `s3` service is a real MinIO S3-compatible store in a private persistent volume. It is exposed on **loopback only** (port 19000). Lab credentials and data must not overlap real storage. The runner checks Docker ownership of this port, the exact `nl-dr-*` bucket and credential equality before injecting faults.

## Launch the isolated lab

From the repository root:

```sh
cd deploy/production
export AWS_ACCESS_KEY_ID='your-isolated-lab-key'
export AWS_SECRET_ACCESS_KEY='your-isolated-lab-secret'
# File .env is local and chmod 600; secrets are not written to command arguments.
chmod 600 .env
# Refuse Compose versions without !override support; inspect final port mappings.
docker compose version
F='-p nl-dr-chaos --env-file .env --profile network-ha -f docker-compose.yml -f docker-compose.network-ha.yml -f docker-compose.chaos-0456.yml'
# Issue commands as explicit arguments instead of shell-evaluating untrusted env.
docker compose -p nl-dr-chaos --env-file .env --profile network-ha \
  -f docker-compose.yml -f docker-compose.network-ha.yml -f docker-compose.chaos-0456.yml \
  config --format json > /tmp/nl-dr-chaos-resolved.json
# Check that nginx has ONLY host 127.0.0.1:18443 and S3 ONLY 127.0.0.1:19000.
docker compose -p nl-dr-chaos --env-file .env --profile network-ha \
  -f docker-compose.yml -f docker-compose.network-ha.yml -f docker-compose.chaos-0456.yml \
  up -d postgres redis s3
# Create the isolated bucket before Backend starts, or /ready will correctly fail.
aws --endpoint-url http://127.0.0.1:19000 s3api create-bucket --bucket nl-dr-chaos
# One-shot migration and then actual API/workers. Do not launch multiple migrating writers.
docker compose -p nl-dr-chaos --env-file .env --profile network-ha \
  -f docker-compose.yml -f docker-compose.network-ha.yml -f docker-compose.chaos-0456.yml \
  run --rm --no-deps -e LAUNCHER_PROCESS_ROLE=migrate -e LAUNCHER_DATABASE_AUTO_MIGRATE=true api
docker compose -p nl-dr-chaos --env-file .env --profile network-ha \
  -f docker-compose.yml -f docker-compose.network-ha.yml -f docker-compose.chaos-0456.yml \
  up -d --build api api-b worker-a worker-b admin nginx
# If the bucket already exists, ensure it is the isolated lab bucket and EMPTY of real data.
```

The script's `s3` service must be configured as the **actual** `LAUNCHER_STORAGE_S3_ENDPOINT=http://s3:9000` for all four API/worker processes, not just for AWS CLI. Check resolved Compose environment (do not upload output containing secrets). If API readiness fails, stop; do not create a success record.

## Execute outages and measure canaries

```sh
python3 scripts/operations/chaos_0456.py \
  --project nl-dr-chaos --confirm nl-dr-chaos \
  --env-file deploy/production/.env \
  --ready-url https://127.0.0.1:18443/ready \
  --s3-endpoint http://127.0.0.1:19000 \
  --s3-bucket nl-dr-chaos \
  --report /var/tmp/nl-dr-chaos-0456.json
```

The runner writes a **committed PostgreSQL row**, then uploads and reads back **real S3 bytes**. It then injects, in order:

1. PostgreSQL `docker compose stop`, require fail-closed HTTPS `/ready`, restart, verify both acknowledged canaries.
2. Redis `stop`, require fail-closed readiness, restart, verify acknowledged canaries.
3. MinIO S3 `stop`, require a **failed real S3 object GET**, restart, verify stored bytes and public readiness.
4. Stop API `api`; verify `api-b` still answers directly and Nginx serves HTTPS `/ready`; restore `api`.
5. Disconnect the actual `worker-a` container from its expected Docker network, require worker readiness to fail while `worker-b` and public API remain healthy; reconnect and verify recovery.

All destructive actions are isolated to a project whose name starts with `nl-dr-`. A successful report is **only** written after every stage passes; stop/reconnect is attempted in `finally` blocks on failures. The database canary remains for later restore verification. The S3 canary is deleted at the end (or its exact residual key is printed if cleanup fails). Do **not** infer worker exactly-once job execution, leader/lease correctness, multi-host survival or Minecraft continuity from readiness alone; those require independent scenario checks.

**RTO in the chaos report** is the measured monotonic duration of each fault until validated recovery (or until the surviving node is confirmed ready for API failover). **Observed canary RPO=0** means only that acknowledged test rows and objects survived *these specific transient faults*. It does **not** mean production RPO=0, no player data loss, no loss of unacknowledged writes or a completed disaster restore. The evidence records UTC event bounds and measured durations, not invented benchmark data. A failed/incomplete run does not publish `status: passed`.

## Separate fresh-host disaster restore acceptance

Create a validated 0.45.6 Network-HA cold snapshot using `scripts/operations/dr_03512.py backup --network-ha` and the documented **stopped** world-backup inputs. Capture its `manifest.json`, `createdUtc`, full external secrets and keys through an independent secret manager, and known acknowledged checkpoint token/digest (if available). Move the snapshot to a **new Linux host**; source and target must not share stateful Docker volumes or S3 bucket. The target Compose image tag must match the snapshot version, **before** attempting a later upgrade. Capture the actual failure timestamp as UTC, not an assumed drill start.

Example (run from the root of **new** host checkout, with the matching TLS and external secrets):

```sh
python3 scripts/operations/restore_accept_0456.py \
  --project nl-dr-recovery --confirm nl-dr-recovery \
  --env-file deploy/production/.env \
  --snapshot /backups/snapshot-0456 \
  --ready-url https://recovery-host.example.org/ready \
  --target-s3-bucket nl-dr-recovery-objects \
  --s3-endpoint https://s3-recovery.example.org \
  --world-destination world1=/srv/minecraft/world1 \
  --incident-utc 2026-11-01T15:45:00Z \
  --checkpoint-token 0123456789abcdef0123456789abcdef \
  --checkpoint-sha256 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef \
  --report /var/tmp/nl-dr-restore-0456.json
```

Replace example arguments with real values. `--world-destination` is required for every world in the backup. `--checkpoint-*` are optional as a pair; do not pass sample values. The underlying DR runner verifies PostgreSQL dump, restores PostgreSQL and worlds, fences existing ServerBridge nodes/jobs, starts **fresh Redis without old leases**, restores S3 to a distinct empty bucket and byte-checks remote readback; it checks both APIs, both workers and the target public HTTPS readiness. The acceptance wrapper independently rechecks an acknowledged PostgreSQL checkpoint if provided and halts all externally reachable API/worker processes if this post-restore check fails.

The restore report includes:

- **Measured RTO**: from operator-supplied actual incident UTC timestamp to verified application recovery UTC (includes decision and operator delay). A separate monotonic duration measures just the restore procedure.
- **RPO exposure upper bound**: time from source snapshot's `createdUtc` to actual incident. This is a conservative **snapshot-age bound**, NOT a measurement of exact records lost. A newer acknowledged write could have been lost after the snapshot; to quantify actual data loss, compare a separate durable sequence/journal from before the incident to records restored on the new host.
- Actual check results for full PostgreSQL restore, world copies, S3 readback, Redis lease discard, ServerBridge fencing, both API replicas and workers, optional retained acknowledged canary.

**Acceptance gate:** require both reports from real isolated hosts, verify the exact source commit and container digests, perform a negative test of stale ServerBridge command/lease rejection and real durable job failover, and record Minecraft join/identity after operator re-enrollment. No local test suite or synthetic receipt substitutes for a real second operator and two-host recovery.
