# NeverLauncher 0.23.5 — Transactional Client Release (D05)

## Implemented in the executable path

`durable_downloads::perform` calls `transactional_release::install`, not the old direct-to-game-root scheduler. This stages the entire signed file set under `.neverlauncher/client-releases/work/<operation-hash>/files`, verifies SHA-256 and sizes, and only then enters the transaction. Desktop download, Repair, resumed durable jobs, and the NeverRuntime `sync` CLI all use the same path.

A cross-process exclusive `release.lock` serializes commit/recovery. While Minecraft is running, NeverRuntime/ProcessSupervisor retain a shared lock for the process lifetime; an update or rollback fails cleanly rather than replacing in-use JARs. Multiple launches may hold shared locks concurrently. The transaction first takes durable, hash-checked copies of every path it might touch under `client-releases/backups/<transaction-id>` and **only after these are synced** publishes a generation-numbered, alternating-slot `switch` journal. During the switch, paths from the signed **previous active release's installed ledger** which are not in the new signed release are retired. No directory traversal or cleanup of unknown files is performed. New paths can only come from the newly verified signed manifest. User-owned/generated paths and `.neverlauncher` are not modified.

After all files have switched, the installed set is rehashed, then the active release pointer is updated in alternating slots. A separate `last-known-good` journal is published and the switch journal is marked `complete`. Before creating a launch plan and before invoking Minecraft (including Tauri's launch command), NeverRuntime performs recovery. After a crash during switching, either a verified completed new set is accepted or all old bytes are restored from the durable backups, then the previous active pointer is reinstated. A crash while explicitly reverting continues the revert rather than accepting the new set. If backups are missing/modified or files are locked, recovery fails closed; the journal is retained to retry.

The previous release is signed and its installed ledger is checked on use. Rollback uses the latest successfully committed `last-known-good` journal even when a newer attempted switch was recovered and aborted. Rollback (`neverruntime rollback-release --root PATH --pinned-public-key KEY`, Tauri `rollback_client_release`) restores the immediately preceding set if the active set is unchanged. Desktop provides the rollback button. After rollback, load the previous signed manifest again before launch. Since this milestone does not yet change the server release generation, a rollback in this version is local only; signed release generation policy is addressed by D10.

## Compatibility and limitations

- Existing 0.23.4 installations without an active pointer are adopted on their first 0.23.5 install: only paths in the new signed manifest are backed up/replaced. No preexisting unregistered paths are deleted; explicit rollback returns those paths to their exact previous bytes.
- A separate already-damaged active release cannot guarantee a healthy previous image without a valid LKG. Switching to a **different** release in that state is rejected until recovery. Reinstalling the same signed manifest can repair it, but a crash may restore the already-damaged input because it was damaged before the transaction.
- Staging requires extra disk space for the new release and old managed files. Disk-space reservation and Windows file-lock UX are expanded in D06. Windows locked target switches fail closed and keep the recovery journal.
- This implementation does not create OS filesystem snapshots and does not pretend multi-file replacement is itself atomic. The guarantee is enforced by the durable journal and by recovery **before launch**. Other processes accessing the directory while a switch is in progress are not isolated. Only NeverLauncher-controlled launch paths are gated.
- The LKG backup is preserved until superseded; previous backups may occupy storage. Garbage collection of historic generations belongs in D06 and must never remove backups needed by an unfinished journal.

## Verification

Added `transactional_release` tests for a complete signed release switch, retirement of only previously registered files, untouched user files, explicit rollback, and simulated process death between file replacement and publication of the active pointer. Run on a machine with Rust toolchain:

```sh
cargo test --manifest-path runtime/neverruntime/Cargo.toml transactional_release -- --nocapture
cargo test --manifest-path runtime/neverruntime/Cargo.toml
cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml
npm ci --prefix apps/desktop
npm run build --prefix apps/desktop
```

Release gate: run fault-injection under Windows, Linux and macOS for power loss and locked files. These executions are **not** confirmed in the generation environment because Rust toolchain is not present. This source patch therefore must not be represented as a verified production binary.
