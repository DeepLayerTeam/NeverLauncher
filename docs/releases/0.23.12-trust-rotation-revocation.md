# 0.23.12 — Trust Rotation & Revocation (D11)

## Implemented execution paths

- **Prestarter/installer (Go)**: Ed25519 root-signed role policy, delegated `bootstrap` signer, `2.0` bootstrap envelope, versioned trust epochs, durable epoch watermark and cached root-signed policy outside the launcher tree. Installation/repair rejects replay/equivocation and revoked keys; installer keeps the policy with its signed bootstrap config. Offline provisioned policy works without contacting an arbitrary server.
- **Component updater (Go)**: the existing compatibility/protocol checks and independent `securityGeneration` remain. For a 0.23.12 component set, verification requires the root-signed `COMPONENT_TRUST_POLICY.json` and the delegated `COMPONENT_SET_SIGNATURE_V2.json`. The signature binds exact manifest bytes, `keyId`, epoch, policy SHA-256, manifest SHA-256 and signed time. The legacy `COMPONENT_SET_SIGNATURE.json` is retained only for a one-way upgrade by an older updater. Root and signing keys are separate and must be injected by a trusted builder. The accepted trust-policy epoch is stored outside managed component directories before activation.
- **NeverRuntime (Rust)**: game manifest `trustEpoch` is signed together with the existing `gameReleaseGeneration`; root-signed policy validates the current `game` role, rejects revocation, expiry and unauthorized keys. New installations require the current policy epoch and an `active` signer. Previously installed releases may still launch under a current policy while their signing key remains valid; `verify-only` is strictly time-bounded. Game policy watermark lives outside replaceable game content. Prestarter provisions the policy location and Desktop reloads it on subsequent starts.
- **API signing (Go)**: in production, signing and signature verification require the provisioned game trust policy and root key. New manifests inherit the current epoch and are signed only by its active game signer. Previously issued signatures are checked by the current policy, including revoke/verify-only checks.
- **Release Verification v2 (Go)**: `verify-only` release keys now have an explicit finite overlap (maximum 48 hours after retirement, optionally shorter via `verifyUntil`). Backdated signatures cannot extend that window.

## Root-signed policy format

`trust-policy.signed.json` (bootstrap) and `COMPONENT_TRUST_POLICY.json` (component bundles) use the same signed envelope:

```json
{"schemaVersion":"1.0","payload":"<base64 of raw JSON policy>","rootSignature":"<hex Ed25519 signature>"}
```

The root signs `NeverLauncher-Trust-Policy-v1\n` followed by the *exact* payload bytes. The payload includes `schemaVersion: 1.0`, `domain: neverlauncher.trust.v1`, strictly increasing `epoch`, canonical UTC `issuedAt` / `expiresAt`, and `keys` with `{id,role,publicKey,status,notBefore,verifyUntil?}`. Roles are `bootstrap`, `component`, `game`, `release`; statuses are `active`, `verify-only`, `revoked`. An epoch may be valid for at most 90 days. Keys in `verify-only` status must have a finite expiry and cannot authorize new content. Revoked keys cannot verify or authorize any update.

**This rotates delegated signing keys under an offline, pre-provisioned root. It does not implement migration of the root key itself.** A root compromise requires an externally authenticated trust-anchor replacement procedure; a downloaded URL cannot replace it.

## Trusted issuance

1. Keep the offline root seed outside the repository; provision its public half in native binaries / deployment config before building.
2. Write canonical UTC policy JSON for the next epoch; include retiring, active, and revoked role entries.
3. Run `NEVERLAUNCHER_TRUST_ROOT_ED25519_SEED=<hex-seed> python3 scripts/release/sign-trust-policy.py --payload policy.json --output trust-policy.signed.json --root-key-hex <pinned-public-root>`.
4. Sign bootstrap with `go run ./cmd/sign-config --payload bootstrap.json --private-key-file delegated-seed.txt --root-public-key <pinned-root> --trust-policy trust-policy.signed.json --key-id bootstrap-2026 --out bootstrap.signed.json` from `prestarter/`.
5. Build branded installers using `--trust-policy trust-policy.signed.json`. The package bundler verifies the root policy and delegated signature before output.
6. For 0.23.12 component sets, release CI must provide `NEVERLAUNCHER_COMPONENT_TRUST_ROOT_PUBLIC_KEY`, `NEVERLAUNCHER_COMPONENT_TRUST_POLICY_FILE`, `NEVERLAUNCHER_COMPONENT_DELEGATED_ED25519_SEED`, `NEVERLAUNCHER_COMPONENT_DELEGATED_KEY_ID`, and the existing v1 compatibility signer for upgrading from 0.23.11. New updaters embed the offline root through `main.componentSetRootKey02312`. Production signing fails without required keys.
7. For game publishing, provision `NEVERLAUNCHER_GAME_TRUST_ROOT_PUBLIC_KEY` and `NEVERLAUNCHER_GAME_TRUST_POLICY_FILE` in the API's trusted runtime. Prestarter's signed configuration must anchor `profilePublicKey` to the same pre-provisioned root.

Never include private signing keys, trust-root seed, or signing-service secrets in a bundle. A trust policy delivered inside a bundle is **data** until its offline root signature and epoch have passed verification.

## Security properties and scope

- Anti-rollback: an accepted higher trust epoch cannot be replaced with a lower epoch; different policies at the same epoch fail (equivocation). Game `gameReleaseGeneration` and component `securityGeneration` remain independent monotonic protections.
- Freeze: current policy expiry is checked against local wall-clock time; expired policy fails closed for new updates.
- Mix-and-match: delegated signatures bind policy epoch, signer identity and file digests to exact bytes; SHA-256 verified staging still applies to every component and game file.
- Revocation: current root-signed policy takes precedence over old signatures. Safe recovery restores only a compatible, still-trusted release. If a signer is revoked, a once-installed executable may be withheld from launch rather than silently downgraded to compromised content.
- Trust anchor: no trust-on-first-use, arbitrary URL acceptance, or trust-root change via mutable manifest fields.

This is a **project-specific Ed25519 role policy**, inspired by TUF rollback/freeze/mix-and-match defenses. It is **not TUF-compatible**: TUF root threshold migration, timestamp/snapshot metadata, consistent-snapshot repository semantics, and recovery from a compromised root are not implemented. See [TUF specification](https://theupdateframework.github.io/specification/latest/).

```bash
(cd prestarter && go test ./... && go vet ./...)

```

**Not certified:** Rust/Tauri compilation and Rust trust-policy tests, integration of real API+database dependencies, signed OS installers, hardware-backed root delivery, and clean-machine multi-OS power-loss tests. These are required before a production GA claim. Local trust watermarks resist network replay, not privileged local rollback of the entire application storage. Runtime and OS APIs cannot guarantee clock correctness under arbitrary clock rollback. No automatic root-key rotation is claimed.
