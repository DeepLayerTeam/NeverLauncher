# NeverLauncher 0.45.5 — Multi-node HA (API replicas + independent workers)

This release adds **running** API/worker process separation and an HA Compose
configuration. It does not claim that a single Docker host survives a host failure;
external PostgreSQL, Redis, S3, network, hypervisor and ingress HA remain operator
responsibilities. Do not label a one-host Compose stack multi-host certified.

## Before starting

1. Start from an existing, backed-up 0.45.4 installation. Complete the
   `0.45.4-network-ha-recovery.md` recovery procedure before enabling writes
   after an actual disaster. Use a valid TLS certificate and production secrets.
2. Ensure your **persistent** PostgreSQL, **fenced** Redis and **shared** S3
   endpoint are reachable to all processes. Use PostgreSQL as the authoritative
   repository and S3 for object contents. Keep an offsite backup of databases,
   objects, signing keys and configuration.
3. Use `deploy/production/env.production.example` as a starting point. Set
   `LAUNCHER_IMAGE_TAG=0.45.5`, TLS paths, public URL, PostgreSQL/Redis and
   S3 credentials, all existing signing and authentication variables.
4. Stop the old single-API stack before migration. Do not run an old API in
   parallel with the new split-role deployment.

## Deploy or upgrade

```sh
cd deploy/production
chmod 600 .env
# Database changes run once, with no HTTP listener or worker claims.
docker compose --profile network-ha \
  -f docker-compose.yml -f docker-compose.network-ha.yml \
  up -d postgres redis
# Run migrations only after verified backup and infrastructure readiness.
docker compose --profile network-ha \
  -f docker-compose.yml -f docker-compose.network-ha.yml \
  run --rm --no-deps -e LAUNCHER_PROCESS_ROLE=migrate \
  -e LAUNCHER_DATABASE_AUTO_MIGRATE=true api
# Four independent product processes + TLS ingress.
docker compose --profile network-ha \
  -f docker-compose.yml -f docker-compose.network-ha.yml \
  up -d --build api api-b worker-a worker-b admin nginx
```

`LAUNCHER_PROCESS_ROLE=api` binds public API, never starts the durable polling
loop or asynchronous extension dispatch. `worker` starts the *same actual API
binary* with SQL-backed publish, rollback and outbox workers (and extension
bus), but exposes only localhost `/health` and `/ready` probes. `migrate` runs
schema migrations and exits without a listener or any workers. The old default
`all` remains available for Standard; it is explicitly rejected in Network-HA.

In HA, `LAUNCHER_DATABASE_AUTO_MIGRATE=false` on all four long-running
processes. Apply migrations **once** using the one-shot role and check its exit
status before starting the pool. Every API and worker uses a unique, fixed
replica ID; sharing one ID across hosts is forbidden. Local working/cache volumes
are distinct per process, not a distributed source of truth.

## Verify actual operation

```sh
docker compose -f docker-compose.yml -f docker-compose.network-ha.yml \
  --profile network-ha ps
# Both API replicas: HTTP readiness, including PostgreSQL/Redis/S3 checks.
docker compose -f docker-compose.yml -f docker-compose.network-ha.yml \
  --profile network-ha exec -T api wget -qO- http://127.0.0.1:8080/ready
docker compose -f docker-compose.yml -f docker-compose.network-ha.yml \
  --profile network-ha exec -T api-b wget -qO- http://127.0.0.1:8080/ready
# Workers: 503 until a successful PostgreSQL poll and full dependency readiness; 200 afterwards.
docker compose -f docker-compose.yml -f docker-compose.network-ha.yml \
  --profile network-ha exec -T worker-a wget -qO- http://127.0.0.1:8080/ready
```

Record the start/recovery time, status of the four containers and an actual
published/rolled-back release. Publish must reach one final state and the
channel head must advance once. The database `durable_scope_leases` fencing
token and the job's own lease token must be checked by the real PostgreSQL
commit path. If PostgreSQL or Redis fails, relevant operations/readiness must
fail closed, not switch to memory. Use an idempotency key when retrying an
ambiguous client request.

## Controlled failover exercises

1. **API:** keep `api-b` healthy; stop `api` with Compose, then call the public
   HTTPS `/ready` and an authenticated read via Nginx. A successful, durable
   operation must still work through `api-b`. Restart `api`, then test the
   reverse direction. Existing long-lived ServerBridge connections may need to
   reconnect; they cannot be transparently migrated by Nginx.
2. **Workers:** enqueue a real durable operation, stop `worker-a`, confirm
   `worker-b` takes expired/unowned work and the database has exactly one
   committed channel change. Do not infer exactly-once external side effects
   from a single green healthcheck. Explicitly test stolen/stale fencing tokens
   against the repository.
3. **Dependencies:** interrupt PostgreSQL, Redis or S3 individually in a
   controlled environment; readiness or affected operations must fail closed.
   Restore dependencies and verify the backlog drains without duplicate
   externally visible changes.
4. Record logs and timestamps. Do not mark GA as passed if any target is
   unexecuted or if the host itself remains the only failure domain.

## Boundaries / recovery

Nginx uses two backend upstreams, dynamic Docker DNS (Nginx 1.28 stable (resolver introduced in 1.27.3)),
passive health/failover and bounded retries for safe operations. **Do not**
retry a potentially committed POST/PATCH blindly: check the idempotency key,
job and release state. Workers do not expose API routes and should never be
attached to the public load balancer.

Nginx returns `404` for legacy `/storage/` node-local files in HA. Packages
are served from the shared S3-backed `/api/v1/files/...` API; do not use local
storage URLs for new publications. Separate caches are not replicated between
processes; existing application paths requiring shared mutable local disks are
not HA-certified by this deployment.

Restoring Network-HA from 0.45.4 requires **discarding stale Redis leases**,
transactionally fencing stored Bridge commands, and re-registering nodes before
resuming. Do not revive a stale Redis AOF or copy existing coordinator volumes
as a shortcut. When upgrading an HA stack, prevent mixed-version writers and
preserve the previous signed release/backup until acceptance completes.

**Acceptance evidence:** Docker Compose resolved configuration, successful
binary build, health and failover exercises, independently verified lease/CAS
behavior, validated rollback/recovery and actual S3/PostgreSQL/Redis nodes.
Source-level tests alone are not an operational acceptance certificate.
