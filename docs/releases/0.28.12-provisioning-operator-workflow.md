# NeverLauncher 0.28.12 — Provisioning & Operator Workflow

This release extends the existing real `nl server-bridge install|upgrade|enroll|rollback` and the existing Host Supervisor. It does not introduce remote shell, claim a new ServerBridge v3 wire protocol, or certify actual Minecraft login E2E.

## 1. First-time setup

Install only a version-matched ServerBridge JAR accompanied by the complete certified release metadata in the same directory. Do not use untrusted or modified JARs for production; detection rejects unrecognized hybrid cores.

```sh
nl server-bridge detect --server-root /srv/minecraft
nl server-bridge install --server-root /srv/minecraft --artifact-dir /secure/release/bridge \
  --bridge-version 0.28.12 --backend https://launcher.example --server-id survival-1 \
  --project survival --profile survival
nl server-bridge host configure --server-root /srv/minecraft --platform paper --server-jar paper.jar
```

In Admin → ServerBridge → *Подключить узел*, a globally authorized `settings:manage` operator may paste **only** the generated `.neverlauncher/server-bridge/enrollment-request.json`. The UI confirms scope and fingerprint and POSTs only `id,name,kind,projectId,profileId,keyAlgorithm,publicKey` to the existing registration API. Private keys remain on the host. Backend enforces permissions and uniqueness. A project-only operator cannot enroll nodes.

Alternatively enroll from the CLI with a short-lived admin token (prefer `NEVERLAUNCHER_TOKEN` from a secret manager over command-line arguments):

```sh
nl server-bridge enroll --server-root /srv/minecraft --backend https://launcher.example
nl server-bridge host start --server-root /srv/minecraft
nl server-bridge verify --server-root /srv/minecraft --backend https://launcher.example
```

`verify` is a **real check**, not just reading `current.json`: it validates the installed JAR SHA-256 and jar shape, configured server/project/profile, local Ed25519 public identity and matching enrollment request, plus the Backend's matching node fingerprint, version, SHA-256, protocol v3, runtime identity, fresh signed heartbeat (≤90 s) and integrity status. It returns a nonzero exit code on discrepancies. `verify --offline` validates the local files only and explicitly reports `installed-unverified-runtime` rather than `healthy`; it needs no Backend credentials.

## 2. Controlled rollout with recovery

For installations managed by the existing **detached Host Supervisor** (not independently restarted by systemd), use:

```sh
NEVERLAUNCHER_TOKEN="$ADMIN_TOKEN" nl server-bridge rollout \
  --server-root /srv/minecraft --artifact-dir /secure/release/bridge \
  --bridge-version 0.28.12 --backend https://launcher.example \
  --health-timeout-seconds 120
```

This command resolves and verifies the release *before* downtime, verifies the configured Host and current managed identity, gracefully stops the JVM through the existing session-bound supervisor when running, waits for the old Host lock to be released, applies the **existing filesystem transaction** (JAR/config/identity), enrolls or matches the public key in Backend, starts the Host, and polls for a matching **new** runtime heartbeat observed after this activation. It checks Host/JVM identity as well as the Backend identity and JAR digest. Success requires a confirmed healthy runtime; installing a JAR alone is not sufficient. Failure attempts to stop the replacement JVM, rollback the previous filesystem transaction, and restore the prior running service state. Errors that cannot safely prove the old child stopped do not blindly rollback over a running process; they require manual reconciliation. Enrollment registration is remote and is **not** automatically reversed during local rollback.

**Important:** The rollout command currently uses detached Host `start/stop`, not `systemctl` or RemoteControl. For deployments supervised by systemd, stop the systemd service first, use `upgrade` (with the same certified release) followed by explicit `enroll` and `verify`, and manage the restart using the service manager. Do not run `rollout` concurrently with a systemd unit that can restart the Host; there is no mixed-manager safety guarantee. Never run this operation against an unknown manually started game process.

If automatic recovery is blocked, inspect `nl server-bridge host status`, the transaction ID from `current.json`, and `nl server-bridge status` before using manual `rollback --transaction <id>`. Rollback refuses a mismatched/incomplete transaction, forged change paths, arbitrary world paths or altered symlink targets. CLI mutations use an exclusive `.neverlauncher/server-bridge/operator.lock` and fail-closed when a previous crashed operation left the lock; a human must reconcile the previous state and remove the lock rather than the process silently stealing it.

## 3. Boundaries and certification

The Admin wizard *registers* a node using the public enrollment request and displays live runtime status; it does not silently install a Minecraft plugin on a remote host. Local installation, rollback and the Host process lifecycle occur through the CLI. The actual running Minecraft server, proxy, player joins and inventory restoration are **not** certified by local fixture tests. Production operators must validate these separately with their target Minecraft versions and actual systemd deployment. Backend health requires a real accessible Backend, admin token, and a live signed ServerBridge runtime; offline tests must never be reported as successful online certification.

Verification commands:

```sh
cd cli && go test ./cmd/neverlauncher -run 'TestBridge|TestServerBridge(Detect|Install|Upgrade|DryRun)' -count=1
cd cli && go vet ./cmd/neverlauncher
cd apps/admin && npm test
python3 scripts/version/manage.py check
```
