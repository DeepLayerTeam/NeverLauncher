# NeverLauncher 0.23.6 — Filesystem & Platform Hardening (D06)

## Executable path

`durable_downloads` → `transactional_release::install` → `download_scheduler` → verified staging → `transactional_release::commit` → `platform_fs`.
`transactional_release::recover` runs before the NeverRuntime launch lease and whenever a new release is installed. Rollback uses the same guarded live-file replacements.

Changes implement the following protections in **live install/rollback code** rather than manifest-only declarations:

- Signed manifest paths reject cross-platform device names (`CON`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9` including superscript digits), trailing dots/spaces, ADS colon, separators, control characters and Win32-invalid punctuation. File/directory alias and case collisions across the manifest are rejected on every publishing platform.
- The runtime checks each existing path component with `symlink_metadata` and rejects symlinks, Windows reparse points (including junctions), non-directory parents and symlinked switch/journal files. Before switch and recovery it scans each on-disk directory at most once per pass to reject case aliases. The execution root is canonicalized for recovery/launch locks.
- Preflight rejects nonregular destinations, read-only files and parent directories. OS ACLs and sharing rules remain authoritative: **the updater never grants additional permission, clears readonly or forces a running process to release a file**.
- Windows existing-file replacement uses `ReplaceFileW`, not unlink/rename-old/rename-new. A sharing violation leaves the old file present. Unix same-volume `rename` is atomic per file. This applies to managed-file switching, restoration and rotating metadata slots.
- Staging checks available disk capacity before copying/downloading, reserving room for up to six concurrent in-flight partial objects. Commit checks capacity for rollback copies and transient restore space before writing even the first backup. Checked arithmetic rejects overflow; reserve margin: 16 MiB. These checks **cannot prevent a different process filling the disk later**. On an in-flight ENOSPC error, the durable journal and synced backup are retained and recovery retries once space is restored.
- On-disk backup copies are flushed; failed copies are removed to avoid consuming recovery space. Staged files are flushed before the write-ahead journal; each switched Unix directory is fsynced, and Windows replaced files are flushed. The active pointer is published last after complete digest verification.
- A new managed path cannot silently overwrite an unrelated preexisting file. A matching SHA-256 is allowed as an explicitly identical object. Changed untracked files require manual resolution/import rather than silent overwrite.

## Recovery policy

The file set is not an atomic filesystem snapshot. All file changes remain behind the transaction journal and shared launch lease: if interruption occurs between two managed-file replacements, recovery runs before NeverLauncher permits the next launch. If Windows sharing denial, ACL errors, or low disk space prevent recovery, the launch is refused; the old backups and journal remain available. Do not delete `.neverlauncher/client-releases` to “fix” a failed transaction.

Physical power-loss guarantees are subject to filesystem, controller and write-cache durability. macOS and Windows directory-entry flush/barrier semantics are not identical to POSIX fsync; real power-cut and forced-stop E2E are mandatory before declaring GA.

## Changes in first-install behavior

Legacy 0.23.4/0.23.5 installs **without a registered active-release pointer** whose untracked file bytes differ from the newly signed manifest are no longer overwritten automatically. This intentional fail-closed change protects player mods. The operator should migrate/import ownership explicitly or remove the conflicting unmanaged file manually after backing up user data.

## Negative test coverage and commands

```bash
cargo test --manifest-path runtime/neverruntime/Cargo.toml --lib file_ownership::tests -- --nocapture
cargo test --manifest-path runtime/neverruntime/Cargo.toml --lib platform_fs::tests -- --nocapture
cargo test --manifest-path runtime/neverruntime/Cargo.toml --lib transactional_release::tests -- --nocapture
cargo test --manifest-path runtime/neverruntime/Cargo.toml
cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml
```

Linux/macOS unit tests cover read-only managed files and directories, parent-file and symlink traversal, names/case collisions, untracked player content, disk-budget rejection before network/switch, recovery of an interrupted two-file switch and previous rollback scenarios. Windows unit tests open a live target with **share_mode(0)** to verify `ReplaceFileW` refuses it without removing the old bytes. Existing Tauri, guard and CLI tests remain part of the full CI.

Manual/privileged E2E still required on release candidates:

1. Windows x64/ARM64: hold a JAR/EXE open without `FILE_SHARE_DELETE`, start client upgrade, terminate/restart Desktop, release the handle and verify recovery and SHA-256 of the whole active release.
2. Windows: create junctions/reparse points into external user data, deny ACL file delete/write and validate no external changes (run on both NTFS and a supported external volume).
3. Linux/macOS: inject ENOSPC on an isolated test volume during staging, backup, switch journal, and restore; free space, restart Desktop and validate complete old or new installation.
4. Force-kill/power-cycle at each barrier: after backing up first file, writing switch journal, switching Nth file, publishing pointer and writing last-known-good. Verify that launch never sees a mixed release and user saves/config remain identical.
5. Publish manifests containing invalid reserved names, mixed case aliases, and file/directory conflicts; reject before filesystem mutations.

These test scenarios are provided in Rust unit tests where practical; **actual power-cut, NTFS junction/ACL matrices and filesystem ENOSPC on a full disk have not been executed in this development environment**. Do not interpret static code checks as release certification.
