# NeverLauncher 0.30.4 — Java Extension Host

**Release deliverable:** an executable Java 17+ JVM host with authenticated bidirectional RPC, Go-side lifecycle readiness, supervised process and resilience to noncooperative callbacks. This is implemented runtime code, not an API-only milestone.

## Runnable deployment path

1. Build a fat JAR containing `ru.neverlauncher.sdk.host.JavaExtensionHost` (Main-Class), NeverLauncher SDK classes, and `NeverLauncher-Extension-Class` pointing to the Java extension implementation.
2. Set manifest 2.0 `backend` target entrypoint to the JAR, e.g. `backend/java-host.jar` (optional `cli` target can reference the same JAR). Package and sign it with the existing Ed25519 NeverExtensions CLI and install through the existing trusted registry/manager. A mere unsigned JAR is not installable by this mechanism.
3. The existing Go `extensionhost.Supervisor` verifies target path and JAR structure, selects a trusted Java executable, enforces heap sizing, launches `java -jar` directly (no wrapper or shell), and provides sanitized identity/credentials only through environment variables.
4. JVM bootstraps by fetching the installed manifest from the Go host with the per-process bearer token (`GET /v1/manifest`). It validates its extension identity and API version before `POST /v1/hello`, starts lifecycle and callback server, then acknowledges `POST /v1/ready` **only after** successful `start()`. Go's `StartInstallation()` waits for readiness before returning.
5. JVM→Go operations use the same permission-checked capability broker, event subscriptions and durable storage provided in 0.30.3. Go→JVM uses `POST /v1/rpc` on an authenticated loopback callback endpoint with fixed method allowlist, version/request identity, bounded JSON and deadlines.
6. Go periodically probes Java RPC responsiveness **asynchronously**, so a blocked JVM cannot hold the Go supervisor's heartbeat/resource monitor. After three failed probes the JVM is terminated via existing process-tree kill/restart/crash-loop logic. Java callback pools/queues are bounded and reply 503/504 when saturated or timed out.

## Test evidence

- Local Java 21 build: 42 Core and 29 runtime API checks passed.
- Local end-to-end: real Java JAR backend and CLI with hello/ready/health/command, bad-token rejection, protocol mismatch and timeout handling passed.
- Legacy Java lifecycle and runtime subprocess E2E passed.
- Existing CLI `extension pack`, Ed25519 signing and verify are tested in CI.
- The real Go supervisor→JVM integration and hung-callback process termination tests are in `java_host_0304_test.go`, executed by `.github/workflows/java-extension-host-0304.yml`. They were **not locally executed** where Go's `github.com/jackc/pgx/v5` dependency could not be fetched. Do not report them as passed until CI completes.

## Boundaries

- Java 17+ must be installed on the backend. `Config.JavaExecutable` can pin an administrator-managed absolute JVM path. The Java host runs as a separate OS process, **not** a Java bytecode sandbox. It inherits service-account filesystem/network access unless an operating-system sandbox/container is configured.
- Normalized local broker RPC is the only platform access interface; direct internal Go, Rust, or LaunchServer/JavaFX API access is not promised. Trusted in-process Minecraft hooks are deliberately outside this release (0.30.6).
- The sample's `hang` command is for supervisor fault injection only; do not deploy that demonstration extension in production.
- Real multi-OS CI and Go race integration remain release gates. Host protocol 1.0 and NeverExtensions manifest 2.0 remain compatible with existing native/legacy extensions.
