# NeverLauncher 0.35.11 — Real performance measurements

This version provides an executable real-process performance tool, not a table of projected results. Each native measurement starts the **compiled** NeverRuntime/Tauri executable and records its SHA-256, wall time, CPU time and resident memory. Data is synthetic and explicitly identified as a certification fixture; it does not demonstrate performance on a production Minecraft modpack.

## Build and run

Build the actual NeverRuntime CLI and certification signer (never a production key):

```bash
cargo build --release --manifest-path runtime/neverruntime/Cargo.toml --bin neverruntime --example cert_sign_fixture
python -m pip install psutil==7.2.2
```

For the real **10,000-file SHA-256** check and **1 GiB / 10 GiB** localhost HTTP Range transfers, use a machine with sufficient free disk space and time. `--confirm-large` is mandatory. Three fresh-cache attempts are performed for each size, each followed by a genuine cached update of the same signed release. Each installed payload is independently rehashed in Python before results can be reported as measured. Large installed files and native caches are removed after each attempt.

```bash
python scripts/performance/benchmark_03511.py \
  --runtime runtime/neverruntime/target/release/neverruntime \
  --signer runtime/neverruntime/target/release/examples/cert_sign_fixture \
  --verify-files 10000 --download-mib 1024 10240 --confirm-large \
  --repetitions 3 --output /var/tmp/neverlauncher-03511-runtime.json
```

For a short **real executable smoke test**, use `--download-mib 32 64`; this **does not** meet the 1/10 GiB milestone. Three actual native measurements still run, but on smaller transferred payloads. The release workflow runs smoke with 10,000 real file checks on Windows/Linux/macOS. It does not claim to execute 10 GiB on small hosted runners.

For Desktop, compile the release frontend and native executable (native WebKitGTK, Windows WebView2 or macOS WebKit must exist), then run:

```bash
python scripts/performance/benchmark_03511.py \
  --desktop apps/desktop/src-tauri/target/release/neverlauncher-desktop \
  --repetitions 3 --download-mib --output /var/tmp/neverlauncher-03511-desktop.json
```

Desktop records the time from process spawn until React has completed two animation frames and the privileged native command has atomically written a timestamp to the unique test marker. Outside an explicit `NEVERLAUNCHER_BENCH_READY_FILE` process environment the command does nothing. The first run is **process-cold only**: this benchmark does not evict OS page cache or imply a cold OS boot. Subsequent process starts are the warm condition. Each process is terminated after its first render, with isolated app cache home but normal OS page cache.

To measure **HTTP latency** on an actual running local Backend (optionally including its process-tree CPU and RAM), use a read-only GET endpoint:

```bash
python scripts/performance/benchmark_03511.py \
  --api-url http://127.0.0.1:8080/api/v1/status --api-pid 12345 \
  --api-requests 100 --api-workers 8 --repetitions 3 \
  --download-mib --output /var/tmp/neverlauncher-03511-api.json
```

Supply a real Backend PID instead of `12345`. For an authorization-required read-only endpoint supply the token via `NEVERLAUNCHER_BENCH_AUTH_TOKEN` in the process environment, never in a URL. Non-loopback endpoints are refused unless the operator explicitly sets `NEVERLAUNCHER_BENCH_ALLOW_REMOTE=YES` and owns the target. Results only characterize the selected API endpoint and its current database/environment, **not all Admin UI interactions**. For a representative Admin latency experiment, run the tool separately against each relevant authenticated GET endpoint, with representative production-like PostgreSQL data.

## Output and release interpretation

The JSON records `status`, measured raw runs, p50/p95/p99, process-tree CPU time, peak RSS, transferred HTTP body bytes, fixture details, OS/CPU and exact executable hashes. Git commit and clean status are included if available. `status: measured` indicates only that all **requested** scenarios succeeded; omitted scenarios must not be inferred as passed. Errors produce `status: incomplete` with a nonzero exit code, not placeholder numbers. Never claim the entire UX09 suite is passed until cold/warm Desktop, real 10k verification, both 1/10 GiB runs and representative Admin latency are all documented with matching hashes and workstation conditions.

Network throughput here is **local loopback**, not Internet/CDN capacity. Repeat measurements on the actual network/mirror/storage topology before promising download speeds to players. Neither GravitLauncher nor any other launcher is used as a benchmark baseline. OS power state, filesystem caches, antivirus, container limits and temperature must be recorded by the operator when making comparative claims.

## Platform limitations

CI compiles real Rust binaries and performs a genuine 10,000-file / 32+64 MiB smoke workload. Linux Desktop startup is attempted under Xvfb. Real 1/10 GiB acceptance requires an explicitly provisioned test stand with sufficient disk capacity; Linux, Windows and macOS packaged-first-launch measurements remain necessary for final GA. CI configuration is not proof of a successful CI run.
