# NeverLauncher 0.32.3 — SQLite Authentication & Revocation (DEP01)

## Implemented

- **Transactional SQLite local login** using the established `localpassword.Verify` (Argon2id and existing verified migrations), persisted sessions with `auth_epoch`, opaque 256-bit access/refresh bearer secrets stored only by SHA-256 digest.
- **Replay-safe refresh rotation**: atomic `BEGIN IMMEDIATE` token consumption, new refresh + access token issued together; replay compromises family, revokes parent Never session, access tokens and dependent Minecraft tokens *in a committed transaction*.
- **Immediate revocation on reads**: every Never/Minecraft bearer validation checks the actual SQLite users/auth sessions/tokens and current `auth_epoch`. User disabled/password/role changes from 0.32.2 invalidate already issued credentials.
- **MFA**: RFC6238 TOTP (SHA1/30 s/6 digits, ±1 step, durable last-step replay fence), AES-256-GCM at-rest secret protected by **separate 32-byte operator key**, eight random 80-bit one-use recovery codes stored by SHA-256, password + factor required for MFA removal, mandatory revocation of sessions on enrollment/removal.
- **Minecraft identities**: stable UUID independent of login email, case-insensitive unique username and fixed issuer/realm/subject provenance; issue and validate hashed Minecraft session token tied to active Never session; revocation can be direct or cascaded.
- **Real local CLI** for operational lifecycle, strict private JSON input and private key file; Go tests of restart, MFA/recovery, replay race, UUID immutability, generation invalidation, upgrade from v322 and SQLite integrity.
- Atomic schema upgrade **322 → 323** preserves existing project/profile/release/user/role/audit data. Requires SQLite core exclusive owner lock and working WAL from DEP00.

## Operator usage (Linux local certified ext4/XFS/Btrfs only)

Prepare a non-shared service-owned directory with mode `0700`. Generate 32 random key bytes once with `openssl rand -out /secure/path/mfa.key 32` and restrict mode `0600`. Back up the key separately from the SQLite database. Losing the key makes existing enrolled TOTP unavailable. Do not pass bearer tokens, passwords or the key through command-line flags or environment variables.

```sh
neverlauncher-sqlite core-init --db /secure/path/never.sqlite
neverlauncher-sqlite auth-hash-password --input /secure/path/password.json
neverlauncher-sqlite core-put --db /secure/path/never.sqlite --kind user --actor bootstrap --input /secure/path/user.json
neverlauncher-sqlite auth-login --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/login.json
neverlauncher-sqlite auth-rotate --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/refresh.json
neverlauncher-sqlite auth-check --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/access.json
neverlauncher-sqlite auth-revoke --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/revoke.json
neverlauncher-sqlite auth-mfa-start --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/user-password.json
neverlauncher-sqlite auth-mfa-confirm --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/mfa-confirm.json
neverlauncher-sqlite auth-mfa-disable --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/mfa-disable.json
neverlauncher-sqlite auth-minecraft-bind --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/minecraft-identity.json
neverlauncher-sqlite auth-minecraft-issue --db /secure/path/never.sqlite --key-file /secure/path/mfa.key --input /secure/path/minecraft-issue.json
```

All `--input` JSON files must be regular files with mode `0600` and no unknown fields. The very first core user must be an active owner; `auth-hash-password` returns a `$argon2id$` hash for `core-put --kind user`'s `passwordHash` attribute. CLI use presumes a trusted machine/operator with database filesystem access. The CLI intentionally does not expose an unauthenticated network listener.

For key rotation, existing TOTP enrollments must be explicitly migrated with re-encryption; merely replacing `mfa.key` will cause authentication to fail closed. A 322 database is upgraded by `core-init` or the SQLite auth CLI. `core-status` never modifies schema and refuses an older schema until upgraded.

## Scope and certification limits

SQLite Authentication Core is **functional data-access and local operational code**, not a fully enabled Single-node HTTP API. The existing HTTP Server still uses the PostgreSQL authentication coordinator and other state machines; **do not select SQLite as the production HTTP repository**. There is no Redis-free coordinator or SQLite join-ticket/replay-nonce implementation in 0.32.3; DEP01 remaining components and DEP02–DEP10 remain required. No false success or memory fallback is introduced. Token formats from this SQLite core are local opaque tokens and are **not interchangeable with PostgreSQL HTTP JWTs**.

In the generation environment, Go 1.27.3 and the pinned `modernc.org/sqlite` module are unavailable, and overlayfs is intentionally rejected. Isolated compilation with temporary local substitutes and SQLite SQL schema checks are not real integration certification. CI must run full real driver + supported local FS + race and restart tests before considering this code production-certified.
