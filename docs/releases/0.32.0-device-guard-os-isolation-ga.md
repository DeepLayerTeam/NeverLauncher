# NeverLauncher 0.32.0 — Device/Guard Trust & OS Isolation GA

## Release scope and actual status

The versioned source contains executable device-key certification, TPM Quote/PCR policy verification, Guard runtime/session policy, signed NeverExtensions permissions, scoped filesystem/network/secrets brokers and kernel-supported Linux/Windows extension isolation accumulated over the 0.31.x development cycle.

**Do not label the 0.32.0 binary security-certified until the signed, exact-commit GA gate returns PASS.** A green offline unit-test run is not remotely verified device provenance, proof of untampered JVM memory, physical PCR attestation, or evidence of OS sandbox containment. This file is shipped with source and is not itself certification evidence.

### Release-specific runtime hardening

- **Windows:** `CreateProcessW` with AppContainer attributes and `CREATE_SUSPENDED` now also sets `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. The child receives explicitly duplicated standard streams only. Arbitrary inherited Win32 handles (including backend service files, sockets or privileged objects) are no longer implicitly allowed. Failure to configure the allowlist fails the launch before resume. A Job Object is applied to the suspended process and AppContainer token SID is checked before resume.
- **Linux:** creation of an isolated child requires a fresh delegated cgroup v2, real `cgroup.kill` availability **and an actual successful write into the empty new cgroup** before any extension starts. Without this, the process tree cannot be reliably terminated after moving to another process group and the launch is rejected. The local socketpair HTTP listener also has race-safe shutdown.
- **macOS:** an appropriately signed App Sandbox helper exists in the codebase, but a hard aggregate descendant resource boundary has not been demonstrated. The runtime still denies `isolated` and does **not** silently run the package as `trusted`.
- **Guard:** TPM proof of key provenance, PCR evidence and Guard runtime evidence remain separate assurance dimensions. Guard runtime trust is tied to current server policy, session/device/epoch, signed artifacts and server-side join rules; user-mode evidence is not anti-cheat proof against privileged OS interference.

### GA security evidence

The GA verification tool is **executable** and uses Ed25519 detached signatures, cryptographic verification of the **exact** report bytes, a release-specific domain separator, exact Git commit SHA, a full tracked-source SHA-256 fingerprint, expiry, strict test name checks and independent per-platform host metadata.

Exactly seven valid, approved reports are required:

| Tier | What must be tested |
|---|---|
| `offline` | Actual Go cryptographic/adversarial, policy, broker, Linux shutdown and host budget tests with race detector |
| `backend-security` | Actual Guard Runtime/ServerBridge HTTP/session/revocation tests against normal Backend dependencies |
| `linux-live` | Namespaces, mounts, seccomp, no_new_privs, inaccessible secrets/network, cgroup.kill and process-group-escaping descendants on unprivileged delegated host |
| `windows-live` | Actual AppContainer identity, package ACL, named IPC broker, network refusal and Job process-tree limits |
| `macos-live` | Signed helper checks and explicit, user-visible **denial** of an unsupported isolation boundary; no implicit trusted fallback |
| `hardware-live` | Physical Windows/Linux TPM Certify, real PCR Quote and policy, key/nonce/epoch replay, root revoke, Guard attach and session rejection |
| `compatibility-live` | Normal overlays, accessibility, antivirus/EDR and development/debugging tools, with results and known limits |

Any absent report, failed named test, `SKIP`, unsigned/modified evidence, incorrect platform, wrong commit, revoked/stale attestation or mismatched source fingerprint yields **BLOCKED**. Hardware/compatibility/macOS reports must describe individual actual procedures and carry external audit-log SHA-256 hashes. Test CI does not self-sign its output. A separate authorized approver operates a private Ed25519 key on a controlled machine; `sign_evidence_0320.py` does not generate keys or silently sign incomplete evidence.

**Important trust boundary:** a cryptographically signed report attests to the human/test-runner signer's assertions; the gate cannot independently observe a physical TPM, external applications or remote test host. Security release approval requires evidence review, isolated signing-key custody, provenance from trusted CI and dedicated physical test hosts.

### Commands

```bash
# Normal code/build validation (CI can install locked dependencies):
python3 scripts/version/manage.py check
python3 -m unittest discover -s scripts/security -p 'test_ga_verify_0320.py' -v
python3 scripts/security/certify_0320.py --tier offline --commit "$GIT_SHA" --output /tmp/offline-0320.json
python3 scripts/security/certify_0320.py --tier backend-security --commit "$GIT_SHA" --output /tmp/backend-0320.json
# Run these *only* on dedicated live hosts:
python3 scripts/security/certify_0320.py --tier linux-live --commit "$GIT_SHA" --output /tmp/linux-0320.json
python scripts/security/certify_0320.py --tier windows-live --commit "$GIT_SHA" --output windows-0320.json

# After external evidence review, an authorized approver signs each of seven
# independently produced PASS reports (key outside repository/CI):
python3 scripts/security/sign_evidence_0320.py --evidence /secure/linux-0320.json \
  --private-key-file /secure/security-ga-signing-key.pem \
  --commit "$GIT_SHA" --source-sha256 "$SOURCE_SHA256"

# Actual production release gate:
python3 scripts/security/ga_verify_0320.py --evidence /secure/{offline,backend,linux,windows,macos,hardware,compatibility}-0320.json \
  --trusted-public-key "$TRUSTED_GA_PUBLIC_KEY" --commit "$GIT_SHA" \
  --source-sha256 "$SOURCE_SHA256" --output /secure/ga-0320-verdict.json
```

`SOURCE_SHA256` is emitted by `certify_0320.py`. Signing requires Python `cryptography>=43,<47` and a 0600-protected PKCS#8 Ed25519 key. The checked-out Git commit must be clean to generate authenticated release evidence. Do not place raw secrets, AK private keys or personal data in reports.

### Known blockers before certifiable production rollout

- Real Linux and Windows sandbox adversarial tests are required on appropriately configured hosts.
- macOS `isolated` remains explicitly **unsupported**, not a production-tested sandbox; only non-isolated/trusted packages may run subject to the project's existing policy.
- Physical TPM/AK provisioning and root chain certification cannot be simulated.
- Attach/injection limits in user mode and compatibility of accessibility, EDR and overlays must be documented per supported configuration.
- Full Go API, Desktop/Tauri, platform installer, database migration and end-to-end ServerBridge builds must pass on normal dependency-enabled CI.

The GA gate is intentionally **BLOCKED** in environments that do not meet these conditions. Do not treat generated source archives or metadata synchronization as deployment approval.
