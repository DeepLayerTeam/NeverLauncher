# NeverLauncher 0.45.7 — безопасное обновление SQLite/PostgreSQL

Этап 0.45.7 вводит **исполняемый** контроллер миграции: он останавливает
записывающие процессы, делает полную резервную копию, вызывает миграцию **нового
backend**, проверяет состояние базы и запуск приложения. При ошибке восстанавливает
данные прежней версии из подтверждённого снимка и повторно проверяет backend.
Контроллер не создаёт собственную схему и не редактирует существующие SQL-миграции.

## Подготовка (обязательно)

- Используйте отдельный тестовый клон для первой репетиции. Запланируйте окно
  обслуживания; резервные копии должны храниться вне обновляемых каталогов и
  Docker volumes. Проверьте права и доступное место для *полного* снимка.
- Для SQLite старый backend должен работать под отдельным пользователем `launcher`,
  корень minimal-установки и его родитель должны принадлежать этому пользователю
  (0700). Корень должен соответствовать `minimal-install.py` и
  `minimal_backup.py`; внешний SQLite по произвольным путям не поддерживается.
- Для PostgreSQL источником является действующий **Standard Compose** (не
  Network-HA). Нужны **два** сохранённых env-файла: версия источника (например,
  0.45.6), версия назначения 0.45.7 с теми же БД, секретами и томами.
  В целевом файле обязательно `LAUNCHER_DATABASE_AUTO_MIGRATE=false`, чтобы
  обновлённые реплики не запускали скрытые DDL в последующих обновлениях.
- Предварительно сохраните вне хоста операторские секреты/ключи и сертификаты:
  Standard DR не экспортирует секреты и TLS. Проверяйте backup-права и KMS отдельно.
- Снимок логически согласован только при остановке всех writers. Внешние
  подключения к PostgreSQL, сторонние job consumers и S3-записи должны быть
  заблокированы вне Compose на всём протяжении окна. Старые подключённые
  клиенты не должны принимать новые операции во время обновления.

## Minimal SQLite / systemd

Требуются root (`systemctl`, `systemd-run`, `runuser`), права владельца каталога,
новый доверенный backend и отдельно созданный приватный каталог для backup.
Параметр `--binary` должен указывать на неизменяемый бинарник **0.45.7**, в то
время как `launcher.service` сохраняет **старый** ExecStart до завершения
миграции. Скрипт создаёт отдельный постоянный systemd drop-in, который
переключает ExecStart на 0.45.7 перед запуском службы; при ошибке удаляет
его и восстанавливает исходную конфигурацию. Это конкретное переключение
backend необходимо для проверки версии и не заменяет общий компонентный
updater, запланированный на 0.45.8.

```bash
sudo python3 scripts/operations/db_upgrade_0457.py sqlite \
  --root /srv/launcher/minimal \
  --env /srv/launcher/minimal/config/backend.env \
  --binary /opt/launcher/releases/0.45.7/bin/launcher-api \
  --backup /srv/launcher/offhost-backups/sqlite-upgrade-0457 \
  --service launcher.service --service-user launcher \
  --expect-schema 327 --ready-url http://127.0.0.1:8080/ready
```

Действия: запомнить состояние службы → остановить API → проверить две SQLite
базы → выполнить `minimal_backup backup` и `verify` под пользователем службы →
запустить новый backend в одноразовом режиме `migrate` через `systemd-run` с
`EnvironmentFile` → проверить `integrity_check`, `foreign_key_check`, версию
схемы и координатор → записать постоянный drop-in для systemd → запустить
службу и проверить **реальную версию 0.45.7** через `/ready`.

Если миграция/проверка не проходит, drop-in ExecStart удаляется, корень с изменёнными данными переносится в
`*.failed-upgrade-<pid>`, проверенная резервная копия восстанавливается на
прежний путь с сохранением конфигурации и секретов; исходный сервис проверяется
по своей старой версии. При ошибке восстановления сервис **не признаётся
работоспособным**. При первоначально остановленной службе обновление её не
включает, поэтому runtime-верификация остаётся отдельным операторским шагом.

## Standard PostgreSQL / Docker Compose

Скопируйте исходный production env-файл в отдельный `source-0456.env` (не
изменяйте после создания), а `target-0457.env` укажите версию 0.45.7 и
`LAUNCHER_DATABASE_AUTO_MIGRATE=false`; одинаковые `POSTGRES_*`, системные
секреты и параметры хранилища обязательны. Два файла должны иметь права 0600,
храниться в контролируемом каталоге, а проект должен использовать тот же Compose
project name. Операция **деструктивна в режиме восстановления**: при неудаче
схема БД полностью удаляется и возвращается из снимка; snapshot храните отдельно.

```bash
python3 scripts/operations/db_upgrade_0457.py postgres \
  --project launcher-prod --confirm launcher-prod \
  --source-env /etc/launcher/source-0456.env \
  --target-env /etc/launcher/target-0457.env \
  --snapshot /secure/offhost/upgrade-0457 \
  --production-source --maintenance-approved
```

Для изолированного `nl-dr-*` проекта достаточно `--confirm`, production-флаги
не нужны. Команда проверит live API источника, **соберёт новый образ до простоя**,
остановит писателей, создаст и проверит полный `pg_dump -Fc` и снимки всех
служебных Docker volumes, проверит PostgreSQL WAL и внешние сессии в начале и
конце резервирования и оставит писателей выключенными. Дальше запускается
**одноразовый реальный Go backend** с `LAUNCHER_PROCESS_ROLE=migrate`
(никакого HTTP/worker); повторный прогон проверяет идемпотентность схемы.
Сервисы запускаются с принудительным `LAUNCHER_DATABASE_AUTO_MIGRATE=false`,
проверяется version=0.45.7 и готовность реального backend.

В случае сбоя писатели вновь останавливаются, проверяется полный snapshot,
удаляется целевая БД, создаётся чистая, проводится `pg_restore`, полностью
восстанавливаются snapshot-тома и повторно проверяется **старый** backend
и прежняя версия. Если хоть один этап не подтверждён, старый backend автоматически
не объявляется восстановленным. Полный снимок сохраняется для расследования.

## Границы гарантий и фактическая приёмка

- Никакого автоматического отката SQL внутри уже зафиксированной миграции нет:
  выполняется **restore всей согласованной копии**. Записи, принятые после
  момента snapshot, не являются частью восстановления и в нормальном сценарии
  запрещены изоляцией writers.
- После фактической миграции на 0.45.7 **не меняйте образ или схему** в обход
  проверенной процедуры; backend 0.45.6 не обязан читать новую схему.
- Network-HA с игровыми мирами/ServerBridge и внешним S3 **не** разрешён этим
  Standard-скриптом: потребуется отдельная координация game writers,
  fencings и S3 на этапе обновления компонентов. Контроллер специально
  отказывает при неподдерживаемой топологии, вместо ложной сертификации.
- Локальная проверка включает настоящие SQLite bytes, обновление схемы с
  последующим восстановлением и негативные тесты PostgreSQL-оркестрации.
  Реальный Go backend/SQL PostgreSQL E2E с Docker и тест восстановления на
  отдельном хосте обязательны перед утверждением промышленного выпуска.
