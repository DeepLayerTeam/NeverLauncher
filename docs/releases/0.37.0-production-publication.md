# Launcher 0.37.0 — выпуск и публикация

Область: **production release**, не проверка того, что 0.37.0 уже имеет опубликованные и независимо аттестованные шесть установщиков. Выпуск начинается со свежих внешних результатов, заканчивается подтверждённой публикацией неизменённых файлов GitHub Release.

## Запуск

Workflow: `.github/workflows/production-release-candidate.yml` из `main` на точном commit. `workflow_dispatch` задаёт идентификаторы необходимых защищённых прогонов, точный staged package, GA `ga_operator_approval_run_id`; для публикации включить `publish_release=true`. По умолчанию **false**: выполняется создание и проверка релизного кандидата без публичного выпуска.

Необходимы GitHub Environments `production-release` (approvals + restricted administrators), рабочие self-hosted стенды для реального DR, GA backend, Windows Authenticode и macOS Developer ID/нотарификации, действительные независимые операторские Ed25519-подтверждения по шести точным пакетам, защищённые `NL_GA_OPERATOR_PUBLIC_KEY_HEX`, `NL_PRODUCTION_RELEASE_ROOT_PUBLIC_KEY_PEM`, `NL_PRODUCTION_RELEASE_TRUST_POLICY_JSON`; приватный ключ release sign используется **только** в job `release-bundle`. Не переносить release signing secret в `publish-release`. Для самого `publish-release` нужен GitHub Token `contents: write` и встроенный GitHub CLI `gh`.

## Порядок исполнения

1. `base-ci` запускает Go/Admin/Desktop/Rust/Java/Bridge, контейнеры, security и реальный E2E. `required-ci` требует `success` от всех своих необходимых jobs. Остальные production jobs выполняют защищённые RC, DR, Admin/Profile GA, Windows/macOS signed outputs, staged runtime и независимые GA.
2. `release-bundle` повторно проверяет собственный commit/версию и актуальные независимые сертификаты, собирает реальные бинарники и подписанные/нотаризованные установщики, проверяет `RELEASE_REHEARSAL_0365.json` с точными SHA-256. Только затем формируется `RELEASE_MANIFEST.json`, `SHA256SUMS`, подписываются provenance и Ed25519 `SHA256SUMS.sig`, выполняется `release publish-check` и `PUBLICATION_DRY_RUN_0365.json` с физическим копированием всех файлов.
3. Промежуточный подписанный bundle из `release-bundle` сохраняется как run-scoped artifact `launcher-final-release-<SHA>-<run>-<attempt>`; отчёт dry-run сохраняется отдельно. Кандидат ещё **не опубликован**.
4. `required-production-ci` допускает только `success` всех предшествующих production jobs, кроме самого gate и зависимого от него `publish-release`; никакие пропущенные, отсутствующие, отменённые или неуспешные проверки не становятся PASS.
5. `publish-release` при явном разрешении скачивает **этого же run/attempt** подписанный bundle, report gate и dry-run, проверяет неизменность `SHA256SUMS`, подпись независимого GA-оператора, срок действия GA, шесть обязательных целевых платформ, девять подтверждений на каждую цель, хеши бинарников/пакетов, `RELEASE_MANIFEST` и повторно запускает **штатный** `launcher release publish-check` с закреплённым release key/policy. Используется отдельное временное trust-state.
6. Публикация создаёт GitHub Release **draft**, не перезаписывая существующий release/tag; загружает все без исключения файлы, скачивает обратно **каждый** asset и сверяет SHA-256. Только после полного совпадения имён и байтов переводит draft в публичный статус. Если что-либо не прошло, draft остаётся закрытым и job завершается отказом. Результат записывается в отдельный `PUBLICATION_0370.json` после публикации; этот отчёт намеренно **не** добавляется задним числом внутрь подписанного bundle.

## Проверка и восстановление

Локальный gate без публикации: `python3 scripts/release/publish_0370.py verify --bundle ... --ci ... --dryrun ... --version 0.37.0 --commit <40-hex SHA> --run-id <id> --run-attempt <attempt> --ga-key ... --release-key ... --trust-policy ... --trust-state ... --cli ... --output ...`. Для публикации вместо `verify` используется `publish` и добавляется `--repository OWNER/REPO`; нужен разрешённый GitHub Token. Этот вызов не заменяет workflow gate или независимую реальную GA-проверку.

Если произошёл сбой при загрузке: релиз **не становится публичным**, пока не завершена полная обратная проверка. Для нового прогона используйте новое подписанное GA-разрешение и заново выполните все обязательные проверки; частичный draft и созданный tag требуют ручного аудита и решения о безопасном удалении до повторной попытки (поверх них автопубликация не выполняется). Не публиковать вручную из UI draft со статусом незавершённой проверки.

Все platform reports и игровые evidence должны возникать из **реального выполнения на соответствующем стенде**, а не из тестовой фикстуры. Unit-тесты `test_publish_0370.py` проверяют исполняемый код проверки и отказов с синтетическими PE/ELF/Mach-O и имитацией транспорта GitHub; они **не** являются независимой шестиплатформенной GA-сертификацией.

## Сохраняемые гарантии

- Выпуск с неизвестной версией, другим SHA, устаревшим run/attempt, истёкшим Ed25519 GA-разрешением или без любого обязательного доказательства блокируется до GitHub API write.
- Смена номера версии не отменяет RC, GA, `required-ci`, `required-production-ci`, `release publish-check` либо сравнение конечных байтов.
- Закреплённые публичные ключи передаются через защищённые переменные/секреты; процесс публикации **не** получает приватный ключ подписи.
- Тег и опубликованные файлы должны соответствовать одному SHA; существующий tag/release не перезаписывается автоматически.
