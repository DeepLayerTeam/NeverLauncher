# NeverLauncher 0.29.1 — Canonical Identity & Issuer

## Deployed behavior (not just data structures)

The running authentication path now resolves **(provider ID, verified issuer, subject)** and never resolves an external identity by email. Existing local accounts retain issuer `neverlauncher`; external identities created before this release remain in the explicit legacy namespace `provider:<provider ID>`. Connector-supplied verified OIDC `iss` and signed, configuration-validated HTTP `issuer` are preserved without case folding. SQL/non-federated providers without protocol issuer remain scoped to their configured provider name; this is a namespace, **not** proof of an external issuer.

- Browser/password logins, auto-provisioning, provider linking and repository persistence all use the same composite identity key. Separate issuers can return the same subject and email without accidentally sharing a Never account.
- JIT provisioned accounts receive a deterministic internal ID derived from provider + issuer + subject and an unrelated unique internal email under `identity.invalid`. The external claimed email remains on `auth_identities` and is **not** silently promoted to Never's canonical login email.
- Existing legacy identities are **never** reassigned to a new issuer simply because the new provider configuration now returns an issuer. If the same external subject already exists in the legacy namespace, ordinary auto-provisioning is refused until the user explicitly links it. Identity linkage also refuses to transfer another user's legacy subject.
- Password linking is an operational endpoint, `POST /api/v1/auth/providers/{providerId}/link/password`, requiring an active signed-in Never session and freshly verified password from the selected registered provider. Body: `{"identifier":"external username","password":"external password"}`. The password is never persisted, returned, or logged. The request is subject to both the global auth-rate limiter and account/IP login-failure lockout. Browser providers retain their existing proof-bearing link flows.
- Refresh credentials for Microsoft/OIDC/HTTP are now stored, selected, replaced, and deleted **by the exact identity ID**. Where more than one issuer is linked for one provider, provider refresh/logout APIs require URL-encoded `?issuer=<exact issuer>`; provider-only operations fail closed with 409 rather than choosing a random credential.
- Minecraft GameProfile `user_id`, `uuid`, `issuer`, `realm`, `subject` are immutable in both production PostgreSQL and memory repositories. A PostgreSQL trigger also rejects direct SQL attempts to silently change ownership, UUID, or legacy identity metadata. Verified transfer of a GameProfile requires a distinct operator-reviewed process in a later version; **0.29.1 never auto-migrates or rewrites the UUID**.

## Database migration and rollout

`0081_auth_canonical_issuer_0291.sql` is included byte-identically in the Backend and embedded CLI migration catalogs. It backfills issuer namespaces without modifying user identifiers or Minecraft UUIDs; replaces outdated uniqueness on `(provider, subject)` and `(user_id,provider)` with issuer-scoped constraints; allows separately stored refresh credentials per identity. The migration validates duplicates/issuer values and installs a database-level immutability trigger for GameProfiles.

1. Back up the production PostgreSQL database; rehearse migration on a restored copy with existing Gravit/Never accounts and Minecraft profiles.
2. Stop old Backend writers; deploy and migrate with **0.29.1 Backend and matching CLI** as a coordinated upgrade. Old 0.29.0 Backend code is not compatible with issuer-bearing rows; don't run it against the migrated database.
3. Validate legacy issuer labels, profile UUID retention, disabled accounts, external login and explicit linking, stored refresh tokens, server authentication and session issuance.
4. Keep current Never authentication sessions protected by the existing validation and revocation controls. Unlinked external identities may need user-driven re-linking or operator-assisted account recovery if the old Never login is unavailable.
5. Do not use an automated SQL down-migration that discards multiple issuers or credentials; restore the verified pre-upgrade backup if rollback of data is unavoidable.

- Executed Go unit and connector tests: `GOPROXY=off go test -tags neverlauncher_nopgx ./internal/model ./pkg/authconnector ./internal/federation ./internal/repository ./internal/oidcconnector ./internal/httpconnector ./internal/microsoftconnector ./internal/dbmigrate` (from `services/api`).
- Executed `GOPROXY=off go test ./internal/dbmigrate` from `cli` to verify the embedded migration catalog.
- Added regression tests for two verified issuers with identical email/subject; explicit proof linking; no implicit email auto-link; identity-based credential storage; preserved Minecraft UUID; ambiguity rejection; and an optional **real PostgreSQL integration test** using `NEVERLAUNCHER_TEST_POSTGRES_DSN` (requires a disposable, migrated test database).
- This local environment has no resolvable `github.com/jackc/pgx/v5`, `github.com/go-sql-driver/mysql`, or `golang.org/x/crypto`, and no disposable PostgreSQL server: full HTTP/API compilation, real DB migration run, browser login, and Minecraft E2E **were not executed locally**. The source implementation is not represented as independently GA-certified solely by these tests. The pre-existing production GA release gate must still pass on the exact commit.
