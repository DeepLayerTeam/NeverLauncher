# 0.32.9 — Signed Installer, Embedded Admin & Owner Bootstrap

## Status and scope

DEP04 (partial, executable): signed **offline** release bundles, CLI install and init,
embedded minimal first-run Admin, owner bootstrap against the existing atomic
PostgreSQL installation endpoint. This does **not** make the Backend SQLite-only:
DEP01/02 HTTP Repository integration is still incomplete. It does not automatically
install PostgreSQL, create the release-specific Guard allowlist, or replace the
full standalone React/Vite Admin application.

The `installer/` directory is a standalone Go standard-library module. For Linux
amd64 (where `renameat2(RENAME_NOREPLACE)` is supported):

```sh
cd installer
go test -race ./...
go build -trimpath -o ./neverlauncher-install ./cmd/neverlauncher-install
```

### Release signing (CI/release machine only)

Prepare a dedicated Ed25519 signing seed (32 random bytes encoded in hex) in a
private mode `0600` file, and distribute its **public** key to operators over an
independent, authenticated channel. Do **not** place the private key or the public
key trust root inside the unsigned release archive and then trust it from there.

```sh
./neverlauncher-install pack --source /build/neverlauncher-release \
  --version 0.32.9 --private-key /secure/release-ed25519-seed.hex \
  --output /build/NeverLauncher-0.32.9.bundle.zip
```

The bundle contains detached `manifest.sig` over exact `manifest.json` bytes. Each
entry's SHA-256, mode (executable or data), and length are signed. The installer
rejects signature failures, changed files, unsigned entries, ZIP symlinks, path
traversal, duplicate filenames, excessive sizes, and existing installation
directories. No executable is run during verification or extraction.

### Operator installation

```sh
./neverlauncher-install verify --bundle NeverLauncher-0.32.9.bundle.zip \
  --trusted-key /etc/neverlauncher/release-public.hex
./neverlauncher-install install --bundle NeverLauncher-0.32.9.bundle.zip \
  --trusted-key /etc/neverlauncher/release-public.hex \
  --target /opt/neverlauncher/releases/0.32.9
```

Release bundles must contain only public artifacts: files are installed read-only for the service user (0644 data / 0755 executables and directories). Never bundle secrets.

Installation writes an entirely new release directory and atomically publishes it
without overwriting existing data or software. Release switching/upgrades are
separate and must include a database backup and health validation.

### First-run configuration and owner

Use an existing PostgreSQL instance (not SQLite-only). The generated file is `0600`,
created with O_EXCL, and contains cryptographically random session, manifest,
ServerBridge, extension and one-time bootstrap credentials:

```sh
./neverlauncher-install init --output /etc/neverlauncher/backend.env \
  --public-url https://launcher.example.org \
  --dsn 'postgres://nl:password@localhost:5432/neverlauncher?sslmode=require' \
  --storage /var/lib/neverlauncher/storage
```

Before starting production, set the real Guard release policy and any other
release-specific settings required by `config.ValidateProduction`, verify the
PostgreSQL connection, complete migrations, configure the system service with
that environment, and pass deployment diagnostics. The generated environment
is **not** a production-readiness certificate. Never share it or commit it.

On a Linux host with a dedicated `neverlauncher` system account and populated
`/var/lib/neverlauncher` state directory, generate the hardened systemd unit:

```sh
./neverlauncher-install systemd-unit \
  --binary /opt/neverlauncher/releases/0.32.9/bin/neverlauncher-api \
  --env-file /etc/neverlauncher/backend.env \
  --output /etc/systemd/system/neverlauncher.service
```

Inspect it and invoke `systemctl daemon-reload`, `enable`, and `start` only after
production configuration validation and directory provisioning. The CLI never
runs those privileged actions without operator control.

To create the **first** owner, use `GET /admin/` on the Backend origin and enter
the protected one-time token, or use the non-interactive CLI with a `0600`
password file. Avoid secrets in shell command arguments or terminal history:

```sh
./neverlauncher-install bootstrap-owner --url https://launcher.example.org \
  --email owner@example.org --name Owner \
  --password-file /etc/neverlauncher/first-password \
  --env-file /etc/neverlauncher/backend.env
```

Owner creation is performed by the existing **transactional** backend endpoint,
which holds the installation row, enforces one-time token consumption, rejects
existing users, inserts identity+audit, and commits them atomically. A failed
or ambiguous HTTP response must be checked via readiness before retrying; do not
reset database state or mint a new bootstrap account.

After bootstrap, log in at `/admin/`. The embedded view can inspect readiness and
the Admin overview, list projects, and create the first project through the
existing authenticated API. The full React/Vite Admin remains separately
built/deployed; the embedded view intentionally covers only installation and
basic post-install operations. The embedded browser never stores access tokens
persistently. HTTPS must terminate before a public production instance.

### Guarantees and limitations

- No private signing seed is ever accepted from the release bundle.
- SHA-256 is checked on every signed payload file before installation.
- The directory publication is no-replace; the installer never overwrites an
  existing release, environment file, or pre-existing data.
- Standalone CLI and embedded Admin have tests that can run offline without Go
  dependencies. Full Backend e2e tests require Go 1.27.3, PostgreSQL, release
  keys and the established product security pipeline.
- A successful 0.32.9 installer build does not certify production readiness of
  the entire NeverLauncher deployment.
