# 0.47.8 — native migration, legacy upgrade and Minecraft integration evidence

**Release status: candidate / not production certified.** This release adds an executable CI matrix and rejects fabricated or incomplete evidence. It cannot certify a live SQLite→PostgreSQL Backend cutover while `sqlitepg.VerifyCutover0475` deliberately returns `readyForBackendCutover=false` and `RejectUnapprovedBackend0475` blocks the imported PostgreSQL. The independent SQLite HTTP Repository, Coordinator and some Extensions data have not been mapped to the Backend repository. An HTTP `/ready` response from another installation is not proof of migration.

## What runs automatically on push / PR

`.github/workflows/integration-matrix-0478.yml` runs:

1. Actual SQLite WAL/restart/backup/legacy-schema tests (`sqlitecore`, `sqlitedurable`, `sqlitecoord`) plus migration operator fault injection and adversarial receipt tests. A host swap test runs with root privileges because the production swap requires root-owned binaries and directories.
2. PostgreSQL 17 **and** 18 services, with a dedicated empty DB per matrix runner. Go builds use the locked module set and the actual `TestLiveSQLiteToSQLRepository0473`: Core SQLite → verified staging → real SQLRepository tables and read-back of imported owner, project, profile, release, state and MFA. There is no mocked PostgreSQL driver.
3. Real Backend HTTP API authorization/publication unit+integration handlers, Admin UI tests and production build, Desktop tests for update and server join. These tests do **not** claim that the Admin is connected to a migrated PostgreSQL Backend.

The test steps are fail-closed. A test that requires a live PostgreSQL DSN is run with a DSN (it may not skip); the source test requires an initially untouched database. Each PostgreSQL version has a separate runner and isolated database.

## Protected full acceptance: manual dispatch with real infrastructure

`workflow_dispatch` additionally requires:

* A protected, independent SHA-256 pin of an HTTPS JSON baseline manifest.
* An accessible actual installed Linux CLI archive for **each** of the thirteen claimed input versions: `0.45.14`; `0.46.0`–`0.46.3`; `0.47.0`–`0.47.7`. This is not a synthetic fixture matrix. The runner downloads each pinned ZIP, rejects traversal/links/duplicates, runs the original installed executable's `version` command, upgrades with the original `legacy_upgrade_0476.py` using the existing root-only native host swap, executes the upgraded binary and verifies all protected file names, contents, permissions, backup and journal. Any absent or mismatched old release fails the job.
* An isolated **destructive** Admin staging deployment already running the exact current commit, with the protected `NL_E2E_*` variables and secrets required by the original `owner-cycle-0390-browser.py`. The browser uses the Admin UI to create/project-profile, reject a bad signed package, publish the good one, roll back and enforce project-scope restrictions. This is separate from testing whether the *migrated* Backend can start.
* An actual Docker PostgreSQL / Minecraft / Java / Rust / Maven / Gradle graphics runner. `run-minecraft-e2e.sh` full mode creates a real signed publication, performs auth/revocation, launches the real Minecraft JVM client, exercises the Paper join and ten live ServerBridge runtimes, and performs Minecraft transactional update/rollback and world backup/restore. Separate real Mojang matching client/server jobs run 1.17.1 (Java 17) and 1.21.1 (Java 21).

The acceptance job rejects **any failed or skipped** suite. It is not a substitute for the unresolved imported Backend cutover; a separate successful cross-store cutover + imported-owner login is required before a production release can be approved.

### Baseline manifest for the real previous-installation matrix

Each archived ZIP must contain the already-installed executable (root-level default `launcher`) and original protected `profiles/` and `settings/` content. Do not generate those from the candidate. If trust keys, secrets or channels live elsewhere, include them in `protectedPaths` and ensure that they are present in the archive. `url` must be HTTPS and `sha256` a lowercase 64-byte hex digest. The full manifest itself must be independently SHA-256 pinned **before** the workflow is dispatched.

```json
{
  "target": "0.47.8",
  "baselines": [
    {
      "version": "0.45.14",
      "url": "https://release-archive.example.invalid/neverlauncher/0.45.14/existing-linux-install.zip",
      "sha256": "REPLACE_WITH_INDEPENDENT_SHA256_OF_ACTUAL_ARCHIVE",
      "binary": "launcher",
      "protectedPaths": ["keys", "channels"]
    }
  ]
}
```

This example is intentionally **incomplete** and cannot pass: provide all 13 authentic release entries, real hashes and accessible archives. Do not use a source ZIP as a substitute for an installed binary. The host upgrade exercises Linux x86-64; native Windows/macOS signed package upgrade certification is separate.
