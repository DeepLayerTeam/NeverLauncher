# NeverLauncher 0.28.9 — Backend Operations

## Scope and actual execution paths

* Admin **Backend Operations** requires the global `backend:control` permission. Project-only permissions or `gameserver:*` do not grant this capability. ServerBridge Protocol v3 and Host Process Control are unchanged.
* `GET /api/v1/operations/backend/status`: process identity, version/commit, uptime, effective operational-config revision, real storage/repository health and recent session counters. No credentials or DSNs are returned.
* `GET /api/v1/operations/backend/clients`: PostgreSQL (or development-memory) Minecraft session activity and authenticated Admin sessions. Only active, unexpired sessions observed within 5 minutes, max 100 of each category, are returned. **These are not live TCP connections or a verified count of players logged into game servers.**
* Configuration validation, CAS apply and rollback remain on existing `/api/v1/admin/config` endpoints, with existing `settings:manage` + fresh MFA enforcement. `POST /api/v1/operations/backend/config/reload` checks the currently stored revision and validation again. Only non-secret hot-read operational settings reload; static env settings (TLS/listen/DB/signing) still require a deployment-controlled process restart.
* `POST /api/v1/operations/backend/notify`: writes a user-targeted message to a **durable PostgreSQL inbox** keyed by actor + `Idempotency-Key`. User cannot receive another user's message; `GET /api/v1/backend/notices` and `POST /api/v1/backend/notices/{noticeId}/ack` require the recipient's valid auth token. Notices expire after 24 hours, with explicit acknowledgement. Admin polls every 30 seconds while signed in. This is **not** an automatic in-game/desktop push or a ServerBridge broadcast.
* `POST /api/v1/operations/backend/restart`: checks global `backend:control`, fresh phishing-resistant MFA, exact 48-character random instance identity, confirmation `RESTART <instanceId>`, and a 16–128 char `Idempotency-Key`. It accepts the command only after a successful PostgreSQL insert to the unique once-per-instance journal. Replayed keys never trigger another exit. A different key for the same runtime returns conflict. A journaled action with unprovable external result is **not retried** automatically.
* Service management: the process owning the HTTP listener receives the internal restart signal, marks `/ready` as draining, calls `http.Server.Shutdown` with 25s grace and exits. There is **no remote shell, direct PID kill, new process spawn or ServerBridge command**. The process must be restarted by an externally managed service (systemd, container runtime, etc.).
* Existing token/session revocation is accessible from Admin **Devices**, durable release/build job monitoring from **Job Monitor**, and installed extension start/stop/restart from **Admin Extensions**. 0.28.9 reuses those working paths rather than inventing a second backend executor.

## Required deployment steps

1. Upgrade the full Backend binary and run database migration `0080_backend_restart_0289` (either the API migrator or the CLI, not both simultaneously). Keep backups.
2. Keep `NEVERLAUNCHER_BACKEND_SUPERVISED_RESTART` **unset** until an external service manager has been configured and verified to restart the process on a clean exit. Restart is disabled unless this flag is exactly `true` **and** the repository is PostgreSQL.
3. Configure the *external* unit/container policy to restart the service after successful termination. For example, use a correctly scoped systemd service with `Restart=always`, `RestartSec=3s` and an ordinary unprivileged service account. Do not give the API shell/root privileges. Check service-manager semantics for planned maintenance before enabling.
4. Confirm `/ready` remains healthy under normal load and fails during graceful draining. Test restart from Admin using a recently verified phishing-resistant session; observe a *different* instance identity after restart. Reissue the same `Idempotency-Key`: it must not restart again.
5. With two Backend replicas, verify each has a unique runtime identity and that a restart request only affects the targeted instance. API load balancers must route the operator's status + restart to that same instance; stale targeting fails closed.
6. Confirm backend notifications across replicas with a recipient Admin session and acknowledgement. Inspect audit events `backend:restart:accepted`, `backend:config:reload`, `backend:notice:queued`.

## Safety, limits and incomplete certification

- Read `/ready` via a supervisor-protected network; status endpoints require global Backend authorization.
- The accepted restart request is persisted *before* scheduling the process-level exit. Losing the reply or crashing before shutdown can leave the result indeterminate. Operators must inspect the journal/supervisor and must **not** use a new key to blindly force a second restart.
- The restart operation requires a PostgreSQL connection; memory-only mode refuses it.
- The notification inbox is durable but requires the client to poll. Only Admin currently polls automatically. Desktop and game-client notification delivery are not claimed.
- Existing release pipelines, signing jobs, token/session revocation and extension lifecycle operations retain their existing API and permissions; no second privileged path is added.
- Source-level tests, migration catalog tests and Admin tests run without infrastructure. Full Go HTTP suite, multi-replica PostgreSQL integration, systemd process-manager E2E and desktop/game runtime E2E are still required for a production-GA claim.
