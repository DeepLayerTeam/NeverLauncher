# NeverLauncher 0.35.9 — Desktop settings, preset updates, player-owned files

## User operations

1. Upgrading Desktop from `config.json` schema `1.0` reads existing settings, validates the signed owner binding and atomically saves schema `1.1`. The exact previous JSON is preserved as `config.pre-0359.json`. Invalid/unknown future schemas cause an error instead of being overwritten. Local preference fields not owned by the current code are retained by native `serde(flatten)`.
2. Opening a new owner-signed client release compares it with the **verified installed release**, not the user's local dropdown. Changes to Java version bounds, distribution, memory, Minecraft/loader and the signed component catalog are displayed before installation. A changed release needs explicit acknowledgement; acknowledgement is keyed to the signed target, and the UI rejects stale preview results.
3. If a previous selection can be reconciled, NeverRuntime supplies the signed-catalog migration. If an incompatible migration is found, installation remains blocked until a user chooses and verifies a supported preset. The proposed preset is not persisted as installed until the native release transaction is complete.
4. A new signed managed file colliding with a player-owned path is not silently replaced. From Downloads or the signed onboarding / component selection screen, the player can review the exact conflicting paths and SHA-256 hashes, then explicitly preserve them under `.neverlauncher/client-releases/player-conflicts/<random-id>/`. The archive contains `index.json` and original file bytes. Existing symlinks, altered bytes, races or a different native Desktop project/game path cause rejection. A partially interrupted move leaves its archive and index for inspection. The original transactional managed-ownership check stays enabled.

## Ownership and failure semantics

- **Do not delete** the `player-conflicts` directory when cleaning caches or rolling back. It is user content, not managed release content.
- If power loss interrupts preservation, inspect `index.json` and the archive before retrying. Each individual file move is a same-filesystem rename; all expected entries are recorded before the first move.
- Files already owned by the previous signed release and locally modified are still **not** automatically retired on a release switch. Repair or manually export them first; this is a deliberate safety limit, not an implicit overwrite.
- The new signed release is not marked installed because the player accepted a preview. Native install, SHA-256 and commit must succeed first.
