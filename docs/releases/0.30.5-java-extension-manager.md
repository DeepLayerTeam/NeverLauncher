# NeverLauncher 0.30.5 — Java Extension Manager

## Что действительно изменилось

Менеджер **не заменён отдельной несовместимой системой**: прежние `extension-installs`, `extension-updates`, repository, transaction lease, backup/rollback и доверенные подписи Ed25519 остались основой. В `0.30.5` новые проверки подключены к **исполняемым переходам** жизненного цикла.

1. `Install` и `Update` загружают, проверяют digest, доверенный ключ издателя и подпись `.nlext` штатным `prepareArtifact0204`, затем **сверяют подписанный manifest** с версией, опубликованной в Registry. Различие приводит к отказу.
2. После извлечения в staging, **до активации current**, проверяются Java backend и CLI JAR: архивные пути, дубликаты, ограничения размера и ZIP-decompression, классы SDK-host и implementation, bytecode и `Main-Class`. Запускается именно системная JVM с `java -version` (не код расширения): версии ниже 17 или ниже версии bytecode отклоняются. Ошибка не заменяет активное содержимое.
3. Разрешаются прямые и транзитивные зависимости с project/global scope fallback; required deps, SemVer ranges, конфликты и циклы. Обновление зависимости, которое ломает уже установленное расширение, запрещается; обратная проверка учитывает project overrides.
4. `Enable` повторно выполняет проверку, требуя активных обязательных зависимостей. `Rollback` проверяет staged backup **до** замены текущего содержимого. Для Java-пакета дополнительно заново проверяется доверенный подписанный архив прежней версии из Registry и побайтовое равенство всего payload; при ошибке (включая отсутствие прежнего архива в хранилище) откат прерывается до активации. При применении update-plan используются существующие update transactions, health-check и компенсационный rollback.
5. `nl extension diagnose <id> --backend URL --token TOKEN [--scope global|project --scope-id ID]` читает состояние установленного расширения через аутентифицированный admin route и исполняет проверку manifest, lockfile, текущего JAR/JVM, зависимостей и статуса supervisor. Вывод `data.javaDiagnostics.healthy/errors/javaTargets`, если есть host — `data.host`. Используется существующее разрешение `extension:manage`.
6. Общий JAR validator используется и supervisor, и installer, чтобы прямой запуск JVM не снижал уровень проверок.

## Примеры

```shell
nl extension install org.example.java-host@0.1.0 --backend https://launcher.example --token "$ADMIN_TOKEN"
nl extension diagnose org.example.java-host --backend https://launcher.example --token "$ADMIN_TOKEN"
nl extension update org.example.java-host --channel stable --backend https://launcher.example --token "$ADMIN_TOKEN"
nl extension rollback org.example.java-host --backend https://launcher.example --token "$ADMIN_TOKEN"
```

`install` и `rollback` работают с неизменяемыми версиями в локальном Registry и резервными копиями; для `update` требуется соответствующий published release и управляемая транзакция. Ключи издателя должны быть доверенными через NeverExtensions trust policy. Недоверенный JAR **не становится безопасным** от одной структурной проверки; подпись подтверждает издателя и целостность, но не отсутствие вредоносных конструкций.

## Проверки / ограничения

- Локально: JDK 21, реальная сборка `examples/extensions/java-host`, Inspect/Java runtime tests, CLI diagnose-test, Go CLI build, Ed25519 pack + verify, проверка метаданных версии.
- **Не подтверждено локально:** интеграционные Go-тесты `extensionlifecycle`, `extensionhost`, `httpapi` из-за отсутствующих извне зависимостей (`pgx/v5`, `x/crypto`, MySQL driver). CI workflow воспроизводит проверку с установкой зависимостей. Тесты добавлены, но релиз нельзя считать production-сертифицированным до их успешного выполнения.
- Не выполнено: полноценная Java package marketplace UI, offline certificate revocation; отдельный multi-JVM sandbox и in-process trusted agent входят в дальнейшие этапы.
- Java rollback **требует доступного подписанного архивного релиза** в Registry storage; полностью автономный offline rollback Java-версии намеренно запрещён, если проверить подлинность резервной копии нельзя. Для не-Java пакетов сохраняется прежний механизм восстановления. Защита от изменения файлов активного payload внешним привилегированным процессом в релиз не добавлена.
