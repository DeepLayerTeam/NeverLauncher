# NeverLauncher 0.23.1 — Shared Download Scheduler (D01)

## What actually runs

`neverruntime::download_missing_files` and `neverruntime::repair_client` both call
`download_scheduler::run` through the signed-manifest, verified-target entry points.
Desktop Tauri commands expose `download_missing_files_with_progress` and
`repair_client_with_progress`; the CLI's existing Rust API also uses the same
scheduler. No new backend endpoint or manifest schema is required.

A task is queued only after checking the existing file's signed size/SHA-256,
manifest OS applicability and protected ownership policy. Executables/version
metadata are prioritized before libraries and bulk assets; ordering within each
priority band follows the manifest. A saturated host is skipped so transfers
from another host can start. Each worker acquires process-wide as well as
per-operation slots **before** it is spawned. Default process limits are six
active transfers total and three to a single scheme/host/port; no more than
six transfers run in one operation. These are conservative hard limits in 0.23.1,
not yet per-user configurable. Download sources that redirect are rejected,
not followed to a host outside the admitted budget.

Responses are streamed to unique `*.nlpart-*` files, chunk by chunk. Writes
are awaited, so disk pressure stops the next HTTP read. Bodies are not fully
materialized in RAM. Signed length and SHA-256 are checked before atomic
replacement; file-path symlink checks and executable permission handling remain.
An unsuccessful file generates a per-file error, and other jobs continue.
Partial files from failed jobs are deleted; persisted HTTP resume belongs to D02.

`DownloadResult.bytesDownloaded` is the count of HTTP body bytes actually
consumed (including bad content), not the count of bytes accepted into the
installation. The number of successfully installed files is `downloaded`.

## Desktop progress events

The Desktop commands emit the Tauri event `neverlauncher-download-progress`.
The event payload has these camelCase properties:

- `operationId`, `phase` (`starting`, `downloading`, `verified`, `failed-file`, `finished`)
- `totalFiles`, `queued`, `active`, `completed`, `failed`, `skipped`
- `bytesExpected`, `bytesTransferred`, `currentFile` (possibly `null`)

Transfer events are throttled to approximately one event per 100 ms for one
operation, plus important state transitions. The download screen listens for
events and displays live counters and transfer volume. `bytesExpected` is the
signed total size of files requiring download; `bytesTransferred` can exceed it
on abnormal streams or retries. Neither quantity means verified installation.

## Verification

From the repository root on a machine with the Rust toolchain:

```bash
cargo test --manifest-path runtime/neverruntime/Cargo.toml download_scheduler -- --nocapture
cargo test --manifest-path runtime/neverruntime/Cargo.toml concurrent_operations_tests -- --nocapture
cargo check --manifest-path runtime/neverruntime/Cargo.toml --all-targets
cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml
cd apps/desktop && npm ci && npm run build
```

The Rust tests spawn a local TCP HTTP server; no public network resources are
used by the tests. One test serves an intentionally incorrect SHA-256 file to
assert isolated failure while the other seven finish. Another starts two
simultaneous independent downloads from the same host and verifies that the
process-wide per-host ceiling is not breached.

## Not in this release

Range/If-Range resume, persistent pause/cancel, signed mirror sets, reusable
content-addressed cache, full release transactions and native bootstrap are
scheduled for later milestones. 0.23.1 is not a certification of those features.
