# 0.46.0 — Operations & Delivery GA: инструкция выпуска и независимой приёмки

## Область результата

Исходный код 0.46.0 содержит исполняемый механизм допуска и проверки, но **не является автоматически независимо сертифицированным GA-релизом**. Публикация разрешается только при реальном выполнении работ на независимых Linux-хостах и шести целевых платформах и с использованием доверенных внешних ключей. Наличие отчётов unit-тестов вместо фактических операций не подходит.

Продолжает действовать весь release gate 0.45.11: BOM/SPDX/SLSA, OS native signatures, точные шесть установщиков, независимое GA игровых сценариев. Новый gate **дополнительный**, ничего не отключает и не заменяет.

## 1. Выполнить эксплуатационную приёмку

Выполнить на реальных изолированных хостах процедуры [Independent Acceptance 0.45.14](../operator/independent-acceptance-04514.md) инструментом `scripts/operations/independent_accept_04514.py` из *исходников 0.46.0*:

- Чистая Standard-установка новой версии с HTTPS и первым администратором;
- Обновление предыдущей 0.45.14 с согласованной резервной копией и повторным входом прежнего администратора;
- Восстановление этой копии на другом Linux-хосте и чтение существовавшего проекта;
- Failover PostgreSQL/Redis/S3/API/worker только в `nl-dr-*` стенде с фактической проверкой подтверждённых данных.

Сохранить четыре `0600` JSON отчёта с действительными временными метками и записями независимого оператора. Отдельно хранить сырые журналы, эксплуатационные метрики и инструкции воспроизведения. Не переносить секреты, токены или файлы MFA в публичный дистрибутив. Прежняя `verify-receipts` проверяет внутреннюю согласованность, а не подлинность подписи; с 0.46.0 результат должен быть дополнительно подписан внешним ключом оператора.

## 2. Подписать свидетельство на фактически собранные установщики

Доверенный оператор получает **все шесть** конечных OS-подписанных пакетов. На отдельном хосте с Python 3.12 и `cryptography` 42+ создать Ed25519 PEM-ключ; `operator-private.pem` (0600) никогда не должен попадать в git, исходный ZIP, release root или CI. Публичный PEM ключ публикуется/закрепляется через независимый доверенный канал. Ключ независимого оператора **обязательно другой**, чем Ed25519 ключ подписи релиза.

Пример выполнения только после фактической приёмки:

```bash
python3 scripts/operations/operations_ga_0460.py attest \
  --bundle /srv/launcher/staged-0.46.0 \
  --source-commit "$(git rev-parse HEAD)" \
  --install-receipt /srv/acceptance/install.json \
  --upgrade-receipt /srv/acceptance/upgrade.json \
  --restore-receipt /srv/acceptance/restore.json \
  --failover-receipt /srv/acceptance/failover.json \
  --operator-private-key /etc/launcher/operator-private.pem \
  --output-dir /srv/acceptance/signed
```

Инструмент повторно сверяет полную связность четырёх отчётов, версии, разных хостов source/restore, наличие аутентифицированного прежнего администратора, фактические шесть файлов и их SHA-256, а также обратную совместимость OpenAPI v1. Отчёты должны быть не старше 14 дней. Отчёт подписывает **именно оператор, записанный как secondOperator**, не первоначальный оператор. Итоговая подпись имеет domain separation и охватывает точные байты `OPERATIONS_GA_0460.json`.

Два созданных файла сохраняются вне публичной зоны до начала сборки. Сами четыре исходных свидетельства остаются в закрытом архиве оператора: в публичном утверждении присутствуют их криптографические хеши, а не пароли, machine-id или приватные журналы.

## 3. Строгая сборка и подписание

Предоставить штатному `scripts/release/build-release.sh` **два** новых параметра окружения:

```bash
export LAUNCHER_OPERATIONS_GA_EVIDENCE_DIR=/srv/acceptance/signed
export LAUNCHER_OPERATIONS_GA_TRUSTED_PUBLIC_KEY_FILE=/etc/launcher/operator-public.pem
```

Запускать штатную сборку с остальными обязательными ключами и внешними результатами GA согласно инструкциям [Signed Distribution](0.45.11-signed-distribution.md). Перед вычислением SHA256SUMS оба файла независимого свидетельства копируются в выпуск. Go `release build` проверяет их подпись, commit, версию, шесть фактических SHA-256 и включение обоих файлов в `RELEASE_MANIFEST.json` как обязательных артефактов. Тот же gate вызывается из **прямого `release sign`**, `release distribution-verify` и `release verify`. Подмена или удаление пакетов/отчётов либо отсутствие внешнего ключа приводит к отказу.

Сборка, защищённая Ed25519-подпись релиза, native signature checks и independent acceptance — разные свидетельства. `OPERATIONS_GA_0460.json` **не подтверждает само по себе** надёжность реального физического HA, нулевой RPO всех игровых операций, успешную игровую совместимость или факт внешней публикации. Эти проверки имеют собственные обязательные акты.

### Защищённый GitHub Actions production workflow

Для `production-release-candidate.yml` оператор после создания подписанных файлов устанавливает в защищённом environment `production-release` два GitHub Secrets: `NL_OPERATIONS_GA_JSON_B64` и `NL_OPERATIONS_GA_SIG_B64` (base64 от **точных** байтов обоих файлов), а также доверенную environment Variable `NL_OPERATIONS_GA_TRUSTED_PUBLIC_KEY_PEM` (публичный PEM ключ другого, независимого оператора). Private key в GitHub не загружается. Workflow устанавливает файлы с правами 0600, включает их в release bundle, затем воспроизводит все действующие release gates. Если любой секрет/ключ не передан, GA блокируется. Никакие unit-test fixtures не используются для обхода. Данные защищённого environment должны быть обновлены для конкретного commit и именно тех шести конечных пакетов; подпись от прошлого выпуска непригодна.

Для независимой проверки на другой машине доступна исполняемая команда:

```bash
python3 scripts/operations/operations_ga_0460.py verify-public \
  --bundle /srv/launcher/release-0.46.0 \
  --trusted-operator-public-key /etc/launcher/operator-public.pem \
  --release-public-key /etc/launcher/release-root-public.pem
```

Отдельный Python verifier используется также **до сетевой публикации** в `scripts/release/publish_0370.py`, даже если ранее собранный CLI не понимает gate 0.46.0. В нём выполняется проверка независимой подписи, BOM и всех шести конечных SHA-256, без обращения к mock HTTP. Применяется `cryptography>=42`.

## 4. Последняя независимая проверка и публикация

- На независимой машине заново выполнить `launcher release verify <bundle> --public-key <external-release-key>` с внешним операторским ключом через `LAUNCHER_OPERATIONS_GA_TRUSTED_PUBLIC_KEY_FILE`.
- Выполнить кроссплатформенную проверку готовых OS-подписанных пакетов на Windows/Linux/macOS x64/ARM64, включая установку, запуск и обновление.
- Опубликовать **те же байты**, которые прошли проверку. Скачать опубликованные файлы заново, сверить SHA256SUMS, доверенный корень, подписи и контрольный запуск. При изменении байтов пройти приёмку снова.
- Пройти реальное N−1/N испытание API и SDK на целевом backend. Статическая проверка OpenAPI в этом релизе не подменяет работающую интеграцию.
- Зафиксировать фактические RPO/RTO на стенде, конфигурацию и независимого исполнителя. `0` секунд для подтверждённых canary-записей не является доказательством нулевой потери всех игровых данных.

Отсутствие доступного второго оператора, внешних ключей, реальных хостов, подтверждённых OS-пакетов или результатов публикационного round-trip означает **GA BLOCKED**, а не условный PASS. Проект остаётся с исходной версией 0.46.0, но не должен объявляться независимо сертифицированным продуктовым GA.
