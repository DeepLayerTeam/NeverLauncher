# NeverLauncher 0.45.8 — Component Upgrade

Этот релиз добавляет **исполняемый контроллер** для замены программных компонентов.
Он использует существующие `dr_03512.py` (согласованный снимок), `launcher update components`
(подписанный транзакционный Desktop/Guard/Runtime updater) и `launcher extension updates`
(серверная транзакция с проверкой состояния расширений). Новая схема БД **не создаётся**,
работающий Minecraft-клиент **не заменяется** под видом API/SDK-заготовки.

## Порядок и границы

1. На тестовом клоне проверьте именно собранный release 0.45.8; нужен Go 1.27.3.
2. Сохраните отдельно действующие секреты, TLS-ключи, предыдущие доверенные пакеты,
   текущие образы и **внешнюю** копию БД/содержимого. Убедитесь, что второй оператор
   действительно может восстановить 0.45.7. Standard/HA DR не копирует TLS и секреты.
3. Остановите/ограничьте любые сторонние PostgreSQL/S3 writers и игровые узлы;
   сценарий не согласует их автоматически. Не допускайте команды обновления из
   пользовательского HTTP-запроса.
4. Серверное обновление выполняйте **до** обновления клиентов и расширений.
   Проверьте доступные протоколы и возможность подключения клиентов 0.45.7.
5. Выдайте ограниченный по времени доступ оператору, имеющему права на обновления
   расширений; для них нужен свежий MFA-согласованный токен.
6. Выпускайте Desktop/Runtime/Guard через уже существующий подписанный пакет
   для каждой ОС/архитектуры; никакой обход подписи либо `--allow-unpinned-development`
   контроллером не используется.

## Standard — API + Admin, холодный cutover

`--source-env` и `--target-env`: отдельные приватные (0600) файлы. Первый с
`LAUNCHER_IMAGE_TAG=0.45.7`, второй с `LAUNCHER_IMAGE_TAG=0.45.8` и
`LAUNCHER_DATABASE_AUTO_MIGRATE=false`; остальные настройки идентичны.
Backup должен быть вне production volumes в заранее созданном каталоге 0700.

```bash
sudo python3 scripts/operations/component_upgrade_0458.py standard \
  --project launcher-prod --confirm launcher-prod \
  --source-env /etc/launcher/source-0457.env \
  --target-env /etc/launcher/target-0458.env \
  --backup /srv/launcher/offhost-backups/component-0458 \
  --production-source --maintenance-approved
```

Реальные действия: проверка действующего `/ready` 0.45.7 → сборка новых Docker
образов API/Admin **до простоя** → проверка ID старых/новых образов → полный
cold `pg_dump -Fc` и проверенные снимки локальных volumes при остановленных
писателях → подтверждение неизменного PostgreSQL WAL → запуск нового API/Admin
с отключёнными миграциями → проверка 0.45.8 в самом API контейнере и HTML Admin →
публикация через Nginx последним шагом. При ошибке новая версия останавливается,
восстанавливаются старые образы и проверяется 0.45.7. Поскольку DDL не
производится, данные из backup **не перезаписываются** при обычном откате
компонентов — это могло бы потерять уже подтверждённые операции. Если старый
API не прошёл проверку, скрипт возвращает ошибку, а не выдаёт ложный успех.

Это не «нулевой downtime»: холодное окно обслуживания необходимо. TLS,
маршрутизатор, базы, пользовательские файлы и криптографические ключи не
заменяются по этому маршруту.

## Network-HA — оба API, workers, Admin

Это отдельный **холодный** маршрут, не rolling upgrade. Остановите **все**
записывающие игровые узлы и оформите снимки миров действительным Go world-backup;
их manifest должен иметь `confirmed-stopped`. Redis сохраняется для cutover
на текущем хосте, но не копируется как источник lease-состояния для DR.

```bash
sudo python3 scripts/operations/component_upgrade_0458.py network-ha \
  --project launcher-prod --confirm launcher-prod \
  --source-env /etc/launcher/source-0457.env \
  --target-env /etc/launcher/target-0458.env \
  --backup /srv/launcher/offhost-backups/ha-component-0458 \
  --world-backup survival=/srv/launcher/world-backups/0123456789abcdef0123456789abcdef \
  --s3-bucket launcher-production --s3-endpoint https://s3.example.com \
  --production-source --maintenance-approved
```

Команда использует Network-HA Compose overlay, создаёт проверенный PostgreSQL,
S3 и world checkpoint, останавливая API/worker/Nginx/Redis, затем запускает
Redis, оба API, обоих workers и Admin. Проверяются реальные `/ready` каждого API,
worker health и Admin; Nginx публикуется **после** них. При отказе запускаются
исходные образы и выполняются проверки 0.45.7. Если откат непроверен —
публичный доступ должен остаться выключен. Для нескольких физических хостов
оператор отдельно координирует их остановку; Compose не является
распределённым stop-the-world на произвольных хостах. Переключение внешних S3
ключей или PostgreSQL-миграции не включены.

## Minimal API, Linux CLI и ServerBridge

Инструмент `linux-host` предназначен для root-owned **реальных исполняемых
файлов**, не для установки через символическую ссылку на произвольный каталог.
Старый файл сохраняется рядом с суффиксом `.previous-0458`; после внезапного
падения процесса его можно вернуть отдельной исполняемой операцией; источник должен
быть root-owned, без права записи группой/остальными, и иметь отдельно
утверждённый SHA-256. Не запускайте параллельные обновления одного пути.

```bash
sudo python3 scripts/operations/component_upgrade_0458.py linux-host \
  --component api --service launcher.service \
  --source /opt/launcher/releases/0.45.8/bin/launcher-api \
  --install /usr/local/bin/launcher-api \
  --sha256 EXACT_APPROVED_SHA256 \
  --ready-url http://127.0.0.1:8080/ready

sudo python3 scripts/operations/component_upgrade_0458.py linux-host \
  --component cli --source /opt/launcher/releases/0.45.8/bin/launcher \
  --install /usr/local/bin/launcher --sha256 EXACT_APPROVED_SHA256

sudo python3 scripts/operations/component_upgrade_0458.py linux-host \
  --component bridge --service launcher-bridge.service \
  --source /opt/launcher/releases/0.45.8/bin/launcher \
  --install /usr/local/bin/launcher-bridge --sha256 EXACT_APPROVED_SHA256
```

После падения процесса обновления (или при решении вернуть прежний
выпуск) используйте точный SHA-256 **старого** бинарника. Команда проверяет
его байты, возвращает прежний файл, отдельно оставляет новый как
`.failed-0458`, проверяет `version` и, для minimal API, `/ready`. Без
подтверждения служба остаётся остановленной:

```bash
sudo python3 scripts/operations/component_upgrade_0458.py rollback-linux-host \
  --component cli --install /usr/local/bin/launcher \
  --previous-sha256 EXACT_APPROVED_0457_SHA256
```

Для minimal API инструмент требует активную `launcher.service` и реальную
готовность `/ready` c `version=0.45.8`; при ошибке возвращает прежний бинарник,
перезапускает службу и проверяет 0.45.7. Bridge проверяет `systemctl is-active`
и версию CLI; это **не** сертификат фактического game-server join. Важно:
`ExecStart` существующей службы должен ссылаться непосредственно на указанный
`--install` файл, а не на иной путь. Если Bridge использует Java-агент,
его JAR и совместимый серверный плагин обновляются отдельной штатной
процедурой ServerBridge с сохранением разрешений/ключей (этот Linux updater
не подменяет Java JAR и не считает его обновлённым).

## Desktop / Runtime / Guard: существующий подписанный updater

Выпускайте отдельный прошедший release gates пакет на каждую из шести целей:
Windows/Linux/macOS × x64/ARM64. Используйте фактический пакет, утверждённую
внешнюю SHA-256 и доверенный delivery manifest. Запускайте на клиентской машине
**после закрытия Desktop** (либо через поддерживаемый updater helper):

```bash
python3 scripts/operations/component_upgrade_0458.py client \
  --cli /opt/launcher/bin/launcher \
  --package /secure/releases/0.45.8-linux-x64.tar.gz \
  --sha256 EXACT_APPROVED_SHA256 \
  --delivery-manifest /secure/releases/DELIVERY_MANIFEST.json \
  --root /home/player/.local/share/launcher
```

Рабочий `launcher update components` проверяет SHA-256 пакета, доверенные
подписи, платформу, набор Desktop/Guard/Runtime и применяет транзакционное
обновление с rollback journal. Контроллер принимает только подтверждение
`status=committed`, `toVersion=0.45.8`. Требуется повторный запуск Desktop и
игровая acceptance-проверка на данной ОС; сам факт обновления файлов не
подтверждает работоспособность Minecraft/Guard. Для восстановления используйте
`launcher update recover --root <root>` и сохранённую ранее доверенную версию.

## Расширения: транзакция backend

Нужны HTTPS, установленный CLI и `LAUNCHER_TOKEN` с актуальной MFA-сессией.
Токен не указывается в командной строке. Указывайте точную версию каждого
расширения; не обновляйте без предварительной проверки несовместимостей и
capability approvals:

```bash
LAUNCHER_TOKEN_FILE=/private/path  # пример пути, не токен
export LAUNCHER_TOKEN="$(cat "$LAUNCHER_TOKEN_FILE")"
python3 scripts/operations/component_upgrade_0458.py extensions \
  --cli /usr/local/bin/launcher --backend https://launcher.example.com \
  --channel stable com.example.extension@1.4.0
unset LAUNCHER_TOKEN
```

Команда действительно выполняет `launcher extension updates plan` и `apply`.
Успех — только `transaction.status=succeeded`. При отказе обязан сработать
уже существующий серверный rollback/health manager; журнал транзакций остаётся
в API. Расширения, требующие новых разрешений, должны получить явное
операторское одобрение через штатный интерфейс, а не обход проверки.

## Приёмка и известные пределы

- Покрыты локальными Python-тестами: реальная запись/замена CLI executable,
  точное сохранение старых байтов, ошибочная версия, повреждённая SHA, cutover
  и возврат образов, HA overlay и отказ recovery, проверка ответов штатного
  updater/extension manager.
- Docker и Go 1.27.3 отсутствуют в доступном окружении разработки. Полный
  холодный cutover с живыми PostgreSQL/Redis/S3, обновление ServerBridge и
  Desktop на шести ОС **не были выполнены локально** и не получают фиктивный PASS.
- Перед production GA обязательно выполните сценарий на независимом стенде,
  зафиксируйте точные SHA конечных пакетов, RTO, подтверждение прежних API,
  состояние задач и фактический вход Minecraft/ServerBridge.
