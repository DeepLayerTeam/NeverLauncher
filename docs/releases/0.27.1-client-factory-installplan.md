# NeverLauncher 0.27.1 — Unified InstallPlan Engine

## What is implemented

`runtime client-factory build` is an executable, source-backed install engine, not a manifest generator. It delegates actual client installation to the same verified Mojang/Fabric/Quilt/Forge/NeoForge materializers already used by `runtime *-install`, records downloaded sources and Forge processors during their execution, then creates a canonical, verified InstallPlan.

- Resolves and pins exact Minecraft and loader versions. An existing factory lock always selects the recorded Minecraft and loader version; mutable selectors (`latest-release`, `latest-snapshot`, `latest-stable`) are not re-evaluated to pick new versions on replay.
- Preserves existing adapter-specific loader resolution locks and SHA-256 verification rather than implementing an independent downloader.
- Records input sources (URL, source SHA-1 where supplied, observed SHA-256, size and kind), resolved loader metadata identity, processor identities and verified outputs, Java major/processor executable digest, OS/arch targets, main class, version profile path, asset index and native directory.
- Hashes all managed output files by SHA-256 (including client, libraries, assets, natives, virtual resources and processed outputs); includes the deterministic ordered inventory and exact metadata in a canonical reproducibility digest.
- Performs installation and verification in a sibling staging directory; a build is promoted only after all adapter tasks, processors and full tree checks succeed. A failed build leaves the previously verified destination unmodified.
- On repeat builds verifies the previous lock and destination, copies the verified contents to staging without sharing writable hard links, replays the pinned adapters, and refuses to publish any output or runtime-identity drift.
- Does not import a pre-existing, unmanaged nonempty client folder into the factory automatically. Use a dedicated empty directory for the first build. Imported workspaces/modpacks are scheduled for later versions.

## Usage

Build Vanilla:

```bash
cd cli
go run ./cmd/neverlauncher runtime client-factory build \
  --loader vanilla --minecraft 1.21.1 \
  --target linux/x64 --client-dir /srv/neverlauncher/clients/example \
  --output /tmp/client-factory-result.json
```

Build Fabric (the requested loader version may be `latest-stable` **only on first build**):

```bash
go run ./cmd/neverlauncher runtime client-factory build \
  --loader fabric --minecraft 1.21.1 --loader-version latest-stable \
  --client-dir /srv/neverlauncher/clients/fabric
```

Build Forge/NeoForge:

```bash
go run ./cmd/neverlauncher runtime client-factory build \
  --loader neoforge --minecraft 1.21.1 --loader-version 21.1.105 \
  --java /opt/java/bin/java \
  --client-dir /srv/neverlauncher/clients/neoforge
```

Verify a previously completed installation **without downloading or running installers**:

```bash
go run ./cmd/neverlauncher runtime client-factory verify \
  --client-dir /srv/neverlauncher/clients/example --output -
```

Inspect the recorded plan and its identity (validates the lock, but does **not** rehash the tree; use `verify` for that):

```bash
go run ./cmd/neverlauncher runtime client-factory inspect \
  --client-dir /srv/neverlauncher/clients/example --output -
```

The authoritative lock and plan are stored together in `CLIENT_DIR/.neverlauncher/install-plan.json`. Its schema is `neverlauncher.client-factory.install-plan.v1`. It is an integrity receipt, **not a cryptographic publisher signature**.

## Safety and operational properties

1. Each factory destination has a separate sibling `.client-factory.lock` that prevents two concurrent builds from publishing the same tree. **After an unclean process exit this file may require operator inspection/removal**; do not remove it while a build is running. Automated crash recovery/worker control belongs to 0.27.3.
2. A first build rejects existing unmanaged files; repeat builds reject missing or modified output hashes, unknown extra files, symlinks and a modified loader resolution lock before touching the destination.
3. Processor execution remains the current Forge/NeoForge processor engine, including its validated outputs and journal. Full external-installer isolation and resource controls are a separate 0.27.3 milestone.
4. A completely different game version, loader or OS/architecture target needs a **different factory directory**. Changing existing lockfile content in place is rejected. This release does not silently update a published client.
5. `inspect` shows lock evidence and `verify` checks file digests; neither command certifies a real graphical Minecraft run. Client/server certification remains a later release gate.
6. Build inputs use existing strict URL / size / checksum validation. Avoid passing untrusted upstream URLs or manually editing lockfiles.

## Testing

The new `TestClientFactory0271*` suite exercises actual HTTP-backed materializer execution with local deterministic fixtures for Vanilla, Fabric, Quilt, Forge and NeoForge, including Forge/NeoForge processor output execution, pinned adapter replay, a mutable Minecraft selector changing upstream, tampered files/lockfiles and unmanaged/symlink output rejection.

The fixture tests do **not** establish real Mojang, Fabric, Quilt or Forge upstream availability and **do not** constitute successful graphical Minecraft client/server runs. Run the existing loader/processor unit suites as well as the dedicated CI job on Linux, macOS and Windows before considering this code for deployment. The full monorepo test suite and cross-platform signed delivery remain separate release conditions.

## What is deliberately deferred

- Worker isolation and general processor-step crash recovery (0.27.3)
- MirrorHelper command-level parity and modpack/local workspace import (0.27.4/0.27.5)
- Permission-aware/manual downloads (0.27.6)
- Advanced libraries/natives and legacy bridge adapters (0.27.7–0.27.9)
- Browser UI, independently versioned adapters and real client/server E2E (0.27.10–0.27.12)
