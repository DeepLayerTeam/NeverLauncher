# NeverLauncher 0.27.9 — Authlib & Classloader Compatibility

The 0.27.9 functionality is part of the actual Go Client Factory CLI and
uses its existing validated InstallPlan, sibling staging transaction and
atomic publication. It is not an alternative configuration-only installer.

## Apply verified classloader additions

1. Build and verify a client normally with `runtime client-factory build`.
2. Prepare local, legally obtainable JARs and calculate their SHA-256.
3. Create a strict JSON request, for example for an **existing Java 8
   legacy client**:

```json
{
  "schemaVersion": "neverlauncher.authlib-classloader.v1",
  "authMode": "official",
  "classpath": [
    {"path": ".neverlauncher/compat/classpath/bridge.jar", "sourceFile": "./bridge.jar", "sha256": "<64-character hex SHA-256>"}
  ],
  "javaAgents": [
    {"path": ".neverlauncher/compat/agents/injector.jar", "sourceFile": "./injector.jar", "sha256": "<64-character hex SHA-256>", "options": "https://auth.example.org/"}
  ]
}
```

`sourceFile` is resolved relative to the request JSON file; source files
are never consumed again at launch time. Replace the hashes with those of
real JARs; never use placeholders in an actual operation. Required files
must be ZIP-format Java archives and an agent must declare `Premain-Class`.

```bash
neverlauncher runtime client-factory compat-apply \
  --client-dir ./clients/legacy --file ./compat.json \
  --output ./compat-result.json
neverlauncher runtime client-factory compat-verify \
  --client-dir ./clients/legacy
neverlauncher runtime client-factory legacy-run \
  --client-dir ./clients/legacy --java /path/to/java8 \
  --username Player --uuid 00000000000000000000000000000000
```

`NEVERLAUNCHER_MINECRAFT_ACCESS_TOKEN` is read at runtime for official and
Yggdrasil authentication. An official-mode client refuses to run without
both token and UUID; offline-mode execution clears game argument placeholders
for the token. Nothing stores a token in the InstallPlan.

For explicit **Yggdrasil agent mode**, set `authMode` to `yggdrasil` and
pass `--allow-auth-agent true` to `compat-apply`. It requires a pinned agent;
this does **not** validate an external authentication service or grant rights
in any Minecraft account. Running unknown Java agents is a security risk.

For Java 9+ **nonlegacy metadata**, the same recipe supports `modulepath`
under `.neverlauncher/compat/modules/` and `addOpens` entries of the form
`java.base/java.lang=ALL-UNNAMED`. Java 8 plans reject both. The 0.27.9
built-in legacy executor cannot launch arbitrary Java 9+ Minecraft targets;
validating a modular compatibility receipt must not be confused with actual
modulepath runtime certification.

All rules are fail-closed. An already configured client cannot be silently
reconfigured in place. To change auth/classloader rules, create a fresh
build or explicit new release with a new identity.

## Verified authlib class overlays

`patch-authlib` retains the existing `--base-sha256`, `--patch-sha256`, and
`--expected-sha256` requirements and additionally saves:

- `.neverlauncher/compat/patches/<SHA-256>.jar`: the byte-for-byte patch JAR;
- `.neverlauncher/authlib-provenance.json`: exact before/patch/after hashes,
  rule identity and ordered history;
- updated immutable InstallPlan sources and output hashes.

Signatures in the original authlib JAR block byte-transforming overlays.
Unknown class paths, changed inputs, bad hashes, unexpected symlinks,
missing patch bytes or malformed provenance block release. This is an
explicit operator-controlled transform, not an auth bypass or assertion
that a patch is licensed for redistribution.

## Verification scope and remaining work

Tests include local source fixtures, actual Java CLI subprocess argument
execution, repeated immutable digest checks, stage rollback, native
Legacy Client Factory fixtures and cross-OS build validation. They do not
establish real Minecraft login, graphical client E2E, proprietary authlib
patch correctness, successful Cleanroom/lwjgl3ify Java 17 bridge, or a
modern modulepath Minecraft launch. Those require independently pinned
working adapters, allowed upstream files and runtime evidence.
