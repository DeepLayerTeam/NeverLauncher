# NeverLauncher 0.31.8: Signed Extension Sandbox Policy

This release enforces the signed policy at the package trust boundary and at each backend/CLI process launch. It **does not** implement OS sandboxing. `isolated` packages **cannot** run on 0.31.8, including after restart, if host capabilities are merely detected. `trusted` means unconfined OS access and is not labeled isolated.

## Signature binding and validation

`sandbox` is embedded in `neverlauncher-extension.json`, validated during registry normalization and parsed under strict JSON rules. Its canonical bytes are covered by the existing manifest SHA256, checksums, package identity and verified Ed25519 signature. Repackaging with a modified policy invalidates verification. No client setting or extension API can disable host-side validation.

Example:

```json
{
  "sandbox": {
    "version": "1",
    "mode": "isolated",
    "filesystemRead": ["package"],
    "filesystemWrite": ["scratch"],
    "networkOutbound": ["example.com:443"],
    "secrets": ["api_token"],
    "maxProcesses": 4,
    "maxMemoryBytes": 536870912,
    "maxCpuPercent": 50,
    "timeoutSeconds": 120
  }
}
```

These declarations describe future OS/broker grants only. **No filesystem, network, secret, CPU, or memory restrictions are enforced by this policy in 0.31.8**. Consequently the host refuses all `isolated` execution rather than falling back to `trusted`. `trusted` processes keep legacy unconfined privileges; administrators must only use them for code they trust at the OS level.

## Owner review on updates

The administrator compares the exact `fromVersion` and `version` using `GET /api/v1/admin/extensions/{extensionId}/permissions?scope=global&fromVersion=1.0.0&version=1.1.0`. The response includes `sandboxReview.required`, the signed target policy and `approvalDigest` bound to `{id, version, permissions, sandbox}`. The administrator must actively inspect the requested rights and supply the **exact** digest in the MFA-protected update call.

- `POST /api/v1/admin/extension-installs/{extensionId}/update` accepts `sandboxApprovalDigest` in the JSON request body.
- `POST /api/v1/admin/extension-updates/apply` accepts `sandboxApprovals` mapping extension IDs to digests for a multi-extension update.
- Unattended updates call `Apply` with no approvals and fail when any security-relevant policy changes. Previously granted capability permissions do **not** bypass this check.
- Direct `Manager.Update` and rollback also fail closed on changed security policies. Failed reviews do not replace active files.
- Review is required even for a policy that narrows access, to prevent silently changing sandbox execution expectations.

Updates retaining exactly the same sandbox and capability permissions remain unattended, subject to existing extension signing/trust gates.

## Compatibility and operational limitations

Older signed manifests without `sandbox` remain *legacy unconfined* and are not reclassified as isolated. New signed `trusted` mode is likewise not sandboxed. `isolated` packages can be installed in the disabled state, but enabling or launching them is rejected with `sandbox-unavailable`. Upgrading an enabled package to `isolated` is rejected prior to file activation; disable first. The native isolation boundaries and broker enforcement are targeted in 0.31.9–0.31.12. No claim about secure access limitations should be made until those engines have passed platform tests.
