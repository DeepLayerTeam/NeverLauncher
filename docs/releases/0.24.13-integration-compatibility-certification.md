# NeverLauncher 0.24.13 — Integration & Compatibility Certification

**Purpose:** executable regression testing of the actual signed Manifest v3 / Catalog v5 client pipeline, not an architecture proposal. **This source patch is not a certificate**: the final result depends on running compiled binaries and verifying real external attestation reports.

## Changes in the executing code

- `neverruntime verify|sync|sync-local --preset <signed-preset-id>` now resolves the **same** signed selected components as Desktop's staging and transactional installer; without `--preset`, the existing installed/default selection behavior is preserved. The command never alters the manifest or accepts locally supplied permissions.
- `scripts/certification/components_02413.py` signs a **temporary** v3 fixture through the production Rust `sign_manifest` implementation and executes the compiled `neverruntime` against a loopback-only HTTP fault server. It tests required-only/optimized/quality preset transitions, dependencies, selected file hashes, poisoned mirror fallback, real HTTP 503/truncated-transfer retry, user-owned file preservation, safe rollback/recovery, pre-download ownership conflicts, invalid public keys and signed-action tampering. A negative result returns nonzero and writes `status: failed`, never `passed`.
- `scripts/certification/record_02413.py` collects source/target-bound component and real Minecraft evidence. **It does not create NeverGuard or ServerBridge receipts**. Separate external reports with the current exact commit and target are required for those checks.
- `scripts/certification/gate_02413.py` fails closed unless six OS/arch targets have valid component tests, guard and join verification, and evidence from a real Mojang Minecraft process. Reports are not signed: independent clean-machine signatures remain governed by the existing 0.24.0 GA gate.
- `.github/workflows/certification-02413.yml` runs six platform runners with real Rust and Go builds, tests and a v3 download/selection/fault-injection scenario. For a **manual** run with `actual_minecraft=true`, it additionally invokes the existing real Mojang client certification harness. No dummy JVM or simulated successful launch is accepted. The final job will remain incomplete/fail until all required live Guard/Bridge receipts are collected.

```bash
# Requires Rust compiler and crate dependencies:
cargo test --manifest-path runtime/neverruntime/Cargo.toml --lib
cargo build --manifest-path runtime/neverruntime/Cargo.toml --bin neverruntime --example cert_sign_fixture
python3 scripts/certification/components_02413.py \
  --runtime runtime/neverruntime/target/debug/neverruntime \
  --signer runtime/neverruntime/target/debug/examples/cert_sign_fixture \

```

The fixture's deterministic signer seed belongs **only** to certification and may never be used as a release signing key. No official Minecraft account, server credential or NeverGuard private key is stored in the suite.

## Real Minecraft and compatibility matrix

The workflow matrix includes `linux`, `windows` and `macos`, both `x86_64` and `aarch64`. The `actual_minecraft` option launches the existing `run-vanilla-certification-case.sh` harness, which downloads a real Mojang Vanilla 1.21.1 installation and invokes the compiled NeverRuntime with Java 21, graphical software rendering where required. That path is **not** replaced by a fake-Java test; the result file must explicitly report `actualClient: true`.

Fabric/Quilt/Forge/NeoForge remain covered by the existing compatibility workflow and its real loader-specific launch cases. To certify *all declared presets*, run the game's actual signed profiles and loader-specific cases in addition to this v3 fixture. A dummy JAR in the v3 fault scenario is an integrity test, **not** proof that the JVM can load the mod.

## Release gate & limitations

To inspect available reports, run:

```bash
python3 scripts/certification/gate_02413.py \
  --commit "$(git rev-parse HEAD)" \
  --output dist/02413/aggregate.json \
  dist/02413/report-*.json
```

If any report is missing, any Java launch is not actually observed, the platform/commit differs, or a Guard/ServerBridge receipt is absent, **the gate fails with `status: incomplete`**. The default workflow cannot self-issue these receipts. They must be produced by separately running NeverGuard continuous attestation and real join-ticket/replay tests on the indicated platform and commit. Receipt JSON alone is not a cryptographic guarantee; the security release gate still demands independently signed clean-machine attestations.

For a complete GA the operator must additionally execute external physical/VM power-loss tests, confirm the six target installers' code signatures, exercise the entitlement-backed permissions configuration (known blocker since 0.24.4), validate real multiplayer admission with policy enforcement, and archive the results. Without these results, 0.24.13 remains **not certified for production**.
