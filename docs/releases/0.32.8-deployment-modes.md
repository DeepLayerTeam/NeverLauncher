# NeverLauncher 0.32.8 — Deployment Modes / DEP05

This release changes the **real API process startup**, not just a contract. The
selector and owner lock execute before PostgreSQL migrations, installation,
workers, or the HTTP listener. Existing production validation remains in force.

## Supported modes (no implicit downgrade)

| `NEVERLAUNCHER_DEPLOYMENT_MODE` | HTTP Repository | Coordinator | Files | Processes | Behaviour |
|---|---|---|---|---|---|
| `auto` (default) | detected | detected | detected | detected | Returns exact mode and reasons; never invents SQLite-only support |
| `standard` | PostgreSQL/pgx | SQLite WAL or Redis | local/S3 | 1 | Exclusive service lock; runtime checks coordinator/limiter health |
| `network-ha` | PostgreSQL/pgx | Redis | S3 | multiple | Requires HA lease policy and Redis, shared S3, no SQLite coordinator |
| `single-node` | SQLite HTTP Repository | SQLite WAL | local | 1 | **Blocked in 0.32.8**: SQLite Core CLI is not connected to the full API Repository |

A Standard deployment with an SQLite-backed coordinator **still requires
PostgreSQL** for the API. The name `single-node` is not silently redefined to
mean "Postgres + SQLite for rate limiting". HA topology detection is
configuration-based; actual Redis, Postgres and S3 health must pass at runtime.
A config that passes detection is not automatically a certified HA deployment:
actual lease/fencing/failover tests remain mandatory.

### Example: Standard, Redis-free coordinator

```dotenv
NEVERLAUNCHER_ENV=production
NEVERLAUNCHER_DEPLOYMENT_MODE=standard
NEVERLAUNCHER_REPOSITORY_DRIVER=postgres
NEVERLAUNCHER_SQL_DRIVER=pgx
NEVERLAUNCHER_DATABASE_DSN=postgres://.../neverlauncher?sslmode=verify-full
NEVERLAUNCHER_STORAGE_DRIVER=local
NEVERLAUNCHER_STORAGE_LOCAL_PATH=/var/lib/neverlauncher/storage
NEVERLAUNCHER_SINGLE_NODE_COORDINATOR_SQLITE_PATH=/var/lib/neverlauncher/coordinator/state.db
NEVERLAUNCHER_SERVERBRIDGE_HA_REQUIRED=false
NEVERLAUNCHER_RATE_LIMIT_ENABLED=true
NEVERLAUNCHER_RATE_LIMIT_FAIL_CLOSED=true
```

Supply all previously required production signing, auth, origins, and backup
parameters; the sample is *not* a complete deployment configuration.

### Example: Network/HA

```dotenv
NEVERLAUNCHER_ENV=production
NEVERLAUNCHER_DEPLOYMENT_MODE=network-ha
NEVERLAUNCHER_REPOSITORY_DRIVER=postgres
NEVERLAUNCHER_SQL_DRIVER=pgx
NEVERLAUNCHER_STORAGE_DRIVER=s3
NEVERLAUNCHER_REDIS_URL=redis://...
NEVERLAUNCHER_SERVERBRIDGE_HA_REQUIRED=true
NEVERLAUNCHER_RATE_LIMIT_ENABLED=true
NEVERLAUNCHER_RATE_LIMIT_FAIL_CLOSED=true
```

Supply PostgreSQL DSN, S3 credentials, production security settings and
independently tested cluster failover. No Network/HA approval is inferred from
config alone.

## Detection and operational checks

Run `neverlauncher-api diagnose deployment`. It outputs the resolved mode,
selection reasons, single-instance requirement, lock file path, and any policy
error as JSON without exposing DSNs or secrets. Exit code `0` means topology
and static production settings pass; exit `2` means they fail. This command is
**read-only** and deliberately does **not** claim dependency connectivity.
Actual startup opens PostgreSQL, performs its schema checks, opens the selected
coordinator/limiter (health required), then starts the HTTP API.

Before database migrations, Standard acquires `flock(LOCK_EX|LOCK_NB)` on a
private, service-owned regular file. For local storage it uses
`<storage-root>/.neverlauncher-api.owner.lock` and refuses a different lock
path for that shared storage. If Standard uses S3 and an SQLite coordinator,
the lock is anchored to `<coordinator-path>.api.owner.lock`. For Standard with
S3 and Redis, configure `NEVERLAUNCHER_DEPLOYMENT_LOCK_PATH` on a stable
persistent volume. Startup refuses lock conflicts, symlink traversal, unsafe
file permissions, an unwritable path, or unverified production filesystems.
The lock stays open until the API process ends. Never unlink a live/stale lock
file: only release its flock. A stale file does not mean the lock is held.

**Trust boundary:** `flock` cannot detect a second instance deliberately
pointed at unrelated paths/volumes. Run Standard with centrally managed
configuration and a single supervised API process. Do not treat local file
locking as a cross-host HA election. Multi-host installations require the
Network/HA architecture and its independently verified fencing.

## Tested and untested aspects

DEP05 tests cover automatic mode choice, explicit mode conflicts, memory
fallback prevention, lock permissions, symlink paths, second process blocked,
and reacquisition after graceful release. The new CI workflow must pass with
the repository's pinned Go toolchain and actual dependencies prior to release.
These changes **do not** connect the SQLite Core CLI to the HTTP Repository or
remove PostgreSQL from production. They do not certify full Network/HA
failover, nor resolve the remaining DEP01/DEP02 parity gaps.
