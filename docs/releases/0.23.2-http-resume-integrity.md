# NeverLauncher 0.23.2 — HTTP Resume & Integrity (D02)

## Execution path

The real NeverRuntime scheduler (`runtime/neverruntime/src/download_scheduler.rs`) invokes
`http_resume::download_verified` for every file in Desktop downloads and Repair. The
signed manifest and target ownership/path verification remain in the caller. No
extra backend endpoint, dummy manifest, or parallel downloader is introduced.

## Durable partials and HTTP semantics

- Partial bodies are written into `<installation>/.neverlauncher/downloads/<sha256(path)[0:2]>/<sha256(path)>.part`.
  The sibling `.part.json` is an fsynced, atomically published validator record containing
  the exact signed URL, size, SHA-256 and server ETag. Using the signed path as the
  internal key avoids accidental deletion of user-owned `*.part` siblings.
- On a subsequent run, a matching manifest object with a *strong* ETag and partial
  length strictly between zero and the signed length is resumed with `Range: bytes=N-`
  and `If-Range: "strong-tag"`. Weak ETags or absent validators are never used for
  ranged resume. In that case the incomplete partial is discarded and downloaded
  afresh. A fully downloaded partial can be installed without network access only
  after verifying the complete signed size and SHA-256.
- On HTTP 206, require identity encoding, exact strong ETag, `Content-Range`
  with the requested start and signed total, and `Content-Length` equal to the
  stated range length when supplied. Any invalid 206 is abandoned, the partial
  is discarded and a fresh unconditional GET is required.
- On HTTP 200 after a Range request (including an ignored If-Range or changed
  ETag), discard old bytes and treat only the complete response as the new object.
  On HTTP 416 discard the stale partial and issue a fresh unconditional GET.
  Fresh GET requires HTTP 200, identity encoding and a content length matching
  the signed size when present. No automatic redirects are permitted.
- Every received chunk is bounded by the advertised range/full signed length
  and persisted with awaited writes. Incomplete network bodies retain their
  partial and ETag for a future invocation; bytes are not activated yet.
- Full SHA-256 and size verification is mandatory before the same managed-file
  atomic replacement used by 0.23.1. A bad final hash deletes the partial and
  validator, leaving the previous installed file untouched. The reported
  transferred bytes count only body bytes consumed this invocation, not a
  reused prefix.
- A process-level per-target mutex prevents concurrent Desktop/Repair invocations
  from manipulating the same partial file in one NeverRuntime process. Concurrent
  downloads to different files still run under the scheduler's global/per-host
  limits. Coordinated multiple-process writer locking is not claimed in D02.

## Tests

`cargo test --manifest-path runtime/neverruntime/Cargo.toml http_resume -- --nocapture`

Tests use a local TCP HTTP server (no Internet) and simulate: truncated 200
followed by valid 206 with `Range`/`If-Range`, changed ETag with 200, invalid
206 range start, mismatched 206 validator, invalid 206 body length, HTTP 416,
wrong SHA-256 with preservation of the previous installed target, and weak
ETag rejection. The earlier scheduler's concurrent-download tests still apply.

### Additional verification before production release

```
cargo test --manifest-path runtime/neverruntime/Cargo.toml
cargo check --manifest-path runtime/neverruntime/Cargo.toml --all-targets
cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml
```

Execute real Desktop download/repair and clean-install tests on supported
Windows, Linux and macOS configurations. Static inspection alone does not
constitute confirmation of compilation, E2E success, or release certification.

## Excluded from D02

No automatic retry with jitter, persistent task queue/pause state, mirrors,
content-addressed artifact cache, multi-file transactions, or Managed Java
rework. Those belong to later roadmap milestones.
