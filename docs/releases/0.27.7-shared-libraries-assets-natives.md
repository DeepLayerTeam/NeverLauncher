# NeverLauncher 0.27.7 — Shared Libraries, Assets & Natives

0.27.7 introduces executable shared artifact caching and correct native archive materialization for multiple OS/architecture targets. The changes are in existing Vanilla, Fabric, Quilt, Forge/NeoForge and Client Factory materializers — **not** a new manifest-only plan.

## How to use

The shared store is **opt-in**. Choose a persistent directory **outside** the client installation directory, with write access restricted to the build operator:

```bash
neverlauncher runtime client-factory build \
  --loader vanilla --minecraft 1.21.1 \
  --client-dir ./clients/client-a \
  --target windows/x86_64,linux/x86_64 \
  --shared-cache-dir ./build-cache/artifacts
```

Use the same `--shared-cache-dir` with subsequent builds, including `runtime vanilla-install`, `fabric-install`, `quilt-install`, `forge-install`, `neoforge-install`, `client-factory import-modpack` and `client-factory apply-workspace`. Loader-specific commands inherit this option. The persistent store is keyed by upstream SHA-1, with SHA-256 verification as bytes are copied into independent client trees. It caches downloaded Mojang assets, verified Maven libraries and native JARs; it does not cache arbitrary unverified installers, account tokens, users' assets, or mutable metadata.

The `vanilla-install.json` report includes `sharedCacheHits` and each restored file includes `sharedCacheHit: true`. This is performance/accounting evidence, **not** release certification. Installation outputs and their SHA-256 remain pinned by the preexisting InstallPlan.

## Security and concurrency

- Every shared entry is checked against the expected SHA-1 and size before reuse and checked against both SHA-1 and SHA-256 while materializing the client copy.
- Entries are first written to temporary cache files, verified, then published via atomic create-if-absent hardlink; independent writers must confirm the winning entry's hash.
- Clients use **copies**, not shared mutable hardlinks. Modifying a client cannot mutate the shared cache or another client installation.
- Corrupt cache entries, unexpected file types, overlapping client/cache roots, and unknown native OS/architecture suffixes stop the build. There is no silent fallback to untrusted content.
- Staging, output checks, exact loader lockfile replay and atomic factory publication from 0.27.1–0.27.6 remain intact.

## Native OS/architecture

- An unqualified legacy native classifier (such as `natives-windows`) may be needed by both x86 and x86_64 targets. It is downloaded once and extracted separately for each target. This fixes the prior single-target overwrite in the task map.
- Explicit classifier suffixes are matched to x86/x86_64/arm/aarch64; unknown suffixes do not fall through to arbitrary architectures. Both `macos` and `osx` spellings are supported.
- If two native JARs contain the same extracted filename, extraction allows exactly identical bytes but **rejects conflicting content** rather than silently overwriting a DLL/shared object.
- Base Vanilla metadata containing incompatible versions of the same Maven group:artifact for an individual target is rejected prior to downloads; target-exclusive libraries and native classifiers remain supported. Custom Forge/loader classpaths are not indiscriminately deduplicated because their order can be significant.

## Scope and verification

Go fixture/integration tests exercise a complete real Vanilla materialization with Windows x86 + x86_64 natives, two independent client directories with a single cache, offline artifact endpoints, tampering, native conflicts, classpath conflicts and invalid cache paths. Run:

```bash
cd cli
go test ./cmd/neverlauncher -run 'TestSharedAssets0277|TestSharedArtifacts0277|TestNativeExtraction0277|TestNativeClassifier0277|TestVanillaLibraries0277' -count=1
```

Run broader Client Factory/loader/Forge regressions using the accompanying CI workflow. These checks are **not** equivalent to a real graphical Minecraft client start or client/server connection. Target-specific runtime certification remains on the 0.27.12 roadmap. A truly offline installation also requires pinned version metadata, installer/profile payloads and the client JAR, which are not all in this shared store.
