# NeverLauncher 0.45.1 — чистая Linux-установка Standard с TLS и первым администратором

## Границы поддерживаемого сценария

Рабочий путь версии 0.45.1: **Linux с Docker Engine + Compose v2, публичным DNS, доверенным TLS-сертификатом, PostgreSQL в Compose, локальным SQLite coordinator, API, Admin и Nginx**. Это Single-Host Standard, **не network-ha**, не SQLite-only и не автоматический ACME-продукт. Для network-ha остаётся существующий overlay, но первый администратор через новый инструмент обслуживается только в Standard.

Установщик реально запускает API и Admin, проверяет статус приложения и TLS снаружи по публичному адресу, а одноразовый bootstrap вызывает существующий backend и проверяет фактический вход под созданной учётной записью. **Без доступа к DNS/ACME/рабочему хосту нельзя заявлять выполнение боевой приёмки.**

## 1. Предварительные требования на чистом хосте

- Linux amd64 или arm64, Docker Engine и Compose v2, Python 3.10+, OpenSSL и доверенные системные корневые сертификаты. Пользователь с правами root для доступа к TLS-ключу и управления Docker.
- DNS `A`/`AAAA` направлены на узел; входящие TCP 80 и 443 разрешены (80 для ACME и редиректа, 443 для API/Admin). Для проверки HTTPS с самого хоста должен работать публичный DNS-маршрут; при отсутствии hairpin NAT проверка из внешнего окружения необходима, а успешная установка текущим скриптом будет заблокирована.
- Как минимум **2 GiB RAM** и **8 GiB свободного места на файловой системе Docker**, свободные внешние порты 80/443 на новом хосте. Внутренние 5432/8080 не публикуются наружу.
- Проверенные Guard и ServerBridge release policies из фактических подписанных артефактов. **Нельзя** использовать вымышленные allowlist и тестовые ключи для выпуска.
- TLS-сертификат для точного публичного hostname от доверенного CA, с полным цепочным файлом. Свои self-signed сертификаты в production отклоняются.

Пример для Ubuntu/Debian с уже установленными Docker Engine/Compose и Certbot; создание сертификата выполняется **до** первого запуска Compose:

```bash
sudo certbot certonly --standalone -d launcher.example.org
sudo install -d -m 0700 /etc/launcher/tls
sudo install -o root -g root -m 0644 /etc/letsencrypt/live/launcher.example.org/fullchain.pem /etc/launcher/tls/fullchain.pem
sudo install -o root -g root -m 0600 /etc/letsencrypt/live/launcher.example.org/privkey.pem /etc/launcher/tls/privkey.pem
```

Для любого иного ACME-клиента используйте аналогичные **обычные** файлы, не symlinks. Ключи и `.env` не добавлять в Git. После продления сертификата снова скопируйте файлы и пересоздайте контейнер `nginx`, поскольку bind mount файла может сохранить старый inode. Контролируйте обновление сертификатов отдельно; автоматизации ACME в 0.45.1 нет.

## 2. Подготовить production-конфигурацию

Из корня исходников версии 0.45.1:

```bash
cd deploy/production
sudo cp env.production.example .env
sudo chmod 0600 .env
sudo chown root:root .env
```

Заполните реальные, независимые секреты (`openssl rand -hex 32` / `openssl rand -hex 48`), параметры из собственного домена и проверенные политики:

```text
LAUNCHER_IMAGE_TAG=0.45.1
LAUNCHER_DEPLOYMENT_MODE=standard
LAUNCHER_PUBLIC_URL=https://launcher.example.org
LAUNCHER_WEBAUTHN_RP_ID=launcher.example.org
LAUNCHER_WEBAUTHN_ORIGINS=https://launcher.example.org
LAUNCHER_CORS_ALLOWED_ORIGINS=https://launcher.example.org
LAUNCHER_TLS_CERT_PATH=/etc/launcher/tls/fullchain.pem
LAUNCHER_TLS_KEY_PATH=/etc/launcher/tls/privkey.pem
LAUNCHER_HTTP_PORT=80
LAUNCHER_HTTPS_PORT=443
```

Далее обязательно задайте `POSTGRES_PASSWORD`, `LAUNCHER_BOOTSTRAP_TOKEN`, `LAUNCHER_AUTH_TOKEN_SECRET`, `LAUNCHER_MANIFEST_SIGNING_PRIVATE_KEY`, `LAUNCHER_GUARD_RELEASE_ALLOWLIST_JSON`, `LAUNCHER_BRIDGE_RELEASE_ALLOWLIST_JSON` и остальные параметры, применимые к вашему окружению. Значения в env-примере — **не** рабочие production-ключи. Не меняйте signing seed после выпуска подписанного клиента без процедуры ротации.

`LAUNCHER_BOOTSTRAP_TOKEN` — уникальный случайный токен не короче 32 символов. Нельзя хранить его в shell history или публиковать в отчётах. Обязательна только действительная выпущенная Guard/Bridge политика, а не просто произвольный JSON.

## 3. Проверить и запустить настоящие контейнеры

Команды выполняются **из корня репозитория**:

```bash
sudo python3 scripts/install/production-deploy.py compose check \
  --mode standard --env deploy/production/.env

sudo python3 scripts/install/production-deploy.py compose up \
  --mode standard --env deploy/production/.env
```

`compose check` проверяет Linux x64/ARM64, Docker daemon и Compose, RAM, диск, доступность портов на чистом хосте и использует OpenSSL для проверки имени сертификата, его срока действия (минимум 7 дней), доверенной цепочки и совпадения публичного ключа с приватным. Проверяет Compose-конфигурацию.

`compose up` реально строит и запускает образы PostgreSQL, API, Admin и Nginx. Ждёт контейнерных healthcheck, затем обращается к **публичному** `https://launcher.example.org/ready` с проверкой сертификата системным CA; проверяет `status=ready` и точную версию `0.45.1`. Только после этого сохраняет локальное состояние развёртывания. При ошибке **не пишет успешный статус**; запущенные контейнеры могут оставаться для диагностики.

Проверки оператора (из другого сетевого узла тоже):

```bash
curl --fail --show-error https://launcher.example.org/ready
curl -I http://launcher.example.org/
# Второй запрос должен перенаправить на https (HTTP 308).
```

На HTTP только `127.0.0.1/health` из контейнера доступен для внутреннего healthcheck. Извне приложение обслуживается только через HTTPS; Nginx отправляет `X-Forwarded-Proto: https` и перезаписывает `X-Forwarded-For` проверенным IP соединения.

## 4. Реально создать первого администратора

Пароль передаётся **только через приватный файл** (не в argv и не через URL). Под root:

```bash
sudo -i
umask 077
read -rsp 'Initial owner password: ' ADMIN_PASSWORD; echo
printf '%s' "$ADMIN_PASSWORD" > /root/launcher-initial-password
unset ADMIN_PASSWORD
python3 /path/to/NeverLauncher/scripts/install/production-deploy.py \
  compose first-admin --mode standard \
  --env /path/to/NeverLauncher/deploy/production/.env \
  --email owner@example.org --display-name Owner \
  --password-file /root/launcher-initial-password
rm -f /root/launcher-initial-password
exit
```

Нужны сложный пароль **минимум 12 символов**, приватный `.env` и файл пароля с правами `0600`. Не удаляйте файл до успешного завершения; после ошибки, возникшей после отправки bootstrap, не повторяйте вслепую. Инструмент проверяет live `/ready`, реальное состояние ещё не использованного bootstrap, выполняет `POST /api/v1/install/bootstrap-admin` c токеном в заголовке, проверяет, что token consumed и admin-user persisted, затем выполняет **реальный** парольный вход через `/api/v1/admin/login` по TLS. Access/refresh токены не печатаются и не записываются на диск.

**Процедура не повторяемая:** после успешного создания администратора повторное исполнение отклоняется. Если bootstrap создал администратора, но ответ HTTP потерян, изучите `/api/v1/install/readiness` и аудит; не пытайтесь сбросить базу или повторно запустить bootstrap.

После успешного входа войдите в Admin и создайте первый проект. Для полной готовности установки `GET /api/v1/install/readiness` должен показывать `installationCompleted: true`. Создание первого администратора само по себе не публикует игровой релиз и не создаёт проект.

## 5. Эксплуатационные границы

- Проверка `compose up` не заменяет проверки выпуска подписанных Desktop, Guard, Bridge и реального Minecraft join. Для этого существуют отдельные release/security/migration gates.
- Production Compose остаётся Standard/Single Host: не обещает отказоустойчивость при потере физического хоста. HA и DR испытываются отдельными версиями.
- Не меняйте пароль PostgreSQL на уже инициализированном volume без явной синхронной процедуры обновления роли БД: изменение `.env` не переписывает существующего пользователя.
- Перед обновлением версии необходимы проверенные копии БД, storage, секретов и внешних данных; `--backup-confirmed` — заявление оператора, а не автоматическая проверка копии.
- Отсутствие Docker, DNS, CA доверия, реального сертификата, подписанных allowlist или доступности публичного адреса блокирует установку; проект не переключается в test/insecure режим.
- Секреты Docker Compose доступны администраторам хоста через Docker API и `docker inspect`; доступ к Docker socket фактически эквивалентен доступу к ключам приложения.

## 6. Проверки кода и ограничения подтверждения

`python3 -m unittest discover -s scripts/install -p 'test_production*py' -v` проверяет управление жизненным циклом, сценарии bootstrap, запрещённое повторение, TLS fail-closed и отказ считать неподтверждённое развёртывание успешным. Конфигурация Nginx проверяется отдельно `nginx -t` с подставленными адресами upstream для стенда.

**Реальная приёмка хоста:** второй оператор должен выполнить шаги 1–4 на новом Linux с настоящим PostgreSQL, DNS и TLS, получить успешный login, затем перезапустить контейнеры и проверить сохранение администратора. В исходном тестовом окружении без Docker/production DNS и с неподходящей версией Go такой live результат не может быть заявлен. Его нужно получить на целевом хосте.
