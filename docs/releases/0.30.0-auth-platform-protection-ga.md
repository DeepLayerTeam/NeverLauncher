# NeverLauncher 0.30.0 — Auth Platform & Protection GA

## Delivered runtime behavior

This is a production-code increment over 0.29.12. All existing local/SQL/signed HTTP/OIDC/Microsoft connectors, canonical identities, MFA, protected sessions, Minecraft/ServerBridge revocation and banning remain part of the live code. The following changes apply to real request handlers rather than new placeholder endpoints:

- `POST /api/v1/auth/oidc/{providerId}/begin|complete`: 16 KiB bounded single JSON object only; duplicate/case-colliding keys, unknown fields and appended JSON fail with 400/413, before PKCE transaction/exchange. Same rules apply to Microsoft link begin/complete and a non-empty Microsoft logout-url body.
- `POST /api/v1/auth/providers/{providerId}/link/password`: signed-in linking requires a single unambiguous password proof; invalid input cannot reach the configured external connector.
- `POST /api/v1/auth/sessions/revoke|logout-all`, `POST /api/v1/admin/auth/sessions/revoke`, `POST /api/v1/admin/protection/users/{userId}/ban`: malformed/ambiguous bodies fail before mutations; 16 KiB returns HTTP 413. Self-service bulk revocation now requires a valid JSON body (`{}` is allowed and revokes all by explicit action); empty or malformed body is a 400 rather than being ignored and resulting in mass revocation. Clients should prefer `{"allExceptCurrent":true}` or `{"allExceptCurrent":false}` explicitly.
- Admin-managed auth provider activation checks every JSON object for duplicates and aliases, including nested secret references and issuer/provider config fields, before running the existing connector validation/probe and preserving the existing environment-variable-only secret policy. Configuration is now limited to 16 KiB.
- Mandatory protection handlers fail closed if they panic or exceed deadlines. Cancellation is checked before, between and after policy handlers, and a request that refers to a parent session denies if the host session store is missing. No panic text is exported to the caller. External handlers still execute synchronously and must honor the supplied context; they cannot be safely interrupted if they block forever.

## Executable certification and release gate

`.github/workflows/auth-platform-protection-ga-0300.yml` builds/vets production Backend, runs real loopback HTTP adversarial coverage, runs PostgreSQL 16 multi-replica refresh/replay and ban, tests cross-replica Postgres revocation/cascade, checks real PostgreSQL/MySQL 8.4/MariaDB 11.4 password adapters, exercises signed HTTP/OIDC/Microsoft integration provider SDK tests, checks the Backend/CLI migration catalogues, and builds Admin. The GA job is a required dependency for `.github/workflows/production-release-candidate.yml` release-bundle.

The gate invokes the real test runner and retains the JSON evidence. `scripts/ga/assert_go_test_0300.py` rejects a missing test, a skipped test, a failed test or failed package (including absent DSN/environment), rather than silently treating a skipped integration as success. External MariaDB/MySQL certificates, production Microsoft tenant, signed platform binaries and real Minecraft JVM/ServerBridge proofs are **not** synthesized by this workflow; existing separately protected release workflows remain mandatory.

### Local verification commands

```sh
python3 scripts/version/manage.py check
python3 -m unittest discover -s scripts/ga -p 'test_assert_go_test_0300.py' -v
cd services/api
go test -race -count=1 ./internal/authrequest ./pkg/protection
go test -race -count=1 ./internal/httpapi -run 'Test.*0300' -v
```

The last command requires third-party Go modules and a suitable build environment. A complete live PostgreSQL certification requires the disposable DSN variables defined in the GA workflow and all three SQL services running. **Do not use live production customer databases as E2E targets.** Passing the two dependency-free local packages is not equivalent to passing Auth GA or native Minecraft/runtime certification.

## Compatibility and rollback

No database migration, provider secret export or token format change is made in this release. Existing token revocation, expiry, binding, and protection behavior remains authoritative. Scripts or clients sending an empty body to destructive session-revocation routes must send `{}` or, preferably, the explicit `allExceptCurrent` field. JSON alias/duplicate configurations and inputs are intentionally rejected; normalize and resubmit configurations instead of weakening policy validation. A service rollback to 0.29.12 restores the earlier lenient decoding and is not a security-equivalent downgrade.
