# 0.23.11 — Release Generations & Anti-rollback

## Executable behavior

### Component security generation

Every new 0.23.11+ component package must carry `securityGeneration` (positive uint64)
inside `COMPONENT_UPDATE_MANIFEST.json`. `COMPONENT_SET_SIGNATURE.json` signs the
**exact manifest bytes**, including the generation, component hashes, the Guard,
Runtime, sensor and updater helper, and protocol requirements. Trust still comes
from the updater's **compiled-in Ed25519 root**, not the downloaded package.

Before touching live files, the external updater rejects a lower generation,
or the same generation with a different signed component-set manifest. An
identical signed set is permitted for idempotent repair. The updater additionally
compares the generation against the installed component state. It writes a
separate crash-safe two-slot high-watermark after a complete, verified update;
`update recover` reconciles a committed but not-yet-recorded generation only
**after hashing each installed component**. Local compatibility-state migration
must not discard a higher security generation.

The release signer needs `NEVERLAUNCHER_COMPONENT_SECURITY_GENERATION=<positive
integer>` (or an explicit `securityGeneration` in the pre-signing manifest) in
addition to its existing private signing seed and public-key pin. Allocate these
numbers monotonically through a trusted release process, **never** from
untrusted URL content or wall-clock timestamps. Reuse of a number with another
component set is rejected. The signer fails if the value is absent or invalid.

### Game release generation

Newly signed game packages receive `gameReleaseGeneration` from the API's
per-project / profile / channel sequence. The API serializes signing across
packages with a durable channel-scope mutation lease and checks against every
published generation at the publication boundary. Existing immutable legacy
releases remain readable; once a channel has published a protected generation,
a generation-zero release cannot be republished as its head.

`NeverRuntime` verifies the Ed25519 signature before install/repair/launch and
stores a separate, alternating game security-generation watermark after the
complete transaction is verified. An older signed manifest is rejected even if
all JARs remain available in SHA-256 cache or their content is unchanged.
Changing content while reusing the same generation is also rejected.

The existing administrative **durable channel rollback** copies the historical
storage objects into a **new release**, preserving file hashes and sizes. That
new manifest has a higher `gameReleaseGeneration` and a signed `rollbackSource`
containing the historical version, its own generation, and the SHA-256 of its
full signed manifest. Publication validates that this historical release was
published and that the new content really matches the historical paths, lengths,
SHA-256 and required/executable flags. This is not a local downgrade.

For protected releases, NeverRuntime's old explicit local `rollback` command
returns an error instructing administrators to publish a new authorized game
release instead. The transaction journal still restores the old intact file set
on an **interrupted, not-yet-completed** installation. User saves and untracked
mods are not in the managed deletion set.

## Migration and limitations

* Legacy component packages 0.23.10 and earlier remain installable only until a
  protected component generation has been accepted. Afterwards, their missing
  `securityGeneration` constitutes a downgrade and is rejected.
* Legacy game manifests without generation remain valid on unprotected fresh
  profiles; the first protected release establishes that installation's floor.
* The two-slot local watermark protects against ordinary failed commits, stale
  packages and accidental corruption. It is **not tamperproof against an
  administrator who deletes both watermark slots, active pointers and state**;
  that adversary would require an independent trusted monotonic anchor such as
  hardware-backed storage or an authenticated server-side device record.
* A crash after component commit but before recording its watermark requires
  verifying all installed binaries during recovery. No security floor is raised
  merely because the local state file claims a newer generation.
* Because game release rollback now must have a new signed generation, UI's
  previous local rollback action reports the server-publish requirement for
  protected installations.
