# NeverLauncher 0.29.3 — Provider Routing & Account Linking

## Live execution path

- `internal/httpapi/auth_accounts.go` calls `federation.Core.RoutePasswordProvider` before the per-identifier rate limiter, and passes **only** the resolved ID to `AuthenticatePassword`. The core independently revalidates the same route. No automatic failover exists for bad passwords, unavailable providers, authorization conflicts or missing links.
- `internal/federation/routing_0293.go` validates and installs one immutable policy from `NEVERLAUNCHER_AUTH_ROUTING_JSON` or `NEVERLAUNCHER_AUTH_ROUTING_FILE`. A non-existent provider, duplicate domain, invalid domain, or unsupported policy version prevents Backend startup. The default without configuration remains `local`.
- Existing browser login paths (`/api/v1/auth/oidc/{providerId}/...`) retain explicit provider routing and server-bound PKCE transaction. Cross-provider browser fallback is not introduced.
- Existing live password and browser linking APIs enforce `linkingAllowProviders` (when non-empty) or `disableLinking`, and linking refuses a disabled Never account. The account must already hold a Never session and prove possession of the external credentials. Microsoft-specific link handlers apply the same policy. Credential refresh of an **existing** linked identity uses `RefreshLinkedIdentity` with an exact persisted identity ID, and deliberately bypasses new-link restrictions while denying issuer, subject or owner changes. Identical email claims do not imply linkage. Collision of canonical `(provider, issuer, subject)` identities is rejected, including SQL uniqueness races.
- The existing Desktop authentication screen loads the public provider catalog, allows explicitly choosing a password provider (or automatic domain routing), and performs a live, authenticated password-proof linking request without persisting the external password. Browser/OIDC linking stays on the protected existing HTTP flow, not an unverified username shortcut.
- Linked identity issuer is emitted in successful password login responses. `GET /api/v1/auth/providers` exposes the effective default and explicit selection flag for client UI, without revealing configured email-domain routing rules.

## Example

```json
{
  "version": 1,
  "defaultProvider": "local",
  "requireExplicitProvider": true,
  "rules": [
    { "emailDomain": "corp.example", "providerId": "corp-sql", "strict": true }
  ],
  "linkingAllowProviders": ["corp-sql", "company-oidc"]
}
```

The `corp-sql` and `company-oidc` connectors must be configured before loading the routing policy. Password-only domain rules do not redirect a browser/OIDC flow. To disable all new account linking, use `disableLinking: true` instead of `linkingAllowProviders`.

## Upgrade and rollback

No schema migration is necessary; canonical issuer-aware identities from 0.29.1 are preserved. Keep routing absent for backward-compatible local default, deploy JSON or file only after configuring all referenced providers. Do not select an alternate weaker provider when the selected provider is unavailable. Rollback is a controlled configuration change followed by a Backend restart; if a strict route or allowlist is removed, explicitly review the resulting security-policy downgrade. Replacing `providerId` does not merge users. Audit denied logins through existing security/attempt events; avoid logging credentials, unverified claims or upstream tokens.
