# 0.30.3 — Java SDK Runtime APIs (implementation)

**Based on 0.30.2.** The existing Manifest `2.0`, Host Protocol `1.0`, Go `ExtensionHost`, EventBus, secrets grants and `nl x` administrator CLI remain authoritative; no alternate extension framework is introduced.

## Production code

- Go: `services/api/internal/extensionhost/runtime_store_0303.go` — durable, bounded JSON documents under `<ExtensionRoot>/runtime-data/<sha256(scope,scopeId,extensionId)>/`, atomic tempfile/sync/rename and permission checks for `runtime.config.{get,put,delete}`, `runtime.storage.{get,put,delete}`. Read and write grants are `storage:read` and `storage:write`. Access is audited through the existing host audit capability path. `secret.get` stays on the existing Go encrypted secrets broker.
- Java: `sdk/java/core` — new runtime services, `HostSession` capability handling and callback hello, event subscriptions and callbacks, schema validator, typed handler/decoder registration, scoped config/state, secrets callback with zeroed bytes, CLI command execution using declared manifest commands, bounded callback server with separate bearer token.
- Executable sample: `examples/extensions/java-runtime` — a real backend process subscribes to `release.published`, stores the version, and a different CLI JVM process returns it through the runtime `status` command. Both targets authenticate with the host. Package is signable with the existing CLI.
- Release metadata and corresponding tests/CI updated to `0.30.3`.

## Boundaries

- Client-side schema validation does not retroactively make existing corrupt/unschematized stored data safe; such data is rejected on read.
- Runtime document writes are per-key atomic, **not** multi-key transactional or compare-and-swap. For strong concurrency semantics use a future transactional API. Config and state should never contain secrets.
- `storage:read`/`storage:write` also protect other broker capabilities for project artifacts, which is intentionally broader than extension-local state; users must approve those permissions.
- The extension JVM and the Go host generally execute under the same OS user. Permissions in the Go broker do **not** constitute filesystem sandboxing. Native Windows executable wrappers and the separate Java Extension Host remain outside this release.
