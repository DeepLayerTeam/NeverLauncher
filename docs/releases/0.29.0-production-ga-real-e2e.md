# NeverLauncher 0.29.0 — Production GA & Real E2E

This change set is the **0.29.0 release candidate source**. A version bump and source checks are **not** proof of Production GA. Do not publish the release as certified until the exact-commit protected CI and external platform/runtime E2E finish successfully.

## Production corrections to real execution paths

- CLI and Backend now embed **identical immutable PostgreSQL migration chains** through `0080`. The missing `0067–0077` set made `nl db migrate apply` lag behind Backend auto-migration, risking an invalid installation. Existing migrations have not been rewritten.
- First-run CLI templates now use the same Docker Compose and production environment files as `deploy/production/`, including texture fetch policy and persistent client-factory storage.
- NeverRuntime's *actual verified/resumable HTTP path* (`durable_downloads → transactional_release → download_scheduler → http_resume → network_resilience`) now honors `Retry-After` and `X-RateLimit-Reset` on HTTP 429. Server wait hints are bounded; paused/cancelled downloads remain interruptible. The obsolete test assertions about unused download constants were replaced with assertions about the real retry implementation.
- Managed Java archive verification rejects symlinked archives, including symlinks with matching SHA-256/size. Cached Java continues to require a full inventory hash and a live `-version`/OS/architecture check. `repository-policy.py` now verifies these real execution paths and current Java record schema 1.3, rather than retired helper names or schema 1.2.

## Real Paper → backup → recovery test

The **full** `e2e/scripts/run-minecraft-e2e.sh` path (after a real Mojang client launch and Paper join) now executes `e2e/scripts/verify-real-world-backup-0290.py`:

1. Call `save-all flush` and `stop` through the test Paper's authenticated **internal-only** RCON. Require acknowledgement and clean exit; never infer world consistency solely from Docker SIGTERM.
2. Copy the *stopped real Paper container's* `/data` (not a fake JVM fixture). Require actual `level.dat`, persisted UUID playerdata and plugin configuration/data files.
3. Use the **built production CLI** `nl server-bridge host world-backup create --consistency stopped`, then `verify` and `restore` to a **new** directory.
4. Compare SHA-256 for every selected player and plugin data file. Confirm overwrite attempts are rejected. Return the real Paper service to healthy state.
5. Save `e2e/runtime/world-backup-0290.json`; `scripts/ga/verify_server_control_0290.py` independently rejects missing/invalid proof, missing join/replay/handoff evidence, incorrect source commit, missing UUID/plugin data, or absent healthy recovery.

The normal **compatibility** E2E mode does not claim full-world GA certification; only the `full` pipeline is allowed to produce 0.29.0 GA evidence. The exact-commit production candidate workflow downloads and verifies the artifact from the protected base CI before it can build a release bundle.

For actual GA, run the protected `ci.yml` **production-e2e** job with Docker, Java 21, Cargo, Gradle, Go, PostgreSQL, Redis, the signed server adapters and the actual Minecraft client. The `server-control-ga` job in `production-release-candidate.yml` must then validate `world-backup-0290.json` at the exact commit SHA.

## What is *not* certified by this source archive

- A real runtime with Docker/Java and an authenticated Minecraft client was **not available in the packaging environment**; the real Paper E2E code could not be executed there.
- Full Backend API/Redis/PostgreSQL multi-replica chaos and user-facing browser Admin E2E were not completed locally. For a production release, verify command fencing after lost ACK, Host/backend crash isolation and a complete Admin create → connect → join → drain → save → update → verify → reopen flow on live infrastructure.
- A real systemd PID 1 host deployment and Windows service lifecycle need platform testing. The previous detached Host and service-management constraints remain.
- The world test verifies actual saved UUID file bytes and plugin data bytes across restoration, **not a subsequent player's loaded inventory inside a restarted Minecraft session**. Such a post-restore gameplay assertion is still required before claiming the full roadmap acceptance criteria.

Do not manually set an E2E PASS flag, hand-write production evidence, or override missing runtime tests. A failing or unexecuted gate remains a release blocker.
