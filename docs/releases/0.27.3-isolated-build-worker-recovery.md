# NeverLauncher 0.27.3 — Isolated Build Worker & Recovery

## Execution path (production source)

`forge-install`, `neoforge-install` and `runtime client-factory build --loader forge|neoforge` invoke **the actual existing install materializers**. Forge/NeoForge processor steps now use `runIsolatedProcessor0273`; this launches the CLI binary as an internal, short-lived worker subprocess and passes one private, bounded JSON job through stdin. That worker invokes the *real* Java processor JAR and returns the actual status. The main CLI does not execute processor JVMs directly.

Each attempt saves a root-local, 0600-permission diagnostic log at `.neverlauncher/worker-logs/processor-NNN.log`, capped at 2 MiB (plus a trailing exit marker), and a processor journal under the installer cache. Log paths are present in journal entries. Logs and journals are excluded from Client Factory's reproducibility output hashes. Logs can contain installer output; restrict access accordingly.

### CPU, heap, filesystem and cancellation

- Parent wall-clock timeout: `--processor-timeout 10m` (1s–1h), with cancellation and process-tree termination. Linux/macOS kill the worker process group; Windows uses `taskkill /T /F` as a best-effort tree cleanup.
- The child worker sanitizes its environment: no NeverLauncher token, cloud secret, Java tool-injection flags, or arbitrary application env variables are forwarded. Temp directory is isolated per attempt and deleted afterwards. The processor Java JVM receives a `-Xmx2048m` maximum heap.
- Linux/macOS set CPU-time, 2-GiB file-size, file-descriptor and core-dump rlimits in the short-lived worker. These limits **do not** provide a complete RSS memory limit; `-Xmx` bounds Java heap, not every native allocation.
- `--processor-sandbox process` (default): subprocess, environment, OS limits and lifetime isolation. **Not a network or filesystem sandbox.** Compatible with fixtures and existing installations on all supported platforms.
- `--processor-sandbox required` (Linux only): require installed `bwrap` (bubblewrap) *and* working user/mount/network namespaces. The worker uses a private root, no host home/secrets mount, no network, read-only OS/JDK runtime mounts, and binds only the client tree writable. There is no fallback to `process` if strict isolation cannot be enforced. This may reject installers that download network content or use unlisted host resources; upstream downloads should be resolved by NeverLauncher before processor execution.

**Important:** bubblewrap may be unavailable on hardened CI/container hosts; this environment has no bwrap and blocks Linux user namespaces. The strict mode has a fail-closed test here, but a successful namespaced execution still requires certification on an appropriately configured Linux build host. macOS/Windows lack an equivalent strict sandbox in 0.27.3: use a dedicated, OS-isolated build node for untrusted JARs rather than assuming process mode is a security boundary.

### Commands

```sh
cd cli
# Working subprocess isolation and recoverable journal
 go run ./cmd/neverlauncher runtime client-factory build \
  --loader forge --minecraft 1.21.1 --loader-version 52.0.1 \
  --client-dir /srv/neverlauncher/clients/forge-1.21.1 \
  --processor-timeout 10m --processor-sandbox process

# Host where Linux bubblewrap and namespaces are available:
 go run ./cmd/neverlauncher runtime forge-install \
  --minecraft 1.21.1 --loader-version 52.0.1 \
  --client-dir /srv/neverlauncher/builds/forge \
  --processor-sandbox required
```

### Recovery guarantees

1. Existing verified Forge/NeoForge input JARs, Java executable, installer binary, exact processor instructions and required outputs are content-fingerprinted. Journal schema 1.1 includes `inputSha256` and `workerLogPath` per processor.
2. An interrupted or failed step with **correct, independently verifiable** output digests and unchanged input JAR digests can be committed without rerun. If hashes or input identity disagree, outputs are quarantined and rebuilt. Missing outputs are never marked completed.
3. Corrupt/mismatched old journals are quarantined, never used as trusted receipts. Outputs are checked for symlink and root traversal before reading. Every processor start/failure/completion is persisted atomically.
4. Client Factory's sibling staging and SHA-256 verification still gate publication; an errored step never publishes a partially built client.

### Test scope

Offline real-subprocess tests exercise secret-scrubbed environment, worker stdout logs, cancellation with a background child process, missing strict-sandbox fail-closed behavior, processor input changes, corrupt output quarantine, symlink rejection, and full Forge/NeoForge/Client Factory fixture installations. Cross-platform *builds* verify compilation; they do not certify Windows/macOS runtime termination and JVM behavior. Full repository tests, live upstream installers, external bubblewrap namespace execution and graphical Minecraft launch are independent release certification gates.
