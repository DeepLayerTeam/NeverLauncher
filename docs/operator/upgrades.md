# Обновление компонентов и безопасный возврат

**Не обновляйте все слои одновременно, пока восстановление не проверено на отдельном стенде.** Для каждого релиза проверяйте исходный коммит, SHA-256, подписи, версии API/Bridge/Desktop/SDK, совместимость схем, доступность резервной копии и свободное место. Откат приложения не равен откату схемы: восстановление БД делается из **согласованного** снимка, а не переписыванием применённых миграций.

## SQLite Minimal / переход на PostgreSQL

Оператор выполняет команды существующего `db_upgrade_0457.py`, а не ручной SQL. Он использует реальный мигратор API, модуль службы systemd, полное резервирование, проверку новой схемы и восстановление прежнего состояния при ошибке. Обязательные аргументы и контролируемый сценарий приведены в [Database Upgrade](../releases/0.45.7-database-upgrade.md).

```sh
python3 scripts/operations/db_upgrade_0457.py sqlite --help
python3 scripts/operations/db_upgrade_0457.py postgres --help
```

Для PostgreSQL перед запуском требуется остановка писателей, отдельные `--source-env`/`--target-env`, `--snapshot`, точное подтверждение `--project`/`--confirm` и `--maintenance-approved`; запишите проверенную предыдущую версию. Нельзя выполнять миграцию под живыми mixed-version API/worker репликами.

## API/Admin/CLI/ServerBridge/клиенты/расширения

```sh
python3 scripts/operations/component_upgrade_0458.py standard --help
python3 scripts/operations/component_upgrade_0458.py network-ha --help
python3 scripts/operations/component_upgrade_0458.py linux-host --help
python3 scripts/operations/component_upgrade_0458.py rollback-linux-host --help
python3 scripts/operations/component_upgrade_0458.py client --help
python3 scripts/operations/component_upgrade_0458.py extensions --help
```

- **Standard API/Admin:** остановить writers; сделать полную Standard копию, собрать образы до простоя, переключить теги, проверить фактический digest контейнеров и `/ready`; при ошибке восстановить образы и согласованную БД.
- **Network-HA:** холодное переключение обоих API, обоих workers и Admin; новые миграции выполняются единожды до возвращения writes. Нужны снимки состояния PostgreSQL/S3/миров и проверка fencing. Смешанные версии не считаются HA.
- **Minimal API/CLI/Bridge:** проверить бинарный SHA-256 и права владельца; атомарно заменить файл с сохранением предыдущего; ServerBridge требует явный модуль службы systemd. Используйте существующий `rollback-linux-host` после ошибки или прерванного переключения.
- **Desktop/Runtime/Guard:** обновление только через штатную проверку подписанного манифеста поставки и транзакционный механизм обновления; повреждённый пакет должен оставлять предыдущий активный слот.
- **Расширения:** обновление через транзакцию backend, проверка статуса и health, откат при сбое; не загружайте недоверенные Java JAR или нативный код как «песочницу».

Полные исполняемые команды (включая обязательные ключи подтверждения и ожидание готовности) см. в [Component Upgrade](../releases/0.45.8-component-upgrade.md) и [Branding GA](../releases/0.45.10-branding-ga.md).

## Условия разрешения трафика после обновления

Проверьте `/ready` реального API, результаты `operator_accept_04513.py live`, вход прежнего владельца, чтение проекта и двоичных объектов, защиту заданий ServerBridge от устаревших исполнителей, выпуск и откат тестовой сборки, загрузку клиента и подключение к Minecraft. Если миграция восстановлена из копии, отдельно сверяйте момент последней подтверждённой записи и возможные потерянные данные. Любое `NOT RUN` остаётся незавершённым критерием приёмки, даже если версия бинарника уже 0.45.14.
