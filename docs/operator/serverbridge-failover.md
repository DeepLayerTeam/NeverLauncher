# ServerBridge 0.51.5: реальное восстановление команд, событий и управления

## Цепочка безопасности

1. Зафиксируйте неизменяемые `LAUNCHER_BACKEND_URLS` из двух действующих HTTPS API узлов с общей PostgreSQL базой, действующим идентификатором узла Ed25519 и корректным закреплённым публичным ключом серверного API. Не создавайте вторую идентичность для старого игрового узла и не копируйте закрытый ключ на произвольные машины.
2. Управляющий канал подтверждает исполнение лишь после `BridgeControlJournal.begin` (fsync) и `complete` (fsync) на игровом хосте. При потере HTTP-ACK журнал передаёт ту же квитанцию на другой узел API. Смена узла серверного API не вызывает повторного исполнения JVM операции.
3. PostgreSQL привязывает доставку к `(server, runtime, channel, token, sequence)`. В 0.51.5 время выдачи и истечения аренды берётся в транзакции PostgreSQL, а не из часов отдельных API. Истёкшая доставка переходит в `indeterminate`, не возвращается в `pending`; поздняя проверенная квитанция принимается только с **исходными** токенами доставки.
4. Поток событий не удаляет записи при отсутствии согласованной возможности протокола: журнал удерживает подписанные события и повторяет отправку до настоящего `ackSequence` от серверного API. Изменение `runtimeId` после рестарта JVM архивирует неподтверждённый журнал прежней среды выполнения; эти события **не** объявляются доставленными. Проверьте `event-stream.journal.stale-*` при инциденте.

## Восстановление удалённого управления хостом после потери ответа

На исходной машине оператора, имеющей сертификат центра сертификации (CA) и секретный служебный токен, повторите только **чтение** результата с первоначальным ключом:

```bash
nl server-bridge host remote call \
  --url https://game-host.example:9443 \
  --ca-file /etc/launcher/remote-ca.pem \
  --token-file /run/secrets/remote-agent-token \
  --action receipt \
  --idempotency-key <original-command-idempotency-key> \
  --output /var/lib/launcher/recovered-receipt.json
```

`receipt` обращается только к `GET /v1/host/receipts/{key}`. Права: `host.status` **и** соответствующий `host.start|host.stop|host.restart`; исходный subject должен совпадать. Запрос не может запускать JVM. Он работает при восстановленном TLS доступе к исходному агенту и его приватному локальному журналу. При уничтожении диска хоста без журнала автоматическое «успешное» восстановление невозможно. `indeterminate` требует ручной проверки состояния миров, процесса и аудита до любых новых операций.

## Обязательная приёмка до объявления HA GA

- Два API экземпляра с отдельными часами (в тесте ±6 часов) и одной PostgreSQL: выдача через A, подтверждение исходной доставки через B, отказ каналу C, отсутствие второй команды после истечения срока аренды.
- Отключение сети между игровым узлом и API после фактического исполнения команды: JVM не повторяет команду; журнал упреждающей записи управляющих операций (WAL) переживает перезапуск; подтверждение возвращается после восстановления соединения.
- Версия серверного API без `events.ordered-stream-v1`: журнал событий не сокращается и не выдаёт фиктивный ACK. После восстановления совместимой версии серверного API действительное подтверждение продвигает курсор.
- Удалённый хост по TLS: потерян ответ POST, затем через GET получена исходная квитанция; команда на хосте исполнена ровно один раз. Без сертификата CA, требуемой области доступа или исходного ключа идемпотентности запрос отклоняется.
- Настоящие Paper/Velocity/Folia/модовые JVM, потеря игрового хоста и согласованное восстановление миров на другом устройстве — **BLOCKED**, пока не выполнены независимые прогоны. Этот код не переносит состояние игрового мира в оперативной памяти без остановки.
