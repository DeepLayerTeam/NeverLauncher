# 0.37.8: минимальный сервер SQLite — интеграционная приёмка на реальном стенде

`minimal-live-e2e-0378` в `.github/workflows/ci.yml` — обязательная, **не симулированная** проверка с реальным бинарником `launcher-api` на Linux и постоянными SQLite-файлами. Работа не считается выполненной по прохождению локальных модульных тестов Python: они проверяют только надёжность исполнителя CI.

## Что реально исполняется в CI

1. Сборка сервера Go из исходников с проверяемым SHA коммита; проверка совместимой локальной файловой системы.
2. Чистый `minimal-install.py init/check/run` без PostgreSQL/Redis, с приватными путями, изолированным HTTP listener и конфигурационными правилами безопасности.
3. Проверка `/ready`, мастера, отсутствия предустановленного администратора; отказ bootstrap без токена и повторного bootstrap; создание администратора, реальный вход по паролю, создание первого проекта/черновика. Черновик не должен отдаваться через манифест стабильного канала.
4. Отказ второго экземпляра Backend и блокировка резервного копирования при работающем API.
5. Штатный `SIGTERM` → новый процесс → проверка состояния и ротации токена обновления.
6. Безусловный `SIGKILL` после подтверждённой записи → новый процесс → проверка уже подтверждённого состояния и токена обновления.
7. Остановка всех процессов записи → резервное копирование двух баз SQLite и файлов проекта → SHA-256 и проверка целостности SQLite → восстановление в новый каталог → повторный запуск реальной серверной части → вход прежнего владельца и сохранение состояния одноразовой начальной настройки.
8. Повреждение SQLite-хеша доменной модели: серверная часть обязана отказаться от запуска. Изменение файла резервной копии: проверка и восстановление должны завершиться отказом, без создания целевого каталога.

## Фиксация результата

Исполнитель CI записывает `nl-live-evidence-0378.json` со статусом `passed` только после **всех** проверок, хешом бинарника и SHA коммита. На ошибке пишет `blocked` и завершается с ненулевым кодом. `required-ci` зависит от `minimal-live-e2e-0378`; отсутствующее, пропущенное или неуспешное задание блокирует итоговый CI. Отчёт не содержит паролей, токенов или ключей. Процессные логи имеют права `0600`, остаются у исполнителя CI и не загружаются в публичные артефакты.

CI создаёт изолированные **тестовые** файлы списков разрешений Guard/Bridge только для проверки обработки промышленной конфигурации; эти значения **не являются** подписями, свидетельствами проверенного клиента или разрешением публикации в стабильном канале. Проверка подтверждает, что черновик **не** публикуется самостоятельно. Она **не** подтверждает GA, запуск Minecraft, реальную аттестацию Guard/Bridge, драйверы PostgreSQL или HA.

Для ручного прогона понадобятся собранный API, реальные файлы конфигурационных политик и пустой приватный каталог на Linux с локальной FS:

```bash
python3 scripts/acceptance/minimal_live_e2e_0378.py \
  --binary /opt/launcher/bin/launcher-api \
  --guard-policy /secure/guard-policy.json \
  --bridge-policy /secure/bridge-policy.json \
  --work-root /private/empty-e2e-directory \
  --report /private/acceptance/minimal-0378.json
```

**Ограничение окружения разработки:** результаты живого E2E подтверждаются только успешным запуском на требуемой версии Go и Linux-файловой системе, а не фактом наличия данного узла CI или конфигурации YAML.
