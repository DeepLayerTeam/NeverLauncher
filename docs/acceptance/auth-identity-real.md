# NeverLauncher 0.52.5 — приёмка авторизации и идентификации

## Изменения промышленной реализации

- Вход OIDC и оба сценария завершения привязки через браузер — Microsoft и универсальный провайдер — теперь **атомарно расходуют** состояние зашифрованной транзакции через существующее постоянное хранилище PostgreSQL `used_nonces` либо координатор SQLite **до** обмена кода издателя. Однократность обеспечивается между репликами API. Отклоняются параллельное повторное использование, повторное запечатывание того же состояния, применение украденного состояния привязки к конечной точке входа и недоступное долговременное хранилище.
- При завершении OIDC нельзя изменить идентичность устройства, закреплённую при начале процедуры. Для браузерной привязки необходима повторная авторизация в течение последних 15 минут. Конечные точки привязки разбирают JSON со строгими ограничениями и отклоняют повторяющиеся либо неизвестные ключи.
- Секрет провайдера и код авторизации не сохраняются в записи одноразового идентификатора; метаданные ограничены провайдером и типом операции. После расходования состояния и сбоя вышестоящего сервиса повторить запрос нельзя: начните новую авторизацию в браузере.

## Реальный операторский запуск (только выделенный тестовый стенд)

Тест **изменяет** привязки идентичностей и **отзывает** сеансы. Его **ЗАПРЕЩЕНО** запускать на личных аккаунтах Microsoft, промышленных клиентских учётных записях, общих идентичностях или обычных развёртываниях. Используйте отдельный максимально приближенный к промышленному HTTPS Backend с PostgreSQL, работающим настоящим SQL-коннектором авторизации, локальным провайдером, реальным издателем OIDC или Microsoft и двумя независимыми одноразовыми аккаунтами Never. Требуются приобретённые оператором права Minecraft Java. Нативный Desktop получает действительный токен доступа Minecraft по настоящей цепочке Microsoft → Xbox → XSTS → Minecraft. Секреты не должны попадать в переменные CI, аргументы CLI и журналы.

Подготовьте абсолютный путь к JSON-файлу, доступному только владельцу (режим `0600`):

```json
{
  "scope": "dedicated-disposable-accounts",
  "allowIdentityMutation": true,
  "origin": "https://staging.example.org",
  "local": {"providerId":"local", "identifier":"owner@example.org", "password":"<PRIVATE_PASSWORD>"},
  "secondary": {"providerId":"local", "identifier":"second@example.org", "password":"<PRIVATE_PASSWORD>"},
  "sql": {"providerId":"sql", "identifier":"sql-account@example.org", "password":"<PRIVATE_PASSWORD>"},
  "oidc": {"providerId":"oidc", "kind":"generic"},
  "official": {"userType":"msa", "authServerBaseUrl":"", "username":"LicensedTestPlayer", "uuid":"0123456789abcdef0123456789abcdef", "accessToken":"<PRIVATE_MINECRAFT_BEARER>"}
}
```

Для коннектора Microsoft OIDC используйте `"kind":"microsoft"`. Если для тестового входа требуется TOTP, добавьте соответствующий `"totpSecret"`. У владельца уже должны быть права для привязки внешних провайдеров. Настоящий SQL-аккаунт необходимо настроить так, чтобы явная привязка вела к тому же каноническому пользователю, а не к отдельно автоматически созданному. Второй аккаунт Never должен принадлежать другому каноническому идентификатору пользователя. Права тестовых ролей необходимо настроить так, чтобы обычный игрок не мог читать административные роли.

1. Подготовьте аккаунты, настоящего внешнего издателя и требуемые учётные данные через защищённый канал оператора. Примените миграции БД, включите HTTPS и ограничьте тестовые идентичности изолированным проектом.
2. На изолированной машине оператора выполните:

   ```sh
   umask 077
   python3 scripts/acceptance/auth_identity_real_0525.py prepare-oidc \
     --secrets /secure/auth-0525-secrets.json \
     --output /secure/auth-0525-oidc-proof.json
   ```
3. Откройте **оба** HTTPS-адреса авторизации из закрытого файла подтверждения в настоящих браузерах. Авторизуйтесь одной и той же контролируемой внешней учётной записью и скопируйте выданный провайдером `code` в поля `link.code` и `login.code` соответственно. Не изменяйте `state`, `transaction`, `generatedAt`, `ownerSha256`. Срок действия — десять минут. Никогда не отправляйте этот файл в GitHub или отчёты.
4. Сразу после этого выполните:

   ```sh
   python3 scripts/acceptance/auth_identity_real_0525.py run \
     --secrets /secure/auth-0525-secrets.json \
     --oidc-proof /secure/auth-0525-oidc-proof.json \
     --source-commit "<exact_40_hex_commit>" \
     --api-package-sha256 "<independently_pinned_64_hex_backend_package_sha256>" \
     --output /secure/auth-0525-report.json
   ```
5. Сохраните **очищенный от секретов** отчёт с нативной платформой, коммитом, хешами релизных артефактов, журналами и независимой подписью оператора в отдельно управляемом процессе сбора доказательств версии 0.52.1. Отчёт одного этого скрипта **не является** сертификатом GA.

Сначала проверяются фактическая версия Backend (0.52.5), исходный коммит, указанный оператором, и независимо закреплённый хеш дистрибутива; результаты фиксируются в закрытом отчёте. Для успешного запуска необходимы наблюдения по 13 группам: действительный локальный вход и неверный пароль; независимый аккаунт; привязка SQL-идентичности по паролю и вход; два настоящих браузерных/OIDC-сценария с отклонением повторного использования; настоящий профиль Minecraft Services, присоединение и `hasJoined`; привязка официального UUID и изоляция владельца; запрет чужой привязки/отвязки; соблюдение ролей; долговременная отвязка; отзыв семейства токенов при повторном refresh; выход. Недостающие результаты, некорректные учётные данные, отсутствующий провайдер, просроченные коды, ошибка HTTPS или принятие повторного запроса **блокируют** завершение. Скрипт никогда не подменяет ответы OAuth имитациями и не обходит реальный Backend.

**Независимая приёмка GA ЗАБЛОКИРОВАНА**, пока фактически не завершены подписанные оператором внешние прогоны, испытания с настоящими пользователями и матрицы Native/Client/ServerBridge/Guard. Обычные тесты CI при отправке коммита не являются такими доказательствами. Физическая ручная задача требует заранее подготовленного браузерного подтверждения с режимом `0600` и не может сфабриковать внешнюю авторизацию OIDC внутри CI.
