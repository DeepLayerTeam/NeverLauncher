# 0.37.8: минимальный SQLite backend — живая интеграционная приёмка

`minimal-live-e2e-0378` в `.github/workflows/ci.yml` — обязательная, **не симулированная** проверка с реальным бинарником `neverlauncher-api` на Linux и постоянными SQLite-файлами. Работа не считается выполненной по прохождению локальных Python unit-тестов: они проверяют только надёжность runner.

## Что реально исполняется в CI

1. Сборка Go backend из проверяемого source SHA; проверка совместимой локальной файловой системы.
2. Чистый `minimal-install.py init/check/run` без PostgreSQL/Redis, с приватными путями, изолированным HTTP listener и конфигурационными правилами безопасности.
3. Проверка `/ready`, мастера, отсутствия предустановленного администратора; отказ bootstrap без токена и повторного bootstrap; создание администратора, реальный password login, создание первого проекта/черновика. Черновик не должен отдаваться через stable manifest.
4. Отказ второго экземпляра Backend и блокировка backup при работающем API.
5. Штатный `SIGTERM` → новый процесс → проверка состояния и refresh-token rotation.
6. Безусловный `SIGKILL` после подтверждённой записи → новый процесс → проверка уже подтверждённого состояния и refresh-token.
7. Остановка всех писателей → backup двух SQLite и файлов проекта → SHA-256 и SQLite integrity verify → restore в новый каталог → повторный запуск реального Backend → вход прежнего владельца и сохранение одноразового bootstrap.
8. Повреждение SQLite-хеша доменной модели: Backend обязан отказаться запускаться. Изменение файла резервной копии: проверка и восстановление должны завершиться отказом, без создания целевого каталога.

## Фиксация результата

Runner записывает `nl-live-evidence-0378.json` со статусом `passed` только после **всех** проверок, хешом бинарника и SHA commit. На ошибке пишет `blocked` и завершается с ненулевым кодом. `required-ci` зависит от `minimal-live-e2e-0378`; отсутствующая, пропущенная или проваленная job блокирует итоговый CI. Отчёт не содержит паролей, токенов или ключей. Процессные логи имеют права `0600`, остаются у runner и не загружаются в публичные артефакты.

CI создаёт изолированные **тестовые** Guard/Bridge allowlist-файлы только для проверки обработки production-конфигурации; эти значения **не являются** подписями, свидетельствами проверенного клиента или разрешением stable-публикации. Проверка подтверждает, что черновик **не** публикуется самостоятельно. Она **не** подтверждает GA, запуск Minecraft, real Guard/Bridge attestation, драйверы PostgreSQL или HA.

Для ручного прогона понадобятся собранный API, реальные файлы конфигурационных политик и пустой приватный каталог на Linux с локальной FS:

```bash
python3 scripts/acceptance/minimal_live_e2e_0378.py \
  --binary /opt/neverlauncher/bin/neverlauncher-api \
  --guard-policy /secure/guard-policy.json \
  --bridge-policy /secure/bridge-policy.json \
  --work-root /private/empty-e2e-directory \
  --report /private/acceptance/minimal-0378.json
```

**Ограничение окружения разработки:** результаты живого E2E подтверждаются только успешным запуском на требуемой версии Go и Linux-файловой системе, а не фактом наличия данного runner или CI YAML.
