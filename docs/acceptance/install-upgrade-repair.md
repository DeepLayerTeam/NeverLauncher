# NeverLauncher 0.52.7 — Install, Upgrade, Repair & Rollback E2E

**Scope:** executable recovery changes to the existing production `neverinstaller`, Prestarter TLS artifact storage and Go transactional updater. This is not a declaration that the independent 0.53.0 final-package acceptance has passed.

## Production behavior

- `neverinstaller rollback --root ABSOLUTE_PATH --no-start` selects the **other** retained and independently verified signed active generation. It rejects missing, corrupted, equal or newer candidates, and a change of project, profile, channel or pinned game trust. It runs the retained verified Prestarter and restores the appropriate shortcut **before** committing a new monotonic activation record. A canceled run does not advance the active slot. User profiles, worlds and saves are deliberately retained, not reverted to an old snapshot. Rolling back the binary is **not** a database/schema or world-data rollback.
- `neverinstaller update`, `repair`, `verify-installed` and `uninstall` retain their existing release-signature requirements. A failed new package must not silently activate arbitrary bytes.
- Transactional updater persists original backup size and SHA-256 in new journals, verifies the backup immediately and **again before rollback**, and refuses corrupted backup bytes. It uses exclusive creation for copy destinations and fresh atomic journal temporaries to avoid writing through leftover symlinks. Recovery also removes interrupted swap/staging files, including after a crash during an earlier rollback. Older in-flight journals retain their previously defined recovery behavior, but never claim to have historical backup checksums they did not record.
- Prestarter's HTTPS fetch/range/ETag/SHA-256 code is exercised against a real `httptest.NewTLSServer` which forcibly disconnects the socket mid-stream, plus a wrong-validator replay. The downloader is not replaced by a mock in these tests.

## Local regression commands

```bash
cd prestarter

GOTOOLCHAIN=local go test ./cmd/launcher -run 'Test(Updater.*0527|TransactionalUpdater)' -count=1
cd ..
python3 -m unittest scripts/acceptance/test_install_upgrade_repair_0527.py -v

```

The updater crash test uses a **separate real OS process**, commits new bytes to disk, kills that process with SIGKILL while post-apply verification is pending, restarts the updater and checks that its durable recovery restored the exact old files and preserved an unrelated game save. No runtime-provided `--skip-signatures` or `--force-success` switch is added.

## Real destructive physical Linux acceptance

Run only on a **dedicated, privileged, disposable Linux runner**. Never run the fault script on an owner-managed production machine. Provision two **real signed and offline-capable** release bundles for the same project/profile/channel, each with a different signed revision, plus an independently SHA-256-approved `neverinstaller` with the actual embedded production trust root. The new release must require upstream network inputs when `--offline` is absent so the disconnected-network test cannot pass from cached data.

The acceptance tool mounts an isolated tmpfs, installs the old package, writes a user save, rejects a corrupted signed installer, then runs the **real updater inside a network namespace with no external interfaces**. It fills tmpfs blocks with `posix_fallocate` until the kernel reports insufficient disk space, verifies that the failed update preserved the active generation and saved data, frees space, installs the new release, corrupts a selected installed managed game file, repairs it to the approved SHA-256, activates the previously verified release via `rollback`, then uninstalls while checking that the save is preserved. It emits a private SHA-256-linked execution receipt **only if all stages succeed**. Missing privileges, absent `unshare`, unsupported namespaces, invalid trust inputs, a network cut that does not interrupt the actual update, or a failed observation block PASS.

The script is invoked through `.github/workflows/install-upgrade-repair-0527.yml` on a protected `neverlauncher-0527-isolated` self-hosted runner. Approve the `installer-physical-acceptance` environment and configure the `NL_0527_*` runner variables in that workflow. No real signed binaries or production signing keys are committed to the repository.

The `--managed-repair-file` must be an immutable file managed by the signed game/runtime payload, **not** `profiles`, `saves`, user-generated worlds or `.launcher-installer` control data; its expected SHA-256 is independently approved. If the chosen game artifact cannot be regenerated by the signed installer, this check fails rather than falsely reporting repair.

## Exit criteria and limitations

1. A release commit and both supplied signed bundles have immutable approved hashes; six actual native platforms pass the corresponding installation / interruption / repair / rollback procedures. The isolated Linux ENOSPC and network test is **additional** evidence, not a replacement for Windows and macOS.
2. Failed network deliveries, exhausted storage, SIGKILL, corrupted package bytes and tampered backup bytes never grant a committed update or destroy the verified prior installation; operator recovery is repeatable and user files survive.
3. All required E2E receipts are tied to the actual final signed packages, source commit, OS/CPU, runner, attempted faults and independent review. Real final acceptance requires the hardware and signed installers, **not only successful Go/Python tests**.

**Current acceptance:** local code tests can pass without this proving an independent full native run. Until a dedicated external operator executes and verifies these tests, real installation acceptance is **BLOCKED**, and overall GA remains blocked.
