# NeverLauncher 0.45.2: Minimal — зашифрованная резервная копия и восстановление на другом Linux-хосте

Это инструкция для **single-node SQLite + локальные файлы**, созданной через `scripts/install/minimal-install.py init`. Это не PostgreSQL/Redis/S3 backup, не резервная копия без остановки и не HA. Используйте один экземпляр API, локальную файловую систему (ext4/xfs/btrfs), приватную учётную запись службы и **тот же проверенный выпуск Backend API** на восстанавливаемом хосте.

## Что переносится

Точный офлайн-снимок двух основных баз `db/http.sqlite`, `db/coordinator.sqlite`, дополнительных SQLite-файлов, локального хранилища, расширений, factory, конфигурации и **секретов внутри `config/backend.env`**. SQLite WAL переносится через SQLite Backup API, а не сырым копированием `*.sqlite-wal`. При переносе в другой каталог обновляются только известные абсолютные локальные пути; ключи авторизации и подписи, сведения об администраторе, его парольный verifier и использованный bootstrap-токен **сохраняются**.

Не входят: API/CLI executable и его библиотеки, unit-файлы systemd, TLS private key/certificate и настройки reverse proxy **вне** каталога установки, внешнее хранилище, ключ/пароль шифрования переносимого файла, внешние OS/DNS/firewall-настройки. Это нужно самостоятельно безопасно развернуть на целевой машине и проверить до переключения трафика.

## Резервирование на исходном хосте

Установить `Python 3.12+` и зависимость из `scripts/install/requirements-portable-0452.txt` **в доверенном окружении**, используя зафиксированный источник пакетов. Создать независимый длинный случайный passphrase в приватном файле (не пересылать рядом со снимком):

```sh
umask 077
mkdir -p /srv/never-transfer
chmod 0700 /srv/never-transfer
openssl rand -base64 48 > /srv/never-transfer/recovery.key
chmod 0600 /srv/never-transfer/recovery.key

# Остановить systemd-сервис Backend API, jobs и ВСЕ внешние writers в storage/extensions/factory.
# Убедиться, что исходная система полностью остановлена.
python3 scripts/install/minimal-install.py backup-portable \
  --root /var/lib/launcher-minimal \
  --output /srv/never-transfer/minimal-0452.nmb \
  --passphrase-file /srv/never-transfer/recovery.key

python3 scripts/install/minimal-install.py verify-portable \
  --input /srv/never-transfer/minimal-0452.nmb \
  --passphrase-file /srv/never-transfer/recovery.key
sha256sum /srv/never-transfer/minimal-0452.nmb
```

Снимок производится под теми же эксклюзивными Linux `flock`, что использует Backend API; если API владеет ими, операция **отказывает**. Но сторонние writers, игнорирующие эти блокировки, должны быть остановлены отдельно. Снимок зашифрован **AES-256-GCM** (ключ выводится через `scrypt`, индивидуальные соль и nonce). Формат `NEVER-MINIMAL-PORTABLE-1`; изменение даже одного байта не позволяет подтвердить его подлинность без пароля. Используйте **отдельный** независимый канал доставки `recovery.key`, с контролем доступа и резервированием этого ключа. Потеря ключа означает невозможность восстановления снимка.

При внезапном выключении сервера до завершения команды могут остаться приватные скрытые `.minimal-portable-source-*` в `backups/`: это **незавершённые plaintext** снимки. При подтверждённой остановке API и после проверки, что ни одна операция резервирования не работает, их нужно отдельно инвентаризировать и безопасно удалить. Никаких успешных меток для них не создаётся. Исходные нешифрованные offline bundles тоже содержат все секреты — не публиковать их.

## Перенос и восстановление

Переносить `minimal-0452.nmb` через защищённый канал на **другой Linux-хост**. Сверить SHA-256 с независимо переданным эталоном. Passphrase доставляется **отдельно**, файлы на целевом хосте находятся под владельцем службы (0700/0600). На другом хосте установить проверенный `launcher-api` **той же версии**, `Python` + `cryptography==46.0.4`, скрипты восстановления из того же исходного выпуска. Настроить приватный родительский каталог установки (например, `/srv/never-recovery`, `0700`, владелец — служба):

```sh
# Выполнять от имени владельца службы, не пересекать разные UID без chown и проверки.
umask 077
mkdir -p /srv/never-recovery
chmod 0700 /srv/never-recovery

python3 scripts/install/minimal-install.py restore-portable \
  --input /srv/never-transfer/minimal-0452.nmb \
  --target-root /srv/never-recovery/launcher-minimal \
  --passphrase-file /srv/never-transfer/recovery.key

# ОБЯЗАТЕЛЬНО использовать доверенный executable из *того же* выпуска.
python3 scripts/install/minimal-install.py check \
  --env-file /srv/never-recovery/launcher-minimal/config/backend.env \
  --binary /opt/neverlauncher/bin/launcher-api
```

`restore-portable` **сначала** проверяет GCM authentication tag, затем строгий список tar-объектов, SHA-256 каждого файла и целостность SQLite. Восстановление осуществляется в закрытый временный каталог и становится доступным **одним атомарным переименованием**. Если целевой каталог уже существует или возникла ошибка, данные в него не записываются. `restore-portable` не перезаписывает и не сливает действующее состояние.

Восстановить TLS-прокси и доверенный сертификат для **того же публичного HTTPS origin**, что указан в `LAUNCHER_PUBLIC_URL`/WebAuthn/CORS. Если домен нужно изменить, требуется отдельная контролируемая миграция WebAuthn RP ID, разрешённых origins, client trust pins и адресов, а не автоматическая замена строки в файле. Восстановить service unit, политику OS permissions, firewall и подключение клиентов. Не запускать оба API одновременно над одними и теми же ресурсами или параллельно принимать записи в старую и новую установку.

## Обязательная проверка до переключения DNS/трафика

1. `minimal-install.py check` запускает **реальный** `launcher-api diagnose deployment` и завершается с нулевым кодом. Подключён только ожидаемый локальный root.
2. Запустить `minimal-install.py run --env-file ... --binary ...` как service user; проверить локальный `/ready`, `/health` и ожидаемую версию. Публичный API обслуживать только через доверенный HTTPS reverse proxy.
3. Войти **существующим** администратором: оригинальный парольный verifier должен работать; `bootstrap-admin` не должен выдавать второго владельца с повторно использованным токеном.
4. Проверить существующий проект, его файлы/хеши и разрешённую роль; выполнить тестовую операцию с сохранением состояния и перезапуском API. Проверить отсутствие пропавших extensions/factory данных и работающий доступ к локальным blobs.
5. Повторить отрицательную проверку (неверный пароль backup / испорченный ciphertext, существующий target): восстановление не должно публиковать частичные данные. Только после этого переводить реальные подключения.

Проверки обеспечивают сохранение snapshot **на момент остановки writers**, но не изменения, возникшие после неё. RPO — время от точки снимка до аварии; RTO зависит от объёма файлов, скорости транспорта, установки бинарников и ручной настройки TLS. Реальные значения необходимо измерить на целевой инфраструктуре.

## CI и границы подтверждения

Тесты: `python3 -m unittest discover -s scripts/install -p 'test_minimal_portable_0452.py' -v`. В обязательной CI-зависимости `minimal-live-e2e-0378` продолжает запускаться настоящий Go backend; теперь добавлены `authenticated_offhost_transfer_and_deployment_check`, `offhost_recovered_backend_start`, `offhost_recovered_owner_project_bootstrap` и проверка отклонения подделанного пакета. Успех тестов локального Python не доказывает, что CI реально запущен или что два физических хоста протестированы. Нельзя объявлять эксплуатационную приёмку пройденной без успешного execution evidence, настоящего переноса на независимый хост и проверки инфраструктуры TLS/DNS.
