# NeverLauncher 0.47.2 — безопасное обновление старых SQLite-хранилищ

Этот релиз добавляет **автоматическую миграцию только распознанных схем**, но не делает восстановление повреждённых баз и не переводит данные в PostgreSQL.

## Поддерживаемые переходы

- **SQLite Core:** `PRAGMA user_version` 322, 323, 324, 325 или 326 → 327. Перед записью проверяются ожидаемые таблицы версии, ключевые колонки, связи проектов/ролей/профилей и корректность JSON разрешений; миграции выполняются атомарно. Для исторического индекса `minecraft_sessions` исправляется конфликт имени с одноимённой таблицей во время выполнения (исторический SQL не переписывается). Для частично добавленных столбцов версии 327 проверяется тип и пропускается повторный `ALTER TABLE`.
- **Coordinator:** исходная схема v0 с таблицами `coord_channels`, `coord_leases`, `coord_limits` (с необязательной `coord_meta` и частично установленными индексами) → v1. Допускаются только объекты с точным известным DDL. После создания таблицы `coord_lease_tokens` существующие пары token/fence копируются из `coord_leases` до переключения версии. Неизвестная схема или повреждённая v1 отвергается.
- **HTTP Repository:** исходная v1 таблица `http_repository_state_0372` при отсутствии поздних `http_runtime_components_0373`, `http_stable_permits_0374` или индекса. Проверяются checksum и уникальность JSON-ключей; дополняются **только перечисленные поздние поля**. Секреты аутентификации запрещено восстанавливать пустыми массивами, если присутствуют связанные пользователи, устройства, токены или другие чувствительные записи. Незнакомые поля и неполная текущая схема отвергаются.

## Гарантии и границы

1. Остановить независимых писателей, убедиться, что 0.47.1 уже закрывает единственное владение файлом SQLite. Не копировать только `.db` при активном WAL.
2. При первом распознанном обновлении создаётся уникальный приватный физический снимок в `pre-upgrade-backups/` рядом с исходной БД. `OnlineBackup` включает подтверждённые WAL-страницы; затем выполняются проверка SHA-256 и пробное восстановление в отдельный путь. Неуспех **блокирует** обновление.
3. Структура и содержимое проверяются до изменения. Изменения SQL выполняются в одной транзакции с новым маркером версии; при ошибке транзакция откатывается. Повторный запуск не добавляет новые резервные копии, если версия уже актуальна.
4. Не удалять `pre-upgrade-backups/` до ручной независимой проверки, включая авторизацию старого владельца, чтение проекта, профиля, историю, runtime-компоненты и подключение Bridge.
5. Не исправлять неизвестные схемы путём изменения `PRAGMA user_version`. Для неподдерживаемых старых схем требуется подготовить отдельную проверяемую миграцию из исходного релиза или восстановить корректный бэкап.

## Проверка на целевой системе

```bash
cd services/api
LAUNCHER_SQLITE_TEST_ROOT=/var/lib/launcher/sqlite-test \
  LAUNCHER_SQLITE_REQUIRE_SUPPORTED_FS=1 \
  go test -count=1 ./internal/sqlitedurable ./internal/sqlitecoord ./internal/sqlitecore ./internal/repository ./internal/sqliteacceptance
```

Требуются Go 1.27.3, закреплённый `modernc.org/sqlite` и реальная поддерживаемая локальная файловая система. Эта инструкция не утверждает, что тесты уже запущены. Созданные резервные копии содержат секреты и должны оставаться приватными. Полноценный переход SQLite → PostgreSQL относится к последующим версиям.
