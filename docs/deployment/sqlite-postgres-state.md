# NeverLauncher 0.47.4 — автономный импорт состояния Core и копирование хранилища

Это обновление расширяет существующий проверенный **автономный** импорт SQLite Core 327 в промежуточную область (`sqlite-to-postgres` + `sqlite-to-postgres-live`). Исторические SQL-миграции PostgreSQL и SQLite не изменяются. **Не переключайте работающее приложение только на основании квитанции об импорте.** Исходная и целевая системы должны быть остановлены, а целью должна выступать новая база PostgreSQL с полностью применёнными миграциями.

## Инструкция оператора

1. Остановите API, координатор, Launcher/Bridge, потребителей очередей, планировщики и все прочие процессы записи. Создайте автономные резервные копии `http.sqlite`, `coordinator.sqlite`, базы Core SQLite, объектов хранилища, конфигурации и ключей шифрования с возможностью независимого восстановления. Проверьте их читаемость.
2. Примените все поставляемые миграции PostgreSQL к **новой пустой** базе данных. Установите `LAUNCHER_POSTGRES_DSN` в окружении оператора.
3. Импортируйте неизменяемую резервную копию SQLite Core в криптографически проверенную промежуточную область с помощью `launcher-sqlite sqlite-to-postgres --backup <core-backup>`. Параметры подготовки и требования к резервной копии приведены в руководстве 0.47.3.
4. Перешифруйте TOTP с использованием того же закрытого MFA-ключа Core, что и в источнике, и того же секрета, что использует целевой HTTP API. Не передавайте секреты аргументами командной строки. Пример:

   ```sh
   export LAUNCHER_POSTGRES_DSN='postgres://...'
   export NEVERLAUNCHER_PG_API_SECRET='the-exact-HTTP-API-secret'
   launcher-sqlite sqlite-to-postgres-live --from-staging \
     --sqlite-mfa-key-file /path/to/private/core-mfa.key \
     --postgres-secret-env NEVERLAUNCHER_PG_API_SECRET \
     --ack-live-import
   ```

   Файл ключа должен содержать ровно 32 исходных байта или 64 шестнадцатеричных символа, быть обычным закрытым файлом с правами `0600` и соответствовать исходному ключу AES-256-GCM. Несовпадение ключа, отсутствие целевого секрета или повреждение исходных данных прерывает **всю** транзакцию PostgreSQL. Ни один действующий MFA не отключается. Методы PostgreSQL используют тот же контейнер шифрования, что и существующий HTTP Backend. Счётчики перенесённых активных TOTP защищены монотонным обновлением при блокировке строк.

5. Сверьте все файловые объекты выпусков: строки `files` из подписанных манифестов сами по себе **не** гарантируют наличия байтов файла. Для изолированного целевого LocalStorage выполните:

   ```sh
   launcher-sqlite sqlite-to-postgres-files --source-root /old/storage \
     --target-root /new/storage --ack-offline
   ```

   Для S3 используйте `--target-s3` вместо `--target-root`, настройте существующие переменные `LAUNCHER_STORAGE_S3_*` (адрес службы, бакет, учётные данные, регион) и выделите изолированный целевой бакет. Каждый байт сверяется с импортированным SHA-256 **после повторного чтения из целевого хранилища**; уже существующие совпадающие файлы принимаются. При обнаружении конфликтующего файла копирование прерывается. Подтверждённая квитанция копирования, привязанная к источнику, сохраняется только после проверки всех объектов и полного каталога файлов. Повторяйте неудачное копирование только после устранения первопричины.

## Поведение импорта

- Записи Core `auth_sessions`, `access_tokens`, `refresh_families`, `refresh_tokens`, `mfa_totp`, `mfa_recovery`, `minecraft_profiles`, `minecraft_sessions`, `auth_revocation_events`, `durable_jobs`, `durable_job_attempts`, `durable_scope_leases`, `durable_outbox`, `bridge_nodes`, `bridge_nonces`, `bridge_join_tickets`, `bridge_runtime`, `bridge_runtime_nonces` и `bridge_commands` сопоставляются с таблицами Runtime PostgreSQL либо явными отметками о блокировании по соображениям безопасности. Строки и контрольные суммы промежуточной области проверяются внутри единой транзакции; исходные идентификаторы и критически важные сведения безопасности сохраняются. Старые сеансы и токены явно отзываются. Незавершённые задания, доставка из исходящей очереди, выполнение команд и аренды Runtime блокируются или помечаются неопределёнными: прежние учётные данные и обработчики не возобновляются скрытно.
- Повторная регистрация **не заменяет** миграцию MFA: секреты TOTP расшифровываются закрытым исходным ключом AES-GCM и немедленно шифруются заново секретом целевого API. Хеши прежних одноразовых кодов восстановления копируются как хеши с сохранением одноразового статуса.
- Активные расширения и любые другие непустые таблицы промежуточной области Core без поддерживаемого работающего отображения SQLRepository **блокируют транзакцию**. Они не пропускаются молча и никогда не считаются успешно перенесёнными данными.
- Импорт Core **не переносит** `http.sqlite`, `coordinator.sqlite`, доверенные устройства PostgreSQL, независимое состояние публикации и плоскости управления, активацию пакетов расширений, конфигурацию расширений и состояние всех внешних служб. Поэтому импорт Core **не гарантирует** полного соответствия служб даже при совпадении всех перенесённых строк. Этап намеренно возвращает `readyForBackendCutover=false`. Операторы должны сохранить исходные файлы и проверить настоящие сценарии API, аутентификации, проектов, публикации, мостов, расширений и Launcher до использования PostgreSQL в промышленной среде.

## Статус проверки

Для этого изменения исходников выполнены проверки синтаксиса и форматирования Go и регрессионные сценарии, но в среде сборки отсутствуют Go 1.27.3 и интеграционный экземпляр PostgreSQL. Настоящая интеграция PostgreSQL, совместимость расширений, переключение, откат и полное соответствие данных остаются **непроверенными**. Не интерпретируйте созданную квитанцию как приёмку промышленного GA или успешную сквозную миграцию.
