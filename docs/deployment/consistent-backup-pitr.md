# Launcher 0.51.8 — работающее согласованное резервное копирование и PITR PostgreSQL

**Это многохостовая контрольная точка, создаваемая в окне обслуживания при блокировке записи.** Процедура намеренно прерывает запись API и рабочих процессов и плавно останавливает затронутые Minecraft-серверы; она не является онлайн-атомарной транзакцией между PostgreSQL, S3 и игровыми JVM. Физическая копия PostgreSQL с непрерывным архивированием WAL позволяет выполнять PITR базы. Объекты S3, состояние расширений, идентичности и игровые миры группы согласованы с одним записанным LSN PostgreSQL. Восстановление PostgreSQL на *произвольное другое время* **не создаёт** согласованную копию S3 и игровых миров.

## Подготовьте реальные зависимости до резервного копирования

1. Требуются как минимум две отдельные Docker-машины, развёрнутые через `deploy/production/docker-compose.multi-host.yml`, исправный основной узел PostgreSQL/Patroni, Redis, S3 и входной прокси. Доверенный оператор должен иметь SSH-доступ к игровым и Docker-хостам с `StrictHostKeyChecking=yes` и закреплённым `known_hosts`. **Вне этого инструмента** остановите посторонних писателей, сторонних провайдеров аутентификации, независимые консольные/SQL-скрипты, публикации, планировщики, миграции БД, релизные операции и пользователей обслуживания с правом записи. Сначала заблокируйте входящие записи на внешнем балансировщике. Другой оператор не должен возобновлять API или JVM Minecraft во время снимка.
2. Подготовьте `pgbackrest` с рабочей конфигурацией `launcher`, отдельным зашифрованным внешним репозиторием и *непрерывным* `archive-push` с основного узла PostgreSQL/Patroni. Обычные параметры PostgreSQL: `wal_level=replica`, `archive_mode=on`, `archive_command='pgbackrest --stanza=launcher archive-push %p'`. Под Patroni используйте поддерживаемый интерфейс конфигурации кластера, а не несогласованное редактирование. Проверяйте `pgbackrest --stanza=launcher check`, `pgbackrest --stanza=launcher info --output=json`, `pgbackrest --stanza=launcher verify --set=BACKUP_LABEL`, следите за `pg_stat_archiver` и задержкой архивации. Закрепите версию pgBackRest с поддержкой `verify`. Инструмент запускает **настоящие** команды, а не имитирует архив WAL.
3. Все шлюзы S3 должны обслуживать **один** авторитетный бакет с **включённым версионированием**. Учётным данным оператора нужны `ListObjectVersions`, `GetBucketVersioning`, `ListBucket`, `GetObject`; загрузка через `aws s3 sync` должна проходить. Не поддерживаются S3 с расщеплением полномочий или шлюзами с расходящимися индексами объектов. Бакет с более чем двумя миллионами версий блокируется до проверки и увеличения ограничений пагинации/памяти. Маркеры удаления с версиями включаются в опись.
4. Отдельно настройте зашифрованное неизменяемое/внешнее хранение **и репозитория pgBackRest, и каталога контрольной точки**. Используйте разные учётные данные резервного копирования и восстановления, защищённое назначение только для записи или добавления; учётные данные приложения/API не должны позволять удалять копии. **Вне инструмента** проверьте неизменяемость, хранение, доступ к ключам KMS, аварийное восстановление ключей и сам процесс восстановления. Локальный каталог группы содержит потенциально чувствительные данные и *не шифруется автоматически*.
5. Установите Python 3.11+, Docker Compose v2, доверенный OCI-образ tar с закреплённым дайджестом, `aws` CLI, инструменты PostgreSQL (`pg_dump`, `pg_restore`, `psql`), pgBackRest и **одинаковый** скрипт 0.51.8 на машине оператора и каждом Docker/игровом хосте. Игровому хосту требуется настоящий исполняемый файл Launcher `nl` с функцией `server-bridge host world-backup`. Данные подключения к БД хранятся только в частном однострочном файле 0600 `postgresql://...?...sslmode=verify-full`, не в argv.
6. Определите всех внешних провайдеров идентичности. Идентичности/роли PostgreSQL, сеансы и состояние установленных расширений внутри БД Launcher включаются в физическую и логическую копии. Если внешний файловый провайдер владеет состоянием идентичности, используйте `--external-auth-policy included --external-source provider=/private/export.json`. Для OIDC, внешнего SQL, HTTP-провайдеров и миров вне зарегистрированного набора заранее получите совместимую независимо согласованную копию или fencing, **либо не заявляйте о полном восстановлении идентичностей**. `--external-auth-policy none` означает, что внешних изменяемых данных авторизации нет.
7. Передайте ключи подписи, доверенные корни, TLS-секреты, ключи KMS и секреты администратора восстановления на отдельное закрытое ответственное хранение с независимой возможностью восстановления. Подготовьте `trust-hashes.json` с правами 0600, например `{"manifest-signing-key":"<SHA-256 из 64 символов в нижнем регистре>"}`. Средство записывает только отпечатки и никогда не экспортирует закрытые ключи.

## Создание полной контрольной точки

На доверенной машине оператора создайте `worlds-0518.json` с правами 0600 и записью для *каждого* управляемого мира Minecraft (ничего не пропускайте):

```json
[
  {"name":"survival","target":"gameops@game-host.example","serverRoot":"/srv/minecraft/survival","backupRoot":"/srv/launcher-world-snapshots","world":"world"}
]
```

Перед началом создайте `/secure/checkpoints` как специальный закрытый/зашифрованный каталог с правами `0700`. Операция остановит API и рабочие процессы на каждом узле, вызовет настоящий протокол остановки/копирования Minecraft через диспетчер хоста на игровых узлах, затем выполнит физическую копию PostgreSQL и проверку WAL, логический дамп, архивы всех десяти локальных томов состояния каждого хоста, опись версий S3, загрузку и обратное чтение с проверкой хешей файлов. **Игровые JVM не перезапускаются автоматически**: оператор должен допустить их после проверки готовой контрольной точки. CLI Go для мира теперь принимает `--hold-id RUN_ID`: шлюз Host Supervisor остаётся атомарно занятым с момента успешной копии мира до явной соответствующей команды `world-backup release`, предотвращая перезапуск игры между снимком мира и контрольной точкой PostgreSQL.

```sh
python3 scripts/operations/consistent_backup.py backup \
  --node a=deployer@api-a.example --node b=deployer@api-b.example \
  --directory /opt/launcher/deploy/production --project launcher \
  --remote-script /opt/launcher/scripts/operations/consistent_backup.py \
  --run-id 1234567890abcdef1234567890abcdef \
  --pg-dsn-file /secure/launcher-writer.url --stanza launcher \
  --s3-bucket launcher-production --s3-endpoint https://s3.internal.example \
  --tar-image 'alpine@sha256:<verified-64-hex-digest>' \
  --world-file /secure/worlds-0518.json --world-cli /opt/launcher/bin/nl \
  --trust-file /secure/trust-hashes.json \
  --external-auth-policy none \
  --destination /secure/checkpoints/0518-first \
  --acknowledge-maintenance
```

Замените пример дайджеста OCI-образа настоящим закреплённым проверенным значением. Для каждой попытки используйте новый 32-символьный шестнадцатеричный `--run-id`, не используйте прежние журналы. Закрытые файлы должны быть обычными, без жёстких ссылок, с правами `0600`. На исходном и целевом хостах оператора должно хватать свободного диска: объём данных может превышать размер дампа БД. Никогда не делайте каталог локальных копий общим с публичными веб-службами.

## Порядок выполняемых проверок

- **Настоящий Compose:** PostgreSQL, Redis и S3 внешние; разные идентичности машин и ID узлов; одна внешняя БД/бакет и две роли: API и рабочий процесс. Перед остановкой рабочих процессов и API каждый хост сохраняет закрытый восстанавливаемый после сбоя `.backup-freeze-0518.json`. Когда все хосты заморожены, CLI игрового хоста выполняет настоящий снимок остановленного мира через уже существующую блокировку/шлюз диспетчера хоста и создаёт проверенный архив `launcher-world-backup/v1`. Копирование файлов работающего мира запрещено.
- **PostgreSQL:** должен быть активным основным узлом с **нулём других SQL-сеансов клиентов**. Последовательность pgBackRest `check → backup --type=full → check → verify --set=LABEL` обязана создать **одну новую физическую копию** с записанным диапазоном начального/конечного WAL. Независимый `pg_dump -Fc` проверяется `pg_restore --list` и содержит идентичности/состояния расширений замороженной группы. Изменение `pg_current_wal_insert_lsn()` во время копирования S3/локальных миров отклоняет снимок.
- **Тома и S3:** каждый хост предоставляет `api_storage`, `api_backups`, `api_factory`, `api_coordinator`, `api_extensions` и пять соответствующих томов обработчика заданий. Все tar читаются потоком со строгой проверкой путей/типов и SHA-256. Исходный бакет S3 копируется и независимо загружается повторно; ID версий и маркеры удаления должны оставаться неизменными. Хешируется каждый байт скопированного объекта. Пропущенный или изменившийся ключ блокирует публикацию.
- **Фиксация:** готовая контрольная точка публикуется переименованием только после проверки манифеста, описи файловой системы, квитанций миров, байтов S3 и репозитория pgBackRest. На выходе средство пытается перезапустить все остановленные им API и рабочие процессы, в том числе при ошибке. Неудачный перезапуск требует **ручного восстановления**, а не PASS. Допуск внешнего ingress и запуск игр остаются под контролем оператора.

## Проверка и подготовка восстановления на другом узле

```sh
python3 scripts/operations/consistent_backup.py verify \
  --backup /secure/checkpoints/0518-first --stanza launcher
```

Команда читает *настоящие* локальные файлы и запускает проверку репозитория pgBackRest для записанной копии. Она не аттестует неизменяемость внешнего хранилища, отсутствие посторонних источников записи или возможность восстановления отдельного хранилища копий/секретов.

**Восстановление PG для согласованной группы** создаёт новый изолированный каталог данных PostgreSQL с `recovery_target_lsn`, равным запечатанному LSN контрольной точки. Табличные пространства также перенаправляются в новый соседний путь, и PostgreSQL никогда не запускается:

```sh
python3 scripts/operations/consistent_backup.py cohort-pg-restore-fresh \
  --backup /secure/checkpoints/0518-first --stanza launcher \
  --pgdata /srv/restore/new-pgdata --confirm 20261103-100000F
```

`--confirm` должен совпадать с меткой физической копии в `manifest.json`, а не примером. Восстанавливайте только на отдельном хосте и от отдельного пользователя, **никогда** поверх работающего PGDATA или существующих табличных пространств. Успех команды означает лишь восстановление дисковых файлов, **не воспроизведение WAL и не готовность приложения**. Запуск PostgreSQL, наблюдение за WAL до `pg_is_wal_replay_paused()` в заданной точке, проверка достижения цели восстановления, возврат S3 в *новый* бакет, fencing старого кластера, восстановление снимков миров и проверка UUID, файлов выпусков и авторизации относятся к 0.51.9 и здесь не выполняются скрыто.

Для **произвольного PITR только PostgreSQL** (например, при расследовании) используйте `pitr-restore-fresh --target-time 2026-11-03T12:00:00Z --pg-only-reconciliation-ack` с теми же аргументами. Не называйте это согласованным много-ресурсным восстановлением и не откатывайте работающую промышленную систему поверх более новых подтверждённых записей.

## Восстановление после неудачного снимка

При прерывании оператора или SSH журналы заморозки остаются в каждом каталоге развёртывания. Проверьте настоящее состояние API и рабочих процессов на каждой площадке; для возобновления точной операции выполните на ней:

```sh
python3 /opt/launcher/scripts/operations/consistent_backup.py local-thaw \
  --directory /opt/launcher/deploy/production --project launcher \
  --run-id 1234567890abcdef1234567890abcdef
```

Если `local-thaw` не удался, сохраните журнал, восстановите связь с Backend, исследуйте здоровье Docker и повторите с **тем же** ID запуска. Если оператор/SSH прерывается, пока удерживается мир, проверьте точное состояние диспетчера хоста/JVM и снимите постоянный шлюз этого мира:

```sh
python3 /opt/launcher/scripts/operations/consistent_backup.py local-world-release \
  --server-root /srv/minecraft/survival --world-cli /opt/launcher/bin/nl \
  --run-id 1234567890abcdef1234567890abcdef
```

Выполняется настоящая команда `nl server-bridge host world-backup release --hold-id RUN_ID`. Неизвестный/частичный шлюз, неверный ID, работающий Supervisor или JVM должны приводить к безопасному отказу и расследованию; нельзя принудительно удалять каталог шлюза. **Не удаляйте журналы восстановления и не запускайте игровые хосты, пока не согласованы устаревшие аренды и полномочия Bridge/мира.** Не считайте неполный подготовительный каталог резервной копией. Для каждой законченной контрольной точки вместе с репозиторием pgBackRest и цепочкой WAL создайте независимую зашифрованную внешнюю копию под отдельно защищёнными учётными данными.

**Граница приёмки:** `test_consistent_backup.py` проверяет настоящие байты файлов/архивов и имитируемые границы вызова команд; он не проверяет рабочий Docker на нескольких хостах, реальный PostgreSQL/pgBackRest, шифрование S3 или независимое восстановление миров Minecraft. Промышленная приёмка HA/PITR остаётся **BLOCKED** до внешней репетиции и проверок 0.51.9/0.52.0.
