# NeverLauncher 0.48.0 — независимая GA-приёмка установленного проекта

## Статус и границы выпуска

`VERSION=0.48.0` **не является сертификатом GA**. Переключение приложения с SQLite на PostgreSQL остаётся небезопасным, пока не перенесены независимые состояния HTTP Repository, Coordinator и Extensions. Оператор версии 0.47.5 намеренно задаёт `cutoverSupported=false`; шлюз запуска PostgreSQL Backend отказывает при наличии импортированных данных SQLite без подтверждённой эквивалентности. Не удаляйте эти защитные проверки ради успешного задания выпуска. В частности, удачный импорт SQL Core, HTTP 200 от `/ready` или зелёные модульные тесты **не означают** успешного переключения работающей системы.

Код 0.48.0 добавляет исполняемые независимые приёмочные проверки старой установки и границу публикации GA с подписью. Для фактической публикации GA нужны внешний промежуточный стенд и реальные тесты Mojang, ServerBridge и браузера. Тесты исходного дерева не создавали свидетельств приёмки GA.

## Закрытый независимый тестовый стенд

1. Подготовьте **изолированный**, выделенный и защищённый исполнитель с копией уже существующей установки поддерживаемой исторической версии NeverLauncher. Не направляйте эти скрипты на промышленный сервер пользователя. Отдельно сделайте резервную копию промышленной системы по обычной процедуре аварийного восстановления.
2. Сохраните учётные данные владельца старого Backend в JSON-файле с правами **0600** (`{"email":"...","password":"..."}`, при необходимости `totp` или `recoveryCode`), а содержащий его каталог ограничьте правами 0700. Никогда не печатайте файл и не включайте его в артефакты сборки.
3. Настройте исходные базы SQLite Core, HTTP и Coordinator и исходный корневой каталог LocalStorage. Все три хранилища SQLite должны быть раздельными. Настройте отдельный каталог хранения PostgreSQL без пересечения путей. Если исходный проект использует S3, этот режим приёмки LocalStorage неприменим и должен завершиться отказом, а не считать байты скопированными.
4. Запустите `live_upgrade_0480.py capture` для **действительно работающего старого Backend**, указав `--old-version`, базовый URL, проект, профиль, канал, учётные данные владельца и три пути SQLite. Будут созданы проверенные онлайн-копии SQLite, исходная точка сравнения аутентифицированных данных владельца/проекта и всех локальных объектов. Выполняйте операцию только на изолированной промежуточной копии.
5. Запустите существующий оператор `sqlite_pg_cutover_0475.py run`. Он блокирует запись служб, проверяет резервные копии, импортирует и сравнивает данные и файлы и пытается переключить систему только если шлюз эквивалентности доменов разрешает это. Отказ возможен. Ошибка оператора означает провал GA; никогда не подделывайте `readyForBackendCutover` и не правьте журнал ради снятия блокировки.
6. Только после успешного переключения выполните `live_upgrade_0480.py verify` с `--baseline`, `--operator-work`, `--backend-env` и `--target-storage`. Проверка заново аутентифицирует **того же настоящего владельца**, сравнивает проекты, профили, каналы, выпуски и ревизии, считывает текущую версию Backend, независимо запрашивает действующий PostgreSQL из конфигурации службы, проверяет логическое содержимое исходной SQLite и повторно хеширует деревья исходного и целевого LocalStorage.
7. Выполните настоящую матрицу обновления исторического CLI Linux и отдельную защищённую матрицу браузера, игры и ServerBridge. Базовые архивы должны быть установлены заранее и закреплены по SHA-256; пропуски и подмена фикстурами запрещены. Проверьте идентичность подписанного установщика на соответствующей нативной ОС. Не приравнивайте простое **наличие** подписи PE/Mach-O к нативной проверке доверия.

Защищённый workflow `.github/workflows/independent-migration-0480.yml` выполняет этапы 4–6 на выделенном исполнителе. Он намеренно завершается ошибкой, если шлюз переключения 0.47.5 остаётся закрытым. При неуспешной реальной проверке артефакт не загружается. Только `live.json` отправляется после успеха; исходные базы, секреты и журналы остаются на стенде.

## Независимое одобрение с подписью оператора

`scripts/release/ga_gate_0480.py` требует закреплённого открытого ключа Ed25519 длиной 32 байта и отдельной подписи длиной 64 байта над `b"neverlauncher.ga0480.independent-operator.v1\0" + raw_approval_json` (не подписывайте канонизированный или заново сериализованный JSON). JSON-одобрение должно содержать схему `neverlauncher.ga0480.independent-operator.v1`, точную версию продукта `0.48.0`, точный 40-символьный коммит исходников и SHA-256 **каждого** файла дерева свидетельств.

Неизменяемое дерево свидетельств должно содержать:

- `live.json`: результат настоящей проверки `live_upgrade_0480.py verify` на независимом стенде.
- `legacy.json`: фактическую полную матрицу исторических обновлений нативного CLI.
- `owner.json`: подтверждённые в браузере и Admin UI действия настоящего владельца.
- `full-game/`, `matching-1.17.1/`, `matching-1.21.1/`: фактические подключения JVM Minecraft, наблюдения ServerBridge, обновления и отката и относящиеся к ним исходные свидетельства.
- `staging-workflow.json`, `game-workflow.json`: подлинные свежие метаданные успешных защищённых запусков GitHub `workflow_dispatch` на том же коммите.
- `signed/`: **фактически окончательные** шесть нативных дистрибутивов, манифест выпуска, описи точных байтов и артефакты подписи.

Проверяющий сверяет все байты с независимой подписью оператора, повторно выполняет существующие подробные проверки игры, владельца, устаревших версий и поставки и отвергает устаревшие метаданные запусков. Публикатор дополнительно сравнивает хеши реально публикуемых подписанных пакетов и манифест выпуска с пакетами, одобренными оператором. Эта независимая подпись не заменяет уже действующие проверки Ed25519 подписи выпуска, Authenticode и нотариализации.

Промышленная команда `publish_0370.py` теперь требует `--ga0480-evidence-dir`, `--ga0480-approval`, `--ga0480-signature` и `--ga0480-trusted-key` для версии 0.48.0. Workflow промышленного кандидата выпуска принимает защищённый `ga0480_evidence_run_id`; без него публикация 0.48.0 **блокируется**, а не пропускается и не признаётся успешной. Для предыдущих версий сохраняются их прежние шлюзы.

## Условия отката

До возникновения возможности записи в целевую систему: оставляйте исходную SQLite источником истины, проверяйте резервные копии и восстанавливайте старую конфигурацию службы по журналу оператора. После того как PostgreSQL мог принять записи, **не перезапускайте автоматически старую SQLite** и не очищайте вручную флаг границы записи; остановите запись и независимо согласуйте изменения. Для отката без потери подтверждённых новых записей необходима проверенная обратная миграция.

## Что в этом выпуске НЕ подтверждено локально

Независимой среды или установленного проекта не было; здесь не запускались службы PostgreSQL 17/18, Go 1.27.3, Rust, нативные подписанные установщики и Minecraft E2E. Регрессионные тесты Python проверяют отказ по умолчанию и приёмочный код, но их нельзя представлять как доказательство промышленного GA.
