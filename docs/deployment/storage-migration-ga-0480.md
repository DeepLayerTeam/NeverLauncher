# NeverLauncher 0.48.0 — independent installed-project GA acceptance

## Status / release boundary

`VERSION=0.48.0` is **not a GA certificate**. The application remains unsafe to switch from SQLite to PostgreSQL when independent HTTP Repository / Coordinator / Extensions state has not been translated. The operator from 0.47.5 intentionally sets `cutoverSupported=false`; the PostgreSQL Backend startup gate refuses imported SQLite data without validated parity. Do not remove those guards to make a release job green. In particular, a successful Core SQL import, a `/ready` HTTP 200, or a green scripted unit test is NOT a live cutover.

The 0.48.0 code adds executable independent old-installation acceptance and a signed GA publication boundary. Actual GA publication requires external staging and real Mojang/ServerBridge/browser tests. No GA acceptance evidence was generated by source-tree tests.

## Private independent staging

1. Provision an **isolated**, dedicated, protected runner with an existing copied installation from a supported historical NeverLauncher version. Do not point these scripts at the user's production host. Back up production separately using the normal disaster recovery procedure.
2. Store old backend owner credentials in a **0600** JSON file (`{"email":"...","password":"..."}`; `totp` or `recoveryCode` as required), and restrict the containing directory to 0700. Never print this file or include it in build artifacts.
3. Configure the original Core, HTTP and Coordinator SQLite databases and the original LocalStorage root. Keep the three SQLite stores distinct. Configure a separate PostgreSQL storage root; avoid overlapping paths. If the source project uses S3, this LocalStorage acceptance mode is not applicable and must fail rather than treating bytes as copied.
4. Run `live_upgrade_0480.py capture` **against the real old running Backend**, supplying `--old-version`, base URL, project/profile/channel, owner credentials and the three SQLite paths. This creates verified SQLite online copies and a baseline of authenticated owner/project data and all original local blobs. Run this on the isolated staging copy only.
5. Run the existing `sqlite_pg_cutover_0475.py run` operator. This freezes the writer services, verifies backups, imports/compares data and files and attempts cutover only if its domain-parity gate allows it. It may refuse. An operator error is a failed GA run; never fake `readyForBackendCutover` or edit its journal to clear it.
6. Only after successful cutover, execute `live_upgrade_0480.py verify` with `--baseline`, `--operator-work`, `--backend-env` and `--target-storage`. It reauthenticates the **same real owner**, compares project/profiles/channels/releases/revisions, reads the current Backend version, runs an independent SQL query against the actual service-configured PostgreSQL, validates source SQLite logical contents, and re-hashes the source and target LocalStorage trees.
7. Execute the genuine historical Linux CLI upgrade matrix and the separate protected browser/game/ServerBridge matrix. Preinstalled baseline archives must be SHA256-pinned; skip/fixture substitution is forbidden. Confirm signed OS installer identity on the relevant native OS. Do not equate PE/Mach-O signature *presence* with native trust validation.

The protected workflow `.github/workflows/independent-migration-0480.yml` executes steps 4–6 on the dedicated runner. It intentionally fails if the 0.47.5 cutover gate remains closed. No artifact is uploaded when live verification fails. Only `live.json` is uploaded on success; raw databases, secrets and journals remain on staging.

## Independent operator-signed approval

`scripts/release/ga_gate_0480.py` requires a pinned 32-byte Ed25519 public key and a 64-byte detached signature over `b"neverlauncher.ga0480.independent-operator.v1\0" + raw_approval_json` (do not sign canonicalized/reserialized JSON). The approval JSON must use schema `neverlauncher.ga0480.independent-operator.v1`, exact product version `0.48.0`, exact 40-character source commit and a SHA-256 for **every** file in the evidence tree.

The immutable evidence tree must contain:

- `live.json`: result from real `live_upgrade_0480.py verify` on independent staging.
- `legacy.json`: actual complete historical CLI native upgrade matrix.
- `owner.json`: live owner Admin UI/browser certification.
- `full-game/` and `matching-1.17.1/`, `matching-1.21.1/`: real Minecraft JVM joins, ServerBridge, update/rollback observations and their referenced raw evidence.
- `staging-workflow.json` and `game-workflow.json`: authentic fresh successful protected GitHub `workflow_dispatch` run metadata, same commit.
- `signed/`: **actual final** six native distribution packages, release manifest, exact-byte inventories and signing artifacts.

The verifier checks all bytes against the independent operator signature, reruns existing detailed game, owner, legacy and delivery checks and rejects stale run metadata. The publisher also verifies that the actual published signed-package hashes and release manifest match the operator-approved packages. This independent signature does not replace existing release Ed25519, Authenticode or notarization checks.

Production `publish_0370.py` now requires `--ga0480-evidence-dir`, `--ga0480-approval`, `--ga0480-signature`, and `--ga0480-trusted-key` for version 0.48.0. The production candidate workflow accepts the protected `ga0480_evidence_run_id`; when absent, 0.48.0 publication is **blocked**, not skipped or marked successful. Earlier versions retain their existing gating behavior.

## Rollback conditions

Before any target write becomes possible: keep original SQLite as the source of truth, verify backups and restore old service configuration according to the operator's journal. After PostgreSQL may have accepted writes, **do not automatically restart old SQLite** or manually clear the write-boundary flag; stop writes and independently reconcile them. A tested reverse migration is required to roll back without dropping confirmed new writes.

## What this release has NOT certified locally

No independent environment or installed project was available, PostgreSQL 17/18 services were not run here, and Go 1.27.3 / Rust / native signed installers / Minecraft E2E were unavailable. Python regressions validate fail-closed behavior and the acceptance code but cannot be promoted to production GA proof.
