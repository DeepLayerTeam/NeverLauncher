# Политика проверенного плана ServerBridge (0.24.12)

## Обязательное применение

Задайте **все три** переменные окружения на каждом экземпляре API:

```sh
LAUNCHER_SERVERBRIDGE_REQUIRE_PLAN_POLICY=1
LAUNCHER_SERVERBRIDGE_PLAN_POLICY_FILE=/etc/launcher/bridge-plans.signed.json
LAUNCHER_SERVERBRIDGE_PLAN_POLICY_PUBLIC_KEY=<64-char-hex-offline-policy-public-key>
```

Указание пути к политике или её публичного ключа также включает принудительную проверку. Отсутствующий файл, неверная подпись, истёкшая политика или отсутствие доверенного устройства **запрещают** защищённое подключение. Если ничего не настроено, для поэтапной миграции остаётся доступен прежний сценарий подключения; **устаревший режим не обеспечивает проверку плана компонентов**. Все реплики Backend должны использовать одинаковую конфигурацию политики. Не размещайте закрытый ключ подписания на сервере.

Пример тела политики в UTF-8 JSON; замените демонстрационные хеши и даты реальными измерениями подписанного выпуска:

```json
{
  "schemaVersion": "1.0",
  "epoch": 1,
  "issuedAt": "2026-10-21T00:00:00Z",
  "expiresAt": "2026-10-22T00:00:00Z",
  "requireContinuousGuard": true,
  "allowedPlans": [
    {
      "serverId": "survival-main",
      "projectId": "demo-project",
      "profileId": "survival",
      "channel": "stable",
      "releaseSignature": "<128 шестнадцатеричных символов в нижнем регистре из Manifest v3, подписанного владельцем>",
      "catalogDigest": "<64 шестнадцатеричных символа в нижнем регистре из подписанного каталога v5>",
      "planSha256": "<64 шестнадцатеричных символа в нижнем регистре из нативного resolved-download-plan.v1>"
    }
  ]
}
```

Каждая разрешённая запись плана представляет собой **полную комбинацию** подписи манифеста выпуска, дайджеста его каталога и точного SHA-256 нативного разрешённого плана загрузки; запись привязывается к серверу, проекту, профилю и каналу ServerBridge. Подпись берётся из существующей подписи Ed25519 в *манифесте выпуска* (это не хеш манифеста). Заполните `planSha256` из доверенного предварительного просмотра Desktop после подготовки и проверки конкретного пресета. Не добавляйте в список разрешённых дайджест, присланный неизвестным клиентом без подтверждения.

Подпишите настоящий JSON-документ политики **автономным** Ed25519 seed в шестнадцатеричном формате:

```sh
cd services/api
go run ./cmd/planpolicy-02412 -policy /secure/policy.json -key /secure/offline-policy-seed.hex -out /secure/bridge-plans.signed.json
```

Команда создаёт оболочку политики с `schemaVersion`, Base64 точных подписанных байтов политики и подписью Ed25519 от `Launcher-ServerBridge-Plan-Policy-v1\n` + этих байтов; публичный ключ выводится для конфигурации. Это **отдельный операторский ключ**, не ключ подписи игрового выпуска и не закрытый ключ узла ServerBridge. Храните закрытый seed автономно.

## Порядок выполнения

1. Desktop запускает проверенный Minecraft и завершает аттестацию Continuous Guard v2. Backend выпускает одноразовый Guard-билет, включающий дайджест аттестации, PID процесса Runtime, хеши и привязки сессии/устройства.
2. Авторизованный Desktop запрашивает `POST /api/v1/server-bridge/plan-challenge` для сервера, проекта, профиля и канала. Backend проверяет права проекта, Device Trust и закреплённую политику, создаёт непредсказуемый запрос-подтверждение со сроком 60 секунд и сохраняет его в `device_challenges` (PostgreSQL или память для разработки).
3. Нативная часть Tauri читает из Runtime подписанный установленный активный выпуск; `verified_active_selection_02410` проверяет все управляемые файлы. Затем пересчитывается точный нативный план загрузки и формируется подпись доказательства с разделением доменов при помощи привязанного **аппаратного ключа устройства P-256**. Произвольные списки компонентов и хеши планов, присланные клиентом, нативная команда подписи не принимает.
4. В `POST /api/v1/session/join` передаются доказательство и одноразовый билет Continuous Guard. API проверяет политику, целевой сервер, сессию, устройство/эпоху привязки, точное совпадение разрешённой комбинации, дайджест аттестации Guard и подпись P-256; одноразовый запрос-подтверждение атомарно погашается. Только затем ServerBridge выпускает одноразовый билет подключения.
5. Зарегистрированный узел криптографически подтверждает `validate-join`; прежние проверки сессии, Guard, доверия, целостности выпуска, однократного погашения и маршрутизации сохраняются. При смене политики ранее созданные непогашенные билеты с датой до `issuedAt` аннулируются.

## Ограничения и модель угроз

- **Обязательный Continuous Guard v2** сейчас сертифицирован для Windows. Допуск по защищённому плану намеренно **запрещается по умолчанию** на платформах без такого доказательства; нельзя незаметно переходить к одной лишь подписанной коллекции модов.
- Доказательство подтверждает, что доверенный нативный лаунчер проверил установленные управляемые файлы на момент аппаратного подписания, и связывает измерение с конкретной аутентифицированной сессией и данными Continuous Guard. Само по себе оно **не** подтверждает фактическую загрузку каждого мода JVM Minecraft или совпадение всех байтов памяти JVM с диском. Для более строгой гарантии потребуется будущий протокол измеряемого загрузчика классов и удалённой аттестации.
- Срок действия политики ограничен 30 днями; её можно отозвать, заменив доверенный файл. Используйте короткие интервалы действия. Постоянная защита от возврата к ранее подписанной, но ещё действующей политике в этом выпуске отсутствует.
- Доказательство используется лишь один раз для всех реплик API PostgreSQL. После погашения запроса повтор требует нового запроса-подтверждения и новой аппаратной подписи. Просроченные, изменённые, межсессионные, межсерверные и повторно предъявленные доказательства отклоняются.
- `REQUIRE_PLAN_POLICY=1` обязателен **на всех** репликах API. Выключение проверки возвращает устаревший сценарий и должно считаться осознанным эксплуатационным решением.
