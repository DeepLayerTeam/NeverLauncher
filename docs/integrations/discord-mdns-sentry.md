# Discord, локальное обнаружение и Sentry (0.42.9)

Интеграции используют действующие сетевые транспорты и IPC. Они **необязательны** и не должны блокировать аутентификацию Minecraft или запуск игры. Тестовый двойник в CI подтверждает код протокола, но не доступность Discord, мультикаст-сетей или Sentry в среде пользователя.

## Расширенный статус Discord Rich Presence

Включите его в настройках Desktop, указав действительный ID приложения Discord. Нативный процесс Desktop открывает локальный сокет/канал Discord `discord-ipc-N` и отправляет `SET_ACTIVITY` с ожиданием подтверждения. Desktop обновляет активность каждые 30 секунд и восстанавливает подключение после перезапуска Discord. При отключении Desktop явно очищает активность. Токен бота Discord не используется.

CLI: `nl discord presence --application-id 123456789012345678 --details 'Minecraft' --state 'Playing' --interactive`. Передавайте через stdin JSON-объекты активностей, разделённые строками (`null` очищает). Обновление ожидает подтверждения IPC; при обрыве IPC во время отправки CLI переподключается и делает одну повторную отправку. Бездействующий интерактивный сеанс обновляется каждые 60 секунд. Отклонённая Discord команда возвращается как ошибка и **не повторяется**. При завершении предпринимается попытка очистить Presence. В интерактивном режиме stdin должен принадлежать доверенному процессу, поскольку он управляет публично видимым текстом и URL статуса.

Для настоящего публичного Rich Presence необходимы запущенный Discord Desktop и зарегистрированное приложение Discord. Unix-сокет в CI — лишь локальная проверка протокола IPC. Встроенный frontend Rust Desktop тестируется отдельно от CLI на Go.

## DNS-SD / mDNS

Публикация: `nl lan publish --instance MyNetwork --url https://192.168.1.5:19443 --fingerprint <leaf-cert-sha256>`; перед объявлением убедитесь, что HTTPS-точка уже работает. Обнаружение: `nl lan discover --timeout 5s`. Проверка: `nl lan verify --url https://192.168.1.5:19443 --pin <independently-obtained-leaf-cert-sha256>`.

Публикатор привязывает исходящий UDP-сокет к выбранному локальному адресу, а не к произвольному системному адресу по умолчанию. В качестве объявлений принимаются только успешные DNS-ответы ожидаемого класса и IPv4-адреса вне loopback. Результаты обнаружения остаются **непроверенными**, пока не совпадёт независимо заданный администратором отпечаток TLS-сертификата. Поле `fp` из TXT mDNS никогда не принимается в качестве собственного якоря доверия. Хост, интерфейс и брандмауэр должны разрешать IPv4 multicast 224.0.0.251:5353. Действующий цикл обнаружения объединяет ограниченное число записей PTR/SRV/TXT/A из отдельных пакетов DNS-SD с учётом TTL каждой записи; сообщения PTR goodbye удаляют найденные экземпляры. Также отклоняются дублирующиеся имена экземпляров, объявляющие другой endpoint, а публикация прекращается при исчезновении выбранного интерфейса IPv4. Даже согласованные записи DNS-SD не считаются доверенными: для подтверждённого TLS-соединения требуется отдельно подготовленный отпечаток SHA-256 конечного сертификата. Публикация IPv6 не входит в этот выпуск; реальная совместимость Bonjour/Avahi между хостами всё ещё требует независимой приёмки в LAN.

## Sentry

Backend требует явных `LAUNCHER_SENTRY_BACKEND_ENABLED=true` и `LAUNCHER_SENTRY_BACKEND_DSN=<dsn>`; по умолчанию телеметрия не отправляется. Desktop требует явного согласия пользователя и настроенного DSN Desktop. Backend собирает ограниченные диагностические сведения об ошибках с удалением чувствительных данных, но не тела запросов, заголовки или токены аутентификации. Desktop отправляет только разрешённые кадры ресурсов JavaScript или фиксированную категорию нативной паники.

Транспорты Sentry для Backend и Desktop **не следуют HTTP-перенаправлениям**, предотвращая передачу пакетов событий и заголовков `X-Sentry-Auth` другим origin. Транспорт JVM также явно запрещает перенаправления. Временные ответы HTTP 429/502/503/504 повторяются не более двух раз в пределах трёхсекундного дедлайна запроса с сохранением ID события; ограниченное значение `Retry-After` учитывается. При завершении Backend очередь осушается не дольше пяти секунд. Доставка Sentry выполняется по возможности: ошибки транспорта, переполнение очереди и сбои хоста всё ещё могут приводить к потере диагностики. Чувствительные данные не попадают в постоянный буфер повторной отправки. Настройте обработку данных, доступ к DSN, брандмауэр и сроки хранения на стороне Sentry.

## Границы проверки

Тесты репозитория проверяют реальное обрамление Unix IPC и перезапуск, валидацию ответов DNS-SD и закрепление конечного TLS-сертификата, приём HTTP-конвертов Sentry, повторы и осушение очереди. Настоящая публикация/обнаружение UDP multicast на одном хосте с закреплённой HTTPS-точкой успешно прошла на Linux; необязательный интеграционный тест повторяется командой `LAUNCHER_LAN_E2E=1 go test ./internal/lanmdns -run TestLiveLANPublishDiscoverAndPinnedTLS0429` из `cli/`. Эти тесты не заменяют приёмку с запущенными Discord и приложением, физической LAN с мультикастом между двумя хостами и реальным экземпляром Sentry. До production-сертификации дополнительно обязательны эти внешние проверки и проверка выпуска на шести платформах.
