# Launcher 0.44.9 — интеграционная приёмка переноса Gravit → Launcher

Этот выпуск добавляет исполняемый шлюз приёмки с отказом по умолчанию. Он **не утверждает**, что проект Minecraft действительно прошёл запуск, вход, подключение, переключение или откат в среде разработчика. `go test` проверяет верификатор, а не игровой процесс Minecraft. Для одобрения промышленного Migration GA нужны три независимо подготовленных настоящих эталонных проекта, защищённый исполнитель CI и сохранённые независимые свидетельства.

## Поддерживаемые исходные классы и обязательные проверки

| Эталонный класс (`referenceClass`) | Требуемая реальная среда | Обязательные проверки класса |
| --- | --- | --- |
| `fileauth-single` | Исходный проект Gravit FileAuth, импортированные UUID игроков, настоящий клиент и Minecraft-сервер | `fileauth-login`, `skins`, `negative-auth` |
| `sql-modded` | Исходный проект с SQL-аутентификацией и **настоящими** тестовыми профилями Forge и NeoForge, необязательными модами и реальными серверами | `sql-login`, `forge-launch-join`, `neoforge-launch-join`, `optional-presets`, `skins`, `negative-auth`, `negative-optional` |
| `proxy-network` | Прокси-сеть Gravit, переписанный исходный код пользовательского модуля для целевого проекта, ServerBridge и аутентифицированные серверы | `official-login`, `serverwrapper`, `module-source-port`, `negative-unknown-module`, `negative-auth` |

**Каждый** эталонный проект дополнительно выполняет `uuid-world-plugin-data`, `admin-permissions`, `desktop-cache-install`, `staged-cutover-canary`, `operational-rollback-drill`, `negative-cutover`, `negative-rollback`. Всего 10 + 14 + 12 = **36 независимых исполняемых проверок** для **трёх отдельных проектов, исходных архивов и запусков миграции**, привязанных к одному коммиту Launcher. При отсутствии необходимой среды результат — `BLOCKED`, а не `SKIPPED` или `PASS`. Запрещено подставлять шаблонный вывод или синтетическую фикстуру успеха.

Отрицательные проверки должны реально пытаться выполнить и наблюдать отклонение: неверных, истёкших или отозванных учётных данных (`negative-auth`), конфликтующих необязательных зависимостей (`negative-optional`), неизвестных или неперенесённых JAR Gravit (`negative-unknown-module`), активации без действительного ограждения исходной системы или живой репетиции (`negative-cutover`), отката с изменённой/истёкшей авторизацией снимка (`negative-rollback`). Положительные проверки должны наблюдать настоящий клиентский/Java-процесс и вход на сервер, а не только код завершения CLI. Сохраняйте исходные журналы и серверные наблюдения без токенов доступа и закрытых ключей. Живая репетиция MIG10 обязательна в Backend-отчёте до подписания любого GA. Для `module-source-port` нужно исполнить реальное пользовательское поведение перенесённого расширения, а не просто зарегистрировать его.

## Сборка и настройка оператором

Соберите продукт на закреплённой инструментальной цепочке проекта и проверьте полный Backend, CLI, Admin и поддерживаемые варианты Desktop. Проверьте миграции PostgreSQL и откат на свежей БД. Исходный ZIP Gravit должен содержать распознаваемый манифест `LaunchServer.jar`, совпадать с независимо закреплённым SHA-256 JAR и соответствовать диапазону Gravit `5.7.0`–`5.7.12` для этого шлюза. Версия `5.7.13` распознаётся инвентаризацией, но здесь не сертифицируется. Храните учётные данные у защищённого исполнителя, никогда не передавайте аргументами проверок или в JSON-журналах.

`tools/migration-ga` предоставляет исполняемые команды `certify`, `verify`, `verify-cohort`. План содержит `referenceClass`, исходный архив и SHA-256 доверенного Gravit LaunchServer JAR, SHA-256 целевого выпуска, полный SHA коммита, ID запуска, ID проекта, HTTPS-адрес Backend, абсолютный путь к ключу подписи и **ровно** требуемые проверки для класса. Каждая проверка содержит:

```json
{
  "name": "fileauth-login",
  "command": ["/opt/migration-ga/checks/fileauth-login", "--config", "/srv/isolated/ga/fileauth.json"],
  "executableSha256": "<64-lowercase-hex-SHA256-of-the-executable>",
  "timeoutSeconds": 300
}
```

Указанный путь служит примером: оператор должен установить рабочий исполняемый файл, который действительно проверяет заявленное поведение. Проверяющий закрепляет точные байты **до и после** исполнения, отвергает символьные ссылки и изменённые исполняемые файлы, ограничивает время выполнения и объём стандартного вывода, удаляет ключ подписи и Backend-секреты из окружения дочернего процесса и не публикует недоверенный stderr в журналах CI. Вывод проверки должен соответствовать уже существующей строгой JSON-схеме `Probe`, включать уникальные дайджесты запуска, отчёта, источника и выпуска и ссылаться на **вновь созданный** абсолютный файл свидетельства. Проверка не может просто вывести `passed:true`: она должна создать реальное подтверждающее свидетельство для независимого анализа. Проверяющий сверяет SHA-256 и копирует точное свидетельство вместе с канонической квитанцией проверки в каталог владельца с запретом перезаписи.

```bash
export LAUNCHER_MIGRATION_GA_TOKEN='<short-lived-admin-token>'
go -C tools/migration-ga run . certify \
  --plan /srv/isolated/plans/fileauth-single.json \
  --output /srv/private/ga/fileauth-single-certificate.json \
  --evidence-dir /srv/private/ga/fileauth-single-evidence

go -C tools/migration-ga run . verify \
  --certificate /srv/private/ga/fileauth-single-certificate.json \
  --public-key /srv/private/trusted-ga-pub.pem \
  --evidence-dir /srv/private/ga/fileauth-single-evidence
```

Повторите на независимых исходных проектах классов `sql-modded` и `proxy-network`. Проверьте всю группу:

```bash
go -C tools/migration-ga run . verify-cohort \
 --public-key /srv/private/trusted-ga-pub.pem \
 --fileauth-single /srv/private/ga/fileauth-single-certificate.json \
 --fileauth-single-evidence /srv/private/ga/fileauth-single-evidence \
 --sql-modded /srv/private/ga/sql-modded-certificate.json \
 --sql-modded-evidence /srv/private/ga/sql-modded-evidence \
 --proxy-network /srv/private/ga/proxy-network-certificate.json \
 --proxy-network-evidence /srv/private/ga/proxy-network-evidence
```

`verify` **требует** исходные квитанции и свидетельства, а не один подписанный сертификат. Он отклоняет отсутствующие, лишние, символьно связанные и изменённые свидетельства, подменённые квитанции, неправильные запуски/источники/цели, несогласованные хеши миров/UUID/плагинов, устаревшие сертификаты, неверный ключ подписи и пропущенную обязательную отрицательную проверку. `verify-cohort` также отклоняет отсутствующие/повторно использованные классы, дублирующиеся ID проектов, архивы источников или ID запусков и смешанные коммиты. Сертификаты используют `launcher.gravit-ga-execution.v2` и подпись Ed25519 версии 0.44.9 с разделением доменов; исторические квитанции 0.34 повторно использовать нельзя.

## Состояние CI, хранилища и выпуска

Защищённый процесс CI `.github/workflows/gravit-migration-ga-0340.yml` сначала выполняет модульные/гонковые тесты, интеграцию БД и полные сборки продукта. Затем его защищённая среда `migration-ga-certification` использует три секрета `MIGRATION_GA_{FILEAUTH,SQL,NETWORK}_PLAN_B64`, токен Admin, секреты подписанта/открытого ключа и переменную окружения репозитория `MIGRATION_GA_EVIDENCE_ROOT`. Последняя должна указывать на существующий закрытый каталог 0700 изолированного Linux-исполнителя. Сводки подписанных сертификатов можно загружать как артефакты CI; исходные свидетельства хранятся **только в этом закрытом каталоге**, без публикации в потенциально общедоступных артефактах. Настройте для него отдельные сроки хранения, ACL, очищенные журналы и защищённое резервное копирование. Одобрение администратора и все 36 независимых проверок нужно выполнять заново при изменении исходного ZIP, операторского заключения, активного выпуска, снимка миграции или коммита.

Успешный процесс GitHub Actions **сам по себе** не доказывает, что собственный агент CI использовал настоящие Gravit/Minecraft-файлы или что злонамеренный доверенный оператор не подделал наблюдения. Независимый анализ исходных журналов, свидетельств игры/сервера и результатов учения по откату остаётся обязательным. Проверяющий не переключает старые секреты аутентификации Gravit, токены сеансов, ключи подписи, исходные миры или внешний прокси-трафик. При неудаче выпуск блокируется; автоматического переключения или отката промышленной системы нет.

### Критерии выпуска

- Три отдельных настоящих источника Gravit и запуска миграции Launcher; все проверки класса пройдены с сохранением свидетельств.
- Интеграция PostgreSQL, сборки Admin/Desktop/CLI/Backend, настоящий вход в Minecraft и на сервер, а также отрицательные тесты выполнены на действительно поддерживаемых конфигурациях.
- Проведена реальная репетиция восстановления и отката без скрытой потери миров игроков, UUID, инвентаря, экономики и данных плагинов; оператор задокументировал ограничения и точку невозврата.
- Независимый оператор проверил полный набор свидетельств и одобрил ручные шаги и внешний контроль DNS, прокси и серверов.

Отсутствие закрытой тестовой инфраструктуры — **препятствие** для сертификации промышленной готовности миграции, а не разрешение заменить её имитированным PASS.
