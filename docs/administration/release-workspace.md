# Release Workspace — Launcher 0.21.8

## Назначение

Рабочая панель Admin `#/release-workspace` предназначена для выпуска пакета без ручного JSON. Смените проект через контекст Admin, сохраните серверный черновик, выберите существующий профиль, Minecraft и загрузчик, создайте пакет и загрузите файлы. Затем выполните `validate`, `sign`, `stage`, `integrity-check`, проверьте runtime policy и запустите публикацию из предпросмотра через Unified Operations. Отдельный экран `#/job-monitor` открывает сохранённое задание по correlation ID, включая историю попыток и возможность разрешённого retry.

## Права и безопасность

- Просмотр и изменение черновиков: `release:prepare` для соответствующего проекта; владельцу черновика требуется действующая авторизация при **каждом** запросе. Другие операторы не могут читать чужие черновики.
- Загрузка: `file:write`; подпись: `release:prepare` + свежая phishing-resistant аутентификация. Публикация и откат: `release:publish` + актуальный step-up MFA.
- Сохранение использует `revision` для защиты от перезаписи между вкладками. Код HTTP 409 требует повторной загрузки черновика (изменения другого браузера не перезаписываются).
- Черновики хранятся в PostgreSQL (`0053_release_workspace_0218.sql`); in-memory хранилище применяется только в тестовом/разработческом режиме и **не переживает** перезапуск API.
- Изменения профиля, канала, версии и загрузчика блокируются после привязки созданного пакета. Связанный пакет проверяется на соответствие идентичности и реально записанной Minecraft/loader metadata; связанную job можно получить только для этого владельца и пакета.
- Подтверждение операций строится по ответу `/api/v1/operations/validate`; изменение канала делает Backend с повторной проверкой прав, integrity/policy, lease/fencing. Предпросмотр не заменяет повторную проверку в момент исполнения.

## Проверка реального запуска

`POST /api/v1/packages/{packageId}/smoke-test` в 0.21.7 — **совместимый псевдоним integrity-check**, который не запускает Minecraft. Release Workspace сознательно не выдаёт его за smoke-test. Фактический smoke/run должен быть выполнен доверенным CI/runtime-agent; импортируйте полученный **подписанный** `runtime-validation/v1` JSON (поля `keyId`, `evidence`, `signature`) через форму. Backend проверяет Ed25519-подпись, ключ из `LAUNCHER_RUNTIME_VALIDATION_KEYS_JSON`, привязку к актуальному digest, OS/JRE/launcher факты и результат реального клиента. Для проектов с `requiredLevel=runtime` (и при необходимости `requireServerJoin=true`) сервер **не выпустит** пакет без соответствующего runtime PASS; устаревшее evidence отвергается. Встроенного браузерного/серверного эмулятора запуска Minecraft эта версия не обещает.

## Сохранение и восстановление

`GET /api/v1/release-drafts?projectId=...` возвращает доступные владельцу черновики. `POST /api/v1/release-drafts` создаёт запись, `GET /api/v1/release-drafts/{id}` читает, `PUT` сохраняет с optimistic revision, `DELETE` удаляет **только черновик**. `GET /api/v1/release-drafts/{id}/operation` восстанавливает связь с операцией публикации даже если браузер закрылся до сохранения `jobId` в черновике: постоянный ключ `release-workspace-{draftId}` ведёт к одному durable job. После потери ответа операции пользователь может возобновить наблюдение и безопасно повторить запрос с тем же ключом, не создавая второй публикации. Отмена возможна только до фактического исполнения.

## Применение миграции и проверки

Перед развёртыванием выполнить стандартный migration apply для Backend; `0053_release_workspace_0218.sql` применяется с контрольной суммой, как и все предыдущие миграции. Рекомендуемые проверки: `cd services/api && go test ./internal/httpapi ./internal/repository -run 'TestRelease' -count=1`, `cd apps/admin && npm ci && npm run test && npm run build`, `python3 scripts/version/manage.py check`.

Архив исходников 0.21.8 был подготовлен без доступного npm registry и Go module cache, поэтому полная production-сборка и E2E должны быть выполнены в CI перед выкладкой.
