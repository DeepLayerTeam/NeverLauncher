# Launcher 0.21.9 — Операции ServerBridge

## Развёртывание

1. Примените миграцию `0054_serverbridge_operator_0219.sql` штатным механизмом миграций Backend. Она добавляет существующей роли `operator` право `serverbridge:control`, но **не** `serverbridge:console`; кастомным ролям права выдаются отдельно. Внутри проекта полномочия ограничены реальным `projectRoles` пользователя.
2. Разверните Backend и Admin из одного коммита и перезапустите API. Протокол v3 и сетевые контракты Bridge/ACK не меняются, плагин узла заменять не требуется.
3. В Admin выберите проект → **ServerBridge**. Для команд потребуется действующая аутентификация с MFA не старше пяти минут. Раздел «Безопасность сессии и ключи доступа» позволяет пройти дополнительную проверку с защитой от фишинга.
4. Проверьте жизненный цикл на действующем узле: `server.save` → `pending` → `leased` → Bridge ACK `succeeded`/`failed`/`indeterminate`. Не считайте `leased` доставкой или исполнением. Проверяйте фактическое состояние сервера при неопределённом исходе.

## Действующий REST API

- `GET /api/v1/server-bridge/projects/{projectId}/overview` — данные только выбранного проекта; сервер проверяет `project:read`, фильтрует nodes, topology, commands и audit. Глобальный `GET /api/v1/server-bridge/overview` сохранён и по-прежнему требует глобальный `project:read`.
- `POST /api/v1/server-bridge/servers/{serverId}/control` — **существующий** протокол команд с полями `type`, `payload`, `idempotencyKey` и недавней проверкой MFA, `serverbridge:control`. Для консольных команд дополнительно нужно разрешение `serverbridge:console`. Авторизация по проекту сервера и криптографическая идентичность среды выполнения проверяются сервером Backend.
- `GET /api/v1/server-bridge/servers/{serverId}/control/{commandId}` — подробности команды и терминальный ACK.

## Статусы и достоверность

| Состояние БД v3 | Отображение Admin | Гарантия |
|---|---|---|
| `pending` | queued | Запрос сохранён, доставки нет |
| `leased` | dispatched | Задание получено при опросе моста, доставки/выполнения ещё нет |
| `succeeded` | executed | Bridge прислал подтверждённый успешный ACK |
| `failed` / `unsupported` | failed | Bridge подтвердил неуспех |
| `indeterminate` / `expired` | indeterminate | Исход не подтверждён; не создавать слепо повтор |

У ServerBridge v3 нет самостоятельного подтверждённого промежуточного состояния `delivered` перед подтверждением выполнения (ACK). Admin **не фабрикует** такое состояние по `leased`: оно отображается только при явном статусе `delivered`, если когда-либо будет поддержано согласованным контрактом. События доставки и ACK в журнале аудита служат диагностикой, но не подменяют статус команды. Протокол v3 не изменён.

Снимок телеметрии можно использовать, лишь если сигнал состояния и сам снимок актуальны (не старше 120 секунд), снимок Admin получен недавно, а `runtimeId` и `runtimeEpoch` совпадают. Несовпадение, отсутствие данных или задержка отображаются как «неизвестно» или «устарело», а не как `0` игроков / TPS. Число игроков доступно, список никнеймов отсутствует в текущем протоколе телеметрии v3. Для player.kick/ban имя вводится вручную.

При потере HTTP-ответа браузер хранит исходное тело запроса и ключ идемпотентности в `sessionStorage`. Кнопка «Повторить с тем же ключом» использует исходное тело запроса. Создавать **новую** команду после неопределённого исхода следует только после проверки реального состояния сервера. После получения ID команда отслеживается через отдельную конечную точку API независимо от обновления страницы; последние команды доступны на обзорном экране.

## Ограничения проверки

Нужно выполнить промышленную сборку Vite с официальными типами React, интеграционные тесты Go на реальной БД PostgreSQL, подписанные сигналы активности и подтверждения от v3 узла и сквозные браузерные тесты с настоящей MFA. Без этих проверок GA эксплуатацию нельзя считать сертифицированной.
