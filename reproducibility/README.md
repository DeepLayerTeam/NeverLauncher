# Launcher 0.53.0 — базовый снимок исходников и независимая нативная воспроизводимость

## Канонические отслеживаемые файлы

- `primary-payload.json` определяет точные имена шести неподписанных артефактов для `VERSION` (0.53.0).
- `baseline.json` фиксирует фактические текущие входные данные сборки и релиза, файлы зависимостей, SDK/инструменты и процессы CI.
- `python3 scripts/release/inputs_guard_0461.py verify` обязан проходить до и после сборок релиза; `freeze` — явная процедура пересоздания базового снимка с обязательным рассмотрением, **а не** проверка.
- Исторические имена инструментов `*_0470.py` обозначают происхождение, а не жёстко заданную версию выпуска.

## Границы

Шесть **неподписанных** пакетов из `primary-payload.json` содержат настоящие скомпилированные исполняемые файлы, зафиксированные **до** платформенного подписания. Оба независимых набора сборщиков должны выпускать побайтно идентичные ZIP/TAR.GZ-архивы, включая все обычные файлы. Это не копии уже подписанных пакетов. Воспроизводимость не превращает поддельную программу в действительный лаунчер; нативная приёмка и существующие требования релизных подписей обязательны.

`reproducible_0470.py` — исполняемый Python, а не заготовка контрактов. Он проверяет формат CPU (PE64/ELF64/Mach-O), наличие обязательных скомпилированных компонентов, безопасность путей, ограничения размера распаковки, SHA-256 всего архива, а также хеш и режим каждого файла. `unsigned_package_0470.py` строит канонические пакеты из действительных скомпилированных компонентов до Authenticode/codesign и отклоняет отсутствие исполняемых файлов и перезапись.

## Независимые прогоны

Тесты воспроизводимости исходников запускаются в `.github/workflows/ci.yml`; для реального выпуска требуются отдельные наборы нативных сборщиков и независимо подписанные доказательства точного совпадения байтов. Успешные модульные тесты не подразумевают автоматического PASS выпуска на шести платформах. Оба сборщика обязаны собирать реальные артефакты ОС/процессора; сравнивающий аудитор перечитывает все архивные байты и проверяет подписи. Условие выпуска отклоняет отсутствующие, изменённые или относящиеся к другому коммиту доказательства. Фиксация Windows и macOS выполняется до платформенного подписания, Linux — до делегированного подписания пакета. Произвольные сборки разработчика никогда не считаются подписанными промышленными поставками.

Внешние предварительные требования: нативные исполнители, совместимые зависимости Go/Rust/Java/Node, `LAUNCHER_COMPONENT_SET_ED25519_PUBLIC_KEY` (точный открытый ключ, встроенный в обе сборки), отдельные удостоверения Ed25519 обоих сборщиков, их независимо закреплённые открытые ключи и чистый точный коммит. Успешный процесс требует настоящих нативных сборок; локальные тесты исходников этого не заменяют.

## Команды проверки

Каждый сборщик фиксирует шесть реальных неподписанных артефактов и подписывает канонический JSON:

```sh
python3 scripts/release/reproducible_0470.py capture \
  --bundle /actual/unsigned --builder builder-a --runner physical-runner-a \
  --commit <FULL_GIT_COMMIT> --out /evidence/a.json
python3 scripts/release/reproducible_0470.py sign \
  --report /evidence/a.json --private-key /external/a-ed25519.pem --out /evidence/a.sig
```

Повторите процесс на другом исполнителе с **другим доверенным ключом** сборщика B. Затем сравните оба неизменяемых набора через `reproducible_0470.py compare --a-report ... --a-sig ... --a-key ... --a-dir ... --b-report ... --b-sig ... --b-key ... --b-dir ... --out ...`. Команда требует совпадения всех шести архивов и каждого файла, перечитывая настоящие байты вместо доверия декларациям JSON.

Платформенная подпись изменяет конечное содержимое PE/Mach-O, поэтому побайтное сравнение подписанных ZIP установщиков с неподписанными архивами — некорректная проверка воспроизводимости. Windows требует нативной проверки цепочки Authenticode и временной метки RFC3161, macOS — codesign, Gatekeeper и нотаризации, Linux — существующей релизной подписи Ed25519 и контрольных сумм. Третий независимый доверенный оператор должен выполнить эти настоящие проверки ОС/CLI для **точно заданных подписанных файлов**, проанализировать преобразование при подписании и создать канонический подписанный отчёт `launcher.native-signing-approval.v1`. Команда `link` проверяет его отдельную подпись Ed25519, точный хеш результатов сравнения неподписанных архивов, SHA-256 всех шести подписанных пакетов, SHA-256 внешнего манифеста релиза, заявление о проверке подписанного релиза и независимость всех трёх доверенных ключей. Существующий релизный CLI действительно проверяет подпись Ed25519 релиза до этого этапа. Команда отклоняет отсутствующую цель и отсутствие нативного одобрения; **она не выполняет** нативную проверку Windows/macOS на Linux.

### Подтверждения настоящей нативной проверки (обязательны)

На нативных платформах используйте `scripts/release/native_verify_0470.py --target windows-x64 --unsigned-dir /verified/unsigned --signed-dir /frozen/signed --release-cli /path/to/launcher-cli --public-key /trusted/release-root.pem --trust-policy /trusted/trust-policy.json --trust-state /verified/trust-state.json --out /evidence/windows-x64.json` (замените цель и пути для каждой ОС). Скрипт проверяет действительное решение о доверии релизного CLI по Ed25519 и настоящий подписанный пакет, а также signtool Windows с цепочкой временных меток, неизменность исполняемых байтов Linux или codesign macOS, Gatekeeper и прикреплённую нотаризацию. На Windows нормализация каталога сертификатов/контрольных сумм также доказывает, что подписант не изменил исполняемый код или посторонние части PE.

Независимый оператор подписывает канонические нативные подтверждения через `reproducible_0470.py sign`; сохраните `<target>.json` и `<target>.sig` для всех шести целей. Их точные SHA-256 должны присутствовать в независимо подписанном отчёте одобрения как `targets[target].nativeReceiptSha256`. Команда `link` требует `--native-reports-dir`, проверяет каждое нативное подтверждение по действительной цели, фактическому неподписанному/конечному SHA-256 и релизному манифесту и отклоняет отсутствующие или сфабрикованные заявления о преобразовании неподписанного файла в подписанный. На macOS преобразования подписей Mach-O после нотаризации всё равно требуют отдельного аудита, поскольку codesign изменяет расположение команд загрузки и linkedit; одна нотаризация не доказывает неизменность исходного исполняемого содержимого.

Отчёт одобрения создаётся **после** окончательного подписания и нативной приёмки; независимый оператор не может заранее одобрить неизвестные будущие подписанные байты. Поэтому для однопроходной сборки релиза одобрение должно ссылаться на уже зафиксированный окончательный кандидат с идентичными байтами и манифестом (подготовка → продвижение). Любое изменение требует нового одобрения. `build-release.sh` блокирует публикацию без внешне утверждённой записи. `REPRODUCIBILITY_LINK_0470.json` — внешнее подтверждение второй подписи, а не скрытая модификация ранее подписанного релизного манифеста.

## Строгий порог приёмки

- Два независимых набора **настоящих** сборок для шести обозначенных сочетаний ОС/процессора; все шесть пар SHA-256 полных архивов должны совпадать.
- Совпадают хеши исходных данных из отслеживаемого `baseline.json` (пересоздаются только через проверенный `inputs_guard_0461.py freeze`), исходный коммит и неизменяемый релизный контракт; неконтролируемое изменение файлов зависимостей запрещено.
- Нативные проверяющие анализируют каждый настоящий окончательный подписанный пакет и проверяют соответствующую платформенную подпись; релизный CLI проверяет конечный манифест Ed25519.
- Разные закреплённые ключи подтверждают сборщика A, сборщика B и оператора; все доказательства относятся к одним точным байтам.
- Отсутствующие, отменённые, пропущенные или неуспешные цели получают **BLOCKED**, никогда `PASS`.

**Локальные тесты исходников не сертифицируют этот выпуск.** Проект не может заявлять независимую воспроизводимость на шести платформах или нотаризацию, пока внешний процесс действительно не завершится успешно и его результаты/подписи не будут доступны. Успешные выдуманные подтверждения и релизные исполняемые файлы намеренно не добавляются в дерево исходников.
