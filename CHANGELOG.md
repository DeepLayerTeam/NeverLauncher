После первого принятия конкретной версии другой `RELEASE_MANIFEST.json` с той же версией отклоняется как одинаковый-версия equivocation.

Параллельный проверяющий модуль не может пройти anti-откат precheck со старым снимок состояние; устаревший блокировка от завершившегося PID восстанавливается автоматически, актуальный PID блокирует второй процесс.

- После долговременный `rolled-back`/`committed` журнал staging/backup/failed полезная нагрузка очищаются, но аудит журнал сохраняется. Очистка никогда не удаляет компонент-дерево путь вне `.neverlauncher/updater`.
- Исправлен репозиторий-политика исполнитель: итоговый FAILED/OK вычисляется после всех политика blocks, поэтому поздние проверки больше не могут без уведомления добавлять ошибки после уже напечатанного `OK`.
- Добавлены regression/self-test контроль `migration-stabilization-01510.py`, модульные тесты доверие-состояние migration/lock/component-state migration/rollback очистка и обязательная интеграция в CI, предварительная проверка, релиз doctor и публикация-проверка.

DB миграция не требуется. Перед развёртывание достаточно сохранить резервное копирование локального install/trust состояние; первый 0.15.10 verify/update мигрирует его атомарно. Для явной проверки используйте `nl update migrate-state --root <install>` и `nl update stabilization-self-test`.

## 0.14.10 — Миграция + стабилизация

`0.14.10` завершает линию ServerBridge 2 перед следующим feature-релизом: схема и runtime-поведение 0.14.1–0.14.9 сохранены, а migration/maintenance путь стабилизирован для долгоживущих active/active инсталляций.

- Миграция `0030_serverbridge_migration_stabilization_01410` безопасно seal-ит уже истёкшие активный подключение tickets/handoffs, устаревший топология и истёкший подписанный одноразовые значения после остановленного/прерванного 0.14.9 обслуживание успешно.

Миграция: резервное копирование → остановить 0.14.9 API реплики → `nl db migrate apply` → `nl db migrate verify` (текущий: `0030_serverbridge_migration_stabilization_01410`) → запустить 0.14.10 реплики. Узел идентичности, релиз хеширует и действительные tickets/handoffs миграция не переписывает.

## 0.14.9 — Публичный ServerBridge Матрица + HA/hardening

`0.14.9` переводит ServerBridge 2 из единый-экземпляр-friendly режима в явно active/active-safe эксплуатацию и публикует каноническую матрицу всех 11 поддерживаемых мост цели. ## 0.14.3 — Одноразовый Подключение Билеты

- Миграция `0023_one_time_join_tickets_0143.sql` добавляет версия идентичность привязка и сохранённый использование доказательство (`redeemed_identity_epoch`, отпечаток ключа, SHA-256 подписанный-запрос одноразовое значение, IP). Активный билеты 0.14.2 отказ с блокировкой инвалидируются при обновление.
- `CreateServerBridgeJoinTicket` получает фактическую текущую идентичность под transaction/advisory блокировка; ротация между предварительной проверкой и выдача не позволяет выпустить билет на выведенный из эксплуатации ключ.
- Использование выполняется одним conditional PostgreSQL `UPDATE... WHERE status='active'` с проверкой билет версия, TTL, сервер ID, выдача идентичность и текущей активный узел идентичность. Параллельный/повторное воспроизведение проверять получает отказ.
- Standard Minecraft/Yggdrasil `/join → /hasJoined` также переведён на одноразовое использование: проверки IP/trust/integrity выполняются до погашения, затем первый валидный `/hasJoined` атомарно меняет `active → consumed`; повторный не авторизует игрока. Устаревший временный строки 0.14.2 очищаются на миграция граница.
- API возвращает `oneTime=true`, `ticketId`, `ticketVersion=2` и публичный выдача идентичность привязка; внутренние access/session/device хеширует в подключение ответ не раскрываются.
- Добавлены concurrency/replay регрессия, точный миграция репетиция `0.14.2 → 0.14.3`, PostgreSQL использование-доказательство E2E и обязательный автономный контроль выпуска.

Миграция: перед запуском 0.14.3 остановите 0.14.2 API экземпляры, примените/проверьте `0023_one_time_join_tickets_0143`, затем выдавайте только свежие подключается. Старые активный авторизация намеренно не сохраняются через граница безопасности.

## 0.14.2 — Криптографический Узел Идентичности

`0.14.2` убирает общий ServerBridge bearer учётные данные из рабочий узел-аутентификация граница. Velocity/Paper/Purpur создают локальную Ed25519 идентичность, Серверная часть хранит только публичный key/fingerprint/epoch в PostgreSQL, а heartbeat/validate/has-joined/audit запросы подписываются по канонический method/path/body SHA-256 с метка времени и одноразовый одноразовое значение.

- Добавлена синхронная API/CLI миграция `0022_serverbridge_crypto_node_identities_0142.sql`: публичный идентичность материал, `identity_epoch`, уникальный отпечаток ключа и PostgreSQL одноразовое значение повторное воспроизведение хранилище. Устаревший 0.14.1 токен хеширует очищаются, активный узлы становятся `identity-enrollment-required`, активный подключение билеты инвалидируются.
- Узел-аутентификация заголовки: `X-NeverLauncher-Node-Id`, `X-NeverLauncher-Node-Key-Fingerprint`, `X-NeverLauncher-Node-Timestamp`, `X-NeverLauncher-Node-Nonce`, `X-NeverLauncher-Node-Signature`; подпись Ed25519 проверяется до разбора полезная нагрузка, метка времени допускает только ограниченный clock skew, одноразовое значение использовать выполняется атомарно.
- `POST /api/v1/server-bridge/servers/{serverId}/rotate-identity` выполняет enrollment/rotation открытый ключ, увеличивает идентичность эпоха, сбрасывает heartbeat/integrity состояние и инвалидирует незавершённые подключение билеты. Старый `/rotate-token` и `ServerToken` удалены из runtime/OpenAPI.
- Мост плагины сохраняют закрытый ключ только в локальном `node-identity.properties`, проверяют keypair/fingerprint при загрузке и подписывают каждый повторить новым одноразовое значение.
- E2E переведён на реальное Ed25519 enrollment/signing; добавлен точный миграция репетиция `0.14.1 → 0.14.2` и обязательный автономный контроль выпуска.

Миграция: перед запуском 0.14.2 примените/проверьте `0022_serverbridge_crypto_node_identities_0142`. После обновление установите мост 0.14.2 и регистрировать его открытый ключ через `rotate-identity`; закрытый ключ Серверная часть не получает.

## 0.14.1 — ServerBridge Протокол v2 + PostgreSQL источник истины

`0.14.1` переводит ServerBridge из process-local/snapshot состояние в отдельный рабочий хранение граница. В PostgreSQL теперь хранятся узел идентичность и сервер учётные данные хеш, плагин integrity/heartbeat состояние, краткоживущий подключение билеты и texture профили; среда выполнения JSON снимок больше не является источником истины для ServerBridge при SQL репозиторий.

- Добавлена синхронная API/CLI миграция `0021_serverbridge_protocol_v2_0141.sql`: `server_bridge_nodes_v2`, `server_bridge_join_tickets_v2`, `server_bridge_textures_v2`, индексы и DB-уровень инварианты Протокол v2.
- Подключение авторизация стал одноразовым: активный билет живёт 120 секунд и после успешных trust/integrity проверок атомарно переводится PostgreSQL `UPDATE... WHERE status='active'` в `consumed`. Повторная сервер валидация не авторизует игрока.
- Register/credential ротация и заменять активного билет сериализованы транзакция-область рекомендательный блокирует; ротация инвалидирует незавершённые билеты этого узел.
- Velocity/Paper/Purpur bridge-клиенты отправляют `protocolVersion: 2` на heartbeat/validate. Серверная часть возвращает `426 Upgrade Required` с `serverbridge_protocol_unsupported` для старого сетевой протокол.
- Устаревший 0.14.0 снимок импортирует только восстанавливаемые узел metadata/textures. Поскольку открытый текст учётные данные и токен хеш намеренно не сериализовались, такой узел получает `credential-rotation-required` и не может аутентифицироваться до административной ротации токен; устаревший активный подключается не переносятся.
- PostgreSQL изменение ошибка для целостность сигнал состояния и texture состояние теперь отказ с блокировкой, а не маскируются успешным API-ответом.

Миграция: перед запуском 0.14.1 примените/проверьте `0021_serverbridge_protocol_v2_0141`. После обновление зарегистрированные через снимок узлы с `credential-rotation-required` необходимо один раз ротировать через административный ServerBridge эндпоинт.

## 0.14.0 — NeverGuard Релиз

`0.14.0` закрывает NeverGuard как рабочий релиз граница поверх уже реализованных Windows/Linux/macOS Защита, аутентифицировать IPC v4, Целостность Свидетельство и проверяемый сервером Защита Аттестация. Сетевой протокол не меняется: совместимость 0.13.x сохраняется на IPC v4, но Настольное приложение теперь после аутентифицировать рукопожатие обязательно запрашивает MAC-защищать `status` и отказ с блокировкой сверяет фактические `productVersion`, платформа идентичность и протокол версия Защита до допуска среда выполнения.

- Серверная часть использует Защита релиз политика **схема 2.0**: точный `NeverGuard SHA-256 + Desktop SHA-256` пара хранится внутри платформа пространство имён (`windows`/`linux`/`macos`). Это устраняет декартово смешивание хеширует из разных сертифицированных сборок и кроссплатформенный повторное использование.
- Для Серверная часть `0.14+` устаревший flat список разрешений отклоняется. Запрос и одноразовый запускать билет криптографически/сессионно связываются с релиз-политика схема, Защита протокол и доверенное устройство платформа; актуальный Minecraft/ServerBridge reevaluation применяет ту же точный-пара политика.
- Рабочий политика требует `authenticode` для Windows и `developer-id-notarized` для macOS; Linux фиксируется как `integrity-only`. Windows артефакт пары дополнительно требуют `requireAuthenticode=true`.
- Платформа пакет builders генерируют v2 fragments из фактических финальных бинарные файлы. `scripts/release/merge-guard-release-policy.py` объединяет только полный Windows+Linux+macOS рабочий задать и отказ с блокировкой отклоняет unsigned/ad-hoc fragments.
- Кроссплатформенный Защита CI получает обязательный `neverGuardRelease0140`, проверяет v2 точный-пара метаданные и фиксирует `releasePolicySchema=2.0` + аутентифицировать релиз идентичность в сертификация свидетельство.
- Новый `neverguard-release-0140` контроль включён в CI, строгий предварительная проверка и `nl release doctor`.

Миграция: база данных схема остаётся на запечатанный `0020`; 0.14.0 меняет release-policy/configuration граница, а не сохранённый DB форма. Перед рабочий развёртывание необходимо заменить `NEVERLAUNCHER_GUARD_RELEASE_ALLOWLIST_JSON` на объединённый политика v2 для 0.14.0.

## 0.13.10 — Миграция, совместимость, стабилизация

`0.13.10` закрывает upgrade/stability-контур NeverGuard после кроссплатформенный сертификация 0.13.9. Релиз не добавляет новый Защита протокол: Windows/Linux/macOS остаются на аутентифицировать IPC v4 и прежних аттестация схемы, но сохранённый безопасность состояние и релиз свидетельство получают отказ с блокировкой инварианты.

### Миграция

- Добавлена синхронная API/CLI миграция `0020_guard_migration_compatibility_stabilization_01310.sql`. Она не «чинит» неоднозначные безопасность строки молча: обновление останавливается, если `integrity_verified=true` имеет неполный/устаревший Защита снимок либо `integrity_verified=false` содержит частичные Защита hashes/version/timestamp.

## 0.13.9 — Кроссплатформенный Защита CI Матрица + сертификация релиза

`0.13.9` связывает уже реализованные Windows/Linux/macOS NeverGuard production-контуры с единым машинно проверяемый контроль выпуска. PASS больше не выводится из наличия платформа задачи или вручную записанного поля: каждая ОС публикует отдельный `guard-ci-result.json` для точный commit/run, aggregator повторно проверяет обязательные проверяет и SHA-256 артефактов, а `nl release publish-check` заново сверяет те же платформа артефакты внутри финального комплект релиза.

### Кроссплатформенный Защита CI матрица

- `guard-ci/targets.json` фиксирует три обязательных цель: `guard-linux-amd64`, `guard-windows-amd64`, `guard-macos-universal`, runner/platform/arch и полный обязательный проверка-задать. Версия диспетчер синхронизирует `productVersion` этого policy-файла с корневым `VERSION`.
- Linux/Windows/macOS CI задачи после нативный тесты и платформа рабочий контроль создают `guard-ci-result.json` с точный исходник фиксация, Действия запуск ID, подписание режим и SHA-256/size пяти объектов: платформа пакет, Настольное приложение, NeverGuard, пакет манифест и Защита релиз список разрешений.
- Агрегат задача отказ с блокировкой отклоняет missing/duplicate цель, несоответствие commit/run, ослабленный проверка-задать, дубликат артефакт filename или изменённый результат свидетельство. Итоговые `GUARD_CI_TARGETS.json` и `GUARD_CI_MATRIX.json` являются CI свидетельство, а не вручную выставляемым статусом.
- CI сертификация намеренно не заявляет владение рабочий поставщик-подписание учётные данные: Windows CI использует неподписанный разработка пакет, macOS — специальный CI подписание, Linux — целостность-только режим. Рабочий Authenticode/Developer ID/notarization остаются отдельными платформа релиз требования.

### Сертификация релиза

- `scripts/guard_ci/stage_release.py` переносит в релиз каталог именно сертифицированные CI артефакты и перед копированием заново проверяет их размер/SHA-256. Пересборка после матрица PASS не считается тем же свидетельство.
- `nl release build` для `0.13.9+` требует Защита matrix/targets и создаёт `GUARD_CI_CERTIFICATION.json`, который фиксирует политика, матрица хеши и точный список сертифицированный платформа артефакты.
- `RELEASE_MANIFEST.json` помечает `guardCICertified`, а все Защита свидетельство и Windows/Linux/macOS binaries/packages/manifests/allowlists входят в общий `SHA256SUMS`/Ed25519/provenance граница.
- `nl release publish-check` повторно валидирует цель политика, матрица, сертификация и хэширует каждый сертифицированный платформа артефакт из комплект. Post-CI replacement/tampering, даже при сохранённом JSON PASS, блокирует публикацию.
- Релиз builder для `0.13.9+` требует одновременно Совместимость, Доверие к устройству и Защита сертификация свидетельство для готовый к публикации комплект; неполный набор остаётся только непубликуемым кандидат.

## 0.13.8 — macOS рабочий реализация

`0.13.8` добавляет отдельный рабочий NeverGuard граница для macOS вместо Linux-compatible резервный вариант. Настольное приложение запускает соседний универсальный Mach-O `neverguard`, взаимно аутентифицирует его по Unix-домен сокет/HMAC протокол v4 и проверяет PID/UID узел учётные данные до выдачи integrity/attestation данных.

### macOS среда выполнения граница

- Настольное приложение и NeverGuard применяют `PT_DENY_ATTACH`, `RLIMIT_CORE=0`, закрытый umask и очищают `DYLD_*`/`_XPC_DYLD_*` окружение; Защита дополнительно ставит kqueue `EVFILT_PROC/NOTE_EXIT` watch на лаунчер родительский. Ошибка усиление защиты блокирует запуск отказ с блокировкой.
- IPC создаётся только в приватном среда выполнения каталог, сокет имеет режим `0600`, а узел PID/UID сверяются ядро учётные данные. Инициализировать секрет передаётся только через inherited стандартный ввод и после рукопожатие заменяется производный сессия ключ.
- Minecraft/Java запускается в отдельной группа процессов; среда выполнения политика и остановка путь управляют всей группой, чтобы дочерние процессы не переживали контролируемый primary процесс.
- macOS Целостность Свидетельство v1 измеряет SHA-256 Desktop/Guard Mach-O, PID/родительский/UID/GID/процесс-group граница и код-подписание состояние. Отдельная macOS Защита Аттестация фиксирует Усиленный Среда выполнения, библиотека валидация и среда выполнения политика в сервер-запрос-привязанный хеш.
- Серверная часть проверяет отдельные macOS схемы, релиз SHA-256 список разрешений, устройство подпись, freshness/replay, UID/GID граница, код подпись, Усиленный Runtime/library валидация и все обязательные macOS процесс-политика флаги.

### Подписанный и нотариально заверенный рабочий пакет

- `build-macos-desktop.sh` строит универсальный `arm64 + x86_64` Desktop/NeverGuard, подписывает их Разработчик ID Приложение с Усиленный Среда выполнения и формирует `.app`. Рабочий сборка требует Команда ID и `notarytool` профиль, отправляет комплект на notarization, выполняет stapling и Gatekeeper assessment.
- `MACOS_PACKAGE_MANIFEST.json` фиксирует version/platform/protocol/hardening/Team ID; релиз Настольное приложение до запуск процесса Защита проверяет структура, ownership/permissions, ожидаемый код-подписание identifiers, Команда ID, Усиленный Среда выполнения, библиотека валидация, deep app подпись и Gatekeeper/notarization состояние.
- Релиз сборка генерирует `GUARD_RELEASE_ALLOWLIST_MACOS.json` из SHA-256 финальных подписанных Mach-O. Специальный подписание разрешён только явным `--allow-ad-hoc` для CI/development и не проходит рабочий пакет проверяющий модуль.
- CI использует отдельный macOS нативный задача: Rust fmt/test/clippy, подписанный Защита интеграционный тест и универсальный сборка. Автономный контроль `macos-production-implementation-0138.py` обязателен в репозиторий policy/preflight.

Граница остаётся пользовательский режим: root/kernel злоумышленник и компрометация Разработчик ID ключа находятся вне локальной модели доверия. Удалённое решение всё равно принимает Серверная часть по hardware/device-key подпись, релиз список разрешений и одноразовой Защита Аттестация.

## 0.13.7 — Linux рабочий реализация

`0.13.7` переносит NeverGuard рабочий граница на Linux как отдельную native-реализацию, а не как Windows-compatible stub. Настольное приложение запускает соседний `neverguard` через приватный Unix-домен сокет, взаимно аутентифицирует процесс инициализировать-секрет/HMAC протоколом v4 и проверяет ядро узел учётные данные до любого integrity/attestation ответа.

### Linux среда выполнения граница

- NeverGuard и Minecraft среда выполнения получают `PR_SET_PDEATHSIG=SIGKILL`, `PR_SET_NO_NEW_PRIVS=1`, отдельную группа процессов и `RLIMIT_CORE=0`; Защита дополнительно отключает dumpability/ptrace exception и использует приватный umask. Ошибка применения/проверки блокирует запускать отказ с блокировкой; остановка/выход primary Java дополнительно завершает всю среда выполнения группа процессов.
- IPC размещается только в владелец-только `XDG_RUNTIME_DIR/neverlauncher` (с безопасным резервный вариант на `/run/user/<uid>`), сокет создаётся с режим `0600`, а обе стороны проверяют PID/UID узел через `SO_PEERCRED`. Инициализировать секрет по-прежнему передаётся только через inherited стандартный ввод и очищается после рукопожатие.
- Linux Целостность Свидетельство v1 измеряет реальные ELF/исполняемый SHA-256, `/proc/<pid>/status`, родительский граница, процесс запуск ticks и SHA-256 набора исполняемый-основанный сопоставление из `/proc/<pid>/maps`. Linux Защита Аттестация включает отдельную процесс-политика схема и сессия-привязанный доказательство.
- Серверная часть принимает Linux доверенный устройства в том же одноразовый challenge/ticket поток, но проверяет отдельные Linux схемы, UID/GID граница, NoNewPrivs, dumpability/core/ptrace/PDEATHSIG состояние и релиз хеширует. Authenticode на Linux не подменяется фиктивным доверие результат.

### Рабочий пакет и CI

- `build-linux-desktop.sh` собирает побочный-через-побочный `neverlauncher-desktop + neverguard`, вычисляет SHA-256/size, создаёт `LINUX_PACKAGE_MANIFEST.json` и `GUARD_RELEASE_ALLOWLIST_LINUX.json`, затем формирует Linux рабочий ZIP. Релиз Настольное приложение до запуск процесса Защита проверяет regular-file/symlink граница, пользователь-или-корень владение, запись разрешения, version/platform/protocol, IPC/усиление защиты метаданные и хеширует.
- Linux NeverGuard интеграционный тест выполняет реальный Unix-сокет рукопожатие, процесс политика, Целостность Свидетельство и запрос-привязанный аттестация. CI/preflight содержит обязательный `linux-production-implementation-0137.py`; комплект релиза обязан содержать Linux NeverGuard и список разрешений.

Эта версия остаётся пользовательский режим граница: root/kernel злоумышленник находится вне модели доверия. Серверная часть релиз список разрешений и привязанный к оборудованию ключ устройства подпись остаются обязательной удалённой точкой проверки.

## 0.13.6 — Windows рабочий усиление защиты

`0.13.6` переводит Windows NeverGuard граница из функционального enforcement-контура 0.13.1–0.13.5 в более жёсткий рабочий среда выполнения. IPC протокол поднят до v4, Именованный Pipe получает явный защищать current-user/System ACL, Настольное приложение удерживает NeverGuard в `KILL_ON_JOB_CLOSE` Задача Объект, а Desktop/Guard применяют отказ с блокировкой куча/DLL-search усиление защиты до основной runtime-инициализации.

### Среда выполнения и IPC усиление защиты

- `HeapSetInformation(..., HeapEnableTerminationOnCorruption,...)`, `SetDllDirectoryW("")` и `SetDefaultDllDirectories(APPLICATION_DIR | SYSTEM32)` обязательны для Windows Desktop/NeverGuard; ошибка блокирует запуск.
- NeverGuard Именованный Pipe создаётся через явный `SECURITY_ATTRIBUTES`/SDDL только для LocalSystem и объект владелец, дополнительно к локальный-только удалённый отклонение и mutual HMAC. Протокол v4 включает усиление защиты version/enforced и secure-ACL бит в аутентифицировать готовый доказательство.
- Настольное приложение назначает NeverGuard в отдельный Задача Объект с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` и проверяет участие до передачи инициализировать секрет. Minecraft запускать требует аутентифицировать Защита, процесс политика, усиление защиты состояние, защищённый ACL, срок жизни задача и рабочий пакет проверка.

### Релиз пакет усиление защиты

- Релиз Настольное приложение до запуск процесса Защита читает соседний `WINDOWS_PACKAGE_MANIFEST.json`, отклоняет symlink/non-regular PE, проверяет version/platform/protocol и размер/SHA-256 обоих исполняемый. Релиз сборка записывает протокол v4 и усиление защиты метаданные.
- `build-windows-desktop.ps1` требует Authenticode для рабочий по умолчанию (`-CodeSigningCertificateThumbprint...`): Desktop/NeverGuard подписываются Authenticode перед хеш manifest/allowlist, подписи повторно проверяются, а `authenticodeRequired` синхронизируется с Серверная часть `requireAuthenticode`.
- Windows нативный интеграционный тест проверяет протокол v4, рабочий-усиление защиты состояние, защищённый pipe ACL и срок жизни Задача Объект; новый автономный контроль `windows-production-hardening-0136.py` обязателен в CI/preflight.

Неподписанный разработка пакет намеренно не проходит релиз-среда выполнения Authenticode контроль и предназначен только для CI/build валидация.

Граница остаётся пользовательский режим и не заявляет защиту от kernel/administrator злоумышленник; на стороне сервера Защита Аттестация, Minecraft/ServerBridge целостность принудительное применение и релиз список разрешений продолжают применяться независимо.

## 0.13.5 — Minecraft/ServerBridge целостность принудительное применение

`0.13.5` переносит Защита Аттестация из одноразового момента выдачи Minecraft токен в актуальный игровой граница. Целостность снимок сохраняется вместе с Minecraft сессия, а каждый последующий токен валидация, Yggdrasil join/hasJoined и ServerBridge validate-join/has-joined повторно проверяет текущий Защита релиз список разрешений. Удаление релиз хеш из рабочий политика немедленно отзывает уже выданные игровые учётные данные и связанные ServerBridge подключается.

### Minecraft целостность хранение и актуальный отзыв

- Миграция `0019_minecraft_serverbridge_integrity_0135.sql` сохраняет проверен Защита attestation/evidence/release SHA-256, лаунчер версия и проверка время в `minecraft_sessions`; API и CLI используют идентичную запечатанный миграция.
- `/api/v1/session/join` для Windows Защита-применять устройство теперь обязан получить конкретный `minecraftAccessToken` и сохранить `minecraftSessionId`. Это закрывает прежний обход, при котором Никогда-сессия могла создать ServerBridge подключение без связи с Защита-проверен Minecraft учётные данные.
- Minecraft токен валидация, Yggdrasil join/hasJoined и ServerBridge валидация заново сверяют снимок с `NEVERLAUNCHER_GUARD_RELEASE_ALLOWLIST_JSON`. Релиз отзыв действует на уже активные сессии без ожидания их TTL.
- Настольное приложение передаёт только что выданный Minecraft токен доступа в ServerBridge подключение до запуска Java, поэтому игровой подключение связан с тем же device/session/binding эпоха и Защита свидетельство, которые прошли Серверная часть проверка.

### ServerBridge артефакт принудительное применение

- Velocity/Paper/Purpur вычисляют SHA-256 собственного запущенного JAR через `CodeSource` и отправляют его в сигнал состояния и каждый `validate-join`. При невозможности измерить JAR плагин отказ с блокировкой, когда `security.requireIntegrity=true` (рабочий по умолчанию).
- Серверная часть принимает сигнал состояния только если `pluginVersion + serverType + pluginSha256` присутствуют в `NEVERLAUNCHER_BRIDGE_RELEASE_ALLOWLIST_JSON`. Принят измерение сохраняется в ServerBridge состояние и повторно проверяется по текущему список разрешений на каждом игровой валидация.
- `validate-join` обязан повторить тот же version/hash, что был подтверждён сигнал состояния. Ротация сервер токен сбрасывает целостность измерение и требует нового сигнал состояния. Legacy/authlib `has-joined` также требует актуальный проверен мост измерение.
- `scripts/build/bridge-plugins.sh` строит реальные платформа JAR, вычисляет их SHA-256, записывает хеширует в `PLUGIN_MANIFEST.json` и генерирует `BRIDGE_RELEASE_ALLOWLIST.json`; комплект релиза включает оба файла. Рабочий запуск требует `NEVERLAUNCHER_BRIDGE_RELEASE_ALLOWLIST_JSON`.

ServerBridge JAR хеш — уровень приложения self-измерение, а не hardware/server аттестация самого Minecraft-сервера: полностью скомпрометированный хост с сервер токен может подделывать пользовательский процесс. Принудительное применение предназначен для релиз список разрешений, accidental/unauthorized артефакт расхождение и актуальный серверная часть политика, а не для утверждения ядро-уровень целостность удалённого сервера.

## 0.13.4 — Защита Аттестация + Серверная часть проверка

`0.13.4` связывает локальный NeverGuard Windows граница с Серверная часть: сервер выдаёт постоянный одноразовый запрос, отдельный `neverguard.exe` формирует свежую запрос-привязанный аттестация поверх Целостность Свидетельство v1 и применять процесс политика, а оборудование P-256 устройство ключ подписывает каноническую привязку `user + device + session + bindingEpoch + release + attestation`. Серверная часть пересчитывает evidence/attestation хеши, проверяет устройство подпись, freshness/replay и точные SHA-256 релиз бинарные файлы; только после этого выдаётся одноразовый короткоживущий Защита запускать билет, обязательный для Minecraft сессия в рабочий.

### Защита-побочный аттестация

- Аутентифицировать IPC поднят до v3: запрос MAC теперь включает полезная нагрузка, а команда `guard-attestation` принимает сервер запрос только внутри уже аутентифицированной Настольное приложение↔NeverGuard сессия. Защита заново собирает Целостность Свидетельство, прикладывает текущий применять процесс-политика отчёт и HMAC-привязывает аттестация хеш к IPC сессия.
- Канонический аттестация фиксирует запрос hash/ID, свидетельство ID/digest, SHA-256 Guard/Desktop, модуль-задать отпечатки, Authenticode результаты, процесс-политика флаги и коллекция время. Настольное приложение повторно проверяет запрос, свидетельство, политика, хеш и сессия доказательство до использования результата.
- Windows интеграционный тест выполняет реальный рукопожатие с `neverguard.exe`, получает запрос-привязанный аттестация и проверяет связь с PID/процесс граница.

### Серверная часть проверка и запускать контроль

- Добавлены `POST /api/v1/auth/devices/{deviceId}/guard-attest/begin|complete`. Запрос хранится в Репозиторий, привязан к текущим `user/device/session/bindingEpoch/launcherVersion/keyFingerprint`, имеет TTL 90 секунд и потребляется атомарно.
- Полный требует привязанный к оборудованию P-256 доверенный устройство с актуальной устройство аттестация. Серверная часть заново вычисляет Целостность Свидетельство SHA-256 и Защита Аттестация SHA-256, проверяет актуальность, родительский граница, применять процесс политика, устройство подпись и релиз список разрешений.
- Успешная проверка выпускает постоянный одноразовый Защита запускать билет с TTL 90 секунд. `/api/v1/minecraft/session` в рабочий требует этот билет и потребляет его атомарно; повторное воспроизведение получает `412 Precondition Failed`.
- `NEVERLAUNCHER_GUARD_RELEASE_ALLOWLIST_JSON` обязателен в рабочий. Windows релиз скрипт формирует `GUARD_RELEASE_ALLOWLIST.json` из фактических SHA-256 `neverguard.exe` и Настольное приложение исполняемый; политика может дополнительно требовать доверенный Authenticode.
- Это уровень приложения сервер проверка, а не TPM/Измеренный Boot кавычки и не ядро античит. Серверная часть доверяет зарегистрированному оборудование устройство ключ, запрос актуальность, точным релиз хеширует и evidence/policy, сформированным список разрешений NeverGuard/Desktop.

## 0.13.3 — Windows runtime/process политика принудительное применение

`0.13.3` переводит NeverGuard Windows политика из наблюдаемого свидетельство в реально применяемую среда выполнения граница. Политики включаются отказ с блокировкой: `neverguard.exe` усиливает собственный процесс до инициализации Tokio, а Java/Minecraft создаётся suspended и начинает выполнение только после успешного назначения в проверенный Windows Задача Объект.

### NeverGuard self-политика

- До создания асинхронный среда выполнения NeverGuard применяет `SetProcessMitigationPolicy` для Динамический Код, Расширение Точка Отключить, Строгий Дескриптор Проверка, Образ Загрузка и Дочерний процесс политика, затем повторно считывает каждую политика через `GetProcessMitigationPolicy`. Ошибка применения или верификации завершает защита до открытия аутентифицировать сессия.
- Защита запрещает динамический код и создание дочерних процессов, отключает устаревший расширение точки, включает строгий-дескриптор проверяет и блокирует remote/low-integrity образ загрузка с предпочтением System32. Применённое состояние доступно через аутентифицировать IPC `process-policy` и привязано к `ready` рукопожатие.
- IPC протокол поднят до v2: готовый доказательство теперь включает процесс-политика version/enforced бит, поэтому клиент не может принять старый защита как политика-применять экземпляр.

### Minecraft среда выполнения дерево принудительное применение

- NeverRuntime на Windows создаёт Java с `CREATE_SUSPENDED`. До выполнения пользовательского bytecode процесс назначается в новый Задача Объект с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` и `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION`. Breakaway флаги запрещены и фактическая membership/limit mask проверяется Win32 API.
- Только после успешного `AssignProcessToJobObject` + `IsProcessInJob` + `QueryInformationJobObject` NeverRuntime находит suspended primary поток и вызывает `ResumeThread`. Любая ошибка до возобновление блокирует запускать и инициирует termination дочерний процесс.
- Задача дескриптор живёт столько же, сколько контролируемый среда выполнения. Закрытие launcher/supervisor граница завершает среда выполнения дерево через kill-на-закрытие; `ProcessStatus` публикует фактически применённый `windowsProcessPolicy`.
- Запрет динамический код намеренно не применяется к Java/Minecraft процесс: HotSpot JIT требует исполняемый сгенерированный код. Вместо несовместимого флага среда выполнения ограничивается Задача Object/process-tree политика, а строгие меры защиты применяются к самому небольшому NeverGuard процесс.

### Релиз проверка

- Windows нативный тест проверяет реальное создание suspended дочерний, Задача Объект assignment, без отделения политика и возобновление; NeverGuard интеграционный тест проверяет аутентифицировать процесс-политика отчёт вместе с Целостность Свидетельство v1.
- CI/preflight получили обязательный `neverguard-process-policy-0133.py`; Windows задача запускает политика unit/native тесты, процесс-граница интеграционный тест и `clippy -D warnings`.
- Это пользовательский режим Windows процесс политика принудительное применение, а не ядро античит и не проверяемый сервером аттестация. Оно не использует агрессивный хуки и служит применять среда выполнения граница для последующих NeverGuard integrity/attestation этапов.

## 0.13.2 — Windows Целостность Свидетельство v1

`0.13.2` добавляет первый рабочий Windows целостность-свидетельство слой поверх отдельного NeverGuard процесс граница из `0.13.1`. Свидетельство собирается внутри `neverguard.exe` только после mutual-аутентифицировать IPC и перед каждым Windows Minecraft запускать; ошибка сбора, нарушение родительский граница, повреждённый хеш или сессия доказательство блокируют запускать.

### Свидетельство коллекция

- NeverGuard независимо сверяет фактический родительский PID через Windows Toolhelp снимок с PID, переданным Настольное приложение, и завершает запуск при несоответствие. Это усиливает прежнюю проверку PID внутри рукопожатие фактическим OS-наблюдаемый родительский relation.
- Для `neverguard.exe` и процесса лаунчер собираются образ путь, SHA-256 файла, размер/mtime и Windows процесс создание FILETIME. Хэш считается самим защита с диска, а не принимается от Настольное приложение.
- Authenticode проверяется локальным `WinVerifyTrust(WINTRUST_ACTION_GENERIC_VERIFY_V2)` без UI и без сетевой загрузки revocation-данных; свидетельство сохраняет `trusted` и исходный WinTrust состояние код, поэтому неподписанный/невалидный бинарный файл не маскируется как доверенный.
- `GetProcessMitigationPolicy` снимает сырой флаги DEP, ASLR, Динамический Код, Расширение Точка Отключить, CFG, Бинарный файл Подпись, Образ Загрузка, Дочерний процесс, Пользователь Shadow Стек и SEHOP. Неподдерживаемая отдельная политика попадает в `queryFailures`, сохраняя остальные свидетельство.
- Toolhelp модуль снимок для защита и лаунчер превращается в детерминированный SHA-256 отпечаток набора загруженных модуль пути + SHA-256 содержимого каждого модуль файл + метаданные файла; отдельно публикуются только basename нестандартных non-system модули, чтобы не раскрывать дополнительные пользовательские пути.

### Аутентифицировать свидетельство транспорт

- Новый IPC команда `integrity-evidence` доступен только внутри уже аутентифицировать NeverGuard сессия. Сбор файлов/Win32 свидетельство выполняется через blocking обработчик, не блокируя Tokio IPC среда выполнения.
- Канонический свидетельство ядро получает собственный SHA-256 (`evidenceSha256`). Защита дополнительно HMAC-привязывает хеш к текущему IPC сессия ключ (`sessionProof`); Настольное приложение заново проверяет schema/version, PID граница, хеш и доказательство constant-время перед возвратом свидетельство вызывающему коду.
- Настольное приложение export-команда `neverguard_integrity_evidence` возвращает только уже локально проверенный полезная нагрузка. Windows `launch_minecraft` становится отказ с блокировкой на свидетельство collection/verification.

### Проверка и граница безопасности

- Windows интеграционный тест запускает настоящий `neverguard.exe`, проходит рукопожатие, получает Целостность Свидетельство v1, проверяет PID/hash/module/session-proof форма и затем корректный завершение. Отдельные платформа-независимый модульные тесты защищают канонический свидетельство хеш от незаметной модификации полей.
- CI/preflight получили обязательный контроль `neverguard-integrity-evidence-0132.py`; Windows задача компилирует и тестирует целостность реализация вместе с процесс-граница интеграционный тест и clippy.
- Целостность Свидетельство v1 является **локальный Windows свидетельство**. `0.13.2` не объявляет его проверяемый сервером аттестация, ядро античит, память целостность доказательство или TPM-основанный кавычки; криптографический сервер проверка остаётся отдельным следующим этапом NeverGuard.

## 0.13.1 — NeverGuard Windows: процесс граница + аутентифицировать IPC

`0.13.1` вводит первый рабочий среда выполнения граница NeverGuard для Windows. Защита запускается отдельным `neverguard.exe` рядом с Настольное приложение, а Windows запускать становится отказ с блокировкой: Minecraft не стартует, пока Настольное приложение не поднимет защита и не подтвердит аутентифицировать IPC.

### Процесс граница

- `neverguard.exe` является отдельным Rust процесс с собственным entrypoint; Настольное приложение не загружает guard-код как хук/DLL в Minecraft-процесс.
- Настольное приложение генерирует криптографически случайный 256-бит инициализировать секрет и передаёт его защита только через унаследованный стандартный ввод. Секрет не помещается в argv, окружение, конфигурация или временный файл и zeroize-ится после рукопожатие.
- IPC использует Windows Именованный Pipe в случайном на-запускать пространство имён `NeverLauncher.Guard.*`, `FILE_FLAG_FIRST_PIPE_INSTANCE`, один сервер экземпляр и `PIPE_REJECT_REMOTE_CLIENTS`.
- Защита принимает только клиент с ожидаемым родительский PID; знание PID не является аутентификацией и проверяется только вместе с владение инициализировать секрет.

### Аутентифицировать IPC v1

- Рукопожатие взаимный: client/server одноразовые значения, HMAC-SHA-256 доказательство в разных directions и отдельный производный сессия ключ. Transcript привязан к эндпоинт, обоим PID, защита запуск время и обоим одноразовое значение.
- После рукопожатие каждый request/response имеет HMAC и sequence/request ID; защита отклоняет повторное воспроизведение и из--order запросы, повреждённый кадр, протокол несоответствие и MAC несоответствие. Размер JSON кадр ограничен 64 KiB.
- Реальные команды `ping`, `status`, `shutdown` проходят только после аутентификация. Потеря pipe завершает защита сессия; Настольное приложение держит дочерний дескриптор с kill-на-drop.
- Windows интеграционный тест запускает настоящий `neverguard.exe`, проходит handshake/ping/status/shutdown и проверяет привязку к родительский PID.

### Дистрибутив и контроль выпуска

- `scripts/release/build-windows-desktop.ps1` собирает Настольное приложение и NeverGuard релиз бинарные файлы, кладёт `neverguard.exe` рядом с Настольное приложение, фиксирует SHA-256/size в `WINDOWS_PACKAGE_MANIFEST.json` и формирует Windows ZIP.
- Основной CI получил обязательный `windows-2022` задача с реальный процесс интеграционный тест, clippy и сборкой побочный-через-побочный пакет; Linux релиз-кандидат задача зависит от успешного NeverGuard Windows задача.
- Добавлен контроль `neverguard-windows-0131.py`; он проверяет, что процесс/IPC/security/release wiring не заменены декларацией.

## 0.12.10 — Миграция + стабилизация

`0.12.10` стабилизирует накопленный Доверие к устройству schema/runtime после `0.12.4–0.12.9` и делает обновление с реальной `0.12.9` БД отдельным обязательным релиз инвариант. Главная исправленная production-проблема: ограничение `device_challenges_purpose_check`, созданный в `0.12.4`, не был расширен после появления `key-rotate`/`key-recover` в `0.12.8`, из-за чего PostgreSQL мог отклонять замена запрос, хотя память регрессия проходил.

### Схема стабилизация

- Миграция `0018_device_trust_stabilization_01210.sql` синхронно входит в API/CLI каталог и расширяет запрос назначение до `register`, `session-bind`, `attest`, `key-rotate`, `key-recover`.
- Старые пустой-string sentinels в `trusted_devices.replaced_by_device_id` и `minecraft_sessions.trusted_device_id` переводятся в SQL `NULL`; репозиторий scanners/writers используют nullable SQL семантика.
- Валидные устаревший отозванный-устройство строки нормализуются в единое конечный состояние (`trust_state=revoked`, `attestation_state=revoked`, timestamp/reason); просроченные незавершённые запрос помечаются использованный.
- Перед установкой ограничений миграция отказ с блокировкой проверяет межпользовательский замена связывает, session/device владение, привязка форма и Minecraft session/profile/device владение. Повреждённая или неоднозначная БД не «чинится» молча.
- После проверки устанавливаются владение внешний ключи и lifecycle/shape CHECK ограничения для доверенный устройства, аутентификация сессии и Minecraft доверие снимки. Замена цепочка остаётся постоянный метка удаления и не может ссылаться на устройство другого пользователя.

### Обновление E2E и релиз принудительное применение

- `e2e/scripts/run-device-trust-migration-e2e.sh` создаёт точную схема `0.12.9` (запечатанный миграция `0001..0017`), сеет допустимые устаревший состояния, доказывает pre-обновление ошибка `key-rotate`, затем запускает поставка CLI `nl db migrate apply/verify` и проверяет `0018` postconditions.
- Обновление E2E требует, чтобы межпользовательский аутентификация привязка, замена связь и Minecraft устройство снимок после миграция отклонялись самой PostgreSQL БД.
- Рабочий Доверие к устройству E2E публикует обновление свидетельство вместе с свидетельство реального запуска; публичный доверие матрица требует `migrationStabilization01210`, поэтому PASS без проверенного `0.12.9 → 0.12.10` обновление невозможен.
- Контроль `device-trust-migration-stabilization-01210.py` включён в репозиторий политика, CI и релиз предварительная проверка; строгий Доверие к устройству поток запускает миграция E2E перед жизненный цикл E2E.

## 0.12.8 — Кроссплатформенный усиление защиты + ключ recovery/rotation

`0.12.8` завершает жизненный цикл Доверие к устройству для потери и плановой замены локального устройство ключ. Ротация сохраняет continuity только при одновременном доказательство владения старым и staged-новым ключом. Восстановление не требует утраченного закрытый ключ, но требует свежий устойчивый к фишингу учётная запись step-up и доказательство новым подготовленный ключ. В обоих случаях Серверная часть создаёт новую устройство идентичность, перепривязывает текущую сессия с новым `binding_epoch`, превращает старый отпечаток в постоянный метка удаления и отзывает учётные данные, связанные со старой идентичность.

### Среда выполнения ключ жизненный цикл

- Desktop/Tauri использует двухфазный `stage → server ceremony → commit`: рабочий локальный ключ не заменяется до успешного сервер ответ; при ошибке до фиксация подготовленный ключ удаляется, а после сервер фиксация подготовленный метаданные сохраняется для согласование.
- Оборудование P-256 замена больше не использует детерминированный метка `backend+user`: каждый подготовленный генерация получает отдельный метка, поэтому TPM/Защищённый Анклав ключ действительно меняется. Программное обеспечение Ed25519 замена хранится отдельной подготовленный записью OS хранилище ключей.
- Ротация подписывает один канонический `NeverLauncher Device Key Replacement v1` полезная нагрузка старым и новым ключом. Восстановление требует свежий `phishing-resistant` step-up и подписывает тот же сервер-выданный одноразовый запрос новым ключом.
- PostgreSQL замена выполняется транзакционно: создаётся новый доверенный устройство, текущая аутентификация сессия получает новый устройство и `binding_epoch`, старая идентичность становится метка удаления с замена связь, sibling sessions/refresh families/Minecraft сессии и незавершённые запросы отзываются. ServerBridge подключается инвалидируются после фиксация.
- Ordinary регистрация из уже привязанный сессия запрещена: замена нельзя обойти вторым ключом в той же доверенной сессия. Если сервер запись исчез/отозван, Настольное приложение больше не удаляет локальный ключ автоматически и переводит пользователя в восстановление.
- Миграция `0017_device_key_recovery_rotation_0128.sql` хранит замена цепочка (`replaced_at`, `replaced_by_device_id`, `replacement_reason`) одинаково в API и CLI каталог.

### Проверка / контроли выпуска

- HTTP регрессия проверяют обязательность старый+новый доказательство для ротация, актуальный устойчивый к фишингу step-up для восстановление, постоянный метка удаления и запрет обход через обычную регистрацию. Предыдущий Minecraft re-привязывать регрессия переведён на настоящий ключ-ротация поток.
- Контроль `cross-platform-key-recovery-0128.py` подключён к предварительная проверка, репозиторий политика и CI и проверяет серверная часть транзакция, миграция parity, нативный подготовленный-ключ жизненный цикл, Настольное приложение согласование и реальные Go регрессия.

## 0.12.7 — Minecraft / ServerBridge доверие принудительное применение

`0.12.7` переносит Доверие к устройству из launcher/auth граница непосредственно в Minecraft игровой граница. Minecraft сессия и ServerBridge подключение теперь фиксируют определяемый сервером снимок `trusted_device_id + binding_epoch`, а последующая на стороне сервера проверка повторно сверяет его с текущей Никогда сессия, состоянием доверенный устройство и риск решение. Поэтому старый Minecraft токен или подключение нельзя продолжить использовать после re-привязывать, отзыв или постоянный риск переход.

### Среда выполнения принудительное применение

- `POST /api/v1/minecraft/session` выдаёт официальный Minecraft учётные данные только активный Никогда сессия с проверен привязанный устройство и допустимой риск политика. Сохранённый Minecraft сессия хранит device/binding снимок через миграция `0016_minecraft_serverbridge_trust_0127.sql`.
- Yggdrasil-compatible пароль аутентификация остаётся совместимым для старых клиентов, но `/sessionserver/session/minecraft/join` отказ с блокировкой требует проверен привязанный устройство. Сам устаревший непрозрачный токен больше не является обходом Доверие к устройству.
- Minecraft validate/hasJoined и ServerBridge `validate-join`/`has-joined` повторно проверяют родительский session/device/risk. `binding_epoch` несоответствие, смена устройство, revoke/missing устройство или отозванный риск делают учётные данные непригодным; устаревший аттестация и сеть-риск step-up дают временный запрещать до восстановления доверие.
- На стороне сервера валидация намеренно не записывает IP/User-Agent игра сервер как контекст игрока: риск observation происходит на launcher/player запросы, а plugin/hasJoined только читает и применяет уже определяемый сервером риск состояние.

### Проверка / контроли выпуска

- HTTP регрессионные тесты покрывают unbound Minecraft denial, успешный привязанный учётные данные, инвалидация после re-привязывать, актуальный ServerBridge риск запрещать и канал закрепление.
- Minecraft E2E регистрирует реальный Ed25519 доверенное устройство ключ и подписывает рабочий регистрация запрос перед подключение к серверу; доверие принудительное применение не обходится synthetic устройство метаданные.
- Контроль `minecraft-serverbridge-trust-0127.py` подключён к предварительная проверка, репозиторий политика и CI и проверяет среда выполнения, хранение, миграция, плагин messages и регрессия покрытие.

## 0.12.6 — Сессия ↔ Привязка устройства + риск интеграционный

`0.12.6` делает связь Никогда сессия с доверенный устройство определяемый сервером. Каждая сессия получает постоянный `binding_epoch`; registration/re-bind атомарно увеличивает эпоха, а Серверная часть сравнивает его и `device_id/device_trust` с каждым доступ JWT. Поэтому токен доступа, выпущенный до нового привязывать, больше не может продолжать работать только потому, что сама сессия ещё активный.

### Привязанный к устройству обновление

- Обновление привязанной сессия требует доказательство текущим регистрировать устройство ключ. Канонический `NeverLauncher Session Device Binding v1` полезная нагрузка связывает `user + session + device + binding_epoch` и SHA-256 текущего токен обновления; сам обновление секрет в подписываемый полезная нагрузка не включается.
- Серверная часть сначала только для чтения проверяет обновление family/session привязка и устройство подпись, и только затем выполняет ротация. Wrong/missing устройство доказательство возвращает `428` и не расходует действительный токен обновления. Повторное воспроизведение уже использованный токен обновления по-прежнему компрометирует всю семейство и отзывает замена токен.
- Настольное приложение подписывает обновление внутри отдельной Tauri IPC-команды `sign_session_refresh`; команда сама строит канонический полезная нагрузка и сверяет локальный сохранённый `deviceId`, поэтому React не может использовать её как произвольный подписание primitive. Программное обеспечение Ed25519 и оборудование P-256 используют уже зарегистрированный ключ.

### Риск принудительное применение

- Миграция `0015_session_device_risk_0126.sql` добавляет `binding_epoch`, `risk_score`, `risk_action`, `risk_evaluated_at`; API/CLI миграция каталог синхронизированы. Риск действия: `allow`, `step-up`, `reattest`, `revoke`.
- IP/User-Agent расхождение становится `step-up`; устаревший оборудование аттестация — `reattest`; missing/revoked/invalid доверенный устройство и токен обновления повторное использование ведут к `revoke`. `risk_updated_at` меняется только при изменении решения, поэтому успешный step-up не становится немедленно устаревшим из-за очередной оценки.
- Критичный обработчики через `requireFreshAuth117` теперь проверяют риск действие до обычной актуальность политика. Step-up очищает сеть-расхождение reasons; оборудование аттестация завершение снимает `reattest` после повторной на стороне сервера проверки устройство состояние.
- E2E покрывает инвалидация pre-привязывать JWT, обязательный привязанный-обновление доказательство, неверный-доказательство non-consumption, обновление повторное воспроизведение семейство компрометация, сохранённый риск решение и секрет-free канонический полезная нагрузка. Контроль `session-device-risk-0126.py` подключён к предварительная проверка, репозиторий политика и CI.

## 0.12.5 — Устройство Управление + Отзыв

`0.12.5` превращает существующий устройство отзыв из разрозненной операции в единый рабочий жизненный цикл. Пользователь видит active/revoked доверенный устройства, текущее устройство, может переименовать устройство, необратимо отозвать одно устройство или атомарно отозвать все остальные. Администратор получает тот же реестр и отзыв после актуальный устойчивый к фишингу step-up.

### Среда выполнения отзыв

- PostgreSQL отзыв выполняется одной транзакцией: доверенный устройство становится постоянный метка удаления, свежая аттестация снимается, незавершённые устройство запросы расходуются, связанные Никогда сессии, токен обновления families/tokens и Minecraft сессии отзываются. Возвращаются фактические счётчики, а не результат повторного в памяти процесса отзыв.
- ServerBridge подключается для затронутых Никогда сессии инвалидируются немедленно. Доступ JWT перестаёт проходить сессия observation после на стороне сервера отзыв; обновление семейство также больше не может ротироваться.
- `POST /api/v1/auth/devices/{deviceId}/revoke` и `POST /api/v1/auth/devices/revoke-others` дают явный управление API; прежний `DELETE` сохранён как совместимый отзыв. `revoke-others` разрешён только сессия, уже связанной с активный проверен доверенный устройство, и сохраняет именно это текущее устройство.
- Отзыв необратим для прежнего устройство key/fingerprint: повторная регистрация отозванного ключа запрещена, повторный отзыв идемпотентен. Для повторного подключения установка должна создать новый устройство ключ.

### Клиенты / эксплуатация / контроли

- Настольное приложение показывает доверенное устройство реестр, current/revoked состояние, rename/revoke/revoke-others. При self-отзыв удаляются локальный устройство ключ и сохранённая аутентификация сессия из OS защищённый хранилище.
- Панель администратора показывает доверенный устройства и выполняет постоянный отзыв через защищённый администратор эндпоинт; критическая операция остаётся за актуальный устойчивый к фишингу step-up.
- HTTP E2E проверяет запрос инвалидация, access/refresh cutoff, метка удаления re-регистрация denial, self-отзыв и идемпотентность. `device-management-revocation.py` включён в предварительная проверка, репозиторий политика и CI. Новая DB миграция не требуется: схема 0.12.4 уже содержит необходимые trusted-device/session/challenge поля; 0.12.5 меняет среда выполнения семантика и транзакция границы, а не добавляет пустую schema-заготовку.

## 0.12.4 — Запрос-ответ аттестация

`0.12.4` добавляет отдельную рабочую attestation-церемонию поверх привязанный к оборудованию идентичность из `0.12.3`. Серверная часть выдаёт короткоживущий одноразовый запрос только сессии, которая уже доказала владение зарегистрированным P-256 аппаратный ключ и привязана к тому же доверенный устройство. Нативный Настольное приложение подписывает отдельный канонический `NeverLauncher Device Attestation v1` полезная нагрузка тем же неэкспортируемый платформа ключ; программное обеспечение Ed25519 резервный вариант к этой IPC-команде не допускается.

### Аттестация жизненный цикл

- Добавлены `POST /api/v1/auth/devices/{deviceId}/attest/begin|complete`. Запрос постоянный, привязан к `user + device + session + fingerprint + algorithm + binding + provider`, имеет TTL 2 минуты и расходуется атомарно до проверки подписи, поэтому повторное воспроизведение и повтор после неверного доказательство отклоняются.
- Успешный доказательство сохраняет `attestation_state=verified`, `attestation_method=challenge-response-v1`, `attested_at`, `attestation_expires_at` и устройство уверенность `challenge-response-attested`. Актуальность окно — 12 часов; после истечения API/JWT эффективно возвращаются к `proof-of-possession`, пока процедура не выполнена снова.
- Доступ JWT и `/api/v1/auth/device-trust` отражают свежий аттестация состояние. Это диагностический устройство уверенность: он не повышает RBAC, MFA/аутентификация сила и не считается устойчивый к фишингу пользователь аутентификация.
- Настольное приложение автоматически выполняет аттестация после registration/session-bind только для `p256/hardware`. Новый нативный `attest_device_payload` принимает исключительно канонический аттестация полезная нагрузка, сверяет user/device/fingerprint/provider и не имеет software/create резервный вариант.

### Граница безопасности / хранение

- Миграция `0014_challenge_response_attestation_0124.sql` добавляет постоянный аттестация state/freshness, расширяет допустимый устройство уверенность и разрешает назначение `attest` в существующем одноразовый запрос реестр. Серверная часть и CLI каталог побайтово идентичный.
- Запрос-ответ подтверждает свежое владение уже зарегистрированным привязанный к оборудованию ключ. Текущий платформа подписант не предоставляет NeverLauncher проверяемый поставщик TPM кавычки / Защищённый Анклав аттестация сертификат, поэтому `hardwareProvider` не объявляется удалённый происхождение; API явно возвращает `hardwareProvenance=not-remotely-verified`.
- HTTP E2E проверяет успех, unbound-сессия отклонение, повторное воспроизведение, неверный-подпись consumption и программное обеспечение-ключ отклонение. Новый автономный контроль `challenge-response-attestation.py` включён в предварительная проверка и CI.

## 0.12.3 — Привязанный к оборудованию идентичности

`0.12.3` добавляет реальный оборудование-основанный ключ устройства путь поверх Доверие к устройству Ядро. Настольное приложение сначала пытается создать неэкспортируемый P-256 ключ подписи в платформа оборудование провайдер (Защищённый Анклав / TPM). Если платформа подписант сообщает keyring/software/test серверная часть, он не считается привязанный к оборудованию: клиент явно остаётся на существующем Ed25519 + OS защищённый хранилище пути.

### Оборудование идентичность жизненный цикл

- Tauri использует закреплённый `hardware-enclave 0.2.10` и P-256 ECDSA. Оборудование закрытый ключ не сериализуется в NeverLauncher metadata/keyring запись и не пересекает IPC; сохраняются только публичный SEC1 ключ, SHA-256 отпечаток, провайдер имя и платформа ключ метка.
- Доверие к устройству протокол теперь принимает `ed25519/software` и `p256/hardware`. Для P-256 Серверная часть проверяет uncompressed SEC1 открытый ключ и сырой IEEE P1363 `r||s` подпись над тем же канонический одноразовый запрос полезная нагрузка.
- Аппаратный ключ автоматически используется в registration/session-bind поток официального Настольное приложение. Если HSM недоступен, резервный вариант остаётся явным `keyBinding=software`, без ложного оборудование состояние.
- Delete/reset удаляет платформа аппаратный ключ и локальную метаданные; существующий `0.12.2` Ed25519 записывает автоматически продолжают работать как программное обеспечение-привязанный идентичности.

### Сервер граница / миграция

- Добавлена миграция `0013_hardware_bound_identities_0123.sql`: `trusted_devices.key_binding`, `hardware_provider`, поддержка `key_algorithm=p256`, реляционный CHECK ограничения и индекс по привязка состояние. Серверная часть/CLI каталог побайтово идентичный.
- Доступ JWT содержит диагностические `device_key_binding` и `device_hardware_provider` для уже проверен устройство. Эти захватывает **не** используются для RBAC, MFA сила или step-up решения.
- `keyBinding=hardware` в `0.12.3` означает локально выбранный неэкспортируемый оборудование провайдер, но ещё не удалённый аттестация. Поэтому на стороне сервера `assurance` остаётся `proof-of-possession`. TPM/Защищённый Анклав attestation/challenge-response проверка является отдельным следующим Доверие к устройству этапом.

### Контроли выпуска

- HTTP E2E выполняет реальный P-256 регистрация + второй-сессия привязывать и проверяет, что оборудование метаданные не повышает уверенность.
- Добавлен `hardware-bound-identity.py`; preflight/repository policy/CI требуют HSM путь, P-256 проверяющий модуль, миграция `0013`, запрет keyring/software promotion и Linux TPM сборка зависимость.

## 0.12.2 — Устройство ключи + OS защищённый хранилище

`0.12.2` переводит Доверие к устройству из сервер-только доказательство API в рабочий Настольное приложение жизненный цикл. Официальный Tauri-клиент сам создаёт Ed25519 устройство ключ, хранит закрытый начальное значение только в нативный OS учётные данные хранилище и автоматически выполняет registration/session-bind доказательство после Никогда вход.

### Устройство ключ жизненный цикл

- Добавлен Tauri-модуль `device_keys`: Ed25519 ключ генерация через OS CSPRNG, детерминированный per-backend/per-user хранилище ключей пространство имён, self-проверка публичный key/fingerprint и zeroization временного seed/serialized секрет.
- Windows использует нативный учётные данные диспетчер, macOS — Keychain, Linux — Секрет Служба через `keyring`; plaintext/file/localStorage резервный вариант отсутствует.
- Закрытый ключ не передаётся React и Серверная часть. IPC возвращает только публичный key/fingerprint/device ID и отсоединённый подпись конкретного сервер запрос.
- Аутентификация сессия запись получил канонический `userId`, чтобы устройство ключ пространство имён не зависел от изменяемого электронная почта. Старые сохранённые сессии восстанавливают `userId` из уже проверенного JWT `sub`.
- После вход Настольное приложение автоматически выполняет `register/begin → local Ed25519 sign → register/complete`; на следующих сессии используется `verify/begin|complete`. Обновлённый проверен-устройство токен доступа атомарно заменяется в OS учётные данные хранилище.
- Если локальная привязка указывает на отозванный/удалённый сервер устройство, Настольное приложение создаёт новую локальный устройство идентичность. Отпечаток конфликт после прерванной регистрации также отказ с блокировкой разрешается новой ключ пара, а не повторным использованием неизвестной сервер привязка.
- Выход удаляет сессия секреты, но сохраняет устройство ключ для следующего доказательство владения.

### Контроли выпуска

- Добавлен `scripts/smoke/offline/device-key-storage.py`; обычный предварительная проверка проверяет наличие нативный ключ generation/keyring/signing путь и запрещает появление закрытый устройство ключ материал в React/localStorage.
- Репозиторий политика закрепляет Tauri команды и автоматический Настольное приложение доказательство поток как обязательную часть `0.12.2`.
- `proof-of-possession + OS secure storage` всё ещё не объявляется привязанный к оборудованию идентичность: TPM/Защищённый Enclave/Windows Hello/Keychain доступ-управление аттестация относятся к следующим Доверие к устройству этапам.

## 0.12.1 — Доверие к устройству Ядро + устройство реестр

`0.12.1` вводит первую рабочую границу Доверие к устройству поверх стабильного Аутентификация Федерация релиз. Старое поле сессия `deviceId` остаётся недоверенной клиентской меткой для совместимости; доверенная устройство идентичность создаётся только после Ed25519 доказательство владения и хранится отдельно в постоянный реестр.

### Устройство реестр / доказательство владения

- Регистрация устройства — реальная запрос-ответ процедура: Серверная часть создаёт краткоживущий одноразовый запрос, клиент подписывает канонический полезная нагрузка Ed25519 закрытый ключ, Серверная часть проверяет подпись и только после этого создаёт доверенный устройство. В БД хранится только открытый ключ; закрытый ключ никогда не передаётся Серверная часть.

- Повторная сессия может доказать владение уже зарегистрированным устройство ключ через `verify/begin|complete`; запрос дополнительно привязан к конкретной Никогда сессия.
- Отзыв устройства переводит устройство в `revoked` и отзывает все связанные Никогда сессии и токен обновления семейство; связанные сессия риск состояние становятся `compromised`.
- Пользователь может list/rename/revoke свои устройства, администратор — фильтровать реестр и выполнять отзыв после свежего устойчивый к фишингу step-up.

### Миграция / контроли выпуска

- Добавлена миграция `0012_device_trust_core_0121.sql`: `trusted_devices`, `device_challenges`, сессия доверие столбцы, реляционный FK/check ограничения и индексы.
- Серверная часть и CLI миграция каталог содержат побайтово идентичный `0012`.
- HTTP E2E проверяет вход → регистрация запрос → Ed25519 доказательство → доверенный сессия → второй-сессия доказательство → запрос повторное воспроизведение отклонение → устройство отзыв → session/refresh-family инвалидация.
- OpenAPI и репозиторий политика считают устройство реестр, доказательство путь и миграция обязательными `0.12.1` контроли выпуска.

## 0.12.0 — Аутентификация Федерация Релиз

`0.12.0` завершает линию Аутентификация Федерация `0.11.1–0.11.10` как стабильный рабочий релиз. Локальный, SQL, HTTP, OIDC и Microsoft являются провайдеры одного Федерация Ядро; ключи доступа/TOTP/восстановление применяются как аутентификация методы/MFA поверх канонический Никогда пользователь, а Minecraft Аутентификация Адаптер получает уже каноническую Никогда сессия независимо от источника входа.

### Стабильный федерация граница

- Рабочий запуск использует стабильный `NewFederationCore(...)`; версия constructors оставлены только для исходник совместимость. Встроенный `local` провайдер теперь проходит тот же Коннектор SDK соответствие контроль, что SQL/HTTP/OIDC/Microsoft.
- Добавлены провайдер-agnostic явный-связь эндпоинты `POST /api/v1/auth/providers/{providerId}/link/begin|complete`. Любой `browser-auth` коннектор может быть связан с уже аутентифицированным Никогда пользователь по доказательству провайдер идентичность; совпадение электронная почта не является доказательством и не запускает автоматический-связь.
- `GET /api/v1/admin/auth/federation/status` показывает health/capabilities/provisioning политика и количество связь идентичности для каждого провайдер. `/ready` дополнительно проверяет, что в реестр есть хотя бы один реально здоровый аутентификация провайдер.
- Внешний провайдер токен остаётся только на стороне сервера учётные данные: он не становится Никогда access/refresh токен и не возвращается из linking/login API.
- Сессия выдача больше не создаёт `local` идентичность как побочный эффект. Passwordless ключ доступа создаёт канонический сессия с `provider=passkey` и без фиктивной `identity-local-*`; MFA continuation после SQL/HTTP/OIDC/Microsoft сохраняет исходные provider/identity. Локальный идентичность принадлежит только реальному локальный-пароль жизненный цикл.

### Релиз миграция / канонический локальный идентичность

## 0.11.10 — Федерация E2E + миграция + стабилизация

`0.11.10` не добавляет новый аутентификация провайдер: релиз превращает Федерация Ядро `0.11.2–0.11.9` в исполняемо проверяемый контроль выпуска. Локальный, SQL, HTTP, OIDC, Microsoft и ключ доступа проходят одну канонический session/Minecraft матрица; рабочий PostgreSQL E2E проверяет restart/multi-instance refresh/revoke/replay, а миграция инструментарий теперь отказ с блокировкой обнаруживает понижение версии, контрольная сумма расхождение и незапечатанные устаревший миграция записывает до изменения схемы.

### Федерация контроли выпуска

- `scripts/test/federation-e2e.py` запускает реальную connector/federation матрица: Локальный, SQL, HTTP, OIDC, Microsoft, ключ доступа, канонический/JIT идентичность правила, Minecraft сессия обмен и безопасность ошибка случай. Это релиз тест, а не manifest/endpoint declaration.
- `e2e/scripts/run-federation-postgres-e2e.sh` поднимает PostgreSQL/Redis и три Серверная часть экземпляры. Тест выполняет вход на, перезапуск, обновление после перезапуск, обновление на B, валидация на C, повторное воспроизведение старого токен обновления на C и проверяет отзыв семейство на A/B/C.
- CI запускает обе матрицы; строгий предварительная проверка дополнительно включает PostgreSQL multi-экземпляр E2E через `NEVERLAUNCHER_PREFLIGHT_FEDERATION_POSTGRES=1`.
- Федерация провайдер реестр больше не сообщает устаревшую внутреннюю версию: среда выполнения метаданные использует текущую `VERSION`.

### Миграция / обновление стабилизация

- Добавлена миграция `0010_federation_stabilization_01110.sql`. Перед добавлением ограничения она отказ с блокировкой проверяет существующие session/refresh/provider-credential данные; повреждённая БД не «лечится» молча.
- Усилена целостность токен обновления семейство: допустимые состояние значения, не более одного `current` токен обновления на семейство, согласованность `session/user/family` и deferrable consistency внешний ключи для транзакционной ротация.
- Провайдер учётные данные теперь дополнительно связаны составной FK с канонический `auth_identity`, поэтому учётные данные не может принадлежать другому user/provider/subject.
- `nl db migrate apply` сначала проверяет unknown/future миграция и контрольная сумма расхождение. Blank контрольная сумма старой известной миграция может быть безопасно запечатан текущим встроенный контрольная сумма; несовпадающий контрольная сумма блокирует обновление.
- Добавлен `nl db migrate verify`: проверяет, что схема полностью применена, нет неизвестный миграция, нет blank контрольная сумма и каждый контрольная сумма совпадает с бинарный файл каталог.
- Серверная часть миграция состояние возвращает `compatible`, `unknown` и `unverified` наряду с current/pending, чтобы обновление инструментарий мог отличить ожидающий обновление от unsafe схема состояние.
- Встроенный CLI и Серверная часть миграция каталог остаются побайтово идентичный; репозиторий политика проверяет это как контроль выпуска.

### Стабилизация / ошибка матрица

- Релиз матрица отдельно проверяет OIDC issuer/audience ошибки, HTTP signature/replay/SSRF, Microsoft tenant/signing-key confusion, WebAuthn wrong-origin/challenge повторное воспроизведение, SQL отключённый/TLS/только для чтения поведение, обновление повторное воспроизведение и канонический идентичность reassignment защита.
- PostgreSQL E2E делает `db migrate verify` до запуска Серверная часть и после replay/multi-instance сценария, поэтому успешный аутентификация тест одновременно подтверждает перезапуск-безопасный схема состояние.
- Новых пользовательских аутентификация семантика в `0.11.10` нет: внешний провайдер токен по-прежнему не является Никогда токен, Minecraft сессия остаётся дочерней к Никогда сессия, а учётная запись связывание не происходит по одному совпавшему электронная почта.

## 0.11.9 — Minecraft Аутентификация Совместимость 2.0

`0.11.9` отделяет Minecraft identity/session от способа входа в NeverLauncher. После локальный/SQL/HTTP/OIDC/Microsoft/passkey аутентификация канонический Никогда пользователь получает постоянный Профиль Minecraft и отдельный непрозрачный Minecraft сессия токен; Minecraft-слой больше не проверяет локальный пароль хеш и не использует Никогда JWT как игровой токен доступа.

### Minecraft идентичность / сессия адаптер

- `minecraft_profiles` хранит стабильный UUID, производный только от неизменяемый канонический Никогда пользователь ID. Email/provider субъект не участвуют в UUID; созданное Minecraft имя также остаётся стабильным при изменении профиля пользователя.
- `POST /api/v1/minecraft/session` обменивает уже аутентифицированную Никогда сессия на отдельную Minecraft сессия. Непрозрачный `nlmc_*` токен хранится только как SHA-256 хеш, связан с родительский Никогда сессия и автоматически перестаёт быть действительным после её revoke/logout.
- Постоянный `minecraft_sessions` и краткоживущий `minecraft_joins` работают между Серверная часть экземпляры. Yggdrasil обновление потребляет старый токен; повторный обновление отклоняется. `hasJoined` повторно проверяет Minecraft сессия и родительский Никогда сессия и при переданном `ip` проверяет его против подключение запрос.
- `profile:launch` достаточно для сессия обмен: обычный игрок не нуждается в admin/project-read разрешение.

### Yggdrasil / Настольное приложение / NeverRuntime

- Реально зарегистрированы `/authserver/authenticate|refresh|validate|invalidate|signout`, `/sessionserver/session/minecraft/join|hasJoined`, профиль поиск и `/api/profiles/minecraft/{username}`. Поддерживающий пароль провайдеры проходят Федерация Ядро; ключ доступа/OIDC/Microsoft используют Никогда-сессия обмен.
- Корень метаданные совместим с authlib-injector. NeverRuntime автоматически добавляет подписанный `authlib-injector*.jar` из релиз манифест как `-javaagent` к текущему Серверная часть; произвольный локальный JAR таким образом не принимается.
- Настольное приложение перед запускать получает Minecraft сессия и передаёт NeverRuntime реальный UUID/токен доступа вместо `offline` и нулевого UUID. Токен редактируется в команда preview/diagnostics. ServerBridge подключение использует то же канонический Профиль Minecraft имя.
- Microsoft подпись-в по-прежнему не считается доказательством Minecraft владение; `0.11.9` реализует Никогда-управляемый Minecraft совместимость identity/session, а не Mojang/Microsoft право владения обход.
- Встроенная миграция цепочка `nl db migrate apply` синхронизирована с Серверная часть миграция `0001–0009`; репозиторий политика теперь отказ с блокировкой проверяет одинаковый набор файлов и SHA-256 содержимого, чтобы manual рабочий обновление не отставал от Серверная часть автоматический-мигрировать.

## 0.11.8 — Сессия Управление 2.0

`0.11.8` переводит Никогда сессии на полноценный рабочий сессия-управление контур: стандартные JWT/JWS доступ токены с `iss`/`aud`/`sub`/`sid`/`jti`/`iat`/`exp`/`kid`/`auth_time`/`amr`, ротация-способный подписание хранилище ключей, постоянный device/risk метаданные и пользовательские/административные сессия средства управления. Токен обновления семейство повторное воспроизведение по-прежнему отзывает всю семейство и теперь явно переводит сессию в `compromised`.

### Сессии / риск / средства управления

- PostgreSQL остаётся источник истины для сессии и обновление семейство; сохраняются identity/provider, устройство, first/last IP и Пользователь-Agent, аутентификация methods/strength/time, последний activity, истечение и риск состояние.
- Изменение IP или Пользователь-Agent переводит активную сессия в `elevated` и пишет `auth_event`; обновление повторное воспроизведение переводит family/session в `compromised` и отзывает её.
- Пользователь может просматривать сессии, переименовывать устройство без изменения устройство ID, отзывать одну сессия, все остальные или выполнить выход-все. Администратор API фильтрует сессии по user/provider/status/risk и умеет массово отзывать user/provider/risk выборку; провайдер-wide компрометация требует свежую устойчивый к фишингу аутентификация.
- Провайдер выход отделён от Никогда выход: поддерживающий отзыв коннектор получает провайдер учётные данные на стороне сервера, учётные данные удаляется после отзыв, но Никогда сессия остаётся активной до отдельного revoke/logout.

### Доступ-токен ротация ключей

- Токен доступа теперь compact JWS/JWT `HS256`, а не custom `base64(payload).HMAC`. Header содержит `typ=JWT`, `alg=HS256`, `kid`; проверяющий модуль проверяет издатель, audience, токен использовать, метки времени, сессия ID и ключ ID.
- `NEVERLAUNCHER_AUTH_TOKEN_KEYS_JSON` задаёт хранилище ключей `kid -> secret`, `NEVERLAUNCHER_AUTH_TOKEN_ACTIVE_KID` выбирает ключ подписи. Предыдущий ключ остаётся проверять-только до истечения выпущенных им доступ токены, после чего его можно удалить. Старые production-конфиги с одним `AUTH_TOKEN_SECRET` продолжают работать через `primary` ключ.

## 0.11.7 — Ключи доступа / WebAuthn + MFA 2.0

`0.11.7` добавляет рабочий WebAuthn/passkeys поверх существующего Федерация Ядро. Ключи доступа являются реальным аутентификация метод: учётные данные и одноразовые запросы сохраняются в PostgreSQL, утверждение проверяет RP ID/origin/challenge/signature/user verification/sign счётчик, а пароль/SQL/HTTP/OIDC/Microsoft вход проходит единый MFA политика до выпуска Никогда сессия.

### WebAuthn / Ключи доступа

- Discoverable учётные данные с `residentKey=required` и `userVerification=required`; поддерживаются ES256, Ed25519 и RS256 COSE ключи.
- Регистрация принимает только `attestation=none`, проверяет RP ID хеш, UP/UV, AAGUID, учётные данные ID и COSE открытый ключ.
- Passwordless вход и ключ доступа continuation для password/federated вход используют одноразовые PostgreSQL-основанный запросы с TTL 5 минут.
- Сессия метаданные содержит `authMethods`, `authStrength` (`single-factor`/`mfa`/`phishing-resistant`) и `authTime`; обновление сохраняет эту силу, а step-up выпускает новый токен доступа.
- Ключ доступа учётные данные жизненный цикл: list/rename/revoke, резервное копирование флаги, транспорт, `lastUsedAt`, подпись счётчик и восстановление-код очистка при отзыве последнего учётные данные.

### MFA 2.0 / Step-up

- На-пользователь политика: `optional`, `required`, `phishing-resistant`. TOTP и восстановление код остаются рабочими; ключ доступа может удовлетворить MFA и обязателен для устойчивый к фишингу политика.
- Критические операции используют актуальный аутентификация: релиз publish/rollback и миграция требуют свежую MFA; пакет подписание, восстановление из резервной копии, пользователь роль изменяет и ServerBridge токен ротация требуют свежую устойчивый к фишингу аутентификация.
- WebAuthn RP ID/origins валидируются отказ с блокировкой в рабочий; критичный ключ доступа/OIDC/Microsoft аутентификация маршруты используют аутентификация rate-ограничение bucket.


## 0.11.6 — Microsoft Коннектор

`0.11.6` добавляет рабочий Microsoft идентичность коннектор как специализацию рабочего OIDC Connector/Federation Ядро, а не отдельный OAuth движок. Поддерживаются Microsoft идентичность платформа v2 Авторизация Код + PKCE S256, `common`/`organizations`/`consumers` и единый-tenant GUID authorities, global/US Gov/China clouds, tenant-независимый издатель валидация, JWKS подписание-ключ издатель валидация и стабильная канонический идентичность на основе `tid + oid`. Microsoft вход не считается доказательством владения Minecraft.

### Microsoft идентичность среда выполнения

- Microsoft провайдер регистрируется через `NEVERLAUNCHER_AUTH_MICROSOFT_PROVIDERS_JSON` / `NEVERLAUNCHER_AUTH_MICROSOFT_PROVIDERS_FILE` и проходит обнаружение/JWKS/health/conformance до открытия API трафику.
- `offline_access` добавляется обязательно для на стороне сервера обновление учётные данные жизненный цикл; app секрет берётся только из environment/file.
- Multitenant токен проверяется одновременно по `tid`, фактическому tenant-specific `iss` и `issuer` конкретного JWKS ключ подписи; `allowedTenantIds` может дополнительно сузить доверенный tenants.
- Стабильный внешний субъект — `tid:oid`; изменяемый электронная почта/UPN/имя используются только как профиль attributes и не участвуют в идентичность владение.
- Microsoft внешний groups/roles не становятся Никогда роли напрямую: повышение возможно только через локальный `roleMappings` политика при JIT предоставление учётной записи.

### Учётная запись связывание / провайдер учётные данные

- `explicit-only` остаётся по умолчанию. Аутентифицировать Никогда пользователь может выполнить `POST /api/v1/auth/microsoft/{providerId}/link/begin` → провайдер доказательство → `.../link/complete`; совпадение электронная почта не используется для автоматический-связывание.
- Microsoft/OIDC обновление токены сохраняются только на стороне сервера в `provider_credentials` как AES-GCM конверт, привязанный AAD к user/identity/provider/subject. Открытый текст провайдер токен не возвращается клиенту и не становится Никогда access/refresh токен.
- `POST /api/v1/auth/providers/{providerId}/credential/refresh` выполняет провайдер ротация через Коннектор SDK и отказ с блокировкой проверяет неизменность субъект. `DELETE.../credential` удаляет локально сохранённый провайдер учётные данные.
- `POST /api/v1/auth/microsoft/{providerId}/logout-url` строит список разрешений Microsoft front-канал выход URL отдельно от Никогда logout/session отзыв.

### Область граница

Microsoft идентичность и Minecraft ownership/profile намеренно разделены. `0.11.6` не интерпретирует успешный Microsoft подпись-в как Minecraft право владения и не запрашивает Xbox/Minecraft владение APIs; это остаётся отдельным entitlement/profile проверка слой последующих совместимость работ.

`0.11.5` добавляет рабочий OIDC федерация поверх Коннектор SDK/Федерация Ядро: OpenID Провайдер Обнаружение, Авторизация Код + PKCE S256, state/nonce, JWKS ротация ключей, ID Токен signature/issuer/audience/azp/time валидация, необязательный UserInfo merge с обязательным совпадением `sub`, configurable захватывает сопоставление, явный-только/JIT предоставление учётной записи и browser/desktop begin/complete поток. ## 0.11.4 — HTTP Коннектор

`0.11.4` добавляет второй внешний рабочий аутентификация провайдер поверх Коннектор SDK/Федерация Ядро: усиленный HTTP Коннектор для существующих CMS/API. `/api/v1/auth/login` и `/api/v1/admin/login` реально маршрутизируют пароль аутентификация в удалённый провайдер по `providerId`; успешный внешний субъект затем проходит обычный канонический идентичность/JIT поток и получает Никогда сессия, а провайдер токен не становится Никогда токен.

### Удалённый аутентификация протокол

- Реальные `POST /authenticate`, `POST /refresh`, `POST /resolve`, `POST /logout` и `GET /health`; пути могут быть переопределены только в запуск конфигурация и всегда остаются относительными к одному `baseUrl`.
- Строгий протокол конверт `neverlauncher-http-auth/1`, обязательный `issuer`, стабильный `subject`, ограниченный идентичность fields/groups/roles/claims и отказ с блокировкой схема decoding.
- `/resolve` обязан вернуть тот же субъект, который был запрошен; изменение субъект считается провайдер misconfiguration.
- Удалённый ошибка состояние преобразуются в типизированный Коннектор SDK ошибки без утечки произвольного текста вышестоящий проект пользователю.
- HTTP провайдер поддерживает SDK пароль аутентификация, пользователь поиск, токен обновление и токен отзыв; соответствие проверяет заявленные возможности при запуск.

### Транспорт безопасность / SSRF защита

- Только HTTPS; перенаправления и прокси окружение отключены. TLS проверка обязательна, поддерживаются custom CA и необязательный mutual TLS клиентский сертификат.
- `hostAllowlist` применяется к каждому dial. Коннектор выполняет DNS разрешение сам, валидирует все полученные IP и соединяется непосредственно с уже проверенным IP, сохраняя TLS имя хоста проверка.
- Локальная петля, закрытый, локальный для канала, общий, multicast, reserved и documentation сеть заблокированы по умолчанию; закрытый эндпоинт требует явного минимального `allowedCidrs`.
- Connect/request/response-header тайм-аут, ограниченный соединение pool, idle тайм-аут и ответ размер ограничение конфигурируются с безопасными пределами.

### Request/response authenticity

- Каждый запрос подписывается HMAC-SHA256 по method/path/timestamp/nonce/body SHA-256; секрет берётся только из переменная окружения или секрет файл, не из провайдер JSON.
- Каждый ответ, включая ошибка ответ, обязан вернуть тот же одноразовое значение и действительный HMAC над status/timestamp/nonce/body. Используются constant-время comparison, метка времени повторное воспроизведение окно и использованный-одноразовое значение кэш.
- Неподписанный, просроченный, повторный или подписанный другим ключ ответ отклоняется до разбора идентичность.

### Федерация / рабочий интеграционный

- `NEVERLAUNCHER_AUTH_HTTP_PROVIDERS_JSON` / `NEVERLAUNCHER_AUTH_HTTP_PROVIDERS_FILE` подключены к реальному запуск реестр рядом с SQL провайдеры; unreachable/misconfigured провайдер останавливает запуск отказ с блокировкой.
- `jit` и `explicit-only` используют тот же Федерация Ядро политика: JIT создаёт канонический Никогда пользователь + `auth_identity`, но не fake локальный пароль; совпадение электронная почта не даёт implicit связывание.
- Рабочий Compose/CLI templates передают HTTP провайдер конфигурация и отдельный HMAC секрет переменная окружения.
- Интеграционный тест поднимает настоящий TLS аутентификация служба, проверяет HMAC request/response поток и выполняет HTTP провайдер аутентификация через `NewFederationCore114` до постоянный канонический идентичность.

## 0.11.3 — SQL Коннектор

`0.11.3` добавляет первый внешний рабочий аутентификация провайдер поверх Коннектор SDK/Федерация Ядро: SQL Коннектор для PostgreSQL, MySQL и MariaDB. Это не отдельный endpoint/manifest слой — `/api/v1/auth/login` и `/api/v1/admin/login` реально маршрутизируют пароль аутентификация в зарегистрированный SQL провайдер по `providerId`, после чего Федерация Ядро разрешает внешний субъект в канонический Никогда пользователь и выпускает обычную Никогда сессия.

### SQL аутентификация среда выполнения

- Конфигурация нескольких SQL провайдеры через `NEVERLAUNCHER_AUTH_SQL_PROVIDERS_JSON` или `NEVERLAUNCHER_AUTH_SQL_PROVIDERS_FILE`; DSN может ссылаться на отдельную секрет переменная окружения через `dsnEnv`.
- Только NeverLauncher-сгенерированный `SELECT`: table/column сопоставление проходит identifier валидация, поиск statements подготавливаются при запуск, вход значения передаются bind-параметрами, произвольный SQL из вход запрос не выполняется.
- PostgreSQL, MySQL и MariaDB; connect/query тайм-аут, ограниченный pool, соединение срок жизни, запуск проверка работоспособности и отказ с блокировкой регистрация.
- TLS включён по умолчанию для внешнего SQL провайдер; режимы с открытый текст резервный вариант (`sslmode=prefer`, `tls=preferred`) запрещены при `requireTls=true`, незащищённый сертификат проверка и открытый текст требуют разных явных opt-в.
- Каждый поиск выполняется в только для чтения транзакция и возвращает не более одной идентичность; ambiguous username/email блокируется как конфликт.
- Сопоставление: внешний ID, username, электронная почта, отображать имя, состояние, группы, роли и Minecraft UUID; groups/roles понимают JSON arrays, comma-отдельный значения и PostgreSQL `text[]`.

### Пароль совместимость

- Argon2ID PHC проверка с привязанный на memory/time/parallelism.
- bcrypt с ограничением допустимого работа factor.
- PBKDF2-SHA256 (включая Django-style формат) с минимальным iteration политика.
- Устаревший SHA-256 выключен по умолчанию и требует `allowLegacySha256=true`.

### Федерация / предоставление учётной записи

- SQL провайдер может работать в `explicit-only` или `jit` предоставление учётной записи режим.
- `jit` после успешной SQL пароль проверка атомарно создаёт канонический Никогда пользователь + внешний `auth_identity`; исходная пользовательская таблица остаётся только для чтения и не мигрируется в NeverLauncher.
- Канонический пользователь ID стабильно выводится из `(provider, subject)`, а не из электронная почта.
- Совпадение внешнего электронная почта с уже существующим Никогда пользователь не используется для автоматический-связывание и завершается конфликт, требуя явной связи идентичность.
- JIT federated пользователь не получает фиктивный локальный-пароль идентичность.

### Рабочий усиление защиты

- Docker сборка теперь копирует `go.sum` и публичный `services/api/pkg`, поэтому рабочий образ действительно собирает Коннектор SDK/Федерация Ядро.
- Добавлены исполняемый тесты на prepared/bound queries, только для чтения транзакция, PostgreSQL arrays, TLS резервный вариант политика, дубликат идентичность обнаружение, Argon2id/bcrypt/PBKDF2/устаревший пароль совместимость, JIT предоставление учётной записи и запрет электронная почта автоматический-связывание.
- Неизвестный identifier выполняет algorithm-equivalent dummy пароль работа; identifier/password имеют верхние привязанный, чтобы снизить timing enumeration и ресурс-abuse поверхность.
- PostgreSQL JIT предоставление учётной записи сериализуется транзакция-область рекомендательный блокировка по нормализован электронная почта, поэтому случай-insensitive электронная почта конфликт остаётся отказ с блокировкой и при конкурентных первых входах.

## 0.11.2 — Коннектор SDK + Федерация Ядро

`0.11.2` переводит рабочий локальный пароль вход на общий Федерация Ядро. Встроенный `local` провайдер использует тот же публичный Коннектор SDK, который предназначен для SQL/HTTP/OIDC/Microsoft коннекторы следующих релизов; прямой пароль-проверка в `/auth/login` и `/admin/login` больше не является отдельным аутентификация движок.

### Коннектор SDK

- Добавлен импортируемый Go SDK `services/api/pkg/authconnector` с типизированный метаданные, возможности, канонический провайдер идентичность, password/browser аутентификация, обновление, профиль разрешение, идентичность связывание и отзыв interfaces.
- Возможности являются исполняемым контрактом: реестр и соответствие suite отклоняют коннектор, который заявляет возможность без соответствующего интерфейса.
- Добавлен повторно используемый `authconnector/conformance` testkit; встроенный `local` коннектор проходит его в серверная часть тест suite.
- Коннектор ошибки имеют стабильные типизированный код (`invalid_credentials`, `identity_disabled`, `unavailable`, `conflict`, `identity_not_found`) вместо сравнения строк ошибок.

### Федерация Ядро

- Добавлен конкурентный-безопасный провайдер реестр и единый пароль-аутентификация dispatch. `providerId` поддерживается в канонический `/api/v1/auth/login` и `/api/v1/admin/login`; отсутствие значения означает `local`.
- После успешной проверки учётные данные провайдер возвращает только аутентификация proof/identity. Федерация Ядро обязательно разрешает `(provider, subject)` через `auth_identities` в канонический Никогда `User`; провайдер токен не становится Никогда токен доступа.
- Реализовано явный-только идентичность связывание с защитой от silent reassignment одного субъект другому Никогда пользователь.
- Локальный провайдер теперь реально зарегистрирован через SDK и обслуживает рабочий вход. MFA, RBAC, access/refresh сессии и аудит выполняются после канонический идентичность разрешение.
- Новые пользователи при создании получают постоянный `local` идентичность; успешный федерация вход обновляет снимок захватывает и `last_authenticated_at`.

### Хранение / API

- Миграция `0005_federation_core_0112.sql` расширяет `auth_identities` провайдер метаданные (`email`, `username`, `display_name`, `claims`, `last_authenticated_at`) и backfill-ит локальные идентичность.
- Репозиторий получил рабочие get/list/save/touch операции для канонический идентичности в память и PostgreSQL реализация.
- `GET /api/v1/auth/providers` показывает реально зарегистрированные providers/capabilities/health до вход; `GET /api/v1/auth/identities` возвращает идентичность связывает текущего Никогда пользователь без провайдер secrets/claims.
- OpenAPI вход схема получил `providerId`; канонический аутентификация возможности теперь объявляют активный Федерация Ядро и реестр провайдеры.

### Проверка

- Серверная часть интеграционный тест проверяет провайдер обнаружение, локальный вход через Федерация Ядро, канонический идентичность эндпоинт и дальнейший сессия refresh/revoke поток.
- Федерация модульные тесты проверяют канонический разрешение и отказ с блокировкой отказ для аутентифицировать, но не связанной внешний идентичность.
- SDK соответствие тесты проверяют соответствие возможность interfaces и работоспособность контракт.

- `clientDir` и существующие компоненты назначение путь проверяются через `Lstat`; symlink-компоненты отклоняются до записи.

- Forge/NeoForge установщик `data/` очищается и пересоздаётся перед обработчик выполнение.

### Среда выполнения / CI свидетельство

- Совместимость Движок в NeverRuntime отклоняет symlink-компоненты при чтении metadata/classpath пути.

## 0.10.4 — Forge + NeoForge

`0.10.4` добавляет рабочую materialization-цепочку Forge и NeoForge поверх `0.10.3` Fabric + Quilt. Реализация использует настоящий основанный на обработчиках установщик формат, а не декларативный установка-plan.

### Forge / NeoForge установщик конвейер

- Добавлены `nl runtime forge-install`, `forge-package`, `neoforge-install`, `neoforge-package`.
- Версия Forge выбирается по официальный Maven метаданные для конкретной Minecraft-версии; NeoForge фильтруется по соответствующей ветке `major.patch`.
- `latest-stable` разрешается в конкретный загрузчик версия до формирования релиз.
- Официальный `installer.jar` скачивается по HTTPS и проверяется по Maven `.sha1`; custom mirror требует явный URL/контрольная сумма.
- Установщик JAR реально разбирается: читаются `install_profile.json` и встроенный `version.json`.
- Встроенный `maven/` извлекается безопасно в `libraries/`; обход и символическая ссылка отклоняются.
- Установщик `data/` извлекается во внутреннее `.neverlauncher` состояние и не попадает в итоговый клиент пакет.
- Installer/runtime библиотеки материализуются с SHA-1/size проверка; локально созданные обработчик выходные данные нормализуются фактическими digest/size.

### Обработчик Движок

- Выполняются клиент обработчики из `install_profile.json` через реальную Java JVM.
- Обработчик `Main-Class` читается из `META-INF/MANIFEST.MF`; путь классов строится из закреплённый Maven coordinates.
- Реализованы установщик variables `{ROOT}`, `{MINECRAFT_JAR}`, `{INSTALLER}`, `{LIBRARY_DIR}`, `{SIDE}` и `data` variables.
- Maven ссылки `[group:artifact:version[:classifier][@ext]]` разрешаются в локальный `libraries/` путь.
- `outputs` проверяются по SHA-1/SHA-256; tokenized хеш значения вида `{PATCHED_SHA}` и кавычки хеши поддерживаются.
- Уже корректный вывод позволяет безопасно пропустить обработчик при повторной материализации.
- Каждый обработчик имеет тайм-аут; запуск идёт без оболочка interpolation.

### Среда выполнения интеграционный

- Дочерний Forge/NeoForge `version.json` нормализуется и сохраняется в `versions/<id>/<id>.json`.
- Итоговый профиль использует существующий `inheritsFrom` Совместимость Движок без отдельного запускать резервный вариант.
- `runtime matrix` теперь объявляет основанный на обработчиках Forge и NeoForge материализатор готовыми.
- Устаревший Forge pre-1.13 остаётся явно вне область `0.10.4`, вместо ложного статуса поддержки.

### Проверки

- Добавлен полный локальный фикстура: Vanilla основа -> проверен установщик -> встроенный Maven -> обработчик выполнение -> вывод хеш -> дочерний профиль -> Никогда клиент пакет.
- Отдельно проверяются Forge/NeoForge Maven версия selection, несовместимая Minecraft/NeoForge ветка, Maven classifier/extension пути и архив обход.
- Восстановлен отсутствовавший в входном `0.10.3` бинарный файл исходник `runtime/neverruntime/src/bin/neverruntime.rs`, на который уже ссылался `Cargo.toml`.

## 0.10.1 — Совместимость Движок

0.10.1 переносит разрешение Minecraft запускать метаданные в исполняемый NeverRuntime и убирает fallback-планы из рабочий среда выполнения путь. Совместимость Движок работает по подписанному содержимому неизменяемый релиз и строит детерминированный план запуска из реального Mojang-compatible `version.json`.

### Исполняемый Совместимость Движок

- NeverRuntime получил отдельный `compatibility` движок: разрешение цепочки `inheritsFrom`, объединение версия метаданные, Mojang library/rule evaluation, OS/architecture/features правила, упорядоченный путь классов, нативный классификатор, `arguments.jvm`/`arguments.game`, устаревший `minecraftArguments`, Java крупный версия и стандартные Mojang placeholders.
- `classpathStrategy=compatibility`/`mojang` теперь используется непосредственно `Desktop -> NeverRuntime -> JVM`: главный класс, путь классов и аргументы берутся из проверенного метаданные, а не из перебора всех JAR-файлов.
- Все метаданные и путь классов пути, которые использует Совместимость Движок, обязаны входить в подписанный релиз манифест; локальный неподписанный `version.json` или JAR отказ с блокировкой блокирует запуск.
- Для multi-платформа релиз NeverRuntime учитывает `targetOs`: чужие OS артефакты не блокируют verify/sync и не попадают в манифест путь классов.
- Java ограничение из версия метаданные участвует в pre-запускать проверке совместимости JVM вместе с политика манифест.

### Серверная часть / релиз интеграционный

- `RuntimeLaunch` поддерживает `versionMetadataPath` и флаги функций для Mojang правила; при отсутствии явного пути применяется `versions/<minecraftVersion>/<minecraftVersion>.json`.
- Серверная часть проверяет метаданные совместимости путь на обход и не публикует совместимость релиз без обязательного подписанного `version.json`.
- Рекомендуемый запускать template и среда выполнения требования переведены на `classpathStrategy=compatibility` без статического Fabric/mainClass placeholder.

### CLI и среда выполнения бинарный файл

- Продукт среда выполнения команды больше не создают резервный вариант запускать plan при отсутствии `version.json`, а загрузчик метаданные без `--metadata`/`--installer-profile` отклоняется.
- Восстановлен фактический `neverruntime` бинарный файл, требуемый релиз конвейер и рабочий E2E: `verify`, `sync`, `launch`; добавлена команда `compatibility` для прямого разрешения локального подписанный клиент дерево.
- Добавлены unit/regression тесты для inheritance, Mojang rules/features, Maven пути, placeholders, обход путей и серверная часть публикация валидация.

## 0.10.0-P3.2v4 — Рабочий усиление защиты

P3.2v4 завершает следующий production-контур рабочим кодом: опубликованные релизы становятся неизменяемыми, client/desktop жизненный цикл выполняет реальные файловые операции, первый запуск становится автономным, а ключ жизненный цикл и supply-цепочка метаданные получают фактическую криптографическую и зависимость-основанный реализацию.

### P3.2v4 — immutable/client/desktop/supply-chain

- Опубликованный релиз стал неизменяемый на HTTP и репозиторий слоях: после `published` запрещены загрузка, manifest/status изменение и повторная публикация; изменение требует новой версии.
- `nl client install/update/verify/repair/cleanup/rollback` выполняют реальный локальный жизненный цикл: SHA-256/size проверка, снимки, карантин orphan-файлов, selective repair и откат предыдущего состояния.
- `nl install first-run` использует встроенную копию канонический `deploy/production`, не зависит от checkout и требует закреплённый API/Администратор образ refs (`@sha256:`); CI-политика проверяет синхронность встроенный templates.
- `nl desktop package/verify` принимает только существующие нативный артефакты, фиксирует размер/SHA-256 и отклоняет отсутствующие или изменённые файлы.
- `nl security rotate-key/revocation-list/attest` используют постоянный Ed25519 ключ реестр, реальные ключ пары, отзыв ключей и отсоединённый подписи; релиз проверка может учитывать отзыв реестр.
- SBOM формируется из реальных Go/npm/Cargo/Gradle зависимость manifests/locks в SPDX 2.3; происхождение формируется как в-toto Statement с SLSA v1 predicate, хеширует artifacts/materials и подписывается Ed25519 (`PROVENANCE.json.sig`).
- Рабочий комплект релиза включает отдельный проверяемый Настольное приложение пакет и требует подписанный происхождение аттестация.

### Безопасность и конфигурация

- Удалён резервный вариант входа администратора через конфигурационный пароль: вход принимает только пароль, хеш которого хранится у пользователя. Добавлен регрессия-тест против повторного появления обхода.
- Production-конфигурация валидируется отказ с блокировкой до запуска API: PostgreSQL/pgx, сильный токен секрет, HTTPS публичный URL, отдельный резервное копирование корень, хранилище и явный CORS список разрешений обязательны.
- CORS маска удалён; предварительная проверка незнакомого источник блокируется, разрешённый источник отражается только из список разрешений.
- S3 больше не переключается молча на локальный хранилище: ошибка инициализации или работоспособность-проверка останавливает Серверная часть API.
- Панель администратора больше не предзаполняет логин и пароль администратора.

### Резервное копирование и восстановление

- Резервное копирование создаёт реальный PostgreSQL custom dump через `pg_dump`, сохраняет фактические storage-объекты, JSON-снимки состояния и SHA-256 каждого файла в потоковый `tar.gz`.
- Резервное копирование хранится в отдельном `NEVERLAUNCHER_BACKUP_ROOT`; архив сначала пишется во временный файл, синхронизируется и атомарно переименовывается.
- `restore-dry-run` безопасно распаковывает архив во временный каталог, запрещает обход/необычные tar записи, сверяет размеры/SHA-256 и проверяет PostgreSQL dump через `pg_restore --list`.
- Добавлен реальный `POST /api/v1/operations/backups/{backupId}/restore`: PostgreSQL восстанавливается через `pg_restore`, хранилище — через текущий хранилище драйвер. Разрушительная операция требует точного подтверждения `backupId` и явного выбора database/storage.
- CLI `nl backup restore` вызывает реальный восстановление и требует `--confirm <backupId>` плюс `--database true` и/или `--storage true`.

### Очистка и контроли выпуска

- Удалены пять неиспользуемых устаревший handler-файлов поколений API 5.4–7.8; используемые общие вспомогательный модуль вынесены отдельно.
- `release doctor` запускает репозиторий политика, версия alignment и OpenAPI валидация и больше не выдаёт ложный `production-ready`; полный рабочий контроль выполняется строгим предварительная проверка.
- `NEVERLAUNCHER_PREFLIGHT_STRICT=1./scripts/release/preflight.sh` требует pgx, клиентская часть, Tauri, ServerBridge и комплект релиза и отказ с блокировкой останавливается при недоступном обязательном контуре.
- Рабочий E2E использует отдельный `e2e-production`: все рабочий защита остаются включены, HTTP разрешён только для локальная петля тестового API.

### Рабочий завершение поверх усиление защиты

- Docker API образ и канонический Compose теперь детерминированно готовят writable storage/backup тома для непривилегированного UID `10001`; отдельный init-служба исправляет владение существующих именованный тома до старта API.
- `release sign/verify` используют настоящий Ed25519 с внешним private/trusted открытый ключ. `release verify` отказ с блокировкой валидирует каждый обязательный артефакт, SHA-256 и подпись.
- Конвейер CLI выполняет настоящие Серверная часть `validate → sign → stage → smoke-test → publish` операции; хранилище audit/consistency сканируют реальные объекты и SHA-256; мигрировать применить выполняет встроенный migrator, откат идёт через подтверждённый восстановление из резервной копии; установка verify/storage-check реально обращаются к Backend/storage.

- Backup/restore защищены обслуживание-блокировка; перед восстановление создаётся безопасность резервное копирование, локальный хранилище переключается атомарным каталог переименование, PostgreSQL восстанавливается одной транзакцией.

- Исторический `/api/v2`–`/api/v5` routers оставаться удалён; реальный продукт возможности являются регистрировать под `/api/v1`.
- Восстановление единый канонический `schemas/openapi.yaml` и 1:1 router/OpenAPI валидация.
- Удалён preflight/release-script ссылки к удалён fake/RC/stable/GitFlic smoke файлы.

### P2 рабочий поведение восстановление

- Настольное приложение использует NeverRuntime напрямую.
- Нативный OS учётные данные хранилище является используется для аутентификация сессия секреты; there является нет открытый текст токен резервный вариант.
- JVM запускать является контролируемый и журналы поток к диск вместо этого buffering whole процесс вывод.
- NeverRuntime загрузка и SHA-256 проверка являются поток.
- S3 загрузка использует диск spooling + incremental SHA-256 вместо этого buffering объект в память.
- Redis-основанный ограничение частоты, доверенный прокси, рабочий Администратор образ, CSP и рабочий Compose являются активный снова.
- Реальный Velocity/Paper/Purpur E2E является восстановление.

### Контракты / тесты

- Канонический Серверная часть тесты теперь exercise `/api/v1` для CRUD, пакет публикация, безопасность усиление защиты, резервное копирование и ServerBridge.
- Исторический API пути являются тест как отсутствующий вместо этого являясь re-включённый для регрессия совместимость.

## 0.10.0-P0 — Рабочий P0 Усиление защиты

P0-патч закрывает критические security/database/release-integrity проблемы стабильной 0.10.0 без расширения продуктового API.

### Безопасность

- Инициализировать владелец защищён одноразовым `NEVERLAUNCHER_BOOTSTRAP_TOKEN`; открытый текст токена не сохраняется в PostgreSQL.
- Состояние установки хранится в `neverlauncher_installation_state`; повторный инициализировать блокируется, после первого проекта фиксируется `installation_completed=true`.
- Изменяющий admin/release/extension эндпоинты предыдущих API-поколений требуют действительную session/permission.
- Настольное приложение Лаунчер отказ с блокировкой проверяет Ed25519 манифест подпись и точное совпадение закреплённый открытый ключ перед download/repair/build-launch-plan/launch.

### База данных

- Добавлен исполняемый рабочий миграция исполнитель с `schema_migrations`, SHA-256 контрольная сумма и PostgreSQL рекомендательный блокировка.
- `nl db migrate apply` реально применяет встроенный миграция цепочка через `psql`.
- Серверная часть автоматически применяет миграция или при отключённом автоматический-мигрировать отказывается стартовать при pending/checksum несоответствие; `/ready` проверяет ту же цепочку.
- Базовая линия миграция нормализует исторические PostgreSQL структура в текущую SQLRepository-схему и отказ с блокировкой останавливается на несопоставимых устаревший файл строки.

### Релиз целостность

- Рабочий `build-release.sh` собирает Серверная часть только с pgx и больше не имеет `neverlauncher_nopgx` резервный вариант.
- Неизвестный репозиторий драйвер больше не приводит к молчаливому переходу на в памяти процесса репозиторий.

### Проверено

- `go test./...`, `go vet./...` для CLI.
- `go test -tags neverlauncher_nopgx./...`, `go vet -tags neverlauncher_nopgx./...` для автономный Серверная часть контура.
- `scripts/release/preflight.sh` проходит для `0.10.0-P0` в offline-контуре.
- Полный pgx/Cargo/live PostgreSQL проверки требуют среды с соответствующими зависимостями.
