## Windows Защита RC / граница доверия релиза — 0.18.12

В `0.18.12` Windows защита считается рабочий-сертифицированный только когда один комплект релиза одновременно содержит точный-фиксация атакующий сертификация и те же Authenticode-подписанный x64/ARM64 байты, которые публикуются пользователям. `WINDOWS_PROTECTION_RELEASE_CERTIFICATE.json` повторно связывает repository/source commit/run, Java `8/16/17/21/25`, 55 adversarial/compatibility выполнение, агрессивный профиль и SHA-256 Windows CLI/Desktop/Guard/Sensor/Runtime/package артефакты.

Сертификат не доверяется как декларация: проверяющий модуль заново проверяет рабочий Windows подписание свидетельство, хэширует артефакты релиза и пересчитывает `boundarySha256`. Затем Windows Защита RC включается в до подписания Рабочий Кандидат в релиз группа и стабильный Рабочий Доставка Релиз якоря. Подмена certificate/evidence или одного из связанных Windows артефакты после сертификация нарушает cohort/signature граница и блокирует публикация-проверка.

Эта сертификация подтверждает конкретный протестированный пользовательский режим релиз группа и не заявляет защиту от локального administrator/kernel/firmware злоумышленник, компрометации CI/signing учётные данные или подмены доверенного корень ключ. Эти угрозы остаются за пределами NeverGuard пользовательский режим граница и требуют независимого key/release/host безопасность.

## Windows Атакующий CI граница — 0.18.11

`0.18.11` добавляет повторяемую attack-simulation границу для Windows пользовательский режим NeverGuard. CI реально запускает защищённую JVM и использует существующие нативный фикстура для попыток загрузки неподписанной DLL, изменения исполняемый образ страница, старта потока из закрытый исполняемый память, актуальный отладчик подключение и внешний исполняемый выделение; отдельная проверка блокирует запуск инструментирование/JDWP до запуск процесса. Параллельно positive случай подтверждают отсутствие ложных срабатываний на раннем Sensor запуск, доверенный нативный модуль жизненный цикл, Непрерывный Защита, Задача-привязанный дочерний процесс и штатный HotSpot JIT.

Сертификация действует только для точный CI группа: Windows Сервер 2022 x64, Java `8/16/17/21/25`, конкретного Git commit/run и конкретных SHA-256 Sensor/probe бинарные файлы. `WINDOWS_ADVERSARIAL_CERTIFICATE.json` не является доказательством неуязвимости, не заменяет рабочий Authenticode, не сертифицирует kernel/administrator злоумышленник и не распространяется автоматически на неизвестные JDK/JVM реализация. Любой отсутствующий Java результат, ошибка scenario, altered вывод хеш или артефакт хеш делает агрегат сертификация отказ с блокировкой.

## Аттестация v2 и сервер-проверен непрерывный свидетельство — 0.18.10

В `0.18.10` на стороне сервера доверие граница получает свидетельство после реального запуска JVM. Pre-запускать Защита Аттестация v1 по-прежнему проверяет Guard/Desktop релиз граница и используется для инициализировать Minecraft сессия, но не считается доказательством состояния уже работающего Sensor. После запуска Настольное приложение собирает актуальный отчёт и формирует Аттестация v2, содержащую health/digests всех Windows защита слой и двусторонний Непрерывный Защита состояние. Серверная часть ограничивает актуальность пятью секундами, проверяет версии компонентов, heartbeat/cross-check parity, поэтапный хеширует и привязанный к оборудованию устройство подпись.

После успешной проверки Серверная часть выпускает одноразовый краткоживущий билет только для ServerBridge подключение. Билет привязан к Никогда session/trusted устройство и дополнительно сверяется с лаунчер версия и точными Guard/Desktop SHA-256 текущей целостность-проверен Minecraft сессия; ошибка repository/device политика обрабатывается отказ с блокировкой. Аттестация v2 не превращает пользовательский режим NeverGuard в ядро якорь доверия: administrator/kernel компрометация и компрометация hardware/device подписание или релиз ключи подписи остаются отдельными границами угроз.

## Непрерывный Защита и двусторонняя целостность среда выполнения — 0.18.9

В `0.18.9` NeverGuard больше не доверяет только одностороннему Sensor→родительский сигнал состояния. Sensor и родительский независимо пересчитывают домен-отдельный SHA-256 цепочка по полным аутентифицировать событие packets. Шестой запуск доказательство `CONTINUOUS_READY` обязан совпасть с родительский цепочка до возврата из `Agent_OnLoad`, после чего родительский возвращает отдельный HMAC-защищённый Защита ACK. В среда выполнения такая сверка повторяется раз в секунду и привязывает Защита ACK к `guardSequence`, `sensorSequence` и текущему цепочка хеш.

Отказ с блокировкой срабатывает при сигнал состояния тайм-аут, отключаться, HMAC несоответствие, последовательность расхождение или несовпадении цепочка корень. Непрерывный Защита не скрывает процесс и не блокирует Windows/EDR: он проверяет живость и согласованность двух пользовательский режим границы безопасности и делает потерю/подмену аутентифицировать поток обнаруживаемой. Administrator/kernel злоумышленник по-прежнему находится за пределами пользовательский режим доверие модель.

## JVM-Учитывающий защита Windows HotSpot — 0.18.8

В `0.18.8` NeverGuard различает штатную HotSpot JIT/Код Кэш активность и исполняемый закрытый память, созданную посторонним native-кодом. Sensor идентифицирует текущий `jvm.dll`, фиксирует его образ range/version идентичность и при каждом перехваченном исполняемый `VirtualAlloc/VirtualProtect` проверяет нативный стек происхождение. Только переход с вызывающая сторона кадр внутри `jvm.dll` относится к JIT; foreign/unknown `MEM_PRIVATE` выполнение граница считается нарушением и приводит к отказ с блокировкой завершению защищаемой JVM.

Политика сертифицирована для Java `8/16/17/21/25` и намеренно не утверждает ядро-equivalent контроль. Существующий образ-код хеш, модуль проверка, поток-источник проверяет и отладка граница продолжают работать независимо. Administrator/kernel злоумышленник, подмена доверенного `jvm.dll` до package/module проверка или компрометация подписание цепочка остаются вне заявленной пользовательский режим доверие граница.

## Защита от отладки и инструментирование / Windows JVM — 0.18.7

В `0.18.7` NeverGuard отказ с блокировкой блокирует нежелательную пользовательский режим debugging/instrumentation граница. Лаунчер отклоняет сторонние `-javaagent/-agentlib/-agentpath`, JDWP/`-Xdebug`, принудительный `StartAttachListener`, отмену `DisableAttachMechanism` и эквивалентные опции из `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`; для защищаемой JVM всегда добавляется `-XX:+DisableAttachMechanism`.

Sensor не пытается скрывать отладчик или вмешиваться в средства Windows безопасность. Он только проверяет фактическое состояние через `IsDebuggerPresent`, `CheckRemoteDebuggerPresent`, `ProcessDebugPort`, `ProcessDebugObjectHandle` и `ProcessDebugFlags`, передаёт HMAC-защищённые READY/HEARTBEAT/TAMPER свидетельство и завершает JVM при нарушении. Administrator/kernel злоумышленник и компонент, способный произвольно изменить весь процесс состояние до проверки, остаются вне заявленной пользовательский режим доверие граница.

## Контроль потоков и процессов / Windows JVM — 0.18.6

В `0.18.6` NeverGuard Sensor непрерывно проверяет происхождение Win32 потоки текущей JVM. Для каждого актуальный TID Sensor получает запуск адрес через `NtQueryInformationThread`, затем `VirtualQuery` подтверждает committed исполняемый `MEM_IMAGE`; запуск адрес из исполняемый private/mapped память считается подозрительным переходом исполнения. Создание и завершение обычных JVM, GC, compiler и служба потоки не блокируется: контролируется их фактическое происхождение, а не сам факт многопоточности.

Процесс граница остаётся пользовательский режим и опирается на Задача Объект, созданный до возобновление JVM: breakaway флаги запрещены, а NeverRuntime на аутентифицировать сигнал состояния перечисляет descendants и проверяет `IsProcessInJob` для каждого живого PID. Это не объявляется защитой от kernel/administrator злоумышленник; слой предназначен для обнаружения и отказ с блокировкой остановки нарушений внутри заявленной Windows пользовательский режим доверие граница.

## Память Целостность / исполняемый память — 0.18.5

В `0.18.5` NeverGuard Sensor непрерывно проверяет исполняемый адрес space текущей JVM. Для загрузчик-основанный `MEM_IMAGE` исполняемый регионы сохраняется SHA-256 базовая линия фактических сопоставленный код байты; изменение байтов или защита состояние после базовая линия считается подмена. Хеш выполняется только после временного удержания загрузчик модуль reference, чтобы обычная DLL выгрузка гонка не превращалась в чтение освобождённой памяти.

Динамический JVM/JIT код обрабатывается отдельно: существующая при arm исполняемый private/mapped память фиксируется как базовая линия, а новые исполняемый закрытый диапазон должны иметь происхождение из успешного перехваченного `VirtualAlloc`/`VirtualProtect`. Переход коллекция использует ограниченный блокировка-free кольцо; overflow отказ с блокировкой. Реализация не использует `WriteProcessMemory`, `VirtualAllocEx`, удалённый потоки или ядро драйвер. Администратор/компонент уровня ядра остаётся вне доверие граница.

## Агрессивный Хук Движок I / защита Windows JVM — 0.18.4

В `0.18.4` ранний JVM Sensor дополнен IAT хук движок, работающим только внутри текущего защищаемого процесса. Реализация намеренно не использует `SetWindowsHookEx`, запись памяти удалённых процессов и создание удалённых потоков. Движок разбирает сопоставленный PE импорт, меняет только известные slots Windows loader/memory API в несистемных JVM/native-модулях, отказывается перезаписывать заранее изменённую неожиданную цель и сразу восстанавливает исходную защиту страницы после каждого изменения IAT.

Sensor протокол v3 требует HMAC-аутентифицированное событие `HOOK_READY` до завершения `Agent_OnLoad`. Непрерывные `HOOK_HEARTBEAT` передают свидетельство покрытия/вызовов и хеш набора хуки; Sensor периодически проверяет каждый установленный IAT slot и перед отказ с блокировкой завершением при расхождение отправляет `HOOK_TAMPER`. Это пользовательский режим усиление защиты, а не эквивалент ядро граница безопасности; компрометация administrator/kernel остаётся вне доверие модель.

## Модуль Защита / Windows JVM — 0.18.3

В `0.18.3` Sensor протокол v2 держит JVM внутри `Agent_OnLoad`, пока Desktop/NeverRuntime не аутентифицирует Sensor, не снимет внешний базовая линия модулей и не подтвердит вооружение Модуль Защита. Sensor использует `LdrRegisterDllNotification` для load/unload жизненный цикл, фиксированный атомарный кольцо и отдельный обработчик; упорядоченный событие поток и сигнал состояния защищены HMAC-SHA-256. Родительский независимо сверяет ToolHelp модуль снимки, SHA-256 событие цепочка и политика происхождения DLL.

По умолчанию модуль загрузка разрешён из канонический Windows, выбранного Java среда выполнения, launcher/Sensor пакет и конкретного JVM работа каталог. DLL вне этих корни обязана пройти WinVerifyTrust/Authenticode; нарушение, overflow, потеря сигнал состояния, событие последовательность/MAC расхождение или расхождение с внешним снимок завершают JVM. Это пользовательский режим отказ с блокировкой управление, а не ядро-equivalent защита: administrator/kernel злоумышленник, компрометация ключи подписи и противник с произвольной записью памяти процесса остаются вне заявленной границы доверия.

# Политика безопасности NeverLauncher

## NeverGuard Sensor / Windows JVM — 0.18.2

В `0.18.2` добавлен `neverguard-sensor.dll` — подписанный нативный JVM agent, который загружается через `-agentpath` до Java/Minecraft главный. Лаунчер создаёт защищённый Именованный Pipe на каждый запуск и случайный 256-битный секрет; `Agent_OnLoad` отправляет HMAC-SHA-256 доказательство, привязанный к версии протокола и PID. Родительский процесс не принимает среда выполнения до проверки доказательство, а ошибка аутентификации завершает JVM. Рабочий пакет проверка и обновлятор связывают Sensor по SHA-256, PE архитектура и Authenticode/RFC3161 вместе с Настольное приложение, Защита и NeverRuntime.

Запуск доказательство подтверждает, что ожидаемый Sensor дошёл до `Agent_OnLoad`, но сам по себе не является непрерывной среда выполнения аттестация. Процесс того же пользователя с возможностью читать/изменять другой процесс, локальный администратор, kernel/firmware злоумышленник или похищенный ключ подписи остаются за пределами этой пользовательский режим доверие граница. Непрерывная module/hook/memory целостность относится к следующим этапам NeverGuard и не должна выводиться из возможностей `0.18.2`.

## Граница доверия Рабочий Доставка Релиз — 0.16.0

Для `0.16.0+` рабочий релиз имеет два последовательных уровня сертификация. `PRODUCTION_RELEASE_CANDIDATE.json` фиксирует точный до подписания группа, после чего `PRODUCTION_DELIVERY_RELEASE.json` промотит этот группа в стабильный GA и отдельно привязывает кандидат hash/cohort, six-цель доставка свидетельство, Управляемый JRE, текущий подписанный корневым ключом доверие политика, публичная матрица, Compatibility/Device Trust/Guard/ServerBridge сертификация, SBOM и происхождение к одному `boundarySha256`.

GA сертификат требует неизменяемый версия HTTPS источник и ровно Windows/Linux/macOS × x64/ARM64. Он не доверяет изменяемый `latest` URL и не разрешает prerelease/build SemVer. `RELEASE_MANIFEST.json` дополнительно фиксирует SHA-256 GA сертификат, `channel=stable` и `releaseStatus=production-delivery-release`; затем весь набор попадает в `SHA256SUMS` и Релиз Проверка v2 Ed25519 подпись.

Публичный E2E не считает локальную сертификация доказательством публикации: `PUBLIC_PRODUCTION_DELIVERY_MATRIX.json` содержит GA сертификат как управление, поэтому процесс после `release.published` заново скачивает публичные байты, подпись средства управления и `PRODUCTION_DELIVERY_RELEASE.json`, после чего запускает полный проверка с внешним корень key/current доверие policy/persistent anti-откат состояние.

Эта граница не заменяет безопасность подписание infrastructure. Компрометация автономный корень, Разработчик ID/Authenticode ключи, GitHub релиз учётная запись или рабочий хост остаётся отдельной угрозой и требует revoke/rotation/audit процедур.

## Граница доверия Рабочий Кандидат в релиз — 0.15.11

Для `0.15.11+` релиз считается рабочий кандидат только после формирования `PRODUCTION_RELEASE_CANDIDATE.json`. Сертификат привязывает кандидат к одному точный Git исходник фиксация и к полному до подписания группа release-файлов через SHA-256/size каждого файла и агрегированный `cohortSha256`; сам сертификат затем входит в `SHA256SUMS` и подписывается Релиз Проверка v2. Поэтому корректная подпись одного `RELEASE_MANIFEST.json` не позволяет незаметно подмешать дополнительный артефакт релиза после RC сертификация.

Исходник фиксация должен одновременно совпадать с Совместимость, Доверие к устройству и Защита CI сертификация и с SLSA происхождение. Рабочий сборка из Git checkout дополнительно требует чистый tracked/staged дерево и `NEVERLAUNCHER_SOURCE_COMMIT == HEAD`. Это не доказывает доверенность самого Git hosting/account, но исключает локальный исходник расхождение между CI свидетельство и собираемым RC.

RC проверка принимает Windows только с рабочий Authenticode + RFC3161 свидетельство, а macOS — только с Разработчик ID Приложение, Принят notarization, stapled билет и Gatekeeper свидетельство. CI unsigned/ad-hoc артефакты остаются допустимы для платформа регрессия задачи, но не могут войти в 0.15.11 рабочий кандидат. Автономный root/release-key жизненный цикл из 0.15.8, постоянный anti-откат состояние 2.1 из 0.15.10 и после публикации публичный E2E из 0.15.9 остаются независимыми обязательными слоями.

## Fabric ServerBridge граница — 0.14.6

Fabric Сервер Мост является сервер-только модом и не доверяет клиентскому Fabric-коду. Вход авторизация удерживается `ServerLoginNetworking.LoginSynchronizer` до завершения подписанный серверная часть валидация; серверная часть I/O выполняется ограниченный исполнитель вне сервер tick. При saturation/backend ошибка режим по умолчанию отказ с блокировкой.

Fabric узел имеет отдельную Ed25519 идентичность и отдельный `fabricSha256` пространство имён. Серверная часть проверяет сервер type, релиз хеш, идентичность эпоха, запрос одноразовое значение и одноразовый подключение билет; хеш другого ServerBridge артефакт не принимается как Fabric измерение. Артефакт self-хеш не является хост аттестация: компрометация JVM/хост или закрытый узел ключ требует revoke/rotation и внешнего хост усиление защиты.

## Minecraft/ServerBridge целостность принудительное применение — 0.13.5

## NeverGuard: Защита Аттестация и Серверная часть проверка — 0.13.4

В `0.13.4` Серверная часть выдаёт постоянный **одноразовый** запрос, который NeverGuard принимает только через аутентифицировать IPC v3. Защита заново собирает Целостность Свидетельство v1, прикладывает применять Windows процесс-политика отчёт и вычисляет запрос-привязанный аттестация хеш; Настольное приложение проверяет локальный IPC `sessionProof`, затем привязанный к оборудованию P-256 устройство ключ подписывает отдельный канонический привязка к `user + device + session + bindingEpoch + launcherVersion + attestation/evidence/release hashes`.

Серверная часть не доверяет присланным хеш как готовым значениям: он пересчитывает свидетельство и аттестация SHA-256, проверяет запрос freshness/replay, регистрировать устройство публичный key/signature, родительский PID граница, обязательные процесс-политика флаги и точное совпадение `neverguard.exe`/Настольное приложение хеширует с рабочий релиз список разрешений. Опциональная релиз политика может требовать доверенный Authenticode. Успешная проверка создаёт постоянный одноразовый запускать билет; Для Windows доверенный устройство Minecraft сессия выдача потребляет его атомарно и отклоняет повторное воспроизведение. Рабочий запуск отказ с блокировкой требует `NEVERLAUNCHER_GUARD_RELEASE_ALLOWLIST_JSON`.

Граница доверия остаётся user-mode/application-level: это не TPM кавычки, не Измеренный Boot, не VBS/ядро аттестация и не ядро античит. Сервер проверка доказывает владение зарегистрированного оборудование устройство ключ и согласованность свежей Защита свидетельство с список разрешений релиз бинарные файлы; она не заявляет невозможность компрометации уже привилегированным kernel/firmware злоумышленник.

## NeverGuard Windows: применение runtime/process политика — 0.13.3

В `0.13.3` NeverGuard применяет Windows процесс меры защиты до создания Tokio среда выполнения и отказ с блокировкой сверяет их через `GetProcessMitigationPolicy`. Защита запрещает динамический код и дочерний-процесс создание, отключает расширение точки, включает строгий-дескриптор проверяет и ограничивает загрузку remote/low-integrity образ. Аутентифицировать IPC протокол v2 включает политика version/enforced состояние в `ready` доказательство и предоставляет отдельный `process-policy` отчёт.

Minecraft Java процесс создаётся с `CREATE_SUSPENDED`, затем назначается в Windows Задача Объект. До `ResumeThread` NeverRuntime обязан подтвердить `AssignProcessToJobObject`, `IsProcessInJob` и фактические ограничения; обязательны `KILL_ON_JOB_CLOSE` и `DIE_ON_UNHANDLED_EXCEPTION`, breakaway запрещён. При неуспехе процесс остаётся отказ с блокировкой и уничтожается. Задача Объект дескриптор удерживается на время жизни контролируемый среда выполнения дерево.

`ProhibitDynamicCode` **не применяется к Java/Minecraft**, поскольку HotSpot JIT генерирует исполняемый код во время работы. Попытка навязать этот мера защиты сделала бы нормальный среда выполнения несовместимым. Эта версия является пользовательский режим process/runtime политика принудительное применение, а не ядро античит, память защита от привилегированный злоумышленник или проверяемый сервером аттестация; агрессивный hooks/injection по-прежнему не используются.

## NeverGuard Windows Целостность Свидетельство v1 — 0.13.2

В `0.13.2` отдельный NeverGuard процесс после аутентифицировать IPC собирает **локальный свидетельство** о собственной Windows процесс граница и о лаунчер процесс. Перед чтением инициализировать секрет защита через Toolhelp проверяет фактический родительский PID; несоответствие с ожидаемым Настольное приложение PID завершает запуск. Свидетельство содержит SHA-256 процесс образ, файл metadata/process создание время, локальный Authenticode результат через `WinVerifyTrust`, сырой мера защиты флаги из `GetProcessMitigationPolicy` и отпечаток загруженного модуль задать.

Свидетельство ядро хэшируется SHA-256 и привязывается HMAC `sessionProof` к текущему производный IPC сессия ключ. Настольное приложение не принимает полезная нагрузка до повторной проверки schema/version, expected/observed PID, хеш и сессия доказательство; Windows Minecraft запускать отказ с блокировкой требует успешного свидетельство коллекция. Authenticode выполняется без UI и с только кэш retrieval, чтобы запускать путь не зависел от произвольного сетевого ответа проверки сертификата. Отдельная неподдерживаемая мера защиты политика отражается в `queryFailures`, а не подменяется значением `0`.

Эта граница намеренно **не является проверяемый сервером аттестация**. `WinVerifyTrust`, файл хеширует, модуль снимок и процесс меры защиты — локальные измерения; Настольное приложение знает IPC сессия ключ, а свидетельство ещё не подписывается отдельным сервер-запрос hardware/process идентичность. Поэтому Серверная часть не должен повышать устройство уверенность или авторизация на основании одного полезная нагрузка `0.13.2`. Проверяемый сервером NeverGuard аттестация, актуальность запрос и anti-повторное воспроизведение на удалённой стороне относятся к следующему этапу.

## NeverGuard Windows 0.13.1

NeverGuard в `0.13.1` является отдельной процесс граница, а не injected DLL/хук. Настольное приложение запускает соседний `neverguard.exe`, генерирует новый 256-бит инициализировать секрет и передаёт его только через унаследованный стандартный ввод. Инициализировать секрет не должен попадать в argv, окружение, конфиг, телеметрия или файл; обе стороны zeroize-ят его после derivation сессия ключ.

Транспорт — Windows Именованный Pipe со случайным на-запускать именем, единственным сервер экземпляр и запрещёнными удалённый клиенты. Само имя pipe и родительский PID не считаются секрет. Mutual аутентификация строится на HMAC-SHA-256 по transcript, который включает эндпоинт, клиент PID, защита PID, время старта и два случайных одноразовое значение; сервер доказательство, клиент доказательство и сессия ключ используют разные метки.

После рукопожатие все IPC request/response MAC-ятся сессия ключ. Запрос обязан иметь точный следующий `sequence`; повтор, пропуск/перестановка последовательность, неверный MAC, протокол несоответствие, повреждённый JSON или кадр >64 KiB закрывают аутентифицировать сессия. `requestId` связывает ответ с конкретным запрос. Настольное приложение перед Minecraft запускать требует `ready + authenticated` и успешный `ping`; при сбое запускать блокируется.

Эта версия не заявляет процесс целостность свидетельство, anti-подмена хуки или проверяемый сервером NeverGuard аттестация. Эти свойства должны добавляться отдельными последующими версиями и не выводятся из факта локального аутентифицировать IPC.

## Миграция усиление защиты Доверие к устройству 0.12.10

`0.12.10` усиливает граница безопасности не новым доверие signal, а целостностью сохранённый состояние. Миграция `0018_device_trust_stabilization_01210.sql` сначала проверяет существующие данные и только затем добавляет реляционный ownership/lifecycle ограничения. Межпользовательский session/device привязка, замена цепочка или Minecraft снимок считаются unsafe состояние и блокируют обновление вместо автоматического переписывания владельца.

Миграция также исправляет рабочий ограничение `device_challenges_purpose_check`: после появления ключ rotation/recovery PostgreSQL обязан принимать `key-rotate` и `key-recover` наряду с прежними назначение. Необязательный replacement/Minecraft устройство ссылки используют SQL `NULL`, чтобы внешний ключи действительно контролировали владение вместо пустой-string sentinels.

Точный-обновление E2E строит схема `0.12.9` из запечатанный миграция `0001..0017`, применяет поставка CLI до `0018`, проверяет контрольная сумма проверка и negative PostgreSQL принудительное применение. Публичный Доверие к устройству протокол результат в `0.12.10` не может получить PASS без этого миграция свидетельство.

## Публичная проверка Доверие к устройству 0.12.9

Безопасность состояние Доверие к устройству не задаётся вручную. `device-trust/targets.json` содержит только обязательные targets/checks, а `.github/workflows/device-trust.yml` строит результат из машинно проверяемый свидетельство, привязанного к точный продукт версия, Git фиксация и Действия запуск ID. Отсутствующий, дубликат, ошибка, несоответствие или изменённый после выполнения свидетельство делает публичная матрица ошибка: результат содержит SHA-256 каждого публикуемого evidence-файла, а aggregator пересчитывает его перед PASS.

PostgreSQL протокол E2E выполняет реальный жизненный цикл устройство идентичность: одноразовый регистрация запрос, привязка эпоха, привязанный к устройству обновление, dual-ротация ключей, постоянный отпечаток метка удаления, ServerBridge инвалидация, риск step-up, P-256 аттестация протокол, восстановление step-up prerequisite и отзыв каскад. В публичный свидетельство не сохраняются access/refresh учётные данные или закрытый устройство ключи; E2E отдельно сканирует готовый к публикации каталог на такие секреты.

Эта матрица не должна интерпретироваться как удалённо подтверждённое происхождение оборудования. P-256 CI случай использует протокол-compatible ключ и проверяет запрос-ответ семантика, но фиксирует `vendorHardwareProvenance=not-verified`. Нативный Linux/Windows/macOS цели компилируют Tauri граница и выполняют ключ-политика модульные тесты; headless CI не является доказательством фактического доступа к TPM, Защищённый Анклав, Windows Учётные данные Диспетчер, macOS Keychain или Linux Секрет Служба на пользовательском устройстве.

## Аутентификация Федерация 0.12 граница

В `0.12.0` единственной аутентификация граница является Федерация Ядро: коннектор проверяет внешний доказательство, затем `(provider, subject)` разрешается в канонический Никогда пользователь и только после этого NeverLauncher выпускает собственную сессия. Локальный пароль провайдер проходит тот же Коннектор SDK соответствие контроль. Общий явный связывание требует одновременно действующую Никогда сессия и завершённый browser-провайдер доказательство; совпадение электронная почта никогда не считается доказательство.

Миграция `0011_auth_federation_release_0120` закрепляет локальный идентичность инвариант на уровне PostgreSQL: поддерживающий пароль пользователь обязан иметь `provider=local, subject=user.id`. Bootstrap/password-reset пути обновлены транзакционно, поэтому инвариант не обходится прямой записью в `users`. Среда выполнения провайдер работоспособность доступен через административный федерация состояние; готовность к эксплуатации не считается успешной, если не осталось ни одного здорового аутентификация провайдер.
Выдача Никогда сессия не имеет права создавать идентичность. В частности, passwordless WebAuthn является аутентификация method/origin (`provider=passkey`), а не доказательством существования локальный-пароль идентичность; внешний-только пользователь с ключ доступа не получает фиктивную `local` идентичность.

## Граница безопасности ротации и восстановления устройство ключ 0.12.8

Плановая ротация требует одновременный доказательство владения старым регистрировать ключ и новым подготовленный ключ по одному сервер-выданный одноразовому запрос. Восстановление применяется при утрате старого закрытый ключ и дополнительно требует свежий `phishing-resistant` учётная запись step-up; знание пароля или владение нового ключа отдельно недостаточны. После успешной операции старая устройство идентичность не перезаписывается: она остаётся отозванный метка удаления, а новая получает отдельные `device_id`, отпечаток и привязка эпоха.

Tauri не заменяет активный локальный ключ до сервер фиксация. Оборудование замена создаётся под новым генерация-specific метка, программное обеспечение замена — в отдельной подготовленный OS-хранилище ключей записи. Ошибка до сервер фиксация удаляет подготовленный материал; ошибка локального фиксация после сервер успех восстанавливается согласование по сервер устройство отпечаток. Старые Never/refresh/Minecraft учётные данные и ServerBridge подключается не должны переживать замена.

## Minecraft / ServerBridge доверие граница 0.12.7

Minecraft токен доступа и ServerBridge подключение больше не считаются автономными учётные данные после выдачи. Серверная часть сохраняет `trusted_device_id + binding_epoch` родительский Никогда сессия и при каждом игровой confirmation повторно проверяет актуальную сессия, доверенное устройство реестр и риск действие. Это закрывает окно, в котором уже выданный игровой учётные данные переживал re-привязывать той же Никогда сессия.

Официальный Minecraft сессия обмен и фактический Yggdrasil `/join` требуют активный проверен доверенный устройство. `session_binding_changed`, `session_device_changed`, missing/revoked устройство и отозванный риск являются постоянный доверие ошибка: устаревший Minecraft сессия отзывается, а ServerBridge подключение инвалидируется. `device_reattest_required` и `session_step_up_required` являются recoverable запрещать и не уничтожают учётные данные до успешного восстановления trust/expiry.

Игра сервер запросы не являются наблюдением пользовательской сети. `validate-join`/`hasJoined` не записывают IP/User-Agent сервера в игрок риск; они только читают определяемый сервером риск состояние, сформированный launcher/player трафик. ServerBridge также pin-ит project/profile/channel, а сервер токен остаётся обязательной отдельной сервер-аутентификация граница. Плагин не может локально отключить игровой доверие принудительное применение.

Миграция `0016_minecraft_serverbridge_trust_0127.sql` backfill-ит существующие Minecraft сессии из текущего родительский привязка при обновление и добавляет constraint/index для последующей live-проверки. Любой последующий re-привязывать меняет эпоха и сразу делает предыдущий снимок устаревшим.

## Привязка сессии к устройству и применение риск политика 0.12.6

Сам по себе доступ JWT больше не считается достаточным подтверждением актуальной привязки к устройству: Серверная часть сверяет `binding_epoch`, `device_id` и доверие состояние с текущей на стороне сервера сессия. Bind/re-bind устройства инвалидирует старые JWT. Обновление привязанной сессия дополнительно требует подпись зарегистрированным устройство ключ по канонический полезная нагрузка, в котором присутствует только SHA-256 токен обновления, но не сам секрет.

Риск решение применяется как `allow`, `step-up`, `reattest` или `revoke`. Изменение сетевого/клиентского контекста требует новой устойчивый к фишингу процедура для чувствительных операций; устаревшая оборудование-ключ аттестация требует повторной аттестация; отсутствующее/отозванное доверенный устройство или повторное использование токен обновления отзывает session/family. Устройство уверенность по-прежнему не заменяет пользовательские MFA/RBAC.

## Устройство Управление + Отзыв 0.12.5

Устройство отзыв является необратимым безопасность переход, а не удалением строки из UI. Серверная часть сохраняет отозванный доверенное устройство запись как метка удаления: прежний отпечаток ключа нельзя зарегистрировать снова, а повторное подключение требует новой устройство идентичность. Повторный отзыв идемпотентен.

В PostgreSQL одна транзакция блокирует device/session строки, переводит устройство в `revoked`, сбрасывает действующий уверенность до `proof-of-possession`, помечает аттестация отозванный, расходует незавершённые устройство запросы, отзывает связанные Никогда сессии, обновление families/tokens и Minecraft сессии. После фиксация ServerBridge подключается инвалидируются по затронутым Никогда сессия ID. Это предотвращает окно, в котором устройство уже отображается отозванный, но старый refresh/challenge ещё пригоден.

`revoke-others` разрешается только текущей сессия, криптографически связанной с активный проверен доверенный устройство, и исключает это устройство из пакет отзыв. Администратор отзыв требует `users:manage` и актуальный устойчивый к фишингу аутентификация. Отзыв не повышает аутентификация сила и не заменяет MFA; она только прекращает доверие к конкретной устройство идентичность и связанным учётные данные.

## Запрос-ответ устройство аттестация 0.12.4

`0.12.4` отделяет оборудование-ключ регистрация от свежей аттестация процедура. Серверная часть выдаёт `attest` запрос только активной Никогда сессия, уже связанной с тем же проверен доверенный устройство. Запрос хранится постоянный, привязан к user/device/session и зарегистрированным fingerprint/algorithm/binding/provider, живёт 2 минуты и расходуется атомарно. Нативный Tauri-команда `attest_device_payload` разрешена только для сохранённый `p256/hardware` ключ и не имеет программное обеспечение резервный вариант.

После успешной P-256 подписи Серверная часть сохраняет `challenge-response-v1` аттестация на 12 часов. Пока актуальность окно действует, устройство уверенность равен `challenge-response-attested`; после истечение внешнее представление снова считается `proof-of-possession`. Этот устройство уверенность не меняет RBAC, MFA/аутентификация сила или устойчивый к фишингу step-up. WebAuthn остаётся отдельной пользователь-аутентификация граница.

Запрос-ответ подтверждает владение уже зарегистрированным аппаратный ключ, но не доказывает поставщик происхождение платформы. Текущий подписант abstraction не предоставляет проверяемый TPM кавычки или Защищённый Анклав аттестация сертификат, поэтому `hardware_provider` остаётся описательной метаданные, а API использует `hardwareProvenance=not-remotely-verified`. Нельзя принимать провайдер имя, `key_binding=hardware` или сам факт успешной процедура за поставщик TPM/Защищённый Анклав удалённый аттестация.

Миграция `0014_challenge_response_attestation_0124.sql` хранит state/method/freshness и расширяет одноразовый `device_challenges` назначение значением `attest`. Отзыв устройства переводит аттестация состояние в `revoked` вместе с существующим session/refresh-family отзыв.

### Привязанный к оборудованию идентичность основа 0.12.3

Настольное приложение создаёт P-256 ключ подписи через платформа HSM abstraction и принимает его как `hardware` только для TPM/Защищённый Анклав/WSL TPM мост серверная часть. Keyring/software/test серверная часть остаётся программное обеспечение-привязанный Ed25519 резервный вариант. Оборудование закрытый ключ не сериализуется в NeverLauncher метаданные, не передаётся React/Backend и используется только внутри нативный подписант. Само наличие оборудование привязка без успешной `0.12.4` процедура оставляет уверенность на `proof-of-possession`.

## Доверие к устройству / устройство ключи 0.12.2

Поле `deviceId` из login/session метаданные не является доказательством устройства. Доверенный устройство создаётся только после Ed25519 доказательство владения: Серверная часть выдаёт одноразовый постоянный запрос, привязанный к канонический пользователь, устройство ID, назначение и Никогда сессия; официальный Настольное приложение подписывает полезная нагрузка ключом, закрытый начальное значение которого находится только в нативный OS защищённый хранилище.

Настольное приложение ключ пространство имён строится по `Backend + canonical user id`, а не электронная почта. Windows использует Учётные данные Диспетчер, macOS Keychain, Linux Секрет Служба через нативный хранилище ключей серверная часть. Plaintext/file/localStorage резервный вариант запрещён; React не получает закрытый начальное значение и может запросить только публичный метаданные или подпись конкретного ограниченный запрос полезная нагрузка. Временные seed/serialized секрет buffers zeroize перед освобождением.

OS защищённый хранилище само по себе не является оборудование аттестация. `0.12.2` сохраняет уверенность `proof-of-possession`; привязанный к оборудованию уверенность будет отдельным уровень доверия только после проверяемой TPM/Защищённый Enclave/Windows Hello/аналогичной аттестация.

В `trusted_devices` хранится только открытый ключ и SHA-256 отпечаток. Закрытый устройство ключ не должен передаваться Серверная часть или попадать в логи. Уверенность этой версии называется `proof-of-possession`; NeverLauncher не заявляет привязанный к оборудованию идентичность до появления отдельной TPM/Защищённый Enclave/OS защищённый-хранилище и аттестация проверки.

`device_challenges` одноразовый и расходуются атомарно; replay/expired запрос отклоняется. После успешного доказательство сессия получает `trusted_device_id/device_trust_state/device_verified_at`, а новый доступ JWT — `device_id/device_trust/device_verified_at`. Отзыв реестр устройство отзывает все связанные Никогда сессии и токен обновления семейство и переводит сессия риск в `compromised`.

Административный отзыв устройства требует свежую устойчивый к фишингу аутентификация. Устройство реестр не заменяет WebAuthn пользователь аутентификация: ключ доступа доказывает пользователя/RP процедура, устройство ключ доказывает владение конкретной зарегистрированной installation/device идентичность.

## Federated провайдер учётные данные

С `0.11.10` миграция история считается частью граница безопасности. Рабочий обновление должен выполняться через `nl db migrate apply` и завершаться `nl db migrate verify`. Unknown/future миграция, контрольная сумма расхождение или незапечатанный контрольная сумма блокируют проверять; применить не продолжает работу при неизвестной миграция или несовпадающем контрольная сумма. Миграция `0010` также отказ с блокировкой проверяет согласованность аутентификация сессии, токен обновления families/tokens и провайдер учётные данные до установки новых реляционный ограничения.

Федерация безопасность регрессия входят в контроль выпуска: HTTP HMAC/повторное воспроизведение/SSRF, OIDC issuer/audience, Microsoft tenant/key издатель, WebAuthn origin/challenge повторное воспроизведение, SQL TLS/read-only/disabled учётная запись и обновление-семейство повторное воспроизведение выполняются как тесты, а не как документационные promises. Строгий предварительная проверка дополнительно требует multi-экземпляр PostgreSQL E2E.

Начиная с 0.11.6 внешние обновление учётные данные (включая Microsoft) хранятся только на стороне сервера в приложение-слой AES-GCM конверт, привязанном к канонический user/identity/provider/subject. Провайдер токен не является Никогда access/refresh токен, не возвращается в login/link/refresh API и не должен попадать в логи или клиентское защищённый хранилище. Ротация `NEVERLAUNCHER_AUTH_TOKEN_SECRET` требует контролируемой миграции/повторной авторизации провайдер учётные данные.

## Ключи доступа / WebAuthn и step-up

С `0.11.7` устойчивый к фишингу аутентификация реализована WebAuthn ключи доступа. В рабочий RP ID и источник задаются явно; источник должен быть HTTPS и находиться внутри RP ID. Регистрация и утверждение требуют пользователь проверка, проверяют challenge/origin/RP ID хеш и криптографическую подпись; запрос одноразовый и хранится в PostgreSQL. Значения закрытый ключ authenticator никогда не передаются Серверная часть — сохраняется только COSE открытый ключ и учётные данные метаданные.

Критические действия не полагаются только на факт существования активной сессия: Серверная часть проверяет `auth_strength` и свежий `auth_time`. Для операций, требующих устойчивый к фишингу step-up, TOTP недостаточен.

## Сессия Управление 2.0

С `0.11.8` доступ токены являются подписанными JWS/JWT с обязательными `iss`, `aud`, `sub`, `sid`, `jti`, `iat`, `exp`, `kid`, `auth_time` и `amr`. Для ротация используйте `NEVERLAUNCHER_AUTH_TOKEN_KEYS_JSON` и переключайте `NEVERLAUNCHER_AUTH_TOKEN_ACTIVE_KID`, сохраняя предыдущий проверка ключ до истечения всех выпущенных им доступ токены. `AUTH_TOKEN_SECRET` остаётся обязательным корень секрет и backward-compatible единый-ключ резервный вариант.

Сессия риск хранится в PostgreSQL: изменение IP/User-Agent переводит сессия в `elevated`, токен обновления повторное воспроизведение — в `compromised` с отзывом всей токен семейство. Массовый провайдер отзыв доступен только после свежего устойчивый к фишингу step-up. Провайдер выход и Никогда сессия выход являются разными действиями: отзыв внешнего провайдер учётные данные сам по себе не завершает Никогда сессия.

## Minecraft Аутентификация Совместимость 2.0

С `0.11.9` Никогда токен доступа и Minecraft токен доступа — разные учётные данные. Minecraft токен является непрозрачный `nlmc_*`, в постоянный хранилище сохраняется только его SHA-256 хеш; запись привязана к канонический пользователь, Профиль Minecraft и родительский Никогда сессия. `validate`, `join` и `hasJoined` повторно проверяют активность родительский сессия, поэтому Никогда logout/revoke не оставляет отдельную игровую сессию действительной. Yggdrasil обновление потребляет старый Minecraft токен и не допускает его повторного использования.

Minecraft UUID не зависит от электронная почта, username внешнего провайдер или Microsoft/OIDC захватывает. Authlib-injector никогда не подхватывается из произвольного локального пути: NeverRuntime ищет его только среди файлов подписанного релиз манифест и передаёт Серверная часть URL только через HTTPS (HTTP разрешён лишь для localhost разработка). Minecraft токен доступа редактируется в запускать preview/log метаданные.

Этот слой не подменяет Microsoft/Mojang право владения: успешный Microsoft идентичность вход не доказывает владение официальной копией Minecraft.

## Резервное копирование и восстановление

Рабочий резервное копирование хранится отдельно от рабочего хранилище в `NEVERLAUNCHER_BACKUP_ROOT`. Архив содержит PostgreSQL custom dump, реальные storage-объекты и манифест с SHA-256. Перед восстановлением используйте `nl backup restore-dry-run`; реальный `nl backup restore` требует точного `--confirm <backupId>` и явного выбора `--database true` и/или `--storage true`.

S3 работает отказ с блокировкой: Серверная часть не имеет автоматического резервный вариант на локальный хранилище при ошибке подключения или работоспособность-проверка.

Backup/restore выполняются внутри обслуживание-блокировка: изменяющий API-запросы блокируются на время согласованного снимка или восстановления. Перед destructive восстановление автоматически создаётся безопасность резервное копирование. Для локальный хранилище восстановление подготавливается в соседнем каталоге и переключается атомарным `rename`; PostgreSQL `pg_restore` выполняется с `--single-transaction`.

## Подпись production-релиза

Для `0.15.8+` `SHA256SUMS.sig` — Релиз Проверка v2 конверт: Ed25519 подпись связывает контрольная сумма задать, hash/version `RELEASE_MANIFEST.json`, доверие эпоха и конкретный релиз ключ. Сетевой релиз закрытый ключ передаётся через `--private-key` / `NEVERLAUNCHER_RELEASE_SIGNING_PRIVATE_KEY_FILE`; автономный корень закрытый ключ используется только для выпуска `RELEASE_TRUST_POLICY.json`. Проверка требует внешний корень открытый ключ, актуальный подписанный корневым ключом доверие политика и постоянный доверие состояние; ключи из самого комплект не становятся якорь доверия. `active → verify-only → revoked` жизненный цикл, retirement окно, доверие-эпоха откат и релиз-версия откат проверяются отказ с блокировкой.

Для `0.15.9+` публичная поставка дополнительно фиксируется `PUBLIC_PRODUCTION_DELIVERY_MATRIX.json`. Матрица не является якорь доверия: она сама включена в подписанный `SHA256SUMS`, а после публикации `delivery public-e2e` сначала проверяет публичные SHA-256/size и затем выполняет полный Релиз Проверка v2 с внешним root/current доверие политика. HTTP запрещён кроме явного локальная петля тест режим; перенаправления ограничены исходным хост и известными GitHub релиз ресурс хосты.

Для `0.15.10+` постоянный доверие состояние обновляется только внутри сериализованный проверка граница. Файл `<trust-state>.lock` содержит PID проверяющий модуль; активный PID блокирует конкурентную проверку, устаревший блокировка удаляется только после проверки завершения процесса. Доверие состояние схема `2.1` сохраняет `highestReleaseManifestSha256`: если та же релиз версия уже принята, другой `RELEASE_MANIFEST.json` не может быть принят даже при валидной подписи текущего релиз ключ. Это закрывает одинаковый-версия replacement/equivocation и гонка между anti-откат precheck и фиксация.

Локальный компонент состояние также стабилизирован: устаревший macOS состояние из обновлятор управление каталог мигрирует в канонический `.neverlauncher/component-update-state.json`; конфликт одинаковой версии с различными хеширует считается ошибкой, а конечный обновлятор staging/backup удаляются только после долговременный `committed`/`rolled-back` журнал.

Исходник архив формируется из git-tracked файлов либо строгого список разрешений при отсутствии `.git`, исключает symlink/secret пути и до формирования релиз манифест проходит секрет scan. `release verify` отказ с блокировкой проверяет наличие, размер и SHA-256 каждого `required=true` артефакт, затем SHA256SUMS, Ed25519 подпись и отсоединённый подпись `PROVENANCE.json.sig`. Происхождение имеет формат в-toto Statement / SLSA v1, а SBOM — SPDX 2.3 и строится из зависимость manifests/locks.

### Совместимость сертификация в релиз доверие граница

Команда `release publish-check` дополнительно требует `COMPATIBILITY_TARGETS.json`, `COMPATIBILITY_MATRIX.json` и `COMPATIBILITY_CERTIFICATION.json`. Сертификация не доверяет полю `status: passed` само по себе: повторно проверяются точный релиз version/commit/run ID, цель идентичность, конкретный загрузчик версия, обязательные реальный клиент проверяет и на-цель `evidenceSha256`. SHA-256 matrix/targets фиксируются в сертификация, а все три файла входят в подписанный `SHA256SUMS`; подмена совместимость свидетельство после сборки поэтому делает релиз signature/checksums недействительными.


## Жизненный цикл signing-ключей

`nl security rotate-key` создаёт новую Ed25519 пару через CSPRNG и сохраняет метаданные в постоянный `trusted-keys.json`; закрытый ключ записывается с правами `0600`. Предыдущий активный ключ переводится в проверять-только либо сразу отзывается по явному флагу. `nl security revocation-list --revoke <keyId>` фиксирует отзыв в реестр, а проверять-поток с `--registry-dir` отклоняет подпись от отозванного открытый ключ. `nl security attest` создаёт отсоединённый Ed25519 подпись для указанного артефакт.

Опубликованный пакет после перехода в `published` считается неизменяемым: загрузка файлов, изменение manifest/status и повторная публикация запрещены на HTTP и репозиторий уровнях. Любое изменение содержимого выпускается новой версией.


## Совместимость материализация усиление защиты

Операции Vanilla/Fabric/Quilt/Forge/NeoForge материализация сериализуются эксклюзивный lock-файлом внутри конкретного `clientDir`. Это предотвращает одновременную запись одного `version.json`, Maven артефакт, ресурс или обработчик вывод несколькими CLI-процессами. Запись в клиент дерево выполняется только через lexical путь валидация и `Lstat` существующих компонентов; symlink-компоненты отклоняются. Символическая ссылка артефакт также запрещён при построении клиент пакет.

Временный вышестоящий проект HTTP ошибки `408/425/429/500/502/503/504` и временные транспорт ошибки повторяются ограниченное число раз; `Retry-After` ограничен верхним пределом, поэтому внешняя сторона не может удерживать материализатор в бесконечном ожидании. Размер одиночного совместимость артефакт ограничен, временные `.nlpart` файлы не становятся рабочим артефакт до hash/size проверка и переносимый замена.

Сгенерированный нативный каталоги не считаются кэшем: `natives/<os>` пересоздаётся перед извлечение, что исключает устаревший DLL/SO/dylib из предыдущей материализация. Forge/NeoForge установщик scratch `data/` аналогично очищается перед обработчик выполнение.

## Управляемый Java и Vanilla supply цепочка

NeverRuntime устанавливает Управляемый Java только из HTTPS метаданные Adoptium/Temurin. Перед публикацией среда выполнения в локальный кэш проверяются ожидаемый размер и SHA-256 архива, платформа метаданные и фактическая major-версия через `java -version`. Загрузка выполняется во временный файл, распаковка — в подготовка; обход путей и внешние символическая ссылка после извлечения отклоняются, а рабочий каталог появляется только после атомарного переименование. Повреждённый ранее установленный среда выполнения помещается в карантин и не используется для запуска.

Vanilla материализатор получает Mojang `version_manifest_v2.json`, затем проверяет опубликованный Mojang SHA-1 для `version.json`, client/libraries/assets/native/logging артефакты и ожидаемый размер. SHA-1 здесь является upstream-идентификатором Mojang, а не внутренним доверие primitive NeverLauncher: после материализации каждый файл получает SHA-256 и далее проходит стандартный подписанный неизменяемый релиз жизненный цикл NeverLauncher. HTTP разрешён только для локальная петля fixture-тестов; внешние источники должны использовать HTTPS. Нативный ZIP распаковываются с проверкой обход, символическая ссылка и escape за пределы целевого каталога.

Fabric/Quilt материализатор использует официальный Мета API только как сетевой исходник до публикации релиз. Изменяемый `latest` никогда не сохраняется в опубликованный релиз: сначала выбирается конкретная загрузчик версия. Полученный загрузчик профиль проверяется относительно выбранной Minecraft-версии и выбранного загрузчик артефакт, затем нормализуется; Maven JAR скачиваются только по HTTPS и в строгий режим обязаны иметь корректный репозиторий `.sha1`. В профиль записываются точные URL, SHA-1 и фактический размер; сам профиль и JAR затем фиксируются SHA-256 и защищаются обычной Ed25519-подписью неизменяемый Никогда манифест. Компрометация локального профиль после публикации обнаруживается Совместимость Движок доверие граница.

Forge/NeoForge материализатор принимает только основанный на обработчиках установщик формат, загружает `installer.jar` по HTTPS и в строгий режим требует корректный Maven SHA-1. `install_profile.json` и `version.json` читаются непосредственно из уже проверенного установщик JAR. Встроенные `maven/` и `data/` записи извлекаются с защитой от обход путей и символическая ссылка. Обработчик запускается как прямой Java процесс без оболочка interpolation; `Main-Class` берётся из манифест обработчик JAR, путь классов строится только из материализовать Maven артефакты, а тайм-аут ограничивает зависший процесс. Установщик variables и Maven ссылки нормализуются в локальные пути. Заявленные обработчик выходные данные проверяются по SHA-1/SHA-256 после выполнения и перед повторным использованием. Установщик JAR, временные данные и служебное состояние остаются под `.neverlauncher/` и исключаются из опубликованного клиент пакет; в неизменяемый релиз попадают только нормализованные среда выполнения артефакты и дочерний версия профиль. Устаревший Forge pre-1.13 не считается поддерживаемым граница безопасности этой версии.

## Доказательство реального Minecraft Клиент E2E

Контроль выпуска не принимает synthetic Java фикстура или один Minecraft рукопожатие как доказательство совместимости клиента. CI материализует полный Vanilla 1.21.1 из Mojang метаданные, выполняет локальный SHA-256 пакет проверять, загружает пакет через Серверная часть API, публикует Ed25519-подписанный неизменяемый манифест, затем скачивает релиз заново в чистый каталог через NeverRuntime. Запуск выполняется реальным Minecraft Java Клиент под изолированным Xvfb отображать. Успех подтверждается одновременно ServerBridge allow-событием и серверным `E2EPlayer joined the game`.

`e2e/scripts/publish-client-package.py` повторно вычисляет SHA-256 и размер каждого локального артефакт непосредственно перед загрузка и сверяет их с пакет манифест и ответом Серверная часть API. Это предотвращает ситуацию, когда E2E публикует дерево, изменившееся после материализация. Среда выполнения watchdog `--max-runtime-seconds` используется только как ограничитель длительно работающего процесса: после таймаута NeverRuntime сам завершает дочернюю JVM и фиксирует `timedOut`; обычный рабочий запускать без флага остаётся неограниченным.

## Усиление защиты публичной Матрица совместимости

Не хранит статусы совместимости в исходном `compatibility/targets.json`. Этот файл задаёт только ожидаемые Minecraft/loader/OS/arch цели. Каждый PASS создаётся `run-compatibility-case.sh` из фактического рабочий E2E и содержит точный `GITHUB_SHA`/`GITHUB_RUN_ID`. Агрегатор отклоняет missing/duplicate цели, несовпадение commit/run, изменяемый загрузчик версия после разрешение и отсутствие пакет проверять, Ed25519 подпись, чистый синхронизация, реальный клиент запускать, Paper мир подключение или revoke/deny свидетельство.

Совместимость uploader запрещает символическая ссылка путь и повторно разрешает каждый пакет путь внутри клиент корень непосредственно перед чтением. Общий E2E связывает ServerBridge профиль с проверяемым загрузчик цель; hard-coded Vanilla профиль для Fabric/Quilt/Forge/NeoForge запрещён. Матрица публикуется как GitHub Действия Summary и JSON/Markdown артефакт, а репозиторий политика запрещает возвращение ручных PASS маркер или фикстура-based совместимость свидетельство.

## CORS

`NEVERLAUNCHER_CORS_ALLOWED_ORIGINS` содержит явный список HTTPS источник через запятую. `*` в рабочий запрещён. Специальный `e2e-production` разрешает HTTP только для локальная петля `localhost/127.0.0.1/::1` и предназначен исключительно для автоматизированного рабочий E2E.

## Критичная область безопасности

Критичными считаются проблемы, затрагивающие:

- обход авторизации или RBAC;
- подмену package/runtime/project манифесты;
- подмену файлов клиента;
- обход SHA-256/integrity проверка;
- небезопасный запуск Java/Minecraft;
- утечку refresh/session/server токены;
- обход ServerBridge проверять-подключение;
- выполнение произвольного кода;
- обход путей при работе с архивами и хранилище;
- доступ к чужим проектам, пакетам, события аудита или резервное копирование артефакты.

## ServerBridge безопасность

ServerBridge должен работать в запрет по умолчанию режиме:

- сервер регистрируется через отдельный мост токен;
- проверять-подключение вызывается на Серверная часть API;
- heartbeat/audit-event пишутся на серверная часть;
- недоступность серверная часть трактуется как запрещать или degraded режим только при явном разрешении оператора;
- ротация сервер токен должна быть штатной операцией.

## Совместимость Движок доверие граница

При `classpathStrategy=compatibility` `version.json`, родительские метаданные из `inheritsFrom` и каждый JAR, попавший в разрешённый путь классов, должны присутствовать в подписанном релиз манифест. NeverRuntime не доверяет локальному metadata-файлу только потому, что он находится в каталоге клиента. Серверная часть также запрещает публикацию совместимость релиз без обязательного `versionMetadataPath` (по умолчанию `versions/<version>/<version>.json`) и отклоняет обход/небезопасные пути.

Mojang правила обрабатываются до выбора library/native артефакты. Файлы с `targetOs` другой платформы не участвуют в verify/sync текущей ОС; `targetOs` и `executable` являются частью подписанного манифест метаданные.

## Целостность пакетов

Для клиентских пакетов обязательны:

- файл-уровень SHA-256 манифест;
- проверка целостности перед запуском;
- repair режим вместо слепого перезаписывания;
- артефакт релиза контрольные суммы;
- запрет доверять локальному состоянию Настольное приложение Лаунчер без на стороне сервера сессия.

## Псевдонимы совместимости

Серверная часть API может читать устаревшие совместимость псевдонимы только для миграции, но документация и production-развёртывание используют канонические переменные:

- `NEVERLAUNCHER_DATABASE_DSN` вместо `NEVERLAUNCHER_DATABASE_URL`;
- `NEVERLAUNCHER_AUTH_TOKEN_SECRET` вместо `NEVERLAUNCHER_TOKEN_SECRET` или `NEVERLAUNCHER_JWT_SECRET`;
- `NEVERLAUNCHER_STORAGE_LOCAL_PATH` вместо `NEVERLAUNCHER_STORAGE_LOCAL_ROOT`;
- `NEVERLAUNCHER_REDIS_ADDR` вместо `NEVERLAUNCHER_REDIS_URL`.

## ServerBridge Прокси семейство 0.14.5

Velocity/BungeeCord/Waterfall не разделяют закрытый узел учётные данные: каждый прокси имеет собственную Ed25519 идентичность. Подписанный heartbeat/join валидация, одноразовое значение защита от повторного воспроизведения, артефакт SHA-256 список разрешений и одноразовый билет семантика остаются обязательными. BungeeCord/Waterfall адаптер отказ с блокировкой проверяет фактическую платформа идентичность, а серверная часть принимает только канонические тип `velocity`, `bungeecord`, `waterfall`.
